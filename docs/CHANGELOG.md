## v1.14.0 · 2026-10-04 · **六种表全接霓虹**（P7-8）

### 问题

`BaseGaugeView` 早就有 `neon` 实例，但**只有圆表和条形表在用** ——
数字表 / 折线表 / 多值表 / G力表在霓虹主题下是**哑的**：
配色变了，但没有一点辉光，和另外两种表放在一起很割裂。

### 做法：五个共用助手，而不是六份辉光循环

`BaseGaugeView` 新增：

| 助手 | 用途 |
|---|---|
| `neonBar` | 发光进度条（数字表底部条 / 多值表各条） |
| `neonText` | 发光文字（数字读数 / 折线当前值 / 多值读数） |
| `neonLine` | 发光线段（G力十字线） |
| `neonDot` | 发光圆点（G力球） |
| `neonPath` | 路径辉光（折线轨迹 —— 几十个点逐段 bloomLine 太贵） |

> **为什么必须抽出来**：6 个视图各写一遍辉光循环的话，层数、扩散、
> `glow` 开关的判定迟早分叉 —— 圆表亮一点、数字表暗一点，用户看得出。

### 关掉霓虹 = 零额外绘制

每个助手都有守卫（`if (on)` / `if (palette.glow)` / `if (!on) return`）。
**有测试钉住这一点** —— 辉光是纯装饰，关掉必须真的不做功。

### 多值三兄弟自动受益

`DualStackGaugeView` / `QuadGaugeView` / `SubDualGaugeView` 只有 ~40 行，
它们**委托给 `MultiValueGaugeView`** —— 所以接了那一个，三个都有了。

### 新增契约测试 `NeonCoverageTest`（4 条）

霓虹是纯绘制，像素级验证要真机。但真正容易出的问题不是"画得对不对"，
而是 **"新加了一种仪表，忘了给它接霓虹"** —— 那种表在霓虹主题下是哑的，
**而且没有任何测试会失败**。

所以检查四个静态事实：

1. 每个仪表视图都**至少调用一次**霓虹绘制
2. 五个助手都定义在 `BaseGaugeView`（不是各视图各写一份）
3. 关掉霓虹时助手**直接跳过**（不做白工）
4. 多值三兄弟确实委托给 `MultiValueGaugeView`

### 验证

| 项 | 结果 |
|---|---|
| Kotlin 单测 | **461 全过**（+4 霓虹契约） |
| 浏览器 17 套件 | **622 断言全过** |
| 构建守卫 | 通过 |
| 装机 | v1.14.0 安装成功，**无崩溃、无 ANR** |

### ⚠️ 没验证的：辉光**真的画出来了**

契约测试只能证明"代码调了霓虹"，**证明不了像素**。我尝试在设备上做
像素对比（同一份设计 glow 开/关，比亮度），但截图管线在这台设备上
反复失败（adb 的 stderr 被 PowerShell 当成错误中断流程），**没跑通**。

**请你目视确认**：仪表盘 → 风格 → 霓虹赛道，看数字表/折线表有没有辉光；
再切到经典琥珀（glow=false），辉光应当完全消失。

### 遗留

- **折线的辉光用 `neonPath` 手写多层描边** —— `NeonPainter` 没有路径版 bloom，
  这里是在 `BaseGaugeView` 里补的，逻辑与 `bloomLine` 平行但独立

  没有"实心圆"的封装（`roundRect` 半径=边长/2 就是圆）

## v1.13.0 · 2026-10-04 · 内嵌主题配色 + 多指针表

### 内嵌主题配色（P8-5，配套工具 v2.16.0）

设计文件带了 `themeColors` 就用它渲染，没有才按设置里的主题 id 查。

> 为什么优先内嵌：设计文件是「作品」，配色是作品的一部分 ——
> 跟着设备当前主题走的话，**同一份设计在两台机器上长得不一样**。

`DesignFile` 里只存 `JSONObject`，**不依赖 ui/** —— `fromJson` 的调用在渲染层，
守住「data/ 不能依赖 ui/」这条红线。

### 多指针表（配套工具 v2.17.0）

`needle` 部件可以各绑一个 PID —— 「转速 + 车速」双针表。

- `GaugePart` 加 `pid`；**只有 needle 解析它**（表盘绑 PID 没意义）
- `GaugePartsView` 从「单个值」改成**值表**（`PID id → 值`）+ `neededPids()`
- 渲染器一次把需要的 PID 取齐推进来 —— 视图**不自己读总线**（红线 4.1.5）

> ⚠️ **量程跟着 PID 走**：车速 0~240、转速 0~8000。车速指针按转速量程映射的话，
> 120 km/h 算成 1.5%，**指针几乎不动** —— 用户会以为「数据没上来」。

## v1.10.4 · 2026-10-03 · 数值动画重做：输入滤波 + 四种缓动曲线 + 收敛策略

用户反馈「动画条要优化、要流畅、0-10 要 +3+5 这样走过去而不是直接跳过去」。
查下去发现**根因不是"没有缓动"，而是缓动的三个层次各有一个问题**。

### 根因：三层各有一处问题

原来的动画只有一层：`displayValue` 用指数逼近 `value`（τ=45ms）。三个问题：

| # | 问题 | 后果 |
|---|---|---|
| 1 | **只有一个写死的曲线** | 没有 ease-in/out 可选，也调不了节奏 |
| 2 | **收敛就吸附并停止动画** | 数据 5Hz 推，两次推送之间目标不变 → 缓动在窗口里早早收敛、**停住**，下次推送再跳一下 |
| 3 | **没有输入滤波** | 数据本身的抖动（传感器噪声、量化）直接进动画，指针看着"毛躁" |

第 2 条是关键：τ=45ms 时一个 200ms 推送周期内走完 **98.8%** ——
指针**几乎瞬间到位**，然后在剩下的时间里"趴"在目标上不动。
数据缓变时（水温上升、正弦峰顶）看起来就是一格一格地跳。

### 新增：`Easing` —— 三层纯逻辑（37 个用例）

```
总线原始值 ──[1. 输入滤波]──→ 平滑目标 ──[2. 缓动曲线]──→ 显示值
                                                            │
                                        [3. 收敛判据] ←──────┘
```

**① 输入滤波**（`valueSmoothingMs`，默认 90ms）
专门压数据本身的抖动，与缓动曲线**解耦**：想更稳调大、想更灵敏调小。

**② 四种缓动曲线**（`easingMode`）

| 模式 | 机制 | 手感 |
|---|---|---|
| 标准（指数） | 增量：每帧走 `k·dist` | 全程减速、收尾长，最不容易看出跳变 |
| 线性（匀速） | 增量：固定速度 | 跳变时最像"指针在扫" |
| 柔和（缓入缓出） | 绝对位置：`3u²−2u³` | 起步慢、中段快、收尾慢 |
| 干脆（缓出） | 绝对位置：`1−(1−u)²` | 起步快、收尾慢 |

**③ 收敛判据**（`Easing.needsMoreFrames`）
把"够不够近"和"要不要继续动画"**拆成两件事**：

- 数据还在动（距上次目标变化 < `HOLD_MS`=600ms）→ 只吸附消除尾巴，**继续动画**
- 数据稳定下来了 → 吸附并停止，不空转

### 关键参数：τ 从 45ms 提到 120ms

一个 5Hz 推送周期（200ms）内：τ=45ms 走 **98.8%**（几乎瞬间到位），
τ=120ms 走 **81%**（永远留余量给下一次推送 → 指针一直在动）。

代价是到位慢一点（3τ≈360ms）。仪表读数本来就不需要瞬时响应，而"顺"是第一眼就能看出来的。

### 重构：抽出 `GaugeAnimator`（状态机）

动画的状态机（起点、总行程、目标稳定计时）原来长在 `stepFrame` 里，
**JVM 单测跑不了**（要 View、要 Choreographer）。而"数据还在变时会不会冻住"
这类问题恰恰只出在状态机上，不在数学上。

抽成独立类后 `BaseGaugeView` 少了约 40 行可变状态，且这些状态有了单一负责人。
这也是重构文档 §2.2 步骤 2 要的那一步。**19 个用例**直接按真实时序喂数据。

### 新增：性能基准页的「流畅度」指标

帧率与掉帧只说明**画得动**，不说明**动得顺**。
指针"一格一格跳"的本质是**部分帧上没有位移**，所以基准页现在直接统计
「显示值真的变了的帧占比」。

**实测（小米平板 5，v1.10.4）**：

| 档位 | 动了 / 总帧 | 占比 |
|---|---|---|
| 8 表 · 主题默认 | 599 / 599 | **99.8%** |
| 8 表 · 夸张（11 层） | 599 / 599 | **99.8%** |
| 8 表 · 关闭辉光 | 599 / 599 | **99.8%** |
| 12 表 · 夸张（极限） | 599 / 599 | **99.8%** |

四段仍然**零掉帧**（帧间隔 p99 ≤ 16.73ms）。也就是说：**动画变顺了，性能没退**。

### 主题编辑器新增「数值动画」一节

缓动曲线下拉（4 种）+ τ 滑块 + 输入滤波滑块，**改完立刻在预览里看出来**。
内置主题只读 → 保存时自动另存为自建主题（与原有行为一致）。

### 过程中实际写出来又修掉的三个缺陷（都记下来）

1. **指数逼近的增量积分漂移**：`v ← v + (v_target−v)·(1−e^(−dt/τ))` 在 60Hz 与 120Hz 下
   同样 250ms 差 **20 个百分点**（55.5 vs 35.0）—— 因为 `1−e^(−dt/τ)` 不是线性的，
   帧多帧少累积出的曲线不同。修法：把每帧混合系数**按参考帧长归一化**
   （`k = 1−(1−k_ref)^(dt/REF)`），这样 k 对 dt 可加。

2. **进度型曲线把"剩余距离"当总行程**：写成"每帧位移 = 剩余距离 × 曲线速度 × dt/时长"，
   看着合理，实际**永远到不了目标**（实测停在 64.76%）—— 剩余距离逐帧缩小、位移逐帧衰减。
   修法：曲线作用在**固定不变的总行程**上（目标变化时固定下来）。

3. **下降方向恒不动**：`journeyStart + journeyDist·curve − from` 对下降方向是**负数**，
   被 `coerceIn(0, dist)` 夹成 0。需要 `abs` 之后统一乘方向。
   **上升方向的用例完全测不出来** —— 是补了下降用例才发现的。

> 第 3 个缺陷特别值得记：它只在"目标下降"时出现，而人写测试时下意识先写上升。
> 现在 `GaugeAnimatorTest` 里有一条专门的下降收敛用例守着。

### 踩坑：改 `build.gradle.kts` 用 PowerShell `-replace | Set-Content -NoNewline`

只想改版本号，结果：
- **换行全被吃掉** → `abiFilters += "arm64-v8a"` 那行被并进注释 → **四个 ABI 全编**
  （APK 6.68 → **9.41 MB**，`lib/` 0.91 → 3.61 MB）
- 文件被写成 **ANSI(GBK)** → 中文注释变乱码，`read` 工具直接报 `invalid UTF-8 text`

修法：用 `[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($false)))`
显式写 UTF-8 无 BOM。**改源码文件不要用 `Set-Content`**（它按 ANSI 写，且 `-NoNewline` 会吃掉换行）。

### 验证

- **415 个单元测试全通过**（+57）：`EasingTest` 37（新建）· `GaugeAnimatorTest` 19（新建）·
  `GaugeEasingTest` 14（改）· `GaugeThemeTest` 25
- 装机实测：流畅度 99.8%、零掉帧（见上表）
- `adb logcat -b crash` 无 `com.icar.obd` 条目

### 遗留

- 各曲线的**手感**最终要靠眼睛定。τ=120ms / 滤波 90ms 是算出来的起点，
  真机上觉得"太慢/太快"直接在主题编辑器里调（有实时预览）
- 进度型曲线（柔和 / 干脆）的总时长固定为 `2τ`，**没有单独的总时长参数**。
  想要"慢起步 + 长滑行"需要再拆一个参数，目前没做
- 「流畅度」指标只统计**第一块表**。8 块表各自动画时它们的占比可能略有差异

## v1.10.3 · 2026-10-03 · 打通「电脑上设计 → 设备上生效」的闭环

### 修复：设计文件在 App 侧**根本没有入口**（这是 v1.10.0 起就有的断点）

用户问了一句「电脑的主题修改有同步修改好吗」，顺着去查才发现：

> `DesignFile.parse` 写好了、22 个用例守着、PC 工具也能产出文件 ——
> 但 **`app/src/main` 里一次都没调用过它**。

也就是说 v1.10.0 引入的 `icar.ui/1` 格式，**只有一半**：能写、能校验，
但**设备上没有任何地方能读它**。工具做得再好也流不到 App ——
只能手动 `adb push` 到 `files/design.json`，而那个文件**没有任何代码会去读**。

这是"规则同步做好了、但数据流是断的"——两件事都得成立才行。

**修法**：仪表盘「风格」对话框新增两个动作项，走 SAF（不需要存储权限）：

| 入口 | 作用 |
|---|---|
| **导入设计文件…** | 选一个 `design.json` → 解析 → **先给用户看结果** → 确认后整体替换自定义仪表盘 |
| **导出当前布局为设计文件…** | 把当前盘面导成 `design.json` 分享出去（回到 PC 工具继续改） |

**为什么导入要两段式**：设计文件的校验**不抛异常**、返回带字段路径的错误列表，
所以有硬错误时可以精确说清"哪一块表的哪个字段错了"；软警告（比如背景路径在本机
不存在）也要显示 —— 那是"能加载但效果可能不是你想要的"，瞒着用户更糟。

## v1.10.1 · 2026-10-03 · 性能基准（终于量准了）+ 统一两套报警概念 + 主题制作工具

> 本轮把 `docs/下一步-主题工具与仪表盘重构.md` 里三件**一直悬着**的事一起做了：

### 新增：仪表盘性能基准页（`ui/BenchActivity` + `ui/BenchHarness` + `ui/dash/DashboardBenchmark`）

**回答的问题**：9 层霓虹辉光在 8 个仪表下守得住 60fps 吗？（文档 §2.4，被推迟了三个版本）

**之前为什么量不出来**，两个原因都修掉了：

1. `dumpsys gfxinfo` 在这台设备上只给头部、没有帧统计；
2. 用真实数据测时**仪表根本没在动** —— 静止的 View 不重绘，测出来的"帧率"是屏幕刷新率，
   和绘制成本无关。基准自己每帧 `updateMulti()` 灌正弦假值，**强制每帧重绘**。

**四段测量**（8 表 × 3 档 + 12 表极限），每段预热 1.5s + 测量 10s。结果：

| 档位 | 仪表 | 帧数 | 帧间隔 平均 | p99 | 最大 | 超时帧 |
|---|---|---|---|---|---|---|
| 8 表 · 主题默认 | 8 | 1199 | 8.33 ms | 8.39 ms | 8.43 ms | **0** |
| 8 表 · 夸张（11 层） | 8 | 1199 | 8.33 ms | 8.38 ms | 8.41 ms | **0** |
| 8 表 · 关闭辉光 | 8 | 1199 | 8.33 ms | 8.38 ms | 8.43 ms | **0** |
| 12 表 · 夸张（极限） | 12 | 1199 | 8.33 ms | 8.38 ms | 8.41 ms | **0** |

**结论：12 个圆表 + 11 层辉光跑满 120fps，零掉帧。** 8 个表更不在话下。

> **⚠️ 判据是「帧间隔」，不是「每帧绘制耗时」—— 这一点差点搞错。**
>
> 第一版报告用 `DrawStats` 的每帧耗时（0.2~0.34ms）下结论，看起来"还有 50 倍余量"。
> 但 Android 开了硬件加速后 `onDraw` 只是把绘制指令**记录**进 DisplayList，
> 真正的光栅化在**渲染线程**上做 —— 那个数**不是绘制成本**。
> 报告里现在把它明确标成"旁证"，主判据换成帧间隔（主线程 + 渲染线程 + 合成器的最终结果）。
>
> 顺带发现：`关闭辉光` 的**记录**耗时（0.34ms）反而**高于** `夸张`（0.28ms）——
> 说明这一列量的是视图层代码，与辉光层数基本无关。这本身也印证了不能拿它当判据。

**踩坑（都记下来，避免下次重犯）**：

1. **画布高度塌成 0**：第一版把控件放进 `ScrollView`，`weight=1` 拿不到剩余空间，
   点「开始测量」直接报"容器还没布局好"。改成固定头部 + `weight=1` 画布，根部不套 ScrollView。
2. **布局监听器越界崩溃**：`onLayoutChange` 里读了 `segments[segIndex]`，
   三段跑完后 `segIndex=3` → `ArrayIndexOutOfBoundsException: length=3; index=3`，
   **真机上崩了两次**。布局监听器现在只读 `currentPreset`，完全不碰索引。
3. **预热被算进测量窗口**：延时按 `SEGMENT_SEC` 算，而预热吃掉 1.5 秒，
   实际只测了 8.5 秒。改成 `WARMUP_MS + SEGMENT_SEC`。
4. **首帧峰值污染统计**：重建视图后第一帧要付 `Paint` 光栅化 / 字体度量 / tessellation，
   峰值 **11393µs**。加了 1.5 秒预热，预热结束才 `reset()` 开始计数。
5. **屏幕刷新率会封顶帧率**：同一页两次测量分别读到 30Hz 和 120Hz
   （`mActiveModeId` 在 30/60/120 之间切）。拿 fps 当判据会得出"刚好达标"的错觉。
6. **本机同时挂着模拟器**：`adb` 不带 `-s` 会报 `more than one device/emulator`。
   所有命令都要写 `-s 7e7d7bb4`。

### 重构：统一两套报警概念（`BaseGaugeView`）

**问题**（文档 §2.1 问题 2）：两个概念并存且**重叠但不相等** ——

| | 来源 | 用途 |
|---|---|---|
| `warn: Boolean` | `isOutOfRange()`，**含下限** | 选颜色 |
| `alertLevel: Int` | `AlertPulse.level()`，**只认上限** | 驱动爆闪 |

`warnLow` 触发时 `warn=true` 而 `alertLevel=NONE`，于是"到底哪个才是报警"永远说不清；
而且 7 个视图各自写了一遍 `if (warn) cWarn else …`，加一档报警要改 7 个文件。

**做法**：

- 删掉 `warn`，新增 `AlertPulse.levelWithLow()`（**保留** `level()` 不动 ——
  它被扫描器沿用，27 个用例钉着它的迟滞边界，不该被顺手改）
- 新增 `AlertPulse.WARN_LOW` 档：**下限只染色、不爆闪**。
  爆闪的语义是"立刻松油门 / 靠边"，数值偏低不需要这种紧迫感；
  硬要闪反而会让驾驶员对爆闪脱敏
- 新增 `BaseGaugeView.alertColor()` / `valueTextColor()` / `extraTextColor()`，
  **报警配色只有一处判定**，7 个视图的重复判断全部删掉

**⚠️ 一处刻意的观感变化**：`CircularGaugeView` 的指针原来只在**危险档**变红
（`if (warn) cDanger else cNeedle`）。现在按报警等级取色 ——
WARN 档指针变橙、CRITICAL 变红。理由是"报警了指针却不变色"本身就不一致。
若不想要这个变化，改回 `alertLevel == AlertPulse.CRITICAL` 即可。

### 修复：`DigitalGaugeView` 的装饰弧跳变（文档 §2.1 问题 5，一行）

`ratio(value)` → `shownRatio()`。这是 `docs/动画实现.md` 记了很久的不一致：
数字表的底部进度条**不参与缓动**，和圆表 / 条形表的平滑观感不统一。

### 修复：`AlertPulse.levelWithLow` 的下限迟滞方向写反了（**自己写出来又被单测抓出来的**）

上限是"超过才报、跌下来才解除"，所以退出阈值**低于**进入阈值（`releaseOf` 用减法）。
下限正好相反 —— 照抄减法会让退出阈值落到进入阈值**下面**，于是**永远进不去**。

新增 `releaseHighOf()`（加法）。这个 bug 是 `下限也有迟滞` 那条用例抓出来的，
手测几乎不可能发现（现象只是"低电压不变色"，很容易归因到别处）。

### 修复：`tools/run-tests.ps1` 用绝对路径调用时直接退出

**症状**：`powershell -File "D:\...\tools\run-tests.ps1"` 报
`Split-Path : Cannot bind argument to parameter 'Path' because it is an empty string`，
**一个用例都没跑**。

**根因**：`param([string]$ProjectDir = (Split-Path -Parent $PSScriptRoot))` ——
从外部用绝对路径调用时 `$PSScriptRoot` 是空串。

**修法**：`ProjectDir` 改为可省略，按 显式传参 → `$PSScriptRoot` → `$MyInvocation.MyCommand.Path`
依次回退；都拿不到时给出明确提示而不是抛栈。三种调用方式都验证过。

### 踩坑：改 `.ps1` 丢了 UTF-8 BOM（**报错完全指向错误方向**）

修上面那条时把 `run-tests.ps1` 写成了**无 BOM** 的 UTF-8。
Windows PowerShell 5.1 对无 BOM 的 `.ps1` 按 **ANSI(GBK)** 解码，于是：

- 中文注释全变乱码；
- 乱码把**行尾吃掉**，下一行的 `if (-not $ProjectDir) {` 被并进上一行注释里；
- 报错是 `Unexpected token '}' in expression or statement` ——
  **看起来像语法错误，实际是编码问题**，顺着报错行查语法会白费很久。

`oncar-check.ps1` 一直有 BOM，可以对照。已在 `FILE_MAP.md` §6.1.1 记下验证方法：
`[System.Management.Automation.Language.Parser]::ParseFile($p, [ref]$null, [ref]$errs)`。

> **`docs/*.md` 与 `.kt` 不受影响**（Markdown 与 Kotlin 都按 UTF-8 读）。

### 新增：[动画实现.md](动画实现.md)

把"仪表盘动画靠什么驱动、数值变化动画怎么算"整理成一份分析。核对代码时发现一处**不一致**：

> `DigitalGaugeView` 第 88 行用的是 `ratio(value)` 而**不是** `shownRatio()`，
> 所以它的装饰弧是**跳变**的，和圆表/条形表的平滑观感不统一。**一行可修。**

文档要点：

- **两套机制性质不同**：数值缓动是"过渡"（会收敛会停），阈值爆闪是"振荡"（不收敛一直在跑）。
  必须分开 —— 只有一套的话，要么报警闪一下就不动，要么数值不动了还在 60fps 空转。
- **全工程只有 `GaugeTicker` 一处动画驱动**（`Choreographer`），
  没有用 `ValueAnimator`/`ObjectAnimator`/`postInvalidateOnAnimation`。
- **缓动是指数逼近**（一阶低通），`k = 1 - e^(-dt/τ)`，τ=45ms。
  时间基准而非每帧固定比例 —— 这台平板能跑 120Hz，按帧缓动会快一倍。
- **收敛判据按像素折算**，不用相对比例（转速量程 8000 时相对千分之一是 8 转，指针会肉眼可见地"爬"）。
- **文本永远用原始值**，只有图形用动画值 —— 读数必须准，指针可以慢半拍。
- **爆闪带迟滞**（退出阈值 = 进入 × 0.97），否则转速在 6500 抖动会让爆闪乱闪。
- 文档末尾列了**已知问题**，其中"性能基准仍未量准"标为**高优先级**。

## v1.10.0 · 2026-10-03 · 缓动改时间基准 + 删除 Sky 主题 + PC 端设计框架

### 修复：个别进度条"一顿一顿"

**根因是缓动的实现方式，不是数据。** 原来是**按帧**逼近：

```kotlin
from + (target - from) * 0.25    // 每帧固定比例
```

两个毛病：

1. **帧率相关**。60Hz 下 200ms 收敛，120Hz 下只要 100ms ——
   同一份代码在不同设备观感完全不同。**这台平板就能跑 120Hz**。
2. **和 5Hz 的数据推送错拍**。数据每 200ms 来一个新目标，
   而按帧缓动要 ~173ms 才到 95%，剩下 5% 是长长的尾巴 ——
   **永远在"快起步、慢收尾"的循环里**，看起来就是一顿一顿。

改成**时间基准**：`k = 1 - e^(-dt/τ)`，τ=45ms。不管多少帧率，固定时间收敛。

顺带把收敛判据从**相对比例**改成**像素级**：
转速量程 8000 时，相对千分之一 = 8 转，条形上是 0.1% 宽度，
但**指针会肉眼可见地"爬"**。现在 `BarGaugeView` / `CircularGaugeView`
按自己的像素尺度覆写 `settleEpsilon`，不到半个像素就吸附。

**新增 7 个测试**，其中两个专门钉"帧率无关"：
60Hz 与 120Hz 跑同样 200ms，结果必须几乎一致。

### 删除：Sky Gauge 主题支持

用户确认可以删。删掉 `SkyTheme.kt` / `DashElement.kt` 及两个测试文件，
清掉 `Store` / `DashFragment` / `LvglDashView` / `LvglBridge` 里的全部引用。

**APK 从 7.21 MB 降到 6.65 MB。**

### 新增：`DesignFile` + [UI设计指南.md](UI设计指南.md) —— **在电脑上设计 UI**

现在调布局只有两条路（手指拖 / 改代码），**都不适合做设计**。
设计文件把它变成"编辑一个 JSON"：

```
PC 写 design.json  →  校验（有明确报错）  →  推到设备  →  App 加载
```

**与刚删掉的 Sky Gauge 格式的关键区别**：

| | Sky Gauge | `icar.ui/1` |
|---|---|---|
| 归属 | **别人的**格式 | **我们自己的** |
| 模型 | 图元级，要写转换层 | **直接复用 `GaugeItem`**，零转换 |
| 表达力 | 受限于他们的词汇表 | = App 能画的东西，一一对应 |
| 坐标系 | 正方形 360×360，非方形屏会变形 | 每轴 0..360，天然适配 |

**校验是这个格式一半的价值**：手写 JSON 一定会写错，而"推到设备上发现没显示"
是最低效的调试方式。所以解析器**不抛异常**，返回带字段路径的可读错误：

- 硬错误（拒绝加载）：JSON 语法 / schema 不对 / unit 不是 360 / 缺 pid / 量程非法
- 软警告（能加载但提示）：**越界**（越界不会报错、只会"看不见那块表"）/ 坐标为负 /
  尺寸过小 / 未知 pid（自定义 PID 是合法场景，不拦）

**22 个测试**。其中一条抓出一个真问题：

> `GaugeItem.fromJson` 用**元素自己的 `unit` 字段**判断新旧格式，没有就 ×360（旧配置迁移）。
> 而设计文件的单位声明在 `canvas.unit` 上 —— 不注入标记的话**每个坐标都会被再乘一次 360**
> （12.5 → 4500）。这个坑是单测抓出来的。

### 验证

**288 个单元测试全通过**，装机无崩溃。

## v1.9.0 · 2026-10-03 · 仪表盘重构：共用霓虹层 + 阈值爆闪

### 新增：`AlertPulse` —— 阈值报警与爆闪（纯逻辑，27 个单测）

抽成独立对象的理由：**迟滞边界**和**时间相位**是最容易写错、又最难手测的两处。
放在 `onDraw` 里这两件事都没法验证；做成纯函数（时间由调用方传入）就能单测。

- **迟滞**：退出阈值 = 进入阈值 × (1 − 3%)。没有它，真实转速在 6500 上下抖动会让爆闪乱闪。
  测试里专门写了一个**反证用例**：不传上一帧等级，同一串样本会被最后那个小值打回 NONE。
- **两档不同节奏**（一眼看出严重程度）：
  - `WARN` ≈1.7Hz **平滑脉冲**（smoothstep）—— 低等级用硬方波太刺眼，长途驾驶会烦
  - `CRITICAL` ≈5Hz **硬方波** —— 干脆、有冲击力
- **染色策略**：不做"整个元素变色"（那会让读数在闪烁中消失），
  只把**辉光和外圈**推向危险色，读数始终可辨。

### 新增：`NeonPainter` —— 共用霓虹绘制层

原来只有圆表有辉光，且是 4 层写死的循环；数字、条形都不发光，
整个盘面看起来是"一个霓虹表 + 一堆素控件"。

- 弧 / 线 / 圆 / 圆角矩形 / 文字，五套辉光原语
- **层数按控件尺寸自适应**（3 / 5 / 7 / 9 层）—— 小控件上叠 10 层既看不出效果又白花钱
- **`onDraw` 零分配**：所有 Paint 复用，不 new

### 重构：`CircularGaugeView`

1. 辉光换用 `NeonPainter`，层数自适应
2. **底轨上标出危险区**：从 `warnHigh` 起就是暗红。原来危险阈值只体现在"超了之后变红"，
   开车时看不到"还有多远到红线"
3. **爆闪**：超过危险阈值时整个环 + 指针按节奏闪
4. **文本格式化加缓存**：文本只随 `value` 变（5Hz），不随缓动变（60fps）
5. 留白按**辉光扩散量**给（原来按描边算，最外层会被裁掉）

### 重构：`BarGaugeView`

霓虹进度条 + 爆闪 + 阈值刻度线在报警时一起变亮。
