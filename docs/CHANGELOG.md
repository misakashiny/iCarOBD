## v1.20.5 · 2026-10-08 · 🔴 **P0：手机（竖屏）一启动就崩** —— `BottomNavigationView` 硬上限 5 项

> 用户报「我在手机端是打不开的」。**是我 v1.20.3 引入的崩溃**，与 OTG 无关。

### 现场（手机上抓的）

```
20:59:04.079  Start proc 27019:com.icar.obd
20:59:04.211  E/AndroidRuntime: FATAL EXCEPTION: main
20:59:04.220  Force finishing activity com.icar.obd/.ui.MainActivity
20:59:04.243  Process com.icar.obd (pid 27019) has died
```

app 自己的日志里只有一行 `===== iCar OBD 启动 =====`，**130 毫秒后就死**。堆栈：

```
java.lang.RuntimeException: Unable to start activity ...MainActivity
  at ...MainActivity.onCreate(MainActivity.kt:58)          ← setContentView
Caused by: android.view.InflateException: Binary XML file line #52 in
           com.icar.obd:layout/activity_main: Error inflating class
           com.google.android.material.bottomnavigation.BottomNavigationView
Caused by: java.lang.IllegalArgumentException:
           Maximum number of items supported by BottomNavigationView is 5.
```

### 根因

`BottomNavigationView`（**竖屏**底部导航）的菜单项**硬上限是 5**。
v1.20.3 给导航栏加了第 6 个 tab（知识库）→ 竖屏布局里的 `app:menu` 在
**构造函数里**就 inflate 菜单 → 直接抛异常。

**为什么平板一直没事**：平板是**横屏**，用的是 `NavigationRailView`，
**没有**这个上限 —— 所以这个 bug **只在手机上暴露**，装机验证时漏了。
（教训：**竖屏必须单独验一遍**，不能只验平板。）

### 修法

已核实 **Material 1.12.0 根本没有 `setMaxItemCount`** —— 把
`material-1.12.0/jars/classes.jar` 里的 `NavigationBarView` / `NavigationBarMenu` /
`BottomNavigationView` 三个类**逐个按字节搜过**，只有 `getMaxItemCount`，没有 setter。
**这个 5 是写死的、没有公开改法。**

但 `getMaxItemCount()` **可重写**，而且 `BottomNavigationView` 的构造函数里是
**虚调用**它（`new NavigationBarMenu(context, getClass(), getMaxItemCount())`）——
Java 的虚调用会派发到子类重写，**在构造过程中就生效**。

所以新增本地子类 **`ui/view/NavBottomBar.kt`**（重写 `getMaxItemCount()` 返回 6），
竖屏布局改用它，`app:menu` 照旧。**10 行代码，不动 Material 版本。**

### 验证

- **手机（竖屏，小米 24122RKC7C / Android 16）**：`pidof` 有值、无 FATAL、
  `ResumedActivity = com.icar.obd/.ui.MainActivity` → **能打开了** ✅
- 平板（横屏）不受影响（它走 `NavigationRailView`）
- 单测全过、构建守卫通过

### 顺带排除的两个误解

1. 用户提到「OTG 已经连接上了」—— 实测手机 `dumpsys usb` 是 **`host_connected=false`**，
   即当时处于 **MTP 从设备模式**（正连在电脑上），**并没有进入 USB 主机模式**，
   所以 OTG 那边也还没生效。
2. **本 app 完全没有 USB / 串口 / OTG 代码**（只有 `BleTransport` 与 `SppTransport`，
   权限也只有蓝牙）—— 要支持 USB 版 ELM327 得单独做一条传输层。
   顺带记录：该手机内核**没有 `ch341` / `pl2303` 驱动**（有 `ftdi_sio` / `cdc_acm`），
   所以 CH340 类 USB 串口芯片在这台手机上本来也认不出来。

## v1.20.4 · 2026-10-06 · 导航栏改**悬浮**（不再挤画布）+ 去掉把手改**双指手势**

> 用户三条反馈。第 3 条（P0）查到了**决定性的结论**，见下。

### 导航栏改成悬浮层（不再挤画布）

用户原话："仪表台里面 tab 页面要以**悬浮窗**的形式去显现，**不然会把画布挤掉**"。

**根因是布局结构**：根容器是 `LinearLayout(horizontal) { navView, divider, pageContainer }`
—— 导航栏占 198px，**画布就少 198px**；而且仪表盘页把它"滑出去"时
`pageContainer` 会重新量一次 → 画布尺寸变化 → 表盘重排 + 闪一下。

**改法**：根容器换成 **`FrameLayout`**，`pageContainer` 永远整屏，导航栏带
`elevation` 浮在上层（横屏贴左、竖屏贴底）。展开/收起只动它自己的
`translationX/Y` + `alpha`，**画布一动不动**。

**实测**：导航栏显示时 `navView [0,0][198,1564]`，而
**`pageContainer` 仍是 `[0,0][2560,1564]`** ✓（改之前会变成 `[200,0]`）。

### 去掉左边缘把手，改**双指横滑** + 双击兜底

用户原话："半透明把手还是有点不好按、**总是触发系统的手势退出**、
要么采用个手势、**双指拖动的时候呼出来**"。

把手这个方案试了两版都不行：第一版贴在 x=4px（≈2dp）—— 正在**系统返回手势的热区**里；
挪到 32dp 后好按了一些，但仍然会误触系统手势。**用户的方案是对的**：

- **双指横滑**：右滑呼出、左滑收起。实现是重写 `MainActivity.dispatchTouchEvent`
  —— **旁听全部触摸但不消费**（照旧交给 `super`）。
  用透明 View 不行：要"看着"双指就得消费 DOWN，那样单指手势会被吃掉。
  双指的好处是**不与任何单指手势冲突**（系统边缘手势、ViewPager 横滑、拖表盘都是单指）。
- **把手整个停用**（不再创建）。
- **双击画布**兜底：因为**双指手势没法用 adb 验**（`adb input` 只能发单指），
  万一在真机上不灵，用户会**卡在仪表盘页出不来** —— 这是不能赌的。
  双击不与任何已有手势冲突（拖表盘是"按下-移动"、横滑是"按下-快滑"，都不产生"两次快速点按"）。

### 🔴 P0（第 3 条）· 结论：**文件是合法的，是"根本没导进去"**

用户报"画布还是不会显示控件"，并给了实际文件（`未命名设计-v1.json`，1132 字节）。

**先排除渲染**：那份文件是 `icar.ui/1`、**没有任何素材**、5 个 PID
（`std_0C/0D/05/42/11`）**全是内置的**、坐标都在 0..360 内 —— 逐条看都合法。
把它做成单测（`DesignFileUserCaseTest`）跑通，**钉住了三件事**：

```
parse → 0 个硬错误
5 块表全部解析 ✓
坐标没有被 ×360（x=0 y=45 w=180 h=180 原样）✓   ← unit 标记注入是对的
5 个 PID 在内置库里都查得到 ✓
```

**再看设备配置**（`files/config/settings.json`）：

```
[0] name=你好    type=2 gauges=8 designJson长度=0
[1] name=画布 2  type=2 gauges=8 designJson长度=0
```

**两套画布都还是 8 个表、`designJson` 全空** → **导入这一步根本没生效**。

所以问题**不在渲染、不在解析**，在**"导入操作"这一段**。下一步要分两种情况定位：

- 没看到确认框 → 是选文件环节（SAF 没选中 / 选完没回来）；
- 看到确认框也点了导入、却还是 8 个表 → 是**导入后被覆盖回去**了，
  优先查 `Store.load()` 里 `dash.json`（v1 遗留镜像）与 `settings.json` 的先后与写回。

⚠️ **日志尾部还停在 23:54**（`AppLog` 批量落盘没刷），所以那次的现场看不到 ——
这也是为什么下一版要把**导入结果做成一眼可见的记录**，而不是靠日志猜。

### 新增单测

`DesignFileUserCaseTest` —— **用用户实际给的失败文件当用例**。
以后再有人动 `DesignFile.parse` / `unit` 注入 / 内置 PID 库，这条会立刻报警。

### 验证方式

单测 **599 全过**、构建守卫通过、`:app:assembleDebug` 通过。
装机实测（小米平板 5 / `7e7d7bb4`）：画布整屏 ✓、把手已移除 ✓、双击呼出导航 ✓、
导航栏显示时画布仍整屏 ✓。
⚠️ **双指手势未验**（adb 发不出多点触控），需要手指实测。

## v1.20.3 · 2026-10-06 · **P0 真凶：`designBaseDir` 从没被赋值** + 导航/知识库/列表三处体验

> 用户一次性报了 7 件事。**其中 P0 我上一版诊断错了** —— 这次找到了真凶。

### 🔴 P0（真凶）· 设计文件里的**素材永远加载不到**

用户报的是「画布不显示我做好的内容、显示是空的」。上一版我以为是"点编辑会覆盖内容"，
修了那个（那也是真 bug），但**没修到点上** —— 用户复测："p0问题还没修复、还是不会显示"。

**真凶**（这次有两条硬证据）：

1. **`designBaseDir` 全项目没有任何地方赋值** —— 只有读（`NodeTreeRenderer.resolveAssetPath`）
   和持久化。而设计文件里的素材是**相对路径**（`assets/背景/carbon.png`）；
2. 导入走的是 SAF **单文件**（`OpenDocument` 选一个 `design.json`）—— **拿不到它旁边的 `assets/`**。

于是：相对路径原样传给 `DashboardBackground.load` → 必然读不到 → **所有素材加载失败** →
由**控件（素材图片）**拼出来的表盘只剩空卡片。
纯程序化绘制的表（圆表/数字/条形）不依赖素材，所以这个 bug 一直没暴露。

**修法（两步）：**

- **不再静默**：`NodeTreeRenderer` 加 `BuildReport`（跳过原因 + 素材缺失清单，有界 8 条），
  `DashRenderer` 每次渲染打一行 `设计渲染 | 节点=N 建出=N 跳过(未绑通道)=… 素材缺失=N`，
  失败时补明细；空态文案也从 v1 那句（"请先连接设备并在 PID 页启用通道" —— 对 v2 完全不对路）
  改成**说人话的原因**。
- **真修复**：导入设计后，若它引用相对路径素材，主动问一次
  「选择素材文件夹」→ `DesignAssets.copyTree()` 把整棵目录树复制进 `files/design/<时间戳>/`
  → 设 `designBaseDir` → 重新应用。与 `DashboardBackground.import` 处理背景图**同一套思路**
  （外部路径不保证长期存在）。背景的**相对路径**也一并解析（原来是原样存的，同样读不到）。

> ⚠️ **未在真机上验完**：需要一份**素材还在**的设计包才能验"选完文件夹后真的显示出来"。
> 用户原来那份测试设计的素材（`files/test-assets/*.png`）在 17:56 那次重装时已丢失。

## v1.20.2 · 2026-10-06 · **P0：内置布局的画布会静默销毁你的作品** + 仪表盘沉浸 + 知识库

> 用户一次提了 8 件事。其中一件是 **P0 级 bug**，而且**日志里留下了铁证**。

### 🔴 P0 · 「画布不显示我做好的内容」的真身

用户原话：「当我自定义主题后、内部有控件的情况下、画布不显示我做好的内容、显示是空的」。
设备日志（2026-10-06 23:52）里是这两行：

```
[23:52:03] 渲染画布 | canvas=默认 type=0 theme=0 count=8      ← 画布是「普通驾驶」
[23:52:06] 画布已转为自定义 | canvas=默认 原类型=普通驾驶 gauges=8
```

**三件事叠在一起：**

1. **描述在说谎**：设置页对内置布局的画布写 `11 个仪表` —— 而屏幕上显示的是**内置布局的 8 个**，
   用户自己那 11 块表是**存着但没显示**的。用户因此以为"我的内容不见了"。
2. **点「编辑」会静默销毁它**：旧实现只有「转为自定义并编辑 / 取消」两个按钮，
   确认后 `convertToCustom` 直接 `customGauges.clear()` + 填内置布局 ——
   用户攒的 11 块表就这么没了（`dash.json` 3730 → 2509 字节），只弹一句"已转为自定义布局"。
3. **没有任何提示**：既没说"你还有一份内容"，也没说"它被覆盖了"。

**修法（三处）：**

- 设置页的描述改成说实话：内置布局时写「内置「普通驾驶」布局 · 另存着 11 块自定义表（未显示）」。
- 操作菜单加一条**非破坏性**的出路：「改用我存着的 N 块表」——只把类型翻成自定义，一个字都不动。
- 点「编辑」时，**只要画布里存着表就必须让用户选**：
  「保留我的 N 块表」（默认）/「用内置布局覆盖」/「取消」。

> 这与 v1.17.7 是同一个病：**两份内容 + 说不清哪份是权威 + 静默覆盖**。

### 仪表盘沉浸模式（左侧 tab 自动隐藏 + 那条"白条"）

用户原话：「仪表盘里自动隐藏左边的 tab 栏目（想个好的方法去实现）或者直接以悬浮UI的方式去做
tab 栏目、通过手势去拖出拖入？」「画布下面的白条太厚了、很明显、搞小点、且带点透明的效果那种」

**"白条"到底是什么 —— 实测出来的，不是猜的**（逐行亮像素统计）：

```
截图 2560x1600，而 App 窗口只到 y=1564
y=1564..1599（36px）平均亮度 27，峰值 80.5   ← 系统导航栏
其余各行平均亮度 12（App 本体 #0A0D12）
```

所以那是**系统导航栏**，不是 App 的控件 —— **改不了它的大小**。能做的只有
①在仪表盘页收起它 ②或者透明化。选了 ①（画布多 36px），并保留
`BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`（从边缘划一下它还会临时出现，不会把人锁住）。

**左侧 tab 栏**：不重新做一套悬浮导航（那就是**两份导航**，本项目因为"两份权威"栽过三次），
而是把现成的 `navView` **平移出去**（`translationX` + `alpha`，**不用 GONE** ——
GONE 会让页面容器重排、画布尺寸变化、表盘跟着重排并闪一下），
左边缘留一条 **6dp 半透明把手**：点一下或往右拖就滑回来，5 秒不操作自动收起。

**实测**：`dashPager` 从 `x=200` 变成 `x=2`（画布**多出 198px**）；
下方那条从亮度 27~80 变成 **11.2**（与 App 背景 12 相同 = 看不见了）。

### 其余六件

## v1.20.1 · 2026-10-06 · 画布名浮标的**位置可选**（四角 / 隐藏）

> 用户对上一条那三个判断的回复：
> ①「编辑态禁用横滑」②「一套画布 = 一屏」→ **都按原样保留**（本版没动）；
> ③ 画布名浮标问「可以自定义位置、或预设四个角？」→ 本版按**四角 + 隐藏**做。

### 新增

- `Settings.canvasNamePos`（**全局**偏好，取值 `DashCanvas.NAME_POS_*`）：
  左上 / 右上 / 左下 / 右下 / **隐藏**。
  入口：仪表盘最右页「设置」→ 全局 → 「画布名浮标」。
- 右下角会自动**让开「编辑」按钮**（多 44dp 下内边距）—— 不加这一下，两个字会叠在一起。

### 为什么是四角预设，不是自由拖拽

1. 车上这块屏**只会设一次**，四个角足够覆盖所有实际诉求；
2. 自由拖拽要和「横滑翻页」抢同一个横向手势 —— **为了挪两个字把翻页搞坏不划算**；
3. 自由坐标会落到「编辑」按钮底下或贴边，又得再加一套避让规则。

真需要任意位置时，正确做法是"**长按浮标进入移动态**"（那时不翻页），
而不是让它在正常浏览时就能拖。这条同时写进了 `DashCanvas.NAME_POS_*` 的注释与迭代清单 P11 ——
免得下一个人把它当成"没做完"再重做一遍。

### 装机验证时抓到的三个真问题（都已修）

**这三个都是"不装机就看不出来"的类型** —— 单测全绿、编译通过，但实际用起来是错的/查不动的。

#### 1. `relayout()` 在**首次渲染之前**就拿空规格渲染了一次

日志里出现：
```
[UI][W] 仪表盘无可渲染的表：PID 全部查不到 | spec=0 ids=
```

根因：`DashRenderer.lastSpec` 的初值是**空列表**，而容器的
`addOnLayoutChangeListener` 在**第一次布局**（`0,0,0,0 → 0,0,W,H`）就会触发 `relayout()` →
`render(lastSpec = 空)`。于是"还没有任何规格"被当成"规格是空的"，
打出一条**误导性的**警告，并把空态提示闪一下。

为什么多画布之后必须挡：**每一页都有自己的渲染器，而非当前页故意不渲染** ——
那些页面被布局时 100% 走到这里，日志里会堆一排查不出所以然的"PID 全部查不到"。
修法：加 `hasRendered` 标记，`relayout()` 在收到第一次规格之前直接返回。

#### 2. 转换日志**自己骗自己**：`原类型=自定义仪表`

`convertToCustom()` 里先 `Store.settings.dashType = CUSTOM` + `saveDash()`，
而 `saveDash()` 会经 `snapshotToActiveCanvas()` **把 `c.type` 就地同步成 CUSTOM** ——
之后才读 `c.type` 打日志，于是原本是「普通驾驶」也被写成「自定义仪表」，
日志里完全看不出它原来是什么。修法：改之前先把 `fromType` 抓下来。

#### 3. `setMessage` + 列表 = **列表被整个丢掉**（最严重的一个）

三个对话框（画布名浮标 / 轮询间隔 / 套用预设）都是"说明文字 + 选项列表"，
在设备上**只剩标题 + 说明 + 取消，一个选项都没有** —— 功能等于不可用。

实测判据（`uiautomator dump` 里 `android:id/text1` 的节点数）：

| 对话框 | message | 列表 | text1 节点 |
|---|---|---|---|
| 行操作菜单 | 无 | `setItems` | **4** ✅ |
| 画布名浮标位置 | 有 | `setSingleChoiceItems` | **0** ❌ |
| 轮询间隔 | 有 | `setSingleChoiceItems` | **0** ❌ |

即 `MaterialAlertDialogBuilder` 同时收到 message 与列表时会丢掉列表。
（全项目只有我这三处用了这个组合；老代码的列表对话框都用 `AlertDialog.Builder` 且不带 message，
所以这个坑以前没暴露过。）

修法：说明**进标题或进选项文字**，列表对话框一律不带 `setMessage`；
轮询间隔那个说明较长，改成**自定义 View（说明文字 + Spinner）** ——
与 `showGridDialog` 走同一条已验证的路子。

### 实现上的两个小决定

- **位置是全局的、不跟着画布走**：跟着走的话横滑时小字会在四个角之间乱跳。
  有 `浮标位置是全局的_切画布不变` 一条用例钉着。
- 用 `layout_gravity` + **padding** 而不是 margin：padding 在四个角上都等价于"离边多远"，
  一套值就够；margin 得为每个角各算一遍 start/end 组合。

### 三个必须记下来的坑（都在这版里踩到并修掉）

1. **`load()` 的顺序反了会重置用户设置**（最危险的一个）。
   `dash.json` 的网格迁移里会调 `saveDash()`，而 `saveDash()` 现在要把画布写进
   `settings.json` —— 旧的读取顺序（先 dash.json 后 settings.json）会拿**还没加载的默认
   settings** 覆写 `settings.json`，用户的轮询间隔、主题、画布全被冲成出厂值，
   **日志里一条都不提**。现在 `load()` 先读 settings 再读 dash，并有注释钉着。
2. **`ViewPager2` 分不清"用户滑的"和"我们调的"**。新增一套画布会把设置页从第 N 页挤到
   第 N+1 页，我们必须自己把 pager 挪过去；挪的过程中 `onPageSelected` 会报出中间页码
   （正好是一套画布）—— 照它切的话，用户只是加了套画布，当前画布却被换成了别人。
   现在凡是程序化翻页都先记 `awaitingPos`，期间一律不切画布（`DashFragment`）。
3. **XML 注释里不能出现 `--`**：`aapt2` 直接报
   `注释中不允许出现字符串 "--"`。我在注释里画了个 Markdown 表格（`|---|---|`），
   资源合并整个失败。改成项目符号列表。

### 设计取舍：`Settings` 里那几个字段现在的身份是"当前画布的实时副本"

`settings.dashType / gaugeTheme / designJson / bgImagePath / dashPageIndex` **保留**，
但由 `Store.snapshotToActiveCanvas()` / `loadActiveCanvas()` 在落盘与切画布时双向同步。

为什么不用"给每个调用点换成转发属性"：那会让**漏改一处就静默读到过期值**成为可能
（渲染、编辑器、主题编辑器加起来 100 多处）；副本方案里漏改只是"少存一次"，
下一次 `saveSettings()` 就补上了。`Store.activeCanvas()` 永不返回 null（空列表/悬空 id 自愈）。

## v1.19.20 · 2026-10-06 · 仪表盘顶栏：修掉「普通/性能/自定义」那一行的**空间分配荒谬**

> 用户原话："普通/性能/自定义这一行**十分的不美观**"。
> 这次不是凭感觉改的 —— 先用 `uiautomator` 把**真实几何**量出来，问题非常具体。

### 量出来的事实（改前）

| 控件 | 宽度 | 问题 |
|---|---|---|
| 「普通」 | **709px** | 占整行 30%，而内容只有 2 个字 |
| 「性能」 | 709px | 同上 |
| 「自定义」 | 710px | 同上 |
| 分段控件整组 | **2124px** | 吃掉整行 |
| 「布局」 | **91px** | 2 个字挤在 91px 里，左右各只剩 12px |
| 「风格」 | 91px | 同上 |

### 根因

```xml
<MaterialButtonToggleGroup
    android:layout_width="0dp"
    android:layout_weight="1"      ← 吃掉全部剩余宽度
    ...>
    <MaterialButton layout_width="0dp" layout_weight="1" />   ← 组内再平分
```

**分段控件（segmented control）本来就该"贴着自己的内容"** ——
给它 `weight=1` 之后，每段 708px 去放两个字，**整段全是空白**，
"分段"的视觉语义完全没了；同时把右边三个真正的操作按钮挤成 91px。

### 改法

1. `dashToggle` 去掉 `weight=1`，改 `wrap_content`（贴内容）
2. 三个分段 `wrap_content` + `minWidth=64dp` + 左右 14dp padding
3. **加一个弹性空白 `View`（weight=1）** 把右侧操作推到行尾 ——
   要占位就用空白，**不要让控件自己撑成空白**
4. 三个操作按钮 padding 8dp → 12dp（不再挤）

### 验证（真机实测几何，判据是数字不是感觉）

| 控件 | 改前 | 改后 |
|---|---|---|
| 「普通」 | 709px | **144px** |

## v1.19.18 · 2026-10-06 · 规则动作：音效可选**自定义音频文件** + 仪表变色可**自动恢复**

> 用户提了四块需求，这是**第一块**（最独立、可测的那块）。
> 另外三块（规则模拟测试 / 仪表盘全屏 / 顶栏重做）见文末「下一步」。

### 1. 播放音效：可以指定音频文件

以前 `sound` 动作的 `p1` 只能是内置音效名（`tick_left` / `tick_right` / `warn` / `beep`）。
现在**也可以是一个音频文件**：

- 动作行上多了个 **📁** 按钮（只在「播放音效」时出现，与 ♪ 一样按类型显隐）
- 点它走 SAF（`OpenDocument` + `audio/*`）选文件
- 选完按钮文案**变成文件名**，`p1` 存 `content://` URI

**三个实现上的要点**（都是"不做就会静默坏掉"的）：

| # | 要点 | 不做的后果 |
|---|---|---|
| 1 | **`takePersistableUriPermission`** | 重启 App 后 URI 没读权限 → 规则触发时**静默不响** |
| 2 | 判据 `RuleAction.isAudioFileSpec()` **只有一份** | 编辑器当成文件、播放器当成名字 → **现象上完全看不出** |
| 3 | 文件加载失败**不回退 beep** | 用户会以为"选的文件就是这声"，而真正的原因被顶替掉了 |

判据是**纯函数**且有用例钉着（`内置音效名不算音频文件` / `用户选的音频文件算音频文件`）。

### 2. 仪表变色：N 秒后自动恢复

`gauge` 动作的 `p3` 以前是"(不用)"，现在 = **N 秒后自动恢复**（空 = 一直保持）。

**为什么需要**：变色规则最常用的写法是"超温变红"，而"恢复正常后变回来"得**另配一条规则**去 reset ——
很容易忘了配，于是**仪表永远红着**，看起来像 App 坏了。

> 用 `p3` 而不是新加 `p4`：动作行只有三个输入框，**加了字段用户也填不了**。

### 3. `RuleAction` 加了 `p4`（第 4 个自由参数）

给"选了音频文件时的**显示名**"用 —— `p1` 存 URI 是给机器看的，
把 `content://media/.../1234` 甩在规则描述里没人看得懂。

有默认值 + `toJson` 里**空值不写出**，所以**存量 JSON 不需要迁移**。

### 4. 规则**模拟测试**（本次的重点）

规则编辑器底部新增 **「▶ 模拟测试（回仪表盘看效果）」**。点它：
保存规则 → 起模拟 → **自动回仪表盘** → 右下角出现悬浮条。

**模拟的语义：只改"条件判定"，别的一律不动。**

被模拟的规则条件**直接判成立**，而 `durationMs` / `cooldownMs` **照常生效**。
这不是偷懒 —— 那正是要看的东西：实车日志里那条"左转向灯音效"

**⚠️ 最容易做错的一处：模拟必须自带节拍。**

## v1.19.17 · 2026-10-06 · P10-1：「这台车不支持」的 PID 自动退出轮询

> 迭代清单 **P10 第 1 条**。症状：那 5 条 `std_0A` / `std_14` / `std_22` / `std_5C` / `std_5E`
> 每分钟都在打 `PID 连续失败进入冷却`，而 `轮询汇总 | 有值 20/25` 永远差 5 个。

### 判据的关键：**只有「ECU 明确说没有」才算**

优化目标是"连续失败 N 次就退出轮询"。**如果什么失败都算**，
一次链路抖动（超时 / 写入被拒）就能把**全部** PID 判成不支持 ——
**车没坏，App 先自己瞎了。**

所以新加的 `ObdProtocol.isUnsupportedEvidence(raw)` **只看原始响应**：

| 响应 | 算不算 | 为什么 |
|---|---|---|
| `NO DATA` | ✅ | ECU 收到了请求、**明确说**没有这个 PID |
| NRC `0x11/0x12/0x31/0x7E/0x7F` | ✅ | ECU **明确拒绝**（服务/子功能不支持、超出范围） |
| **空串（超时）** | ❌ | **我们没问到** —— 不是车说没有 |
| `CAN ERROR` / `BUS ERROR` / `UNABLE TO CONNECT` | ❌ | 总线/连接问题，与 PID 无关 |
| `STOPPED` / `ERROR` | ❌ | 适配器状态问题 |
| NRC `0x13`（报文长度错） | ❌ | **我们自己发了畸形帧**，是 App 的错 |

> ⚠️ 容易踩的点：`ElmSession.request` **超时返回空串**，而 `NO DATA` 是**有内容**的响应 ——
> 两者在 `parse` 里**都会塌缩成「无有效响应」**。所以**只能看原始响应，不能看错误串**。

### 改了什么

| 位置 | 内容 |
|---|---|
| `ObdProtocol.isUnsupportedEvidence()` | 纯函数判据（新增，可测） |
| `ObdProtocol.negativeCode()` | 取出 NRC **码** —— 按码判断，**不按中文名**（名字一改判断就静默失效） |
| `ObdEngine` | `unsupportedStreak` 计数；连续 **3** 次明确回绝 → 加入 `unsupportedPids`、**退出轮询**、记一行 W |
| `ObdEngine` 轮询 `due` 过滤 | 判定不支持的**直接不问**（不再白占总线、不再刷冷却行） |
| `ObdEngine` 汇总 | 分母**只算还在轮询的** → `有值 20/20`；尾注「另有 N 条本车不支持」 |
| `ObdEngine.reEnable()` / `ObdController.reEnablePid()` | **手动重启用** |
| `PidAdapter` | 判定不支持的行**标灰**（alpha 0.45）+ 备注「本车不支持，已退出轮询 —— **长按重新启用**」 |

**为什么判据要"连续"**：成功一次就清零 `unsupportedStreak` ——
长期累积会把"偶发几次 NO DATA 但一直有值"的 PID 误判掉。

**为什么必须留手动出口**：判定依据是 ECU 回绝，但车况会变（换适配器 / 换车 / 上次总线正忙）。
**判定错一次就不让用户改，等于把 App 写死。** 判定是**内存态**，重启 App 自然重测。

## v1.19.15 · 2026-10-06 · 「对比基准」找位工具：把找信号从"人工差分"变成"点两下"

### 背景：下一个瓶颈不是"能不能收"，而是"每个信号都要人工找位"

转向灯走通了（`0x09A` bit2/bit3），但**那一位是我在电脑上手工差分找出来的** ——
每收一个新信号就要一个人工环节：跑两次探测、把日志拉回来、写一段脚本比对。
`0x09A` 那一次花了不少时间。**这个环节必须消失**，否则剩下那些信号一个个来会拖很久。

### 做了什么

- **`CanDiff`（新，纯逻辑 + 5 条回归测试）**：把一个 CAN ID 出现过的**所有不同取值**
  折算成**每一位**的状态 —— `CONST0` / `CONST1` / `VARIES`，再比两次探测的**状态**。

  ⚠️ **判据是"状态"，不是"两个值 XOR"**：单次采样会撞相位
  （转向灯 1.4 Hz，采到亮还是暗是掷硬币），XOR 会把相位差异当成信号。
  "某一位从恒定变成在变"才与相位无关。

- **「对比基准（找位）」按钮**：「CAN 探测」页。把**上一次探测**当基准，
  列出状态变化的位，每行一个「加为监听」按钮。
- **一键加为监听型 PID**：`★ 09A 第3字节 bit2：恒0 -> 在变` + 一次点击 ->
  `Store.upsertPid` 生成 `source="monitor"` / `header="09A"` / `formula="bit(C,2)"` 的条目
  —— 于是它**立刻**能用在下拉框、仪表和规则里。用固定 id，同一处再加是**覆盖**不是堆积。
- 收尾时**自动打印差分**（`CAN 差分位 | … 公式=bit(C,2)   <== 这次操作引起的`），
  所以即使不点按钮，日志里也有。
- 基准的提升只在 `start()` 里做；`reset()`（清空按钮）**不动**基准 ——
  否则在两次对照之间按了清空，基准就被换掉，"对比基准"直接失效。

### 修掉的那条**已被实验推翻的前提**

`docs/迭代清单.md` 原文写着：

> 13 个指示灯 → **厂家 Mode 22，号必须扫描器实测**

**这是错的。** 转向灯实测证明它是**广播帧的一个位**（`0x09A`），**不是 Mode 22 的 DID**：
Mode 22 扫了 `1100~11FF`（3 个应答）和 `DA00~DAFF`（50 个应答），**一个都没有转向灯**。
所以那 13 个指示灯大概率都在广播帧里，**用同一套工具（探测 + 对比基准）就能收**，
而且**不需要 `header`**（广播就能问到）。迭代清单已加更正说明。

## v1.19.8 · 2026-10-06 · 转向灯找到了：`0x09A` 的低两位

### 结论

**CAN ID `0x09A`，数据第 3 字节（`A B C…` 里的 `C`）：**

| 状态 | `0x09A` 数据 | 公式 |
|---|---|---|
| 都不亮 | `00 00 00 00 88 00 03 00` | —— |
| 左转 | `00 00 04 00 88 00 03 00` | `bit(C,2)` |
| 右转 | `00 00 08 00 88 00 03 00` | `bit(C,3)` |

完整证据链见 `stage/oncar-evidence/turn-signal-09A.md`。

### 为什么前面四组实验全都失败 —— 采样率

`0x09A` 只以**约 2.1 Hz** 广播。不过滤时克隆版总共只漏出约 77 帧/秒，
摊到约 80 个 ID 上就是**每个 ID 每秒 1 帧**，20 秒只采到 4~5 帧 —— 1.4 Hz 的闪烁被完全抹平。

加上 CAN 过滤器（`ATCM700+ATCF000`）把带宽让给它之后：

```
75/76:  0.7 帧/秒  ->  20 帧/秒
总帧数:  77/秒     ->  344/秒
```

`changed` 第一次能反映真实翻转：关灯 `changed=1`，开灯 `changed=13`（两次独立复现）。

**教训：判断"能不能看见一个信号"之前，先算 `适配器实际帧率 ÷ 目标 ID 广播频率`。**

### 工具上的三个关键补齐

- **CAN 接收过滤器**（`ATCRA` / `ATCM`+`ATCF`）：探测页新增「过滤器」输入框。
  掩码版一趟覆盖 256 个 ID，16 趟扫完整个 11 位 ID 空间。
- **取值集合**（`Aggregate.values`，有界 8 个）：聚合里的 `lastData` 只是**最后一帧**的值，
  周期信号很容易正好停在暗相位 —— 实车 `09A` 左转/右转两次的 `last` **都是 `00`**，
  光看 `last` 根本分不出左右。**这个字段是最后一块拼图。**
- **收尾必须重新初始化**：`ATAR`/`ATCM000`/`ATCF000` 三条**都回 `OK` 却清不掉过滤器**
  （AT 命令由适配器内部处理，而 `01 xx` 要等 CAN 应答，正好被挡住）。
  唯一确定有效的是 `ATZ` 全复位 —— 所以用过过滤器就自动 `initializeAndStart()` 一次。

### 顺带修掉的三个坑（都在收尾/准备阶段）

- **收尾的重新初始化是异步的** → 用户可以在它跑完前开始下一次探测，
  它的 `ATZ/ATE0…` 会和新探测的 `ATMA` 互相打架（实车：`frames=110`，正常应为 2728）。
  现在 `finish()` 有重入保护，且**收尾期间拒绝新探测**。
- **`finish()` 没有重入保护** → 到时自动停止 + 手动停止各跑一遍收尾（日志里两条「探测结束」）。
- **准备前没排空 ATMA 残余输出** → 第一条 AT 读到上一次的积压，
  表现为 `ATH1 -> STOPPED`，后果是**整趟探测作废**（`lines=3700 parsedFrames=0`）。
  现在准备前先 `\r` + 等 300ms，且 `ATH1`/`ATS1`/`ATL1` **各试 3 次、只认 `OK`**。

### ⚠️ 尚未解决：广播帧怎么进规则引擎

`0x09A` 是**广播帧**，不能像 PID 那样主动请求，只能靠 `ATMA` 被动监听；
而 **`ATMA` 期间适配器独占（半双工），无法同时轮询**。
所以要驱动「左转/右转滴答」两条规则，需要新能力：**「监听帧 → 虚拟 PID」+ 与轮询分时复用**。
已记入待办。

## v1.19.3 · 2026-10-06 · CAN 接收过滤器（探测终于能看清闪烁类信号）；以及一个"看起来像链路坏了"的坑

### 新增：CAN 探测支持 `ATCRA` 过滤器

ATMA 抓不到转向灯的**根因是采样率**（约 77 帧/秒 ÷ 约 80 个 ID = **每 ID 每秒 1 帧**），
而解决它的钥匙是 **CAN 接收过滤器**：过滤到少数 ID 之后，同样的带宽全给它们。

- 实车探针确认 **克隆版支持 `ATCRA`**：`ATCRA228` -> `OK`。
- 「CAN 探测」页新增 **过滤器** 输入框（`etSniffFilter`）。
  填 CAN ID（如 `228`）则在 `ATMA` 之前发 `ATCRA228`；**留空 = 不过滤**（原行为不变）。
- 每条 AT 的应答照旧记日志（`探测准备 | ATCRA228 -> OK`）。

### ⚠️ 坑：过滤器会**连带挡住正常 OBD 的应答**

正常 OBD 请求发给 `7DF`、应答回 `7E8`；而 `ATCRA228` 只放行 `228` ->
**应答全被过滤掉**，表现是「链路突然全是超时」，而**从界面上完全看不出原因**。

实车踩到的原始记录：

```
[14:35:52] 轮询汇总 | 有值 20/25 ...        <- 最后一次正常
[14:35:40] TX | ATCRA228                    <- 过滤器设上
[14:36:00] 超时无响应 | cmd=01 A6 timeout=600ms
[14:36:00] 超时无响应 | cmd=01 0D timeout=600ms
[14:36:01] 超时无响应 | cmd=01 42 timeout=600ms   <- 连续 11 条全部超时
```

对策（两层）：

1. `CanSniffer.finish()` 里**必须**发 `ATAR`（Automatic Receive，关掉接收过滤），
   并**记录应答**；应答不是 `OK` 时打 `E` 级日志，明确指向"重新初始化"这个兜底动作。
2. 兜底：初始化第一步是 `ATZ`，**会复位一切**（含 CAN 过滤器）——
   所以"到「连接」页重新初始化一次"永远是有效的恢复手段。

### 顺带更正一处过时的注释

`CanSnifferActivity` 的类注释原本写「转向灯、车门、刹车这类信号**只能**被动监听」。
2026-10-06 实车证明这句是错的：这些车身信号 **Mode 22 主动请求也能问到**
（广播 `22 DAxx` 一次就问到 50 个 DID），而且**主动请求的采样率由我们自己定**。
注释已按事实改写。

想用被动监听找**转向灯**（标准 OBD 里没有它）。做了四组对照实验，全部无效：

| 实验 | 结果 |
|---|---|
| 转向灯 关 / 左转 | 两次的 **81 个 ID 一个不差**，`changed` 差异 <=3（帧数缩放的正常波动） |
| 刹车 松 / 踩 | 第一次 `166` 看着像（`30 10`->`31 88`），**复测没复现**（`70`/`62` 同样在抖） |

（`header` 只加在了 PID 上，没加在扫描器上）—— 已记入待办。

- **AT 应答记日志**：`探测准备 | ATH1 -> OK`。三次探测的 AT 序列曾经逐字相同却结果不同，

- **`CAN ID(changed)` 排序**：闪烁类信号 count 不高但 changed 高，按 count 排会被埋掉。
- `AGG_LOG_MAX` 40 -> 130（全量 ID）；`RAW_LOG_MAX` 12 条原始行（有界，防洪水）。

## v1.18.7 · 2026-10-06 · 🔴🔴 **支持位图枚举少加 1 —— "位图漏报"的真身**

`PidScanner` 解位图时写的是 `out.add(block + i)`。但 `01 00` 响应的**最高位代表 PID `01`**，
正确是 **`block + 1 + i`**。**整条链每个块都少加 1**，于是扫描器去问的是
"每个被声明支持的**前一个** PID"：

| 位图位 | 应用算的 i | 应用去问 | 真正的 PID |
|---|---|---|---|
| `A8` b7,b5,b3 | 16,18,20 | `01 10` `01 12` `01 14` | `01 11` `01 13` `01 15` |
| `13` b4,b1,b0 | 27,30,31 | `01 1B` `01 1E` `01 1F` | `01 1C` `01 1F` `01 20` |
| `14`（A0 块） | 3,5 | `01 A3` `01 A5` | **`01 A4` `01 A6`** |

实车对照（2026-10-06 阿特兹）：扫描窗口里扫描器实际发出的正是
`01 00` `01 12` `01 1B` `01 1E` —— 与"少加 1"的预测**逐字吻合**。

### 两个后果，都很能骗人

- **车厂声明了的 PID 没被问**（`11`/`13`/`15`/`1C`）-> 看起来像"这台车不支持"
- **去问的那个 PID 碰巧也能答**（`10`/`12`/`1B`）-> 看起来像"位图在漏报"

> ⚠️ **撤回 v1.18.4 里"支持位图漏报 `11`/`21`/`A6`"那条结论 —— 它是错的。**
> 位图没漏，是枚举偏了一位。`21` 同理（0x20 块声明了 `21`，应用去问 `20`）。
> 更要紧的是：**车厂其实声明了 `A4`（挡位）与 `A6`（总里程）**，只是应用去问了
> `A3`/`A5` —— 这才是"挡位一直能找到、却从来没被问过"的真正原因，
> 也解释了 `A5` 为什么回 `NO DATA`（它本来就没人声明要支持，是被错位问到的）。

### 修法

把解位图抽成**纯函数** `PidScanner.decodeSupportBitmap(block, data)`，修正为
`block + 1 + i`，并加两条用**实车真实字节**的回归测试：

- `01 00` 的并集 `FE 3F A8 13` -> 断言最高位映射到 `01`，且**不能**映射出 `00`
- `01 A0` 的并集 `14 00 00 00` -> 断言解出 **`A4` 与 `A6`**

> 写完就跑挂一条：我断言 `0x10`"没被声明"，其实 `0x3F` 的 `b0` 正好是 PID `0x10`。
> **是测试抓到了我，不是代码错** —— 这正是加它的意义。

## v1.18.6 · 2026-10-06 · Mode 字段不补零 → 发出畸形帧（用户填错了却毫无提示）

实车同一天踩了两次，都是"Mode 只填了 1 位十六进制"：

```
12:04  PID 测试 | req=2 A4   raw=7F2A7F        ok=false
12:37  PID 测试 | req=1 A4   raw=NO DATA       ok=false
       PID 测试 | req=01 A4  raw=41A403000DE1  ok=true   <- 填 01 才对
```

### 根因

`PidDefinition.normalize()` 只做 `trim` + 压空白 + 大写，**不补零**：

```kotlin
fun normalize(s: String) = s.trim().replace(Regex("\\s+"), " ").uppercase()
```

Mode 填 `1`，发出去就是 `1 A4` —— ELM327 把 `1A4` 当**三个 nibble**，帧是畸形的，
ECU 回 `NO DATA` 或否定响应。**属于"用户填错了却没有任何提示"的那类错。**

### 修法（刻意收窄，避免改坏别处）

- **只补长度为 1 的 token**：`1` -> `01`、`4` -> `04`
- **只有整串都是十六进制时才动** —— `ATI` / `ATSH7E0` 这类 AT 命令不能被碰
- `7E0`（长度 3）**不动**：补成 `07E0` 会把 CAN 头毁掉

`requestString()` 与 `customRequest` 都走这条路，所以**旧配置里已存的没补零的串
也会被就地纠正**。

## v1.18.5 · 2026-10-06 · 🔴 **支持位图链被"另一个模块的应答"提前掐断 —— 扫描结果取决于谁先回**

上游：同一天两次扫描给出**完全不同的"这台车支持什么"**。

| 扫描 | 读到的位图块 | `supported` | 命中 |
|---|---|---|---|
| 11:56 | `00` `20` `40` **`60`** **`80`** **`A0`** | **57** | 31 |
| 12:34 | `00` `20` `40`（`60`/`80`/`A0` 全没读） | **16** | 12 |

### 根因：两个模块的 nextBit 相反，而到达顺序会变

这台车对每个位图块回**两份应答**（两个模块），它们对「还有下一块」
（`byte3` 的 `bit0`）判断**相反**：

```
01 40 -> 41 40 FE D0 8C 81   <- 模块1：0x81，bit0=1，「还有」
         41 40 C0 80 00 00   <- 模块2：0x00，bit0=0，「没有了」
```

而这两份的**先后顺序在两次运行之间会变**：

```
11:56  01 40 -> FE D0 8C 81 先到 -> 继续 -> supported=57（含 A1~C0）
12:34  01 40 -> C0 80 00 00 先到 -> 断在 0x40 -> supported=16
```

`querySupportedPids` 原来只取**第一份**应答（`extractData(..., ecuIndex = 0)`），
再拿它的 `bit0` 决定要不要继续 —— **于是"这台车支持什么"取决于哪个模块先回。**

12:34 那次 `0x61`~`0xC0` 整段不可见，而**挡位 `A4`、总里程 `A6` 就在那一段**。
**v1.18.0 把 `maxBlock` 从 `0x60` 提到 `0xC0` 只治了"上限"，没治这个提前退出。**

### 修法（`PidScanner.querySupportedPids`）

- 每一块**遍历所有模块的应答取并集**（`extractData(..., ecuIndex = 0,1,2,3)`，
  取不到即止；只用每份的**前 4 字节**，别把下一份的字节算进来）
- **不再用 `nextBit` 提前退出**：`mode 01` 全链只有 7 个请求
  （`00/20/40/60/80/A0/C0`），只在"这一块一个应答都没有"时才停
- 新增 D 级日志 `位图块 | block=.. ecu=.. PIDs=..`，下次实车能直接看出每块收了几家应答

**确定性 > 省两三个请求。**

## v1.18.4 · 2026-10-06 · 🔴 **日志页切走再切回来会 ANR（被系统杀）—— `hide()` 不触发 `onPause()`**

同一次实车（v1.18.3 跑通之后），用户切到「日志」页看日志，**App 被系统杀了**。

### 不是崩溃，是 ANR

```
12:06:13 am_anr : [com.icar.obd, Input dispatching timed out
   (MainActivity is not responding. Waited 5001ms for MotionEvent(action=DOWN))]
12:06:22 am_kill: [com.icar.obd, user request after error]
12:06:22 Zygote  : Process 13935 exited due to signal 9 (Killed)
```

crash buffer 里**没有 Java 异常**，`files/last-crash.log` 也**没有**（说明不是被捕获的异常），
是主线程卡死 5 秒导致输入分发超时，随后被 SIGKILL。

### 根因：GONE 的 RecyclerView 会无限堆积 adapter 通知

页面切换时间线（同一次会话的应用日志）：

| 时刻 | 事件 |
|---|---|
| 11:57:03.888 | `切换页面 \| log` —— 第一次打开（只看了 **3.4 秒**） |
| 11:57:07.287 | `切换页面 \| dash` —— 切走 |
| （隐藏 **8 分 59 秒**） | 监听器仍在收日志（~47 条/秒），而日志页不跑 layout |
| 12:06:07.070 | `切换页面 \| log` —— 再切回来 |
| 12:06:07.665 | 第一条 `超时无响应 \| cmd=01 49 timeout=600ms` |
| 12:06:13.009 | **ANR** |
| 12:06:22 | SIGKILL |

链条：

1. `MainActivity.switchTo` 用 **`hide()`/`show()`**（不是 `replace()`）—— 为了切页不重建、仪表盘不闪。
2. 但 **`hide()` 不触发 `onPause()`**（被隐藏的 Fragment 仍是 RESUMED）。
3. 所以 `LogFragment.onPause()` 里的 `unsubscribe` **永远不执行**，监听器在隐藏后仍然挂着。
4. 隐藏时 RecyclerView 的 View 是 **GONE** → 不跑 layout → 每次
   `notifyItemInserted` / `notifyItemRemoved` 都堆进 `AdapterHelper` 的待处理队列，**永不被消费**。
5. 47 条/秒 × 539 秒 ≈ **2.5 万个待处理 op**。
6. 切回来时第一次 layout 一次性回放全部 op → 主线程卡死 5 秒 → ANR。

**这也解释了为什么第一次打开（11:57）正常、第二次（12:06）必死** —— 堆积需要时间。

### 旁证：把「主线程被卡死」和「协议超时」分开

ANR 期间日志里有 26 条 `超时无响应 | cmd=01 .. timeout=600ms`，
但**每条命令的 RX 都到了**（`TX 01 49` → +46ms `RX 414927` → +603ms 才报超时）。
因为 `onRx` 是经 `main.post` 回调的：**主线程被卡死 → 回调不执行 → 协议层误报超时**。
所以这 26 条超时是 ANR 的**症状**，不是链路问题 —— 本次会话前半段 `超时无响应 = 0`。

### 修法（`LogFragment`）

- 监听器里加 `if (isHidden) return@addListener` —— 隐藏期间**不碰** RecyclerView。
- 新增 `onHiddenChanged(hidden)`：隐藏时停掉 `uiTick`；**切回来时用一次 `submitAll`**
  （整表替换，只发一次 `notifyDataSetChanged`）把落后的缓冲补齐，
  而不是把积累的两万多个 op 一次性喂给 RecyclerView。

> ⚠️ **同类风险不止这一页**：任何「RecyclerView + 在 `onResume` 里注册监听器」的页面，
> 只要会被 `hide()` 切走，就有同样的堆积路径。日志页只是**刷新率最高**（~47 条/秒）
> 所以第一个炸。新增这类页面时请一并实现 `onHiddenChanged`。

| 项 | 结果 |
|---|---|
| Kotlin 单测 | **550 全过** |
| 构建 | `BUILD SUCCESSFUL` |
| APK | `dist/iCarOBD-debug-v1.18.4-android.apk`（versionCode 37） |

### 追加实车结论：`01 A4` 到底能拿到什么（同日 · 无代码改动）

v1.18.0 的调研写的是：`A4`(164) = Transmission Actual Gear，4 字节，`(256C+D)/1000`，
**字节 B 是枚举的挡位状态**，值到挡位的映射"待停车场实测"。**实测做完了 —— 一半对，一半错。**

114 个样本、P/R/N/D 各反复测，**只有 3 种帧，零抖动**：

| 挡位 | 原始帧 | A | B | C | D | 样本数 |
|---|---|---|---|---|---|---|
| **P / N** | `41A403000DE1` | 03 | **00** | 0D | E1 | 85 |
| **R** | `41A403100DE0` | 03 | **10** | 0D | E0 | 14 |
| **D** | `41A403100DE1` | 03 | **10** | 0D | E1 | 15 |

**四条结论：**

1. **`A4` 存在、且完全确定性** —— 零抖动，可以当数据源用。
   （顺带：**它也不在车厂声明的支持位图里** —— 今天第二次撞到"位图漏报能用的 PID"。）
2. **"字节 B 是枚举挡位"这条是错的。** B 只有 `00` / `10` 两个取值，
   它是**1 bit 的「在挡 / 不在挡」标志** —— **P 和 N 的帧一模一样**，B 根本分不出它们。
3. **齿比 `(256C+D)/1000` 在静止时是死的**：P/N/D 全是 **3.553**、R 是 **3.552**。
   真实"实际齿比"不可能在 P、N、D 之间几乎不变 —— 所以它在这个状态下不携带挡位信息。
4. 实际能拿到的是**三态**：

   | 判据 | 含义 |
   |---|---|
   | `B=00` | **P 或 N** |
   | `B=10` 且 `D 字节=E0` | **R** |
   | `B=10` 且 `D 字节=E1` | **D** |

   可直接填的公式（产出 0/1/2）：**`bit(B,4)*2+bit(D,0)-1`** → `0=P/N`、`1=R`、`2=D`。

> ⚠️ 字节 `A=03`、字节 `C=0D` 在四个样本里全一样，是**常量**（大概率是"支持位 / 格式"字段）。

**拿不到 1~6 挡。** 要拿到必须让车动起来 —— 看齿比随升挡下降
（新建 PID：Mode `01` / PID `A4` / 公式 `(C*256+D)/1000`，开 CSV 记录 1Hz，慢速开一段）。

**显示成文字还没接上**：`valueLabels` 挂在 **`GaugeItem`（仪表显示项）** 上，
**不在 `PidDefinition` 上** —— 所以数字 0/1/2 能显示，要变成 `P/N · R · D`
得走主题工具往设计文件的节点里写映射表（P9 方向 A 的原设计如此）。

### 然后去看了一个我一直没看的层：**BLE 的连接建立**

对比两份日志（**同一个适配器、同一个特征**）：

```
10-03 成功那次：  已写 CCCD → MTU 协商 → CCCD 写入完成 | status=0    ← 回调回来了
10-06 失败那次：  已写 CCCD → MTU 协商 → （没有「CCCD 写入完成」）   ← 永远没回来
```

**回调丢了。** 而 Android 的硬约束是：**同一连接同时只允许一个未完成的 GATT 操作**。
回调不来 → 栈上永远挂着那个描述符写 → **之后每一次 `writeCharacteristic()` 都返回 false**。

**于是 902 条"写入被拒"、900 条"超时无响应"、一条数据都没有** —— 全对上了。

### 根因在我们自己的代码里（一个 12ms 的竞态）

```kotlin
L193: runCatching { g.requestMtu(512) }   // GATT 操作 ①
L194: enableNotify(g)                      // 里面 writeDescriptor(cccd) → 操作 ②
```

**两个操作背靠背发，中间不等任何回调。** 第二个被丢弃、第一个的回调也可能丢。

**而且那个"兜底"是死代码**：

```kotlin
main.postDelayed({
    if (state == State.DISCOVERING) { ... }   // ← onMtuChanged 已把 state 推成 READY
}, 1200)
```

`onMtuChanged` 12ms 后就回来了、把 state 推成 READY ——
于是这个兜底**永远不触发**，App 照样宣布"已就绪"，然后开始疯狂写入。

> **这就解释了"时好时坏、改了很多版都不行"**：它是一个**竞态**。
> 10-03 那次运气好没撞上（日志里 `CCCD 写入完成` 是**有**的）→ 真数据流出来了。
> 而**我们一直在改协议层**（ATCAF0、NRC、ok 判据、位图链…），
> **凶手根本不在那一层。**

### 三处修复

| # | 修复 | 说明 |
|---|---|---|
| 1 | **串行化 GATT 操作** | 先 `requestMtu`，**在 `onMtuChanged` 里**才 `enableNotify`。两个操作不再重叠 |
| 2 | **让兜底真的会触发** | 判据从 `state == DISCOVERING` 改成显式的 `cccdPending` —— 后者不会被 MTU 回调提前改掉 |
| 3 | **回调丢了就重连，不要假装就绪** | 2 秒等不到 `onDescriptorWrite` → 判定"GATT 栈已卡死" → 记 E 日志 + **主动断开**（走既有自动重连）。重连过一次还失败就如实标"CCCD 未确认"，不假装正常 |

另外 `notifyStarted` 保证"开通知"这个操作**只发一次**（`onMtuChanged` 与兜底都会调它，
两个都发就又撞车了）；`onServicesDiscovered` 里复位三个标志（重连要能重来）。

## v1.18.0 · 2026-10-06 · 外部资料研究：**挡位/总里程是标准 PID，不用等车**

用户给了 4 个参考（ELMduino、Wikipedia OBD-II PIDs、一个马自达 ND3 逆向项目、carscaner），
让我观摩并顺便找找别的。**收获很大，而且直接改了我们一个错误假设。**

### 🔴 最重要的一条：**我们犯了一个已被别人明确记录过的错**

马自达那个项目（[drewid74/2024-nd3-mazda-obdii](https://github.com/drewid74/2024-nd3-mazda-obdii)，
把读数与真实里程表对过）在「Dead Ends」一节里写：

> A Mode 22 NACK means *that module address is dead*, **not** that the signal is unavailable.
> … Gear position was previously (incorrectly) treated as unreachable **on exactly this reasoning
> — it was in `01 A4` the whole time.**
>
> **Always probe `01 00 → 01 20 → 01 40 → 01 60 → 01 80 → 01 A0 → 01 C0`**
> and enumerate what the car actually advertises **before** concluding anything is out of scope.

**我们犯的是同一个错**：把「挡位 / 总里程」归进"要厂家 Mode 22、要等车"那一堆。
它们其实**一直在标准空间里**。而且那个项目挖到底，Mode 22 只找到 **2 个**真正有用的信号
（机油温 `22 13 10`、刹车位置 `22 2B 0D`）—— **其余全在标准空间**。

### 落地一：`01 A6` 总里程（守卫 15 → 14）

| 来源 | 内容 |
|---|---|
| [Wikipedia OBD-II PIDs](https://en.wikipedia.org/wiki/OBD-II_PIDs) | `A6`（十进制 166）Odometer，4 字节，0~429,496,729.5 km，`(2²⁴A+2¹⁶B+2⁸C+D)/10` |
| 马自达项目 | 同一公式，且**与真实里程表对过**（原话 "drift matched real"） |

两处独立来源一致 → 已加 `std_A6`，别名 `obd.odo`，控件 `g_odo` 直接可用。
**这正是我 v1.17.6 说"查证不到、不敢加"的那条** —— 现在有权威来源了。

### 落地二：扫描器的位图链**停在 01 60，永远发现不了 A4/A6**

我们的扫描器**已经在走位图链**了（这一点原来做得对），但：

```kotlin
val maxBlock = if (mode == "09") 0x40 else 0x60   // ← 只到 0160
```

于是 **A1~C0 段永远枚举不到** —— 而挡位 `A4`、总里程 `A6` 就在那一层。
连带 `ScannerActivity` 的 Mode 01 默认范围也是 `00~60`，候选还要过一道 `from..to` 过滤，
**两处都得放宽**才有效。现在：`maxBlock → 0xC0`、默认范围 `00~C0`，
并抽成 `PidScanner.maxSupportBlock(mode)` + 回归守卫。

| 项 | 结论 |
|---|---|
| **响应前缀** | 马自达项目的「Response-Prefix Fix」说：**正响应 SID = 请求 SID + 0x40，别硬编码 `62`** —— **我们本来就是这么写的**（`matchData` 里 `(mode + 0x40)`）✓ |
| **`01 14` 氧传感器** | 该项目实测：ND3 上 **`0114` 根本不在支持位图里**，B1S1 是**宽域**传感器（走 `01 34` 的 lambda+电流）。我们 `std_14` 的说明原写"0.1~0.9V 来回跳是正常的" —— **对马自达是错的**，已改正 |
| **`01 65`** | 是**推荐挡位（换挡提示）**，**不是当前挡位**。别拿它当挡位用 |

## v1.17.6 · 2026-10-05 · 修一个**我自己上一版引入**的风险 + 一个被守卫抓到的编码坑

### 1. `ok=false` 现在也启动轮询（修 v1.17.2 的副作用）

v1.17.2 把 `ok` 的判据**加严**成"`0100` 真的解析出 4 字节位图"（原来只判"没看见错误关键字"）。
判据本身是对的，但它有一个**我当时没想到的副作用**：

```kotlin
if (r.ok) startPolling() else AppLog.e(...)   // ← ok=false 就完全不轮询
```

判据加严 → **假阴性概率变高** → 而假阴性会从"日志里报个错"放大成
**"明明能通却什么都不做"**。实车会话 B 恰恰就是 `ok=false` 却有真实数据。

现在改成**照常轮询**：真不通时由**总线负载保护**自动降频，
30 秒后的「轮询汇总」会明说「有值 0/N」—— **比静默不动更容易看出问题**。

> **教训：收紧一个判据时，要同时检查它的失败分支会做什么。**
> 我只改了判据，没看它下游接的是什么 —— 而下游是"什么都不做"。

### 2. ⚠️ 被守卫抓到的一个坑：**编辑工具会抹掉 `.ps1` 的 BOM**

改 `tools/run-all.ps1` 的超时之后，构建守卫当场报红：

```

```

原因是**编辑工具把文件开头的 UTF-8 BOM 抹掉了**（首字节从 `EF BB BF` 变成 `<`）。
而 [`接手大纲.md`](接手大纲.md) §4.1 早就写着这条红线：
**无 BOM 的 `.ps1` 会被 Windows PowerShell 5.1 按 ANSI(GBK) 解码，
中文注释变乱码并吃掉行尾，把下一行代码并进注释里** ——
报错是 `Unexpected token '}'`，看起来像语法错，实际是编码问题（v1.10.1 实测栽过一次）。

**已恢复 BOM，守卫转绿。** 顺便说明：**这条守卫的价值不在"防我写错代码"，
而在"防工具悄悄改掉我没打算改的东西"。**

420 / 600 → **240 / 240**。实测 Kotlin ~16s（冷启 37s）、浏览器 ~60s；
原值是"Gradle 会卡死"那个时代的产物，真卡住时白等 10 分钟。

按红线「**厂家 PID 的号不要猜**」，**查不准就不加**，只记在这里等确认。

> 这和"要等车"不同：**它是"信息不足"**。信息不足时该做的是**标注未知**，
> 而不是先填一个看起来合理的值 —— 那会变成下一个 `ATCAF0`。

| 项 | 结果 |

## v1.17.4 · 2026-10-05 · 两处**不用等车**的 P9 缺口：平均油耗 + 故障灯 MIL

> P9（非数值 PID 模型）的"模型"那一半在 v1.17.0 就做完了，
> 剩下的是"给 18 个控件找数据源"，一直以为**全都要等车**。
> 这一版发现**其中两个根本不用等** —— 要么是标准 PID，要么纯本项目就能算。

### 1. 平均油耗（`calc_avg_l100`）—— 纯派生，不依赖任何厂家 PID

```
平均油耗 = 累计用油 ÷ 累计里程 × 100
```

- **累计用油**：`calc_lh`（L/h）对时间积分 → L。而 `calc_lh` 要么来自标准 PID `015E`，
  要么由 MAF（`0110`）推算 —— **两条路都不需要厂家地址**
- **累计里程**：`calc_km`（车速积分），本来就有

放在 `Derived.integrateDistance()` 而不是 `computeAll()`：它需要 `dt` 才能把 L/h 积成 L，
而 `computeAll` 算的是瞬时量。同一个 `dt` 也让**里程与油量的时间基准一致** ——
两边用不同的 dt，平均油耗会慢慢漂。

**两个刻意的取舍**：

- **里程 < 0.5km 时不出值**：0.2km 上用了 0.05L 会算出 25L/100km 这种噪声，
  一上路就显示"25 个油"比先显示 `--` 更糟
- **怠速时平均油耗上升是正确行为**（烧油不走路），有用例专门钉着，
  免得以后有人把它当 bug"修掉"

### 2. 故障灯 MIL（`std_01`）—— **标准 PID，不用扫描器实测**

Mode 01 PID 01 的字节 A：bit7 = 故障灯亮/灭，低 7 位 = 故障码条数。
公式直接写 `bit(A,7)`（公式引擎本来就有 `bit()` 函数）。

> **它是布尔，不是连续量** —— 而这正是 P9 方向 A 里**不需要映射表**的那一类：
> `min=0, max=1, warnHigh=0.5` 就够，值 1 会走成 critical，
> **指示灯的既有三态图直接可用，零新代码**。
> 这一条正好把 [`主题设计大纲.md`](主题设计大纲.md) §2.110 里
> "布尔不需要 valueLabels"的说法**在真代码里验证了一遍**。

## v1.17.3 · 2026-10-05 · 协议搜索竞态 + 让成功路径可见（**但不刷屏**）

> 继续清 v1.17.1 实车日志暴露的遗留。这一版把最后两条也收了。

### 1. 协议搜索竞态（实车 5 次 `STOPPED` 的来源）

`ATSP0`（自动）下，**第一次真实请求才会触发协议搜索**，搜索期间适配器回 `SEARCHING...`。
此时立刻开始轮询会**打断搜索**并拿到一串 `STOPPED` —— 实车日志正是如此
（`0100` 的响应里带 `SEARCHING...`，之后 5 次 `STOPPED`）。

**修法**：初始化末尾（自动协商时）**等协议锁定**再返回。
判据抽成纯函数 `ObdProtocol.protocolLocked()`：

| `ATDPN` | 含义 | 锁定？ |
|---|---|---|
| `A0` | 自动协商，**协议还没定下来** | ❌ |
| `A6` | 自动协商，已锁定到协议 6（ISO 15765 CAN 11/500） | ✅ |
| `6` | 用户显式指定了协议 6 | ✅ |

最多试 6 次 × 700ms ≈ 4.2 秒。**超时不报错、只警告** ——
协议没锁定时未必什么都拿不到（实车会话 B 就是在未锁定状态下偶然拿到数据的），
拦住不让轮询反而更糟。

> 为什么不用"响应里还有没有 `SEARCHING...`"当判据：那要**重发一条真实请求**，
> 而那正是会打断搜索的动作。`ATDPN` 是只读的。

## v1.17.2 · 2026-10-05 · 让「数据不通」能被自己看出来（NRC 上报 + 探测加严）

> 承接 v1.17.1。那次能查出 `ATCAF0`，靠的是**日志里有完整 TX/RX** ——
> **不是靠 App 的报错**。这一版补的就是那个缺口。

### 1. 否定响应不再被吞掉（**最重要的一条**）

改之前：ECU **明确拒绝**（`7F <服务> <NRC>`）和「总线上没人回答」
**都被归成同一句 `无有效响应`**。2026-10-05 的实车日志里
**29 条否定响应全被吞掉** —— 其中就有根因的指纹 `7F 11 13`（NRC 0x13 报文长度错误）。

现在 `ObdProtocol.negativeReason()` 把它翻成人话：

```
ECU 拒绝 | 服务=0x11 NRC=0x13 报文长度或格式错误
```

**只报十六进制不够**，所以加了一张 ISO 14229 常用 NRC 表
（`0x13` 报文长度错误 / `0x78` 响应挂起 / `0x7F` 当前会话不支持该服务 …）。
查不到的码**如实标「未知 NRC」**，不编一个说明。

> ⚠️ 有个反直觉的细节值得记：请求 `01 11`，ECU 回的却是 `7F 11 13` ——
> **服务字节是 0x11 而不是 0x01**。因为当时开着 `ATCAF0`，发出的帧没有 PCI 字节，
> ECU 把第一个数据字节 `01` 当成了长度、把 `11` 当成了服务。
> **「服务号对不上」本身就是畸形请求的指纹**，所以这里**如实报 ECU 说的服务号**，不做纠正。

**判据（为什么不误报）**：`negativeReason` **只在 `extractData` 已经失败之后才调用** ——
此时串里的 `7F xx yy` 几乎只可能是否定响应。
`NO DATA` / `CAN ERROR` / `STOPPED` 里没有十六进制，扫不出东西，
仍然回落成 `无有效响应`；数据字节里**碰巧**有 `0x7F` 的肯定响应（如燃油液位 `41 2F 7F`）也有用例钉着不误报。

### 2. `初始化完成 ok=` 现在有确切含义，并补了一次**真实 PID 探测**

改之前：`ok = 响应里没有错误关键字`。于是实车会话 A 里
`0100` 回了 `SEARCHING... 064100981A800300`（没有错误关键字）→ **`ok=true`**，
**但之后每条 PID 都失败**。

改之后：

| 改动 | 说明 |
|---|---|
| `ok` 判据加严 | 要求 `0100` **真的解析出 4 字节位图**，不再是"没看见错误关键字" |
| 日志文案 | 改成 `ok=…（只代表 0100 有响应，不代表后续轮询可用）`，免得下一个人再被它带偏 |
| **新增探测 2** | 再试一个**轮询真正会用的** PID（`01 0C` 转速，OBD-II 强制支持） |

`0100` 通过而 `01 0C` 不通过时，打一条明确的警告：

```
[OBD][W] 探测通过但真实 PID 无响应 | 01 0C → NO DATA | 请求可能没被 ECU 接受（检查 ATCAF / 协议设置）
```

> **这一条如果早就有，那次实车故障不需要翻 TX/RX 就能定位。**

只报警告、**不改 `ok`**：某些车 / 某些状态下某个 PID 可能确实不回，
算成"初始化失败"会误伤（而且 `ok=false` 会让轮询根本不启动）。

### 实车日志（`ver=1.15.0`，IOS-Vlink + ELM327 v2.3，SDK 36 设备）

|---|---|---|
| `01 0D` 车速 | `41 0D 00` | **0 km/h** |
| `01 05` 冷却液 | `41 05 84` | **92 ℃** |
| `01 42` 电压 | `41 42 38 48` | **14.4 V** |
| `01 04` 负荷 | `41 04 3B` | **23.1 %** |
| `01 11` 节气门 | `41 11 28` | **15.7 %** |
| `01 0F` 进气温度 | `41 0F 62` | **58 ℃** |

> 电压 14.4V + 负荷 23% + 水温 92℃ + 节气门 15.7% —— 这是**热车怠速**的样子。
> 初始化本身也全绿：`ATZ/ATE0/ATL0/ATS0/ATH0/ATAT1/ATSP0` → `OK`，
> `ATDPN` → `A0`，`ATRV` → `14.6V`，`0100` → 真实的支持位图 `98 1A 80 03`。

### 根因：`ATCAF0`（`ObdProtocol.kt`）

`ATCAF0` 关掉 CAN 自动格式化后，ELM327 **发出的请求也不再补 PCI 字节** ——
`01 11` 这种正常请求在 ECU 看来是**畸形帧**，于是回 NRC 0x13
（incorrectMessageLengthOrInvalidFormat），或干脆 `NO DATA`。

会话 B 里 `ATCAF0` 没发出去（初始化中断），CAF 保持**出厂默认（开）**，
同一个请求就正常了 —— **变量只有一个，因果清楚**。
另有两条独立佐证：会话 A 的响应带 PCI 前缀（`064100981A800300`），
会话 B 的不带（`41 0D 00`）；且会话 B 的回显是**开着**的
（`01 0D 41 0D 00`），证明那次初始化连 `ATE0` 都没生效。

**修法**：删掉那一行。复位（`ATZ`）后 ELM327 默认就是 CAF1，
所以**不需要写 `ATCAF1`**（非 CAN 协议会回 `?`）。

**为什么当初会加**：注释写的是"保留原始字节，便于自定义 PID / ISO-TP 多帧重组"。
但 `matchData` 本来就是**扫描「响应模式 + PID」**，带不带 PCI 前缀都能认 ——
**解析器两种格式都兼容，CAF0 从一开始就不是必需的**。

### 顺带修：已知 UUID 表把写 / 通知写反了

日志每次连接都打一条：

```
[BLE][W] 已知 UUID 属性不符，改用属性配对 | svc=000018f0 notify=WnW write=NI
```

而实车 GATT 表是 `2AF0 = NI（通知）` / `2AF1 = WnW（写）`。
`BleTransport.KNOWN` 那条写成了（通知 2AF1，写 2AF0）—— **反的**。
属性配对兜住了（所以能连上），但表本身错了会让人以为"这适配器不标准"。
**文档同步更正**：`接手大纲` §4.3 里写的「写 2AF0 / 通知 2AF1」也是反的。

### 补充：同一份日志的**后半段**（20:47:48 起全是 `CAN ERROR`）

不是同一个 bug，别混起来：**用户在界面上把协议从「自动」改成了 `8`（CAN 11bit 250k）**，
而这台车是 **CAN 11bit 500k**（会话 B 的 `ATDPN` 已经自检出来了）。
波特率对不上 → 适配器回 `CAN ERROR`（178 条，占整份日志全部的 error 行）。

**教训（对排障有用）**：`CAN ERROR` 强关联"协议不对"；
而 NRC `7F xx 13` 是"帧本身畸形"。两者**指向完全不同的方向**，
日志里却都被归成同一个 `无有效响应`。

### ⚠️ 一个观测缺口：App **从不记录成功的数值**

`RULE` 模块整份日志只有 1 行（启动时 `规则已加载 | count=5`），**一次都没触发过** ——

失败会大声记，成功一个字都不记。
按 `matchData` 的算法（扫描「响应模式 + PID」），`01 0D 41 0D 00` 里的
`41 0D 00` 是能被提取的，**但这是推断，不是观测**。

## v1.17.0 · 2026-10-05 · 非数值 PID 模型（方向 A）：数值 → 文字映射表

### 解决什么

主题工具里 **18 个控件绑着不存在的 PID**。根因不是"忘了配 PID"，
而是**模型缺一类数据**：现有 PID 是 `min~max` 的**连续数值**，
塞不进 `P/N/R/D`（枚举）、亮/灭（布尔）、`P0301`（文本）。

用户拍板**方向 A**：**值仍然是一个数，显示时查一张映射表**。

### 新增

| 位置 | 内容 |
|---|---|
| `data/ValueLabels.kt` | **纯模型**：`labelFor` / `isUsable` / `parse` / `toJson` + `MAX = 32` |
| `GaugeItem.valueLabels` | 仪表节点的映射表（空 = 不用映射） |
| `BaseGaugeView.format()` | **唯一入口**：先查映射表，没有才走数字格式化 |
| `BaseGaugeView.primaryFormat()` | 同上（多值表的读数走这条） |

### 为什么放在 `format()` 一处

圆表 / 条形表 / 数字表 / 折线表 / G力表 / 多值表**全都调这一个函数**。
放到这里而不是各视图各判一次 —— **6 处判定迟早分叉**。
本项目在"报警配色"上已经栽过一次（v1.10.1 把它收敛成 `alertColor()` 一处）。

### 语义（与工具侧 `valueLabelFor` 逐字一致）

| 情况 | 结果 |
|---|---|
| 空表 / 全空串 | 不用映射（读数按量程格式化） |
| 值是 NaN / null | `--` |
| `round(value)` 越界 | 夹到 `0..size-1` |

> ⚠️ **必须 `round` 而不是截断**：`4.999` 是"第 5 挡"，
> 截断会写成 4 —— 指针已经指在第 5 挡的位置，**两者都不报错**。
> `ValueLabelsTest` 有一条专门的用例钉着它。

### 兼容性

- **旧文件完全不变**：没有 `valueLabels` 字段 → 空表 → 数字格式化（老行为）
- **回写时不写空字段** —— 旧版本 App 打开新文件不会看到不认识的键

## v1.10.4 · 2026-10-03 · 数值动画重做：输入滤波 + 四种缓动曲线 + 收敛策略

用户反馈「动画条要优化、要流畅、0-10 要 +3+5 这样走过去而不是直接跳过去」。
查下去发现**根因不是"没有缓动"，而是缓动的三个层次各有一个问题**。

### 根因：三层各有一处问题

原来的动画只有一层：`displayValue` 用指数逼近 `value`（τ=45ms）。三个问题：

| # | 问题 | 后果 |
|---|---|---|
| 1 | **只有一个写死的曲线** | 没有 ease-in/out 可选，也调不了节奏 |
| 2 | **收敛就吸附并停止动画** | 数据 5Hz 推，两次推送之间目标不变 → 缓动在窗口里早早收敛、**停住**，下次推送再跳一下 |
| 3 | **没有输入滤波** | 数据本身的抖动（传感器噪声、量化）直接进动画，指针看着"毛躁" |

第 2 条是关键：τ=45ms 时一个 200ms 推送周期内走完 **98.8%** ——
指针**几乎瞬间到位**，然后在剩下的时间里"趴"在目标上不动。
数据缓变时（水温上升、正弦峰顶）看起来就是一格一格地跳。

### 新增：`Easing` —— 三层纯逻辑（37 个用例）

```
总线原始值 ──[1. 输入滤波]──→ 平滑目标 ──[2. 缓动曲线]──→ 显示值
                                                            │
                                        [3. 收敛判据] ←──────┘
```

**① 输入滤波**（`valueSmoothingMs`，默认 90ms）
专门压数据本身的抖动，与缓动曲线**解耦**：想更稳调大、想更灵敏调小。

**② 四种缓动曲线**（`easingMode`）

| 模式 | 机制 | 手感 |
|---|---|---|
| 标准（指数） | 增量：每帧走 `k·dist` | 全程减速、收尾长，最不容易看出跳变 |
| 线性（匀速） | 增量：固定速度 | 跳变时最像"指针在扫" |
| 柔和（缓入缓出） | 绝对位置：`3u²−2u³` | 起步慢、中段快、收尾慢 |
| 干脆（缓出） | 绝对位置：`1−(1−u)²` | 起步快、收尾慢 |

**③ 收敛判据**（`Easing.needsMoreFrames`）
把"够不够近"和"要不要继续动画"**拆成两件事**：

- 数据还在动（距上次目标变化 < `HOLD_MS`=600ms）→ 只吸附消除尾巴，**继续动画**
- 数据稳定下来了 → 吸附并停止，不空转

### 关键参数：τ 从 45ms 提到 120ms

一个 5Hz 推送周期（200ms）内：τ=45ms 走 **98.8%**（几乎瞬间到位），
τ=120ms 走 **81%**（永远留余量给下一次推送 → 指针一直在动）。

代价是到位慢一点（3τ≈360ms）。仪表读数本来就不需要瞬时响应，而"顺"是第一眼就能看出来的。

### 重构：抽出 `GaugeAnimator`（状态机）

动画的状态机（起点、总行程、目标稳定计时）原来长在 `stepFrame` 里，
**JVM 单测跑不了**（要 View、要 Choreographer）。而"数据还在变时会不会冻住"
这类问题恰恰只出在状态机上，不在数学上。

抽成独立类后 `BaseGaugeView` 少了约 40 行可变状态，且这些状态有了单一负责人。
这也是重构文档 §2.2 步骤 2 要的那一步。**19 个用例**直接按真实时序喂数据。

### 新增：性能基准页的「流畅度」指标

帧率与掉帧只说明**画得动**，不说明**动得顺**。
指针"一格一格跳"的本质是**部分帧上没有位移**，所以基准页现在直接统计
「显示值真的变了的帧占比」。

**实测（小米平板 5，v1.10.4）**：

| 档位 | 动了 / 总帧 | 占比 |
|---|---|---|
| 8 表 · 主题默认 | 599 / 599 | **99.8%** |
| 8 表 · 夸张（11 层） | 599 / 599 | **99.8%** |
| 8 表 · 关闭辉光 | 599 / 599 | **99.8%** |
| 12 表 · 夸张（极限） | 599 / 599 | **99.8%** |

四段仍然**零掉帧**（帧间隔 p99 ≤ 16.73ms）。也就是说：**动画变顺了，性能没退**。

### 主题编辑器新增「数值动画」一节

缓动曲线下拉（4 种）+ τ 滑块 + 输入滤波滑块，**改完立刻在预览里看出来**。
内置主题只读 → 保存时自动另存为自建主题（与原有行为一致）。

### 过程中实际写出来又修掉的三个缺陷（都记下来）

1. **指数逼近的增量积分漂移**：`v ← v + (v_target−v)·(1−e^(−dt/τ))` 在 60Hz 与 120Hz 下
   同样 250ms 差 **20 个百分点**（55.5 vs 35.0）—— 因为 `1−e^(−dt/τ)` 不是线性的，
   帧多帧少累积出的曲线不同。修法：把每帧混合系数**按参考帧长归一化**
   （`k = 1−(1−k_ref)^(dt/REF)`），这样 k 对 dt 可加。

2. **进度型曲线把"剩余距离"当总行程**：写成"每帧位移 = 剩余距离 × 曲线速度 × dt/时长"，
   看着合理，实际**永远到不了目标**（实测停在 64.76%）—— 剩余距离逐帧缩小、位移逐帧衰减。
   修法：曲线作用在**固定不变的总行程**上（目标变化时固定下来）。

3. **下降方向恒不动**：`journeyStart + journeyDist·curve − from` 对下降方向是**负数**，
   被 `coerceIn(0, dist)` 夹成 0。需要 `abs` 之后统一乘方向。
   **上升方向的用例完全测不出来** —— 是补了下降用例才发现的。

> 第 3 个缺陷特别值得记：它只在"目标下降"时出现，而人写测试时下意识先写上升。
> 现在 `GaugeAnimatorTest` 里有一条专门的下降收敛用例守着。

### 踩坑：改 `build.gradle.kts` 用 PowerShell `-replace | Set-Content -NoNewline`

只想改版本号，结果：
- **换行全被吃掉** → `abiFilters += "arm64-v8a"` 那行被并进注释 → **四个 ABI 全编**
  （APK 6.68 → **9.41 MB**，`lib/` 0.91 → 3.61 MB）
- 文件被写成 **ANSI(GBK)** → 中文注释变乱码，`read` 工具直接报 `invalid UTF-8 text`

修法：用 `[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($false)))`
显式写 UTF-8 无 BOM。**改源码文件不要用 `Set-Content`**（它按 ANSI 写，且 `-NoNewline` 会吃掉换行）。

### 验证

- **415 个单元测试全通过**（+57）：`EasingTest` 37（新建）· `GaugeAnimatorTest` 19（新建）·
  `GaugeEasingTest` 14（改）· `GaugeThemeTest` 25
- 装机实测：流畅度 99.8%、零掉帧（见上表）
- `adb logcat -b crash` 无 `com.icar.obd` 条目

### 遗留

- 各曲线的**手感**最终要靠眼睛定。τ=120ms / 滤波 90ms 是算出来的起点，
  真机上觉得"太慢/太快"直接在主题编辑器里调（有实时预览）
- 进度型曲线（柔和 / 干脆）的总时长固定为 `2τ`，**没有单独的总时长参数**。
  想要"慢起步 + 长滑行"需要再拆一个参数，目前没做
- 「流畅度」指标只统计**第一块表**。8 块表各自动画时它们的占比可能略有差异

## v1.10.3 · 2026-10-03 · 打通「电脑上设计 → 设备上生效」的闭环

### 修复：设计文件在 App 侧**根本没有入口**（这是 v1.10.0 起就有的断点）

用户问了一句「电脑的主题修改有同步修改好吗」，顺着去查才发现：

> `DesignFile.parse` 写好了、22 个用例守着、PC 工具也能产出文件 ——
> 但 **`app/src/main` 里一次都没调用过它**。

也就是说 v1.10.0 引入的 `icar.ui/1` 格式，**只有一半**：能写、能校验，
但**设备上没有任何地方能读它**。工具做得再好也流不到 App ——
只能手动 `adb push` 到 `files/design.json`，而那个文件**没有任何代码会去读**。

这是"规则同步做好了、但数据流是断的"——两件事都得成立才行。

**修法**：仪表盘「风格」对话框新增两个动作项，走 SAF（不需要存储权限）：

| 入口 | 作用 |
|---|---|
| **导入设计文件…** | 选一个 `design.json` → 解析 → **先给用户看结果** → 确认后整体替换自定义仪表盘 |
| **导出当前布局为设计文件…** | 把当前盘面导成 `design.json` 分享出去（回到 PC 工具继续改） |

**为什么导入要两段式**：设计文件的校验**不抛异常**、返回带字段路径的错误列表，
所以有硬错误时可以精确说清"哪一块表的哪个字段错了"；软警告（比如背景路径在本机
不存在）也要显示 —— 那是"能加载但效果可能不是你想要的"，瞒着用户更糟。

**为什么必须有导出**：没有它，用户在设备上微调过的布局就回不到 PC 工具上，
只能从头重画。闭环的另一半。

### 修复：主题写的是数字 id，而不是设计文件规定的别名

设计文件格式规定 `theme` 写 `"neon"` 这样的**名字**，但 App 存的是数字 id。
导出时直接写 id 的话，导入端（甚至另一台设备）会报「主题不存在」。

- 新增 `GaugeTheme.aliasOf(id)` / `byAlias(alias)` —— **内置主题的别名是冻结的跨层契约**
- 放在 `GaugeTheme` 而不是 `DashFragment`：这是主题自己的属性；
  而 `data/DesignFile.kt` 导出时也要用它（`data/` 不能依赖 `ui/`，所以由调用方传入）
- **自建主题没有别名** → 导出时留空（= 用当前主题）。自建主题的 id 在不同设备上
  必然不同，写进文件只会让导入端报"主题不存在"
- 别名映射有 5 条用例守着（`GaugeThemeTest`），漏一个内置主题就失败

### 新增：仪表盘性能基准页（`ui/BenchActivity` + `ui/BenchHarness` + `ui/dash/DashboardBenchmark`）

**回答的问题**：9 层霓虹辉光在 8 个仪表下守得住 60fps 吗？（文档 §2.4，被推迟了三个版本）

**之前为什么量不出来**，两个原因都修掉了：

1. `dumpsys gfxinfo` 在这台设备上只给头部、没有帧统计；
2. 用真实数据测时**仪表根本没在动** —— 静止的 View 不重绘，测出来的"帧率"是屏幕刷新率，
   和绘制成本无关。基准自己每帧 `updateMulti()` 灌正弦假值，**强制每帧重绘**。

**四段测量**（8 表 × 3 档 + 12 表极限），每段预热 1.5s + 测量 10s。结果：

| 档位 | 仪表 | 帧数 | 帧间隔 平均 | p99 | 最大 | 超时帧 |
|---|---|---|---|---|---|---|
| 8 表 · 主题默认 | 8 | 1199 | 8.33 ms | 8.39 ms | 8.43 ms | **0** |
| 8 表 · 夸张（11 层） | 8 | 1199 | 8.33 ms | 8.38 ms | 8.41 ms | **0** |
| 8 表 · 关闭辉光 | 8 | 1199 | 8.33 ms | 8.38 ms | 8.43 ms | **0** |
| 12 表 · 夸张（极限） | 12 | 1199 | 8.33 ms | 8.38 ms | 8.41 ms | **0** |

**结论：12 个圆表 + 11 层辉光跑满 120fps，零掉帧。** 8 个表更不在话下。

> **⚠️ 判据是「帧间隔」，不是「每帧绘制耗时」—— 这一点差点搞错。**
>
> 第一版报告用 `DrawStats` 的每帧耗时（0.2~0.34ms）下结论，看起来"还有 50 倍余量"。
> 但 Android 开了硬件加速后 `onDraw` 只是把绘制指令**记录**进 DisplayList，
> 真正的光栅化在**渲染线程**上做 —— 那个数**不是绘制成本**。
> 报告里现在把它明确标成"旁证"，主判据换成帧间隔（主线程 + 渲染线程 + 合成器的最终结果）。
>
> 顺带发现：`关闭辉光` 的**记录**耗时（0.34ms）反而**高于** `夸张`（0.28ms）——
> 说明这一列量的是视图层代码，与辉光层数基本无关。这本身也印证了不能拿它当判据。

**踩坑（都记下来，避免下次重犯）**：

1. **画布高度塌成 0**：第一版把控件放进 `ScrollView`，`weight=1` 拿不到剩余空间，
   点「开始测量」直接报"容器还没布局好"。改成固定头部 + `weight=1` 画布，根部不套 ScrollView。
2. **布局监听器越界崩溃**：`onLayoutChange` 里读了 `segments[segIndex]`，
   三段跑完后 `segIndex=3` → `ArrayIndexOutOfBoundsException: length=3; index=3`，
   **真机上崩了两次**。布局监听器现在只读 `currentPreset`，完全不碰索引。
3. **预热被算进测量窗口**：延时按 `SEGMENT_SEC` 算，而预热吃掉 1.5 秒，
   实际只测了 8.5 秒。改成 `WARMUP_MS + SEGMENT_SEC`。
4. **首帧峰值污染统计**：重建视图后第一帧要付 `Paint` 光栅化 / 字体度量 / tessellation，
   峰值 **11393µs**。加了 1.5 秒预热，预热结束才 `reset()` 开始计数。
5. **屏幕刷新率会封顶帧率**：同一页两次测量分别读到 30Hz 和 120Hz
   （`mActiveModeId` 在 30/60/120 之间切）。拿 fps 当判据会得出"刚好达标"的错觉。
6. **本机同时挂着模拟器**：`adb` 不带 `-s` 会报 `more than one device/emulator`。
   所有命令都要写 `-s 7e7d7bb4`。

### 重构：统一两套报警概念（`BaseGaugeView`）

**问题**（文档 §2.1 问题 2）：两个概念并存且**重叠但不相等** ——

| | 来源 | 用途 |
|---|---|---|
| `warn: Boolean` | `isOutOfRange()`，**含下限** | 选颜色 |
| `alertLevel: Int` | `AlertPulse.level()`，**只认上限** | 驱动爆闪 |

`warnLow` 触发时 `warn=true` 而 `alertLevel=NONE`，于是"到底哪个才是报警"永远说不清；
而且 7 个视图各自写了一遍 `if (warn) cWarn else …`，加一档报警要改 7 个文件。

**做法**：

- 删掉 `warn`，新增 `AlertPulse.levelWithLow()`（**保留** `level()` 不动 ——
  它被扫描器沿用，27 个用例钉着它的迟滞边界，不该被顺手改）
- 新增 `AlertPulse.WARN_LOW` 档：**下限只染色、不爆闪**。
  爆闪的语义是"立刻松油门 / 靠边"，数值偏低不需要这种紧迫感；
  硬要闪反而会让驾驶员对爆闪脱敏
- 新增 `BaseGaugeView.alertColor()` / `valueTextColor()` / `extraTextColor()`，
  **报警配色只有一处判定**，7 个视图的重复判断全部删掉

**⚠️ 一处刻意的观感变化**：`CircularGaugeView` 的指针原来只在**危险档**变红
（`if (warn) cDanger else cNeedle`）。现在按报警等级取色 ——
WARN 档指针变橙、CRITICAL 变红。理由是"报警了指针却不变色"本身就不一致。
若不想要这个变化，改回 `alertLevel == AlertPulse.CRITICAL` 即可。

### 修复：`AlertPulse.levelWithLow` 的下限迟滞方向写反了（**自己写出来又被单测抓出来的**）

**交叉核对过**：脚本扫描全部布局文件，确认布局里的控件 ID **一个不漏**都在文档里
（第一次漏了 `btnTpl2/3/4`，因为我用了 `btnTpl1..btnTpl5` 的范围写法，已展开）。

### 新增：[动画实现.md](动画实现.md)

把"仪表盘动画靠什么驱动、数值变化动画怎么算"整理成一份分析。核对代码时发现一处**不一致**：

> `DigitalGaugeView` 第 88 行用的是 `ratio(value)` 而**不是** `shownRatio()`，
> 所以它的装饰弧是**跳变**的，和圆表/条形表的平滑观感不统一。**一行可修。**

文档要点：

- **两套机制性质不同**：数值缓动是"过渡"（会收敛会停），阈值爆闪是"振荡"（不收敛一直在跑）。
  必须分开 —— 只有一套的话，要么报警闪一下就不动，要么数值不动了还在 60fps 空转。
- **全工程只有 `GaugeTicker` 一处动画驱动**（`Choreographer`），
  没有用 `ValueAnimator`/`ObjectAnimator`/`postInvalidateOnAnimation`。
- **缓动是指数逼近**（一阶低通），`k = 1 - e^(-dt/τ)`，τ=45ms。
  时间基准而非每帧固定比例 —— 这台平板能跑 120Hz，按帧缓动会快一倍。
- **收敛判据按像素折算**，不用相对比例（转速量程 8000 时相对千分之一是 8 转，指针会肉眼可见地"爬"）。
- **文本永远用原始值**，只有图形用动画值 —— 读数必须准，指针可以慢半拍。
- **爆闪带迟滞**（退出阈值 = 进入 × 0.97），否则转速在 6500 抖动会让爆闪乱闪。
- 文档末尾列了**已知问题**，其中"性能基准仍未量准"标为**高优先级**。

## v1.10.0 · 2026-10-03 · 缓动改时间基准 + 删除 Sky 主题 + PC 端设计框架

### 修复：个别进度条"一顿一顿"

**根因是缓动的实现方式，不是数据。** 原来是**按帧**逼近：

```kotlin
from + (target - from) * 0.25    // 每帧固定比例
```

两个毛病：

1. **帧率相关**。60Hz 下 200ms 收敛，120Hz 下只要 100ms ——
   同一份代码在不同设备观感完全不同。**这台平板就能跑 120Hz**。
2. **和 5Hz 的数据推送错拍**。数据每 200ms 来一个新目标，
   而按帧缓动要 ~173ms 才到 95%，剩下 5% 是长长的尾巴 ——
   **永远在"快起步、慢收尾"的循环里**，看起来就是一顿一顿。

改成**时间基准**：`k = 1 - e^(-dt/τ)`，τ=45ms。不管多少帧率，固定时间收敛。

顺带把收敛判据从**相对比例**改成**像素级**：
转速量程 8000 时，相对千分之一 = 8 转，条形上是 0.1% 宽度，
但**指针会肉眼可见地"爬"**。现在 `BarGaugeView` / `CircularGaugeView`
按自己的像素尺度覆写 `settleEpsilon`，不到半个像素就吸附。

**新增 7 个测试**，其中两个专门钉"帧率无关"：
60Hz 与 120Hz 跑同样 200ms，结果必须几乎一致。

### 删除：Sky Gauge 主题支持

用户确认可以删。删掉 `SkyTheme.kt` / `DashElement.kt` 及两个测试文件，
清掉 `Store` / `DashFragment` / `LvglDashView` / `LvglBridge` 里的全部引用。

**APK 从 7.21 MB 降到 6.65 MB。**

### 新增：`DesignFile` + [UI设计指南.md](UI设计指南.md) —— **在电脑上设计 UI**

现在调布局只有两条路（手指拖 / 改代码），**都不适合做设计**。
设计文件把它变成"编辑一个 JSON"：

```
PC 写 design.json  →  校验（有明确报错）  →  推到设备  →  App 加载
```

**与刚删掉的 Sky Gauge 格式的关键区别**：

| | Sky Gauge | `icar.ui/1` |
|---|---|---|
| 归属 | **别人的**格式 | **我们自己的** |
| 模型 | 图元级，要写转换层 | **直接复用 `GaugeItem`**，零转换 |
| 表达力 | 受限于他们的词汇表 | = App 能画的东西，一一对应 |
| 坐标系 | 正方形 360×360，非方形屏会变形 | 每轴 0..360，天然适配 |

**校验是这个格式一半的价值**：手写 JSON 一定会写错，而"推到设备上发现没显示"
是最低效的调试方式。所以解析器**不抛异常**，返回带字段路径的可读错误：

- 硬错误（拒绝加载）：JSON 语法 / schema 不对 / unit 不是 360 / 缺 pid / 量程非法
- 软警告（能加载但提示）：**越界**（越界不会报错、只会"看不见那块表"）/ 坐标为负 /
  尺寸过小 / 未知 pid（自定义 PID 是合法场景，不拦）

**22 个测试**。其中一条抓出一个真问题：

> `GaugeItem.fromJson` 用**元素自己的 `unit` 字段**判断新旧格式，没有就 ×360（旧配置迁移）。
> 而设计文件的单位声明在 `canvas.unit` 上 —— 不注入标记的话**每个坐标都会被再乘一次 360**
> （12.5 → 4500）。这个坑是单测抓出来的。

### 验证

**288 个单元测试全通过**，装机无崩溃。

## v1.9.0 · 2026-10-03 · 仪表盘重构：共用霓虹层 + 阈值爆闪

### 新增：`AlertPulse` —— 阈值报警与爆闪（纯逻辑，27 个单测）

抽成独立对象的理由：**迟滞边界**和**时间相位**是最容易写错、又最难手测的两处。
放在 `onDraw` 里这两件事都没法验证；做成纯函数（时间由调用方传入）就能单测。

- **迟滞**：退出阈值 = 进入阈值 × (1 − 3%)。没有它，真实转速在 6500 上下抖动会让爆闪乱闪。
  测试里专门写了一个**反证用例**：不传上一帧等级，同一串样本会被最后那个小值打回 NONE。
- **两档不同节奏**（一眼看出严重程度）：
  - `WARN` ≈1.7Hz **平滑脉冲**（smoothstep）—— 低等级用硬方波太刺眼，长途驾驶会烦
  - `CRITICAL` ≈5Hz **硬方波** —— 干脆、有冲击力
- **染色策略**：不做"整个元素变色"（那会让读数在闪烁中消失），
  只把**辉光和外圈**推向危险色，读数始终可辨。

### 新增：`NeonPainter` —— 共用霓虹绘制层

原来只有圆表有辉光，且是 4 层写死的循环；数字、条形都不发光，
整个盘面看起来是"一个霓虹表 + 一堆素控件"。

- 弧 / 线 / 圆 / 圆角矩形 / 文字，五套辉光原语
- **层数按控件尺寸自适应**（3 / 5 / 7 / 9 层）—— 小控件上叠 10 层既看不出效果又白花钱
- **`onDraw` 零分配**：所有 Paint 复用，不 new

### 重构：`CircularGaugeView`

1. 辉光换用 `NeonPainter`，层数自适应
2. **底轨上标出危险区**：从 `warnHigh` 起就是暗红。原来危险阈值只体现在"超了之后变红"，
   开车时看不到"还有多远到红线"
3. **爆闪**：超过危险阈值时整个环 + 指针按节奏闪
4. **文本格式化加缓存**：文本只随 `value` 变（5Hz），不随缓动变（60fps）
5. 留白按**辉光扩散量**给（原来按描边算，最外层会被裁掉）

### 重构：`BarGaugeView`

霓虹进度条 + 爆闪 + 阈值刻度线在报警时一起变亮。

### 验证

- **288 个单元测试全通过**（+27 个 `AlertPulseTest`）
- 装机：无崩溃；**模拟信号活过界面切换**（v1.8.0 的生命周期修复生效）

### ⚠️ 未完成 / 未验证（**下一轮优先**）

1. **性能没有量准**。`dumpsys gfxinfo` 只采到 5 帧（12 秒），
   且当时布局只有 2 个仪表、数据也没到位 —— **样本太小，不能下结论**。
   霓虹的层数上限（9 层）**是否能在 8 个仪表下守住 60fps，尚未验证**。
   **这是本轮最大的遗留风险**：这个项目已经因为"选型不量性能"栽过一次（LVGL）。
2. 数字 / 折线 / 多值 / G力值四种仪表**还没接霓虹**
3. 屏幕级报警叠加（整屏边缘辉光）未做
