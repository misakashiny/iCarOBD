# 仪表盘动画实现分析

> 回答两个问题：**仪表盘的动画靠什么驱动？数值变化的动画是怎么算的？**
>
> 结论先说：**有两套机制，性质完全不同** —— 一套是"过渡"（会收敛、会停），
> 一套是"振荡"（不收敛、一直在跑）。
>
> **数值过渡本身又分三层**（v1.10.4 起）：输入滤波 → 缓动曲线 → 收敛判据。
> 三层各自解决不同的问题，**混在一起就一定做不好**（见 §三）。

---

## 一、两套机制的本质区别

| | **A. 数值缓动** | **B. 阈值爆闪** |
|---|---|---|
| 驱动什么 | 指针角度 / 弧长 / 条长 | 辉光强度 / 颜色染色 |
| 数学性质 | **过渡**：`from → target`，会收敛 | **振荡**：`0 ↔ 1` 循环，**永不收敛** |
| 何时停 | 数值收敛**且目标稳定**（见 §三） | 报警解除才停 |
| 输入 | 新数值（5Hz 到达） | 时间（每帧都在变） |
| 实现 | `Easing.step()`（由 `GaugeAnimator` 驱动） | `AlertPulse.intensity()` |
| 位置 | `Easing.kt` + `GaugeAnimator.kt` | `AlertPulse.kt` |

**为什么必须分开**：缓动的"停"是特性（收敛了就不该再烧 GPU），
爆闪的"不停"也是特性（报警期间必须一直闪）。
如果只有一套，要么报警闪一下就不动了，要么数值不动了还在 60fps 空转。

## 二、共同的驱动源：`GaugeTicker`（共用动画时钟）

**全工程只有这一处动画驱动** —— 没有用 `ValueAnimator` / `ObjectAnimator` / `postInvalidateOnAnimation`。

```
Choreographer.getInstance().postFrameCallback(GaugeTicker)
        ↓ 每帧一次（跟随屏幕 vsync）
GaugeTicker.doFrame(frameTimeNanos)
        ↓ 遍历所有注册的视图
view.stepFrame(nowMs)   ← 返回 true = 还要继续
        ↓
invalidate()            ← 触发重绘
```

### 关键设计

| 点 | 做法 | 为什么 |
|---|---|---|
| 时钟源 | `Choreographer` 的 vsync 时间戳 | 和屏幕刷新天然对齐。用 `SystemClock` 会在掉帧时让动画"追赶"，闪频会抖 |
| 注册表 | `WeakHashMap<View, Boolean>` | 视图忘了反注册也不会泄漏 |
| 生命周期 | `onDetachedFromWindow` → `GaugeTicker.release(this)` | 页面切走后不能还在 60fps 空转 |
| 结束条件 | 所有视图都返回 `false` 就停止投递 | 静止时零开销 |
| 容错 | `try/finally`，异常也要正确收尾 | 否则 `running` 会卡在 `true`，时钟再也不启动 |

### 为什么不用"每个视图各自 `postDelayed`"（**这是被实测推翻的旧方案**）

旧实现：每个仪表自己 `postDelayed(animator, 16)`。8 个仪表就是：

```
每秒 480 次消息投递
各自按 16ms 猜 → 和 vsync 错拍（有时一帧画两次、有时一次都不画）
无法统一节流
```

用户反馈"模拟信号的时候特别卡"。改成共用时钟后不再卡。

## 三、机制 A：数值过渡（**三层，v1.10.4 重做**）

### 完整链路

```
ObdEngine 轮询（真车）
SignalSimulator（合成，10Hz）
        ↓ 写入
VehicleBus（按 pidId 存最新值）
        ↓ 拉取（**不是推**）
DashRenderer.pushValues()   ← 5Hz（REFRESH_MS = 200）
        ↓
view.updateMulti(values, override)
        ↓
BaseGaugeView：
    value = primary                      ← **原始值**（文本用）
    alertLevel = AlertPulse.levelWithLow(...)   ← 带迟滞判定
    if (changed || alertLevel != NONE) startAnimationIfNeeded()
        ↓
GaugeTicker.request(this)                ← 加入时钟
        ↓ 每帧
BaseGaugeView.stepFrame(nowMs) → GaugeAnimator.step(value, nowMs, epsilon)
        ↓
drawGauge(canvas) 用 shown() / shownRatio() 取 displayValue
```

### 为什么分三层（**这是 v1.10.4 的核心**）

```
总线原始值 ──[1. 输入滤波]──→ 平滑目标 ──[2. 缓动曲线]──→ 显示值
                                                            │
                                        [3. 收敛判据] ←──────┘
```

| 层 | 解决什么 | 参数 |
|---|---|---|
| **1 输入滤波** | **数据本身的抖动**（传感器噪声、5Hz 量化） | `GaugeTheme.valueSmoothingMs`（默认 90ms） |
| **2 缓动曲线** | **数值跳变时的过渡手感**（0→10 要"走"过去） | `GaugeTheme.easingMode` + `easingTauMs` |
| **3 收敛判据** | 什么时候停止重绘（不能冻住，也不能永远空转） | 子类 `settleEpsilon` + `Easing.HOLD_MS` |

**为什么滤波必须与曲线分开**：缓动解决"跳变要过渡"，但**数据本身带抖动**。
抖动直接喂给缓动，指针会小幅高频地抖（看着"毛躁"）。两层混在一起的话，
想更稳就得把缓动调慢，于是过渡也变得迟钝 —— **两个诉求互相打架**。

### 第 2 层：四种缓动曲线（`Easing.step`）

| 模式 | 机制 | 手感 |
|---|---|---|
| `MODE_STANDARD` 标准（指数） | **增量**：每帧走 `k·dist` | 全程减速、收尾长，最不容易看出跳变 |
| `MODE_LINEAR` 线性（匀速） | **增量**：固定速度 | 跳变时最像"指针在扫" |
| `MODE_SOFT` 柔和（缓入缓出） | **绝对位置**：`3u²−2u³` | 起步慢、中段快、收尾慢 |
| `MODE_SNAPPY` 干脆（缓出） | **绝对位置**：`1−(1−u)²` | 起步快、收尾慢 |

**两种机制不能混用**，这是本项目踩得最深的坑之一：

- **增量**（标准 / 线性）：每帧朝目标走一部分。简单，但"走完"是个渐近过程。
- **绝对位置**（柔和 / 干脆）：目标变化时记下 `起点` 与 `总行程`，
  每帧算 `位置 = 起点 + 总行程 × 曲线(已走时间 / 总时长)`。

> ⚠️ **进度型曲线绝不能用"剩余距离 × 曲线速度"**。
> 那个写法看着合理，实际是**又一个衰减曲线**：剩余距离逐帧缩小 → 位移逐帧衰减 →
> **永远到不了目标**（实测停在 64.76%）。曲线必须作用在**固定不变的总行程**上。

### 第 2 层的关键参数：τ（时间常数）

| 参数 | 值 | 理由 |
|---|---|---|
| `easingTauMs` | **120ms** | 一个 5Hz 推送周期（200ms）走 **81%**，永远留余量给下一次推送 |
| `dt` 上限 | 100ms | 切页面回来时 dt 可能几百毫秒，不夹住会"瞬移"，看着像闪一下 |
| 参考帧长 | 16.67ms | 混合系数按它归一化，使 `k` 对 `dt` **可加**（见下） |

**⚠️ τ 从 45ms 提到 120ms 是这次改善的关键。** τ=45ms 时一个推送周期内走完
**98.8%** —— 指针几乎瞬间到位，然后在剩下的时间里"趴"在目标上不动，
等下一次推送。数据缓变时（水温上升、正弦峰顶）看起来就是**一格一格地跳**。

代价是到位慢一点（3τ≈360ms）。仪表读数本来就不需要瞬时响应。

### 为什么是"时间基准"而不是"每帧固定比例"（**v1.9.0 改的**）

旧实现：`from + (target - from) * 0.25`，**按帧**逼近。两个毛病：

1. **帧率相关**：60Hz 下 200ms 收敛，120Hz 下只要 100ms ——
   **这台平板就能跑 120Hz**，同一份代码观感完全不同。
2. **和 5Hz 推送错拍**：按帧缓动要 ~173ms 才到 95%，剩下 5% 是长长的尾巴。
   数据每 200ms 来一个新目标 → **永远在"快起步、慢收尾"的循环里**。

### ⚠️ 增量积分的帧率漂移（**v1.10.4 修的一个实质缺陷**）

光写 `k = 1 − e^(−dt/τ)` **还不够**。增量积分 `v ← v + (target−v)·k` 的步长
不同，累积出的曲线就不同 —— 同样 250ms，**60Hz 与 120Hz 差 20 个百分点**
（实测 55.5 vs 35.0）。这与"时间基准"的初衷正好相反。

修法：把每帧混合系数**按参考帧长归一化**

```kotlin
k = 1 − (1 − k_ref)^(dt / REF_FRAME_MS)      // REF_FRAME_MS = 16.67
```

这样 `k` 对 `dt` 是**可加的**（同样时长不论分几帧，结果一致），
且 `dt = REF_FRAME_MS` 时 `k = k_ref`，行为不变。修完 60Hz 与 120Hz 差 < 1。

### 第 3 层：收敛判据（**"够近"与"要不要继续"是两件事**）

```kotlin
// 够不够近 —— 决定要不要吸附（消除指数逼近的尾巴）
fun shouldSnap(dist: Float, epsilon: Float) = dist <= epsilon

// 要不要继续动画 —— 决定时钟还跑不跑
fun needsMoreFrames(dist: Float, epsilon: Float, sinceTargetChangeMs: Long): Boolean {
    if (dist > epsilon) return true
    return sinceTargetChangeMs < HOLD_MS     // 数据还在变 → 继续
}
```

| 常量 | 值 | 理由 |
|---|---|---|
| `HOLD_MS` | **600ms** | 3 个 5Hz 推送周期。太短则数据缓变时仍会"停一下再跳"；太长则数据真停了还空转 |

**旧实现把这两件事混成一件**（`settled` 为真就吸附并停止），于是数据 5Hz 推、
两次推送之间目标不变 → 缓动在窗口里早早收敛、**停住**，下次推送再跳一下。
现在只有**目标也稳定了**才允许停。

`epsilon` 由各子类**按像素折算**覆写：

| 视图 | `settleEpsilon` | 理由 |
|---|---|---|
| 默认（`BaseGaugeView`） | `1e-3 × (1 + \|value\|)` | 兜底 |
| `BarGaugeView` | `span / 宽度 × 0.5` | 半个像素 |
| `CircularGaugeView` | `span × 0.5 / (2πr × 0.75)` | 针尖半个像素的弧长 |

**为什么不能用相对比例**：转速量程 8000 时，相对千分之一 = 8 转，
在条形上只有 0.1% 宽度（看不出），**但指针会肉眼可见地"爬"**。

> ⚠️ **`epsilon` 必须远小于单次数据增量**。若 ε 和增量同量级（增量 1、ε=0.5），
> 指针会一吸附就停住、等下次推送再跳 —— 和改造前一样。真实参数下不会这样：
> ε 是半个像素（转速约 5.6），而数据每次变 20~50。这条由子类覆写保证。

### 谁用"动画值"、谁用"原始值"

| 视图 | 图形用 | 文本用 | 效果 |
|---|---|---|---|
| `CircularGaugeView` | ✅ `shownRatio()` | `value` | 弧和指针平滑滑动，读数准确 |
| `BarGaugeView` | ✅ `shownRatio()` | `value` | 条长平滑增长，读数准确 |
| `DigitalGaugeView` | ✅ `shownRatio()` | `value` | 底部进度条参与缓动（v1.10.1 修） |
| `DualStackGaugeView` | — | `value` | 纯文本，无动画 |
| `QuadGaugeView` | — | `value` | 纯文本，无动画 |
| `SubDualGaugeView` | — | `value` | 纯文本，无动画 |
| `GForceGaugeView` | — | `value` | 纯文本，无动画 |
| `LineChartView` | 历史原样 | `value` | **刻意不做缓动** —— 趋势图缓动会掩盖真实波动 |

### 一个刻意的取舍

**文本永远用原始值，不用动画值。**

指针可以慢半拍（那是"动效"），但**读数必须准** ——
用户看的是数字，数字跟着动画慢慢爬会让人以为仪表坏了。

### 怎么判断"动得顺不顺"（v1.10.4 新增指标）

**帧率与掉帧只说明"画得动"，不说明"动得顺"。**
指针"一格一格跳"的本质是**部分帧上没有位移**，所以性能基准页直接统计
「显示值真的变了的帧占比」（`BenchHarness.motionRatio()`）。

**v1.10.4 实测**（小米平板 5）：8 表 × 3 档 + 12 表极限，四段都是 **99.8%**，
且零掉帧（帧间隔 p99 ≤ 16.73ms）。也就是说**动画变顺了，性能没退**。

## 四、机制 B：阈值爆闪

### 完整链路

```
updateMulti：
    alertLevel = AlertPulse.level(value, warnHigh, criticalOf(), alertLevel)
        ↑ **必须传上一帧的等级**才有迟滞
        ↓
stepFrame：
    if (alertLevel != NONE) needMore = true    ← **强制时钟继续跑**
        ↓
drawGauge：
    alertIntensity() → AlertPulse.intensity(alertLevel, clockMs)   ← 0..1
    alertTint()      → AlertPulse.tintMix(alertLevel, clockMs)
        ↓
    把这些乘进辉光透明度 / 危险区亮度 / 阈值线粗细
```

### 等级判定（`AlertPulse.level`）—— **带迟滞**

```
进入阈值 = warnHigh
退出阈值 = warnHigh × (1 - 3%)

危险阈值 = warnHigh + (maxVal - warnHigh) × 0.5    ← 由量程推出，不是写死
```

**迟滞是必须的**：真实转速在 6500 上下抖动是常态。没有迟滞，
爆闪会随机乱闪，看起来像坏了。测试里专门写了一个**反证用例**证明这一点。

**危险阈值为什么按比例推**：不同 PID 量程差几个数量级
（转速 8000 / 车速 240 / 油温 150），写死必然对不上。

### 两档节奏（`AlertPulse.intensity`）

| 等级 | 波形 | 周期 | 占空比 | 观感 |
|---|---|---|---|---|
| `WARN` | 平滑脉冲（smoothstep） | 600ms | — | ≈1.7Hz，柔和 |
| `CRITICAL` | **硬方波** | 200ms | 0.5 | ≈5Hz，刺眼 |

**为什么两档不同**：低等级用硬方波太刺眼，长途驾驶会烦；
危险档用平滑脉冲又不够冲击力。**节奏本身就是严重程度的信号。**

### 染色策略（`AlertPulse.tintMix`）

```
CRITICAL: 0.35 + 0.65 × 方波   → 0.35 ~ 1.00
WARN:     0.25 + 0.45 × 脉冲   → 0.25 ~ 0.70
```

**不做"整个元素变色"** —— 那会让读数在闪烁中消失。
只把**辉光和外圈**推向危险色，**读数在任何时刻都可辨**。

## 五、为什么不用 `ValueAnimator` / `ObjectAnimator`

| 方案 | 问题 |
|---|---|
| `ValueAnimator` | 每个动画一个实例 + 一个 Choreographer 回调。8 个仪表 = 8 套独立时序，**和共用时钟的初衷矛盾** |
| `ObjectAnimator` | 需要属性反射；且每块表的量程/单位不同，动画目标不是同一个属性 |
| `postInvalidateOnAnimation` | 每个视图各自投递，回到"各自为政"的老问题 |

**共用时钟的收益**：每帧一次回调、所有仪表同帧重绘、天然和 vsync 对齐、
统一节流只需改一处。

## 六、性能考量

| 措施 | 位置 | 作用 |
|---|---|---|
| 收敛即停 | `stepFrame` 返回 `false` | 静止时零开销 |
| **数据稳定前不许停** | `Easing.needsMoreFrames` | 数据还在变就继续跑 —— 这是"顺"的前提，不是浪费 |
| 像素级收敛阈值 | 各子类的 `settleEpsilon` | 避免在"看不出差别"的范围内继续跑 |
| `onDraw` 零分配 | 各视图复用 Paint / RectF / Path | 60fps 下每次分配都会给 GC 压力，表现是周期性掉帧 |
| 文本格式化缓存 | `valueText()` | 文本只随 `value` 变（5Hz），不随缓动变（60fps） |
| 绘制耗时统计 | `DrawStats`（由时钟每帧结算） | 应用内可查，`dumpsys gfxinfo` 在本机不可用 |
| **流畅度统计** | `BenchHarness.motionRatio()` | 「显示值真的变了的帧占比」—— 帧率测不出"顺不顺" |

> **v1.10.1 已量准**：8 表 × 3 档 + 12 表极限，四段全部**零掉帧**
> （120Hz 下帧间隔 p99 ≤ 8.39ms）。9 层霓虹**守得住**，
> `NeonStyle` 默认值与 `layersFor` 档位不需要因为性能而调整。
> 详见 `接手大纲.md` §7.4 与 CHANGELOG v1.10.1。

## 九、改动画时的注意事项

1. **不要在 `onDraw` 里推进动画**。动画只由 `stepFrame` 推进，
   `drawGauge` 只读 `displayValue`。混在一起就没法单测，也会在掉帧时算错时间。
2. **新增曲线必须满足三条**（`EasingTest` 逐个模式钉着）：
   单调逼近、不过冲、**帧率无关**。只测一条会漏（本项目漏过帧率无关性）。
3. **进度型曲线必须用固定总行程**，不能用剩余距离（否则永远到不了目标）。
4. **`journeyDist` 对下降方向是负数**，算位移后要取 `abs` 再统一乘方向。
   漏了会**只有下降方向不动**，而上升方向的用例完全测不出来。
5. **加了新状态就要在 `restart()` 里清掉**。否则切页面回来会带着上一轮的状态
   （比如"目标已稳定"的计时），第一帧就判停。
6. **改完重跑性能基准**（连接页 →「运行选项」→「性能基准」）：
   看**流畅度**是否还高、**帧间隔**是否还没掉帧。
