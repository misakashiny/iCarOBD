# 仪表盘 UI 设计指南

> **在电脑上设计仪表盘，推到设备上加载。**
> 不用改代码、不用重新编译、不用在平板上用手指拖。
>
> 格式标识：`icar.ui/1` · 实现：`data/DesignFile.kt` · 测试：`DesignFileTest.kt`（22 个用例）
>
> **控件名字查 [UI控件清单.md](UI控件清单.md)** —— 所有 View 类、控件 ID、颜色、样式、drawable 都在那一份。

---

## 一、为什么要有这个

现在调布局只有两条路，**都不适合做设计**：

| 方式 | 问题 |
|---|---|
| 在平板上用手指拖 | 慢；屏幕只有那么大，看不清整体比例 |
| 改代码 | 要重新编译装机，一轮几分钟 |

设计文件把它变成**编辑一个 JSON**：

```
PC 写 design.json  →  校验（有明确报错）  →  推到设备  →  App 加载
```

---

## 二、文件长什么样

```json
{
  "schema": "icar.ui/1",
  "meta": {
    "name": "赛道模式",
    "author": "me",
    "description": "大转速 + 四联表"
  },
  "canvas": { "unit": 360 },
  "theme": "neon",
  "background": { "path": "/sdcard/icar-bg/carbon.png", "fit": 0 },
  "gauges": [
    { "pid": "obd.rpm", "style": 0, "min": 0, "max": 8000,
      "warnHigh": 6500, "x": 0, "y": 0, "w": 180, "h": 180,
      "neonPreset": "强烈", "ringStyle": 1, "ringSegments": 40,
      "cardStyle": 2 },

    { "pid": "obd.speed", "style": 1, "x": 180, "y": 0, "w": 180, "h": 90 },

    { "pid": "obd.coolant", "style": 2, "min": 0, "max": 150, "warnHigh": 105,
      "x": 180, "y": 90, "w": 180, "h": 45 },

    { "pid": "obd.voltage", "style": 2, "min": 10, "max": 16, "warnLow": 11.8,
      "x": 180, "y": 135, "w": 180, "h": 45, "cardStyle": 1 }
  ]
}
```

> 上例里转速表 `cardStyle: 2`（完全透明，露出背景图）、电压表 `cardStyle: 1`（无边框）
> —— **混合盘面**正是这个字段存在的理由。

## 三、坐标系（**最容易搞错的一节**）

**每轴 0..360**，不是像素，也不是 0..1。

| 想放到 | 写 |
|---|---|
| 左上角 | `x:0, y:0` |
| 水平居中 | `x:180` |
| 右下角 | `x:360, y:360`（配合 `w/h` 要减去尺寸） |
| 占满整行 | `x:0, w:360` |
| 占一半 | `w:180` |

**换算公式**（如果你按像素设计的）：

```
x_设计 = x_像素 / 屏宽 × 360
y_设计 = y_像素 / 屏高 × 360
```

**x/y 是左上角，w/h 是尺寸。** 注意这一点和 Sky Gauge 不同（他们的 label 用中心点）。

> 为什么不做成像素：同一份设计要在手机小屏和 10 寸平板上都好看。
> 像素坐标换一块屏就废了，比例坐标不会。

## 四、字段参考

### 顶层

| 字段 | 必填 | 说明 |
|---|---|---|
| `schema` | ✅ | 必须是 `"icar.ui/1"`。**写错会被明确拒绝**，不会静默按旧规则画 |
| `meta.name` | 建议 | 设计名。缺了只警告 |
| `meta.author` / `meta.description` | — | 备注 |
| `canvas.unit` | 建议 | 必须是 `360`。写别的会报错并提示换算公式 |
| `theme` | — | 主题 id：`neon` / `ice` / `amber`。空 = 用当前主题 |
| `background` | — | **可选**（v1.10.2）。背景图片，见下 |
| `gauges` | ✅ | 仪表数组，1..32 项 |

### `background` 段（可选）

| 字段 | 说明 |
|---|---|
| `path` | 图片路径。**只存路径，不内嵌图片数据** —— 设计文件要能被人读、被 diff 看 |
| `fit` | `0` 铺满（裁切，默认）`1` 完整显示（可能留边）`2` 居中原始大小 |

**路径不存在只警告、不报错。** 设计文件常在不同设备/机器之间传递，
写死绝对路径必然对不上 —— 拦下整个设计太粗暴，仪表布局本身是好的，
只是背景要重新选一张。

> 图片本身由 App 的「风格 → 选择背景图片」导入到 `files/bg/`（会下采样并复制到私有目录）。
> 缺 `path` 时整个 `background` 段被忽略；`fit` 取值非法时回落到「铺满」并警告。

### 单个 gauge

字段与 `GaugeItem` **完全一致**（不引入第二套规则）：

| 字段 | 说明 |
|---|---|
| `pid` | **语义名或 PID id**，见下一节 |
| `style` | `0`圆表 `1`数字 `2`条形 `3`线型图 `4`双数据上下 `5`四数据 `6`主子双数据 `7`G力值 |
| `min` / `max` | 量程。`min ≥ max` 会报错 |
| `warnLow` / `warnHigh` | 报警阈值。**超出 `warnHigh` 会触发爆闪**（危险档由它和 `max` 推出） |
| `x` `y` `w` `h` | 坐标，0..360 |
| `neonPreset` | 霓虹档位：`关闭`/`克制`/`标准`/`强烈`/`夸张`。省略 = 跟随主题 |
| `cardStyle` | **卡片外框覆盖**（v1.10.2）：`1` 无边框（保留卡片底）`2` 完全透明 `3` 不画卡片。省略 = 跟随主题 |
| `ringStyle` | `0`无 `1`外圈刻度线段 |
| `ringSegments` | 刻度段数 8..120 |
| `extraPids` | 副参数（style 4/5/6 用），字符串数组 |
| `role` | `0`主参数 `1`子参数 |

> **`cardStyle` 为什么是枚举而不是三个数值**：存 `radius/stroke/alpha` 三个数会让 JSON 变胖，
> 而且用户真正要选的只有三种观感。枚举既够用，又不会和主题的字段语义打架 ——
> 否则「用户改了主题的圆角，覆盖项里的圆角要不要跟着变」永远说不清。
>
> 想做「大盘透明 + 小表带底」的混合盘面就靠它。

## 五、PID 语义名

**写 `obd.rpm` 而不是 `std_0C`** —— 前者一眼知道是什么，后者要去翻 PID 表。
这是"能在电脑上做设计"的前提之一。两条路都通，直接写 id 也可以。

| 语义名 | PID | 单位 |
|---|---|---|
| `obd.rpm` | std_0C | rpm |
| `obd.speed` | std_0D | km/h |
| `obd.coolant` | std_05 | ℃ |
| `obd.load` | std_04 | % |
| `obd.intake` | std_0F | ℃ |
| `obd.maf` | std_10 | g/s |
| `obd.stft` | std_06 | % |
| `obd.ltft` | std_07 | % |
| `obd.fuel_rate` | std_5E | L/h |
| `obd.map` | std_0B | kPa |
| `obd.fuel_level` | std_2F | % |
| `obd.ambient` | std_46 | ℃ |
| `obd.oil_temp` | std_5C | ℃ |
| `obd.baro` | std_33 | kPa |
| `obd.timing_advance` | std_0E | ° |
| `obd.throttle` | std_11 | % |
| `obd.pedal_d` | std_49 | % |
| `obd.run_time` | std_1F | s |
| `obd.mil_distance` | std_21 | km |
| `obd.voltage` | std_42 | V |
| `calc.l100` | calc_l100 | L/100km |
| `calc.fuel_hourly` | calc_lh | L/h |
| `calc.boost` | calc_boost | kPa |
| `calc.trip` | calc_km | km |
| `calc.gforce` | calc_gforce | G |
| `calc.gx` / `calc.gy` | calc_gx / calc_gy | G |

> **v1.10.2 起，每个默认启用的内置 PID 都有别名**（20 标准 + 7 派生 = 27 条）。
> `ThemeStudioSampleTest` 的 `每个内置 PID 都有语义别名` 用例守着这条 ——
> 漏一个就失败，不靠人记得同步三处。
>
> 厂家模板（`tpl_*`，4 条）**刻意没有别名**：它们是占位示例（默认 `enabled=false`，
> PID 号是猜的）。给它们起个"好听的语义名"反而会让人以为可以直接用 ——
> 必须先用扫描器实测。
>
> 用**自定义 PID** 也可以：直接写它的 id。校验会提示"不在内置库"，
> 但**不拦下** —— 自定义 PID 是合法场景。

## 六、校验（**这个格式一半的价值在这**）

手写 JSON 一定会写错。而"推到设备上发现没显示"是最低效的调试方式。

所以解析器**不抛异常**，返回**带字段路径的可读错误**：

### 硬错误（拒绝加载）

| 情况 | 报错 |
|---|---|
| JSON 语法错 | `JSON 语法错误：...` |
| 缺 `schema` | `缺少 schema 字段。应当写 "icar.ui/1"` |
| schema 不认识 | `不支持的 schema：icar.ui/2（本版本只认 icar.ui/1）` |
| `canvas.unit` 不对 | `canvas.unit = 1600，但本版本只支持 360。如果你按像素设计的，请换算：坐标 / 屏宽 * 360` |
| 缺 `gauges` | `缺少 gauges 数组` |
| `gauges` 为空 | `gauges 是空的 —— 仪表盘上什么都不会显示` |
| 缺 `pid` | `gauges[0] 缺少 pid（可以写语义名如 obd.rpm，或直接写 PID id 如 std_0C）` |
| 量程非法 | `gauges[0]（std_0C）量程非法：min=8000 ≥ max=0` |
| 超过 32 项 | `gauges 有 40 项，超过上限 32` |

### 软警告（能加载，但效果可能不是你要的）

**越界不会报错、只会"看不见那块表"** —— 所以必须主动提示，但不拦下整个设计
（可能你就是故意让它露一半）。

| 情况 | 警告 |
|---|---|
| 超出画布 | `gauges[0]（std_0C）超出画布右下角：右=480 下=180（上限 360）` |
| 坐标为负 | `gauges[0]（std_0C）坐标为负：x=-10 y=0，会被画到屏幕外` |
| 尺寸过小 | `gauges[0]（std_0C）尺寸过小（3×3），几乎看不见` |
| 未知 pid | `gauges[0] 的 pid std_FF 不在内置 PID 库里 —— 需要先在 App 里导入对应 PID` |
| 没有 meta | `没有 meta 段（不影响渲染，但建议写上名字方便识别）` |
| 背景路径不存在 | `background.path 指向的文件在本机不存在：… —— 请用「风格 → 选择背景图片」重新选一张（仪表布局不受影响）` |
| 背景缺 path | `background 段没有 path —— 已忽略该段（不影响仪表布局）` |
| 背景 fit 不认识 | `background.fit = 99 不认识（本版本只认 0..2：…）—— 已回落到「铺满（裁切）」` |

> **`background.path` 不存在这条警告只有 App 能给** —— 浏览器读不到设备路径
> （沙箱限制），所以主题工具只校验 path 非空。这条差异在工具的
> 「与 App 规则的差异」页里显式列出。
>
> `cardStyle` 取值非法**不是错误也不是警告**：回落成「跟随主题」。
> 理由与 `neonPreset` 一致 —— 那是"这块表没有覆盖"，语义上完全合法。

## 七、PC 端工作流

### 1. 写文件

任何文本编辑器。建议开 JSON 语法高亮（VS Code / Sublime / 记事本++）。

### 2. 校验

改完先跑测试校验，**不要直接推到设备**：

```bash
# 把设计文件放到测试资源里，或临时改测试里的字符串
./gradlew testDebugUnitTest --tests '*DesignFileTest*'
```

> 更好的做法是用 `tools/theme-studio/index.html` 的「校验」按钮 ——
> 它的规则与 `DesignFile.kt` 同源（有跨语言比对守着），改完立刻看到结果。

### 3. 导入到设备（**v1.10.3 起有 App 内入口**）

**推荐**：把 `design.json` 传到设备（微信 / 网盘 / USB 都行），然后在 App 里

> **仪表盘 → 风格 → 导入设计文件…** → 选中该文件

会先弹一个确认框，显示设计名、块数、主题、背景，以及**全部软警告**；
确认后才整体替换自定义仪表盘。

**手动推（调试用）**：

```bash
adb push design.json /data/local/tmp/design.json
adb shell chmod 644 /data/local/tmp/design.json
adb shell "run-as com.icar.obd cp /data/local/tmp/design.json files/design.json"
```

> ⚠️ **不要用 `cmd /c ... < file` 或 `adb shell` 的 stdin 重定向传文件** ——
> 会截断（本项目实测：204288 字节传过去只剩 16484）。
> `adb push` 是二进制安全的，`chmod` 是为了让 `run-as` 读得到。

### 4. 反向：把设备上的布局导回电脑

> **仪表盘 → 风格 → 导出当前布局为设计文件…**

走系统分享面板，把 `design.json` 发给电脑，再在 `tools/theme-studio/index.html`
里打开继续改 —— **闭环**。

导出的主题写的是**别名**（`neon`/`ice`/`amber`）而不是数字 id，因为 id 会随自建主题
分配变化，同一份文件在不同设备上 id 可能不同。自建主题没有别名 → 导出时留空
（= 用当前主题）。

### 关于"PC 端预览"

这是**投入产出比最高**的一项：写一个几百行的 HTML 页面，
读同一个 JSON、用 Canvas 画出矩形和文字，就能在改完的一瞬间看到布局。
不需要和 App 的渲染完全一致 —— 只要**位置和比例对**，就能省掉大量"推设备→看→改"的往返。

## 九、和已被删除的 Sky Gauge 格式的区别

本项目曾实现过 Sky Gauge 主题导入，后来删掉了（见 [LVGL-放弃记录.md](LVGL-放弃记录.md)）。
两者的关键区别：

| | Sky Gauge | 本格式 |
|---|---|---|
| 归属 | **别人的**格式 | **我们自己的** |
| 模型 | 图元级（arc/label/image），要写转换层 | **直接复用 `GaugeItem`**，零转换 |
| 表达力 | 受限于他们的词汇表（6 个数据源、3 种元素） | = App 能画的东西，一一对应 |
| 坐标系 | 正方形 360×360，非方形屏会变形 | 每轴 0..360，天然适配任意宽高比 |
| 字体 | 内嵌 `lv_font_bin`，要解析 | 用系统/应用字体，不用管 |

**教训**：借用别人的格式，表达力就被别人的需求定义了。
自己的模型自己定，反而更简单、更贴合。
