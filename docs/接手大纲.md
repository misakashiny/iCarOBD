## 0. 30 秒了解

把 **Vgate iCar Pro 2S**（ELM327 兼容的 OBD 蓝牙适配器）读到车辆数据，
变成手机/平板上的实时仪表盘，并按规则触发告警（变色、音效、Toast）。

**贯穿全局的设计目标**：
> **新增一种车辆数据不需要改代码、不需要重新编译 APK。**
> 在 App 里「添加 PID → 测试 → 保存 → 选进仪表盘」即可。

所有架构决策都服务于这一条。评判一次改动好不好，先问它有没有破坏这条。

## 3. 项目大纲

### 3.1 分层（依赖只能自上而下）

```
┌─ ui/ ────────────────────────────────────────────┐
│  MainActivity · 5 Fragment · 6 Editor Activity    │
│  ui/adapter/ · ui/dash/ · ui/view/                │
│  BenchActivity（性能基准，见 §7.4）                │
└────────┬──────────────────────┬───────────────────┘
         │ 读 VehicleBus         │ 写 ObdController（唯一入口）
         ▼                       ▼
┌─ obd/ ───────────────────────────────────────────┐
│  VehicleBus（数据总线，含有界历史环形缓冲）          │
│  ObdController（进程级单例门面）                    │
│  ObdEngine（轮询） · RuleEngine（规则）             │
│  ObdProtocol（纯函数解析） · PidScanner（安全扫描）  │
│  CanSniffer（ATMA 被动探测） · GForceSource        │
│  SignalSimulator（合成数据源）                      │
│  ElmSession（一问一答串口语义）                     │
└────────┬─────────────────────────────────────────┘
         ▼
┌─ ble/ ───────────────────────────────────────────┐
│  ObdTransport（接口：只管收发字节，不认识 OBD 语义）  │
│  BleTransport / SppTransport（两个实现）           │
└────────┬─────────────────────────────────────────┘
         ▼
┌─ data/ ──────────────────────────────────────────┐
│  PidModels · Formula · BuiltInPids · Store         │
│  DashLayout · DesignFile · Backup · GaugeTheme※    │
│  AppLog · CsvRecorder · AudioPlayer · Defaults     │
└──────────────────────────────────────────────────┘
service/ObdService → 只依赖 obd/ 与 data/，不依赖 ui/
```

> ※ `GaugeTheme` 在 `ui/view/`，不在这里 —— `data/` 不能反向依赖 `ui/`（红线 §4.1.7）。
> 所以 `Store` 存的是**原始 JSON 字符串**，schema 由 `GaugeTheme` 自己负责。

### 3.2 数据流（**这个非对称是刻意的，别改**）

```
写（推送）：BLE → BleTransport → ElmSession → ObdEngine → ObdProtocol
            → VehicleBus → RuleEngine / DashRenderer / CsvRecorder
读（拉取）：DashRenderer 内部 5Hz 定时器去 VehicleBus 取值
动画：      GaugeTicker（Choreographer）每帧一次回调 → 所有仪表一起重绘
```

**为什么读是拉取而不是推送**：仪表盘刷新率（5Hz）与 OBD 轮询率（每条约 8Hz 分摊）
本来就不一致，用拉取可以天然解耦、丢帧不累积。改成推送会引入背压问题。

**为什么动画是共用时钟而不是各自 postDelayed**：8 个表各自 postDelayed 是每秒 480 次
消息投递，且各自按 16ms 猜、和 vsync 错拍。见 `docs/动画实现.md`。

其他已知坑：
- `dl.google.com` 不可达 → `settings.gradle.kts` 里的**阿里云镜像不能删**
- `--offline` 构建会失败
- 版本号在 `app/build.gradle.kts` 的 `versionCode` / `versionName`
- **路径含空格与中文**（`D:\AI Dsh\车机项目`）：AGP 默认拒绝构建，
  已用 `android.overridePathCheck=true` 放行；细节见 [`FILE_MAP.md`](FILE_MAP.md) §6

**跑单元测试**（415 个用例）—— **不要**直接 `./gradlew testDebugUnitTest`：

```powershell
powershell -ExecutionPolicy Bypass -File tools\run-tests.ps1
```

> 原因：非 ASCII 路径会让 JVM 启动器解码坏 `-cp`，全部测试类报
> `ClassNotFoundException`。脚本会先建 ASCII 目录联接 `D:\icarobd` 再跑，
> **工程本身不动**，构建产物也仍在原处。
> （v1.10.1 起 `-ProjectDir` 可省略，三种调用方式都验证过。）

> ⚠️ **改 `tools/*.ps1` 时必须保留 UTF-8 BOM。**
> Windows PowerShell 5.1 对**无 BOM** 的 `.ps1` 按 ANSI(GBK) 解码，
> 中文注释会变乱码**并吃掉行尾**，把下一行代码并进注释里 ——
> 报错是 `Unexpected token '}'`，看起来像语法错，实际是编码问题。
> v1.10.1 实测栽过一次（`run-tests.ps1` 被写掉了 BOM，一个用例都没跑起来）。
> `oncar-check.ps1` 一直有 BOM，可以对照。

## 5. 动手前必须知道的三件事

### 5.1 新增车辆数据的标准流程（**最重要**）

详见 [`HANDOVER.md`](HANDOVER.md) §5。要点：

1. 「PID」页 → 新建 → 填 Mode / PID / 公式 / 单位 / 量程
2. **先在编辑器里「发送测试请求」**，确认能拿到合理数值
3. 保存 → 启用 → 在「仪表盘 → 自定义 → 添加仪表」里选它

**厂家 PID 的号不要猜。** 错误的 PID 号比没有更危险（可能写到 ECU 的写寄存器）。
内置的阿特兹模板默认 `enabled=false` 就是这个原因。

### 5.2 横竖屏自适应（四条机制，缺一不可）

详见 [`ARCHITECTURE.md`](ARCHITECTURE.md) §3。简述：

1. **不锁方向** —— 任何 Activity 都不得加 `screenOrientation="portrait"`
2. **导航按方向切换** —— 竖屏 `BottomNavigationView`（底部），
   横屏 `NavigationRailView`（左侧）。两个布局 **id 相同**（`navView`）
   且都继承 `NavigationBarView`，所以 `MainActivity` 用基类接收，**零方向分支**
3. **仪表盘是归一化自由画布** —— 每块表自带 `x/y/w/h`（每轴 0..360），
   与屏幕尺寸无关。**不要改回网格 + `span`**（v1.5.0 起已废弃，见红线 §4.5.19）
4. **宽屏表单限宽 + 自动分栏** —— `ui/view/MaxWidthViews.kt` 把内容夹到 720~900dp 并居中；
   `ui/view/ColumnFlowLayout.kt` 再按可用宽度**自动分 1 列 / 2 列**（瀑布流，
   列分配与 `onMeasure` 共用同一个纯函数 `assign`）。
   **一套 XML 适配两方向，刻意不做 layout-land 副本**（复制 1000 行 XML 不划算）

### 5.3 日志系统有自我保护，不要拆

详见 [`HANDOVER.md`](HANDOVER.md) §12.4。四条防线：
重复消息抑制 / 单日文件上限 24MB / 落盘队列有界 / 监听器批量派发。

**背景**：实车上 BLE 写入失败进入无限重试并逐次写日志，
2 小时刷出 **113 万行 / 57.9MB**，把日志页一起拖崩。
**任何一处单点刷屏都可能重演**，所以在循环里写日志前先想想。

## 7. 验证方法（本项目踩过坑的地方）

### 7.1 装机后必查

> **上车场景直接用 `tools\oncar-check.ps1`** —— 它把下面这些检查连同 GATT 表、
> AT 命令 TX/RX、超时、初始化结果、扫描器日志一次性收齐，并按 GATT 表给出判定。

```bash
$ADB logcat -d -b crash                      # 崩溃
$ADB logcat -d | grep -icE "ANR in"          # ANR
$ADB exec-out run-as com.icar.obd cat files/log/obd-$(date +%Y%m%d).log | tail -30
```

App 内日志开头应有 `===== iCar OBD 启动 ===== | ver=x.y.z`。

### 7.2 两条血泪教训

**① 环形缓冲类组件必须用压力注入验证溢出路径。**
日常 UI 测试里日志只有几十条，永远碰不到 3000 上限，
而日志页崩溃恰恰只在超过上限时触发。

**② 验证一个分支，要确认该分支真的被执行了。**
第一次压力测试一次性投放 8000 条，结果被 500 条的派发队列截断，
适配器只收到 512 条，**根本没走到溢出分支** —— 差点得出「已验证」的错误结论。
改成分批投放（每 200 条 + 40ms）后才真正压到，从界面上 `3000 条（缓冲 3000）`
这个数字确认它确实在溢出状态。

> **判据要落到可观测的数字上，不要凭「没崩」就认为通过。**

### 7.3 排查数据链路问题

**第一步永远是看自动转储的 GATT 表**（v1.3.0 起连接后自动打印）：

```
[BLE][I] ===== GATT 表开始 ===== | 服务数=N
[BLE][I] SVC 000018f0-...
[BLE][I]   CHR 00002af0-... | props=Wn writeType=1 dsc=2
[BLE][I]   CHR 00002af1-... | props=N writeType=0 dsc=2
[BLE][I] ===== GATT 表结束 =====
```

关注写特征的 `props=`：
- 含 `Wn`（write-no-response）或 `W` → 具备写能力，正常
- 只有 `N`（notify）没有写属性 → UUID 表选错了特征
- 整张表没有任何可写特征 → 该适配器可能不是 BLE 透传，需改走经典蓝牙 SPP

### 7.4 量渲染性能（v1.10.1 起有现成工具）

**入口**：连接页「运行选项」→「性能基准」（`ui/BenchActivity`）。
8 个圆表 4×2 铺满，**每帧强制重绘**，四段各「预热 1.5s + 测量 10s」，
报告写进 `files/bench-dashboard.txt`。

**为什么必须用这一页，而不是 `dumpsys gfxinfo`**：

1. `dumpsys gfxinfo` 在这台设备上只给头部、没有帧统计；
2. 用真实数据测时**仪表根本没在动** —— 静止的 View 不重绘，
   测出来的"帧率"是屏幕刷新率，和绘制成本无关。

**⚠️ 判据是「帧间隔」，不是「每帧绘制耗时」**：

开了硬件加速后 `onDraw` 只是把绘制指令**记录**进 DisplayList，
真正的光栅化在**渲染线程**上做。所以 `DrawStats` 那个 0.2~0.3ms
**不是绘制成本**，拿它下结论会得出过于乐观的答案。

真正能回答"守不守得住"的是**帧间隔**（主线程 + 渲染线程 + 合成器的最终结果）。
判据 = 刷新周期 × 1.5（120Hz → 12.5ms，60Hz → 25ms），超时帧数必须为 **0**。

**v1.10.1 实测结果**（小米平板 5，120Hz）：

| 档位 | 仪表 | 帧间隔 平均 | p99 | 最大 | 超时帧 |
|---|---|---|---|---|---|
| 8 表 · 主题默认 | 8 | 8.33 ms | 8.39 ms | 8.43 ms | **0** |
| 8 表 · 夸张（11 层） | 8 | 8.33 ms | 8.38 ms | 8.41 ms | **0** |
| 8 表 · 关闭辉光 | 8 | 8.33 ms | 8.38 ms | 8.43 ms | **0** |
| 12 表 · 夸张（极限） | 12 | 8.33 ms | 8.38 ms | 8.41 ms | **0** |

**结论：12 个圆表 + 11 层辉光跑满 120fps，零掉帧。**
所以「9 层辉光守不住 60fps」这个风险**不成立**，`NeonStyle` 的默认值和
`layersFor` 的档位**不需要因为性能而调整**。

**改渲染层之后请重跑一次**，尤其：

- 给数字 / 折线 / 多值 / G力值四种表接霓虹（v1.9.0 遗留，它们现在不发光）
- 调整 `NeonPainter.layersFor` 的档位阈值或 `spreadRatio`
- 新增会参与动画的控件（要接 `GaugeTicker`，见 §5.2 与 `动画实现.md`）
