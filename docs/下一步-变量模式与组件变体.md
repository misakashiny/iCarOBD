## 一、要解决什么

现在做一套主题，改一个颜色要在 8 个表上各点一次；换一套配色要重做一遍。
`themeColors` 只能管**主题的 12 个色**，管不到"这个文字控件用什么颜色"。

要补两个能力：

| 能力 | 一句话 | 典型场景 |
|---|---|---|
| **变量 + 模式** | 把值抽成有名字的变量；一个模式 = 一套取值 | "三套配色" · "大表/小表两套尺寸" |
| **组件 + 变体** | 一个母版 + 若干变体；改母版，所有实例跟着变 | "8 个圆表改一处全改" |

**非目标**（这一轮明确不做）：多人协作 · 自动布局 · 矢量编辑 · 原型连线 · 插件系统。
**硬约束：App 侧（Kotlin / LVGL）零改动。**

## 二、为什么不能"直接照搬 Figma"

摸底时确认了两条 App 侧的硬事实，它们决定了整个方案：

| # | 事实 | 出处 |
|---|---|---|
| 1 | App 对未知 `type` **报硬错误**（"type `instance` 不认识"），不是忽略 | [`DesignNode.kt:309`](../app/src/main/java/com/icar/obd/data/DesignNode.kt) |
| 2 | App **忽略**未知的顶层键与未知的节点字段 | [`DesignFile.kt:342`](../app/src/main/java/com/icar/obd/data/DesignFile.kt) |

事实 1 ⇒ **`type:"instance"` 的实例节点绝不能进 `nodes`**，否则 App 直接拒绝加载。
事实 2 ⇒ 顶层可以安全新增 `tokens` / `modes` / `bindings` / `library`。

### 2.1 真正的问题：绑定信息存哪

- 只把**解析后的字面值**写进 `nodes` → App 能读，但**工具重新打开就丢了绑定**
- 把**引用**（`"$accent"`）写进 `nodes` → App 读到会**静默回落**

后者是本项目最该避免的失效方式：不报错、不崩，就是颜色不对，直到推上设备才发现。

### 2.2 ⚠️ 一个已经存在的静默陷阱

`normalizeFont`（[`schema.js:366`](../tools/icarui/js/schema.js)）的判据是：

```js
if (typeof o.color !== "string" || !/^#[0-9a-fA-F]{6}$/.test(o.color)) o.color = window.FONT_DEFAULT.color;
```

**不匹配就回落默认色，不报错。** 所以 `"$accent"` 一旦流到 `normalizeFont` 就会被无声吃掉 ——
画布上显示的是 `#E8EEF7`，用户以为"绑定没生效"。

这是设计这个功能时**必须先拆掉的雷**，见 §4.2。

## 三、格式：`icar.ui/2` 的扩展

新增四个**顶层键**（App 全部忽略）：

```json
{
  "schema": "icar.ui/2",
  "tokens":     [ ... ],
  "modes":      [ ... ],
  "activeMode": "m1",
  "bindings":   { ... },
  "library":    [ ... ],
  "nodes":      [ ... ]
}
```

### 3.1 核心不变式（写死，不许破）

> **`nodes` / `pages[].nodes` 里永远不出现 `$` 引用，也不出现 `instance` 节点。**
>
> 它们是**编译产物**：由 `tokens` + `modes` + `activeMode` + `bindings` + `library` 唯一决定。

这条不变式是「App 零改动」的**全部依据**，也是 §5 漂移检测的判据。
任何让它不成立的改动（哪怕"只是调试一下"）都会让 App 静默画错。

### 3.2 `tokens` —— 变量

```json
"tokens": [
  { "id": "tk1", "name": "accent", "type": "color",  "value": "#FF8A00", "builtin": "accent" },
  { "id": "tk2", "name": "radius", "type": "number", "value": 12 },
  { "id": "tk3", "name": "title",  "type": "string", "value": "转速" }
]
```

| 字段 | 说明 |
|---|---|
| `id` | 稳定标识。**引用优先用 id** —— 改名不会断引用 |
| `name` | 显示名，也允许被引用（`$accent`） |
| `type` | `color` / `number` / `string`。决定解析成什么、UI 用什么控件 |
| `value` | **默认值**。模式里没覆盖时用它 |
| `builtin` | 有它 = **内置变量**，指向 `THEME_COLOR_FIELDS` 的键（12 个颜色） |

**12 个内置变量**由 `THEME_COLOR_FIELDS` 生成（背景/卡片底/卡片边/主色/高亮色/暗主色/轨道/刻度/指针/数值/标签/次要文字）。
它们**同时**是 App 主题系统的 `themeColors` 字段 —— 这是本方案能"零 App 改动"的关键复用点。

### 3.3 `modes` —— 模式

```json
"modes": [
  { "id": "m1", "name": "霓虹赛道", "values": { "tk1": "#FF8A00", "tk2": 12 } },
  { "id": "m2", "name": "冰川科技", "values": { "tk1": "#28D7FF" } },
  { "id": "m3", "name": "经典琥珀", "values": {} }
]
```

- **`values` 只存差异** —— 与 `themeColorsOverride` 同一套哲学：
  没写的变量回落到 `tokens[].value`，所以"改默认值"能影响所有没覆盖它的模式
- 三个内置模式由 `GAUGE_THEMES`（`neon` / `ice` / `amber`）生成
- 内置模式**可改名、可改值，不可删**（`GAUGE_THEMES` 是跨语言契约，见 §8）

### 3.4 `bindings` —— 绑定

```json
"bindings": {
  "n3": { "font.color": "$accent", "card.radius": "$radius" },
  "n7": { "@component": "c1", "@variant": "v1", "min": 0, "max": 8000 }
}
```

| 键 | 含义 |
|---|---|
| 普通字段路径（`font.color` / `labelFont.color` / `card.radius` / `text` …） | 值 = **引用串**，解析后写进 `nodes` 的对应字段 |
| `@component` / `@variant`（阶段 2） | 血缘：这个节点是哪个组件的哪个变体展开出来的 |
| 其它裸字段名（阶段 2） | **覆盖**：用户手改过的字段，重建时保留 |

⚠️ **只有"被绑过 / 被覆盖过"的字段才写进 `bindings`**。没绑的字段照旧直接写在 `nodes` 里 ——
否则 `bindings` 会变成每个节点一坨全量字段的第二份真相（§2.16 的教训）。

### 3.5 引用语法

```
"$accent"   → 按 name 找变量
"$tk1"      → 也接受 id
```

**为什么不用 `{ "$t": "tk1" }` 这种对象**：字符串前缀在 JSON 里人眼一眼能认出是引用，
而对象形式和普通值长得太像；而且解析点可以收敛成"字符串以 `$` 开头"这一条判据。

### 3.6 可绑定的字段（白名单）

**第一版只放开这几处**，其余一律不绑（白名单比黑名单好审）：

| 位置 | 字段 | 类型 |
|---|---|---|
| 文字节点 | `font.color` | color |
| 文字节点 | `text` | string |
| 仪表节点 | `labelFont.color` | color |
| 仪表节点 | `card.radius` | number |
| 仪表节点 | `card.alpha` | number |

> 为什么不做"任意字段可绑"：`pid` / `style` / `min` / `max` 这些绑了之后，
> 属性面板、校验、量程推导全都要跟着改语义，收益远小于复杂度。
> 需要时再逐个放开。

## 四、解析：唯一入口

```
window.resolveDesign(design) → design'     // 深拷贝，nodes 全部字面化
```

**两个调用点，同一个函数**：

| 时机 | 位置 |
|---|---|
| 渲染前 | `canvas.js` 的 `draw()` 开头 |
| 序列化前 | `model.js` 的 `toV2Json()` |

> ⚠️ **不许各写一份。** v2.49.0 已经踩过同一个坑：`model.js` 拼 `themeColors`、
> 而画布不读它，于是"切主题画布完全不变"。两处实现迟早分叉，症状是
> 「画布上看到的」和「导出后 App 看到的」不一样。

### 4.1 解析顺序

```
1. 解析 activeMode → 每个 token 的**当前值**（mode.values[t] ?? token.value）
2. 把 12 个内置变量 → themeColors（= 内置主题打底 + 覆盖）
3. 遍历 bindings：
   a. 普通字段路径 → 把引用换成字面值，写进对应节点的字段
   b. @component/@variant → 从 library 取模板展开（阶段 2），再套用覆盖字段
4. 输出深拷贝，原 design 不动
```

**原 design 不动**是关键：解析结果只是"这一帧 / 这一次导出"的视图，
用户的编辑永远作用在 `bindings` 上。

### 4.2 ⚠️ 必须先于 `normalizeFont`，并给它加一条防线

`resolveDesign` 在渲染/序列化的**最外层**跑，保证下游拿到的永远是字面值。
但这只挡住"正常路径" —— 手改 JSON、或将来有人插一个新的调用点，`$` 还是会漏下去。

所以给 `normalizeFont` 补一条**显式**行为：

```js
// 引用串**原样保留**，不回落默认色。
// 回落会把"绑定写错了"变成"颜色悄悄变了"，而前者能报错、后者不能。
if (typeof o.color === "string" && o.color.charAt(0) === "$") return o;   // 交给校验去报
```

配套：校验器看到 `$` 开头的 color **且**该字段不在 `bindings` 里 → **报硬错误**
（"nodes[3].font.color 是 `$accent`，但 bindings 里没有这条 —— 引用不能写在 nodes 里"）。

**这条是 §2.2 那个静默陷阱的解药**：把"颜色悄悄变默认"变成"校验报错"。

## 五、漂移检测

打开文件时（`parseDesignRoot` 之后、进入编辑器之前）：

```
对每个 bindings 条目，算出"按 tokens/library 应该是什么值"
                ↓ 与 nodes 里的实际值比对
```

| 情况 | 级别 | 文案 |
|---|---|---|
| 一致 | — | 不说 |
| 不一致 | **警告** | `n3 的 font.color 在 nodes 里是 #E8EEF7，但 bindings 指向 $accent（= #FF8A00）。已按 bindings 重建。` |
| bindings 指向不存在的变量 | **错误** | `bindings.n3 引用了不存在的变量 $accent` |
| `nodes` 里出现 `$` 引用 | **错误** | 见 §4.2 |

> **为什么"不一致"只算警告**：手改 JSON 是合法用法（本工具的定位就是"JSON 能直接改"）。
> 只是这种改法会被 bindings 覆盖 —— 所以要**报出来**，让用户知道自己的改动去哪了。
>
> 这正是 [`主题设计大纲.md`](主题设计大纲.md) §2.16 那条教训的直接应用：
> **不能两个都写**，但可以"以 bindings 为准 + 显式告知"。

## 六、UI

### 6.1 「🎨 主题配色」→「🎨 变量与模式」

对话框（复用现有 `#themeColorsDlg` 的 `<dialog>`）分三区：

```
┌─ 变量与模式 ────────────────────────────────────────────┐
│ 模式  [霓虹赛道 ✓] [冰川科技] [经典琥珀]  [+ 新建模式]     │
│ ─────────────────────────────────────────────────────── │
│ 变量              类型    本模式的值        绑定          │
│ 主色 accent       color   ■ #FF8A00  ↺     3            │
│ 高亮色 accentHot  color   ■ #FFE45C  ↺     0            │
│ 圆角 radius       number  [ 12 ]      ↺    1            │
│ …                                                       │
│ [+ 新建变量]                                             │
│ ─────────────────────────────────────────────────────── │
│ ⚠ 前 12 个是**内置变量**，同时喂给 themeColors（App 的     │
│   主题系统）。改它们 = 改导出文件里的主题配色。            │
└─────────────────────────────────────────────────────────┘
```

- **切模式** = 改 `design.activeMode` → 立刻重画（复用 `window.draw()`）
- **改值** = 改 `modes[i].values[tokenId]`（只存差异）；`↺` = 删掉这条覆盖
- **绑定数列** = 有多少个 `bindings` 条目指向这个变量；点它跳到那些节点
- 内置变量**不可删**，只能改名/改值

### 6.2 属性面板：字段旁的 `$` 绑定按钮

在 §3.6 白名单字段的输入框旁加一个小 `$` 按钮：

- 未绑定：点开下拉，列出该类型兼容的变量
- 已绑定：输入框**禁用**，显示 `$accent` + 「解绑」按钮 + 当前解析值（灰字）

> ⚠️ 已绑定时输入框必须禁用而不是"改了就解绑" —— 后者会让用户在不知情的情况下
> 把一个绑着变量的字段改成字面值，而且**没有任何提示**。

见 §8。

## 七、阶段 2：组件 + 变体

### 7.1 格式

```json
"library": [
  { "id": "c1", "name": "圆表",
    "variants": [
      { "id": "v1", "name": "大", "node": { "type": "gauge", "style": 0, "w": 240, "h": 240, ... } },
      { "id": "v2", "name": "小", "node": { "type": "gauge", "style": 0, "w": 120, "h": 120, ... } }
    ] }
]
```

- 复用现有 `controls`（自定义控件库）的结构 —— 它本来就是"一个模板节点 + 子树"，
  只是现在是**一次性展开**，没有血缘
- `variants[].node` 是**模板**，可以含子树、可以含 `$变量引用`

### 7.2 放置与重建

```
放置：按变体模板深拷贝 → 写进 nodes（普通节点）
     同时在 bindings 记 { "@component": "c1", "@variant": "v1" }

改母版：下次 resolveDesign 时从 library 重新展开
       —— 未覆盖的字段跟着母版变，覆盖过的保留
```

**所以是自动联动，不需要手动点「同步」** —— 这是相对"记血缘 + 手动同步"的关键改进。

### 7.3 ⚠️ 覆盖只对"标量字段"生效

`children` / `parts` 这类数组：**要么整份来自母版，要么整份覆盖**，不做逐项合并。

理由：逐项合并的规则没人能预测，而且母版增删子项时数组下标会错位 ——
结果是"我在母版里加了个指针，某个实例上多出来一个不知道从哪来的刻度"。

### 7.4 与 `controls` 的关系

| | `controls`（现有） | `library`（新） |
|---|---|---|
| 用途 | 个人控件库，拖出来即用 | 设计系统的母版 |
| 血缘 | 无（纯深拷贝） | 有 |
| 变体 | 无 | 有 |
| 母版改动 | 不影响已放置的 | 自动传播 |

**不合并**：`controls` 是"我的常用零件"，`library` 是"这套设计系统的组件"。
两者的生命周期完全不同（前者跟着人走，后者跟着设计文件走）。
但**编辑器 UI 可以放在同一栏**，用分组区分。

### 7.5 `MAX_NODES` 的影响

`MAX_NODES = 200` 是**展开后**的节点数（工具与 App 两侧都查）。
组件化会让"看起来 20 个控件"的设计展开成 150 个节点 ——
所以**校验必须对展开后的结果计数**，并在接近上限时提前警告。

## 八、App 侧影响：**零**

| 关注点 | 结论 |
|---|---|
| `nodes` 里的节点类型 | 仍然只有 `group` / `image` / `gauge` / `text` |
| 未知顶层键 | App 用 `optJSONObject` / `optJSONArray` 读，**未知键返回 null**，不报错 |
| 未知节点字段 | 同上，只读它认识的那几个 |
| `themeColors` | **照旧写出**，且必须是完整 15 字段（12 色 + `glow` + 别名）—— 见下 |

### 8.1 ⚠️ `themeColors` 的跨语言契约不能动

`verify-crosslang.js` 逐条核对 12 个颜色字段 + `glow` + 主题别名列表。
所以：

- `tokens` 里的 12 个内置变量**必须**与 `THEME_COLOR_FIELDS` 一一对应
- 解析后写出的 `themeColors` 必须**逐字段等于**今天 `内置主题打底 + themeColorsOverride` 的结果
- **这是一条可测的等价性**（见 §9 的 T1）

### 8.2 「与 App 规则的差异」页新增三条

1. **一致**：`nodes` 的字面值语义与 App 完全一致（由 T1 的等价性守着）
2. **差异**：漂移检测只在工具侧做（App 不认识 `bindings`，也就无从检测）
3. **未做**：App 侧**不能**切模式 —— 一个设计文件 = 一个模式。
   要三套配色就得导出三份文件。

### 9.3 迁移规则

打开老文件时（有 `themeColorsOverride`、没有 `modes`）：

```
1. 生成 3 个内置模式（由 GAUGE_THEMES）
2. 生成 12 个内置变量（由 THEME_COLOR_FIELDS + 当前主题）
3. 把 themeColorsOverride 写进**当前主题对应的那个模式**的 values
4. themeColorsOverride 字段不再写出（由 modes 取代）
```

⚠️ **迁移必须在 `parseDesignRoot` 里一次做完**，不要"读的时候走老路径、存的时候走新路径" ——
那又是一次"两处真相"。

## 十二、已拍板（2026-10-09，实施中）

> 这一节是**决定记录**，优先级高于上文里与之冲突的写法。

### 1. §3.6 可绑定字段白名单：**就 5 处，不加**
`font.color` / `text` / `labelFont.color` / `card.radius` / `card.alpha`。
理由：核心价值（12 个内置颜色变量）已覆盖；每多开一处都是线性成本
（属性面板按钮 + 校验 + 漂移检测 + 已绑定禁用输入），漏一处就出现"改了没生效"。

### 2. §6.1 对话框：**替换**现有的「🎨 主题配色」入口（不是并列）
理由：这个项目最痛的教训就是"两份权威"，两个入口 = 两套概念。
⚠️ **替换的前提是 T1 等价性成立** —— 老文件迁移后导出的 `themeColors` 必须与迁移前**逐字段相同**
（老用户数据不能变，变的只是入口位置）。

### 3. 🚩 `$$` 转义：**从格式里取消**（推翻 v2.80.1 的决定）

**为什么取消**：
- `$$` 是**工具单方面的约定，App 完全不认**（`NodeTreeRenderer` 就是 `tv.text = node.text`，
  全 `app/src` 搜不到 unescape）→ 文件里写 `text: "$$100"`，**平板上显示 `$$100`**，而工具里显示 `$100`
- 更糟：v2.80.1 的警告文案**正在教用户这么写** → 用户照做 → 设备显示就错
- 这种失效**不报错、不崩，只是显示不对** —— 本项目最怕的一类
- 而按 §3.1 的核心不变式，**`nodes[].text` 永远是字面值**（引用只存在于 `bindings`）
  → `$100` 根本不是引用 → **不需要转义** ✓
- 当初要转义只因"`text` 里 `$` 开头算硬错误"，而那条**已降为警告** → **转义的唯一理由消失**

**取消后的规则**：
- `nodes[].text` **永远是字面值**，写什么显示什么（工具与设备一致）
- `$` 开头只是"**看起来像引用**"的**警告**，文案要说清"想绑定变量就加 bindings 条目；是字面值就忽略这条"
  —— **不许再出现"请写成 `$$100`"这种教错人的话**
- 颜色 / 数值字段（`font.color`/`labelFont.color`/`card.radius`/`card.alpha`）出现 `$` **仍是硬错误**
  （那些字段不可能有字面 `$`，必然是笔误）

**要顺带改的**：`js/schema.js` 的转义相关函数、`js/validate.js` 的警告文案、
`tests/verify-tokens.js` 里钉着 `$$` 的断言（改成"字面值原样显示 + 只有警告"）。
