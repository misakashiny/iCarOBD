## ⚠️ 零、本阶段最重要的两条纠正

### 纠正 1：P4P-1B 说「headless 不落盘」是**错的**

P4P-1B 报告写：

> 不是「强杀丢数据」，而是 **headless 的 `--user-data-dir` 不持久化到磁盘**

**这是错误结论。** P4R-0 用严格控制的实验查明：

| 写入后等待 | 磁盘 `000003.log` | 强杀重启后 |
|---|---|---|
| 500 ms | 30 B | ❌ **丢失** |
| 800 ms | 30 B | ❌ 丢失 |
| 1200 ms | 30 B | ❌ 丢失 |
| 1600 ms | 30 B | ❌ 丢失 |
| 2000 ms | 30 B | ❌ 丢失 |
| **2500 ms** | **37484 B** | ✅ **完整保留** |
| 3000 ms | 37511 B | ✅ 完整保留 |
| 8000 ms | 37511 B | ✅ 完整保留 |

**真相**：Chromium 的 localStorage 有 **约 2.0~2.5 秒的异步落盘窗口**。
窗口内强杀 → 丢；窗口外强杀 → **数据完好**。

> 这不是产品缺陷，也不是 headless 限制，而是 **Chromium 存储机制本身**。
> P4P-1B 当时写入后立刻 `taskkill`，正好落在窗口内，于是误判成"环境不落盘"。

### 纠正 2：撤销历史**没有被覆盖或清除**，只是没人读回

P4P-1B 猜测"启动时可能覆盖历史"。实测：

| 项 | 刷新后 |
|---|---|
| localStorage 里的撤销栈 | **1401 字节 / 2 步，完好** |
| 运行时撤销栈 | **depth 0 / size 1 / label `初始`** |
| 当前设计名 | `未命名设计` |

**结论**：`init()` 只重置了**内存栈**（`undo.reset()`），**localStorage 一个字都没动**。
数据一直在磁盘上，从头到尾没有任何代码调用 `loadUndoStack()` 把它读回来。

## 一、当前设计保存机制的完整调用链（任务第十二部分第 1 项）

### 1.1 三条独立链路

```
┌─ 链路1：手动保存（唯一真正持久化设计的路径）
│
│  index.html:24  按钮 onclick="saveFile()"
│      ↓
│  app.js:3137  saveFile()
│      ├─ validateNow()          校验错误会二次确认
│      ├─ download(name+".json", getVal("jsonArea"))
│      │     └─ Blob + <a download>  →  浏览器下载到磁盘
│      └─ toast(... + "别忘了把素材图片放到 assets/ 下")
│
├─ 链路2：打开/导入设计
│
│  index.html:23  按钮 onclick="pickFile()"
│      ↓
│  app.js:3099  pickFile()
│      ├─ <input type=file accept=".json">
│      ├─ FileReader.readAsText()
│      ├─ validateText()          校验失败 → toast + 保留当前设计
│      ├─ confirmJsonReplace()    当前有内容 → 二次确认
│      └─ replaceDesign(candidate.design)
│
└─ 链路3：撤销栈（写入但从不读回）
   │
   │  commit() → saveUndoStack() → localStorage["icar-studio-undo"]
   │                                    ↑ 每次 commit 写 1.19MB
   │  init() → undo.reset()             ← 内存栈重置为空白设计
   └─ loadUndoStack()  ← ★ 定义了、导出了、**从未被调用**
```

### 1.2 `saveFile()` 的实际行为

```js
window.saveFile = function () {
  const r = validateNow();
  if (r.errors.length) { if (!confirm(...)) return; }
  download((S.design.name || "design") + ".json", getVal("jsonArea"));
  toast(...);
};
```

**它把内容写进一个 Blob 然后触发浏览器下载 —— 不碰任何浏览器存储。**

## 二、数据丢失边界与风险分级（任务第十二部分第 2 项）

### 2.1 五类数据 × 八道流程

| 流程 | A 当前设计 | B 已保存文件 | C 撤销/重做 | D 素材数据 | E 选择/页面/编辑态 |
|---|---|---|---|---|---|
| 新建设计 | ❌ 丢弃（有确认）| ✅ 不受影响 | ❌ 重置 | — | ❌ 重置 |
| 修改设计 | ✅ 仅内存 | ✅ 不受影响 | ✅ 内存 | ✅ 仅内存 | ✅ 仅内存 |
| **手动保存/导出** | — | ✅ **写入磁盘** | — | ⚠️ **仅提示用户自己搬 assets/** | — |
| 打开/导入 | ❌ 替换（有确认）| ✅ 不受影响 | ❌ 重置 | ✅ 随设计替换 | ❌ 重置 |
| **刷新页面** | ❌ **全部丢失** | ✅ 不受影响 | ⚠️ **磁盘有、内存不加载** | ❌ **全部丢失** | ❌ 重置 |
| **关闭重开** | ❌ **全部丢失** | ✅ 不受影响 | ⚠️ 同上 | ❌ **全部丢失** | ❌ 重置 |
| **浏览器异常退出** | ❌ **全部丢失** | ✅ 不受影响 | ⚠️ 同上 | ❌ **全部丢失** | ❌ 重置 |
| UndoStack 恢复 | — | — | ⚠️ **从不发生** | — | — |

### 2.2 风险分级

| 级别 | 风险 | 说明 |
|---|---|---|
| 🔴 **P0** | **设计无自动保存，刷新/崩溃即全丢** | 用户改了半天，刷新一下全没了 |
| 🔴 **P0** | **撤销历史写盘但从不加载** | 每次 commit 付 15.6ms，收益为 0 |
| 🟠 **P1** | **素材不随设计文件保存** | `saveFile` 只提示"别忘了搬 assets/"，靠人记 |
| 🟠 **P1** | **设计名可重复，不能作身份** | 实测同名不同设计会**错位加载历史** |
| 🟡 **P2** | 撤销历史 1.2MB 预算已触顶 | 40 步即满，更大设计**静默丢步** |
| 🟡 **P2** | localStorage 2~2.5s 落盘窗口 | 崩溃可能丢最近 2 秒的写入 |

| `app.js:649` | **`window.loadUndoStack = loadUndoStack` 赋值** |

**没有任何一处是"调用"。**

### 3.2 测试套件里的调用（证明只有测试在用）

```
verify-bugfix.js:347 / 785 / 803 / 818 / 829
verify-p4p1b-undo-persist.js:162 / 172 / 192
```

### 3.3 `init()` 的实测

```
init() 共 70 行
  含 loadUndoStack?  false
  含 saveUndoStack?  false
  含 undo.reset?     true     ← ★
  含 restore?        false
```

### 3.4 `init()` 关键两行

```js
S.design = blankDesign();
undo.reset(snapshot(), "初始");   // ← 内存栈重置为「空白设计」
```

**这解释了为什么"数据在磁盘上却用不了"**：
`undo.reset()` 把内存栈清成一条"空白设计"记录，而 `loadUndoStack()` 从未被调用去覆盖它。

### 3.5 ⚠️ 任务明确警告：「不得直接把 loadUndoStack 加到 init」

**这个警告是对的。** 如果直接加，会遇到下面四个问题：

| # | 问题 | 后果 |
|---|---|---|
| 1 | **调用顺序** | 必须在 `undo.reset()` **之后**，否则被覆盖 |
| 2 | **designName 匹配失效** | 启动时 `S.design = blankDesign()`，名字是 `未命名设计`，与磁盘里的真实名字**永远不匹配** |
| 3 | **同名不同设计** | 实测会**错位加载**（§八）|
| 4 | **历史与设计不同步** | 加载了历史，但当前设计还是空白 → 撤销会跳到磁盘快照，**覆盖用户当前工作** |

**所以必须先解决"设计身份"和"设计草稿恢复"两件事，撤销历史才有意义。**

## 六、三种恢复架构比较（任务第十二部分第 6 项）

### 6.1 前置实测数据

| 数据 | 实测值 | 影响 |
|---|---|---|
| 无素材设计（60 控件）| **17,467 字节** | 可存 |
| **5 张素材的设计** | **517,991 字节（29.7×）** | ⚠️ base64 内嵌 |
| localStorage 配额 | 约 **5 MB** | 存不下几张素材 |
| `asset.data` 是否必需 | **不是** —— `canvas.js:1339` 是 `a.data \|\| a.path` | 可剥离 |
| localStorage 落盘窗口 | **2~2.5 s** | 崩溃可能丢最近写入 |

### 6.2 方案比较

#### 方案 A：仅恢复最后编辑设计

| 项 | 内容 |
|---|---|
| 做法 | 把设计快照写 localStorage，启动时若无当前设计则恢复 |
| **存储位置** | localStorage（单键）|
| 与手动文件冲突 | ❌ **会** —— 无法区分"用户刚打开的文件"和"旧草稿" |
| **素材问题** | ❌ **致命** —— 5 张素材 518KB，几次快照就爆 5MB |
| 设计识别 | 无（只有一个槽位）|
| 已保存 vs 草稿 | 无法区分 |
| 创建恢复点 | 每次 commit（太频繁）|
| **结论** | ❌ **不推荐** |

#### 方案 B：保留手动文件保存，另建自动恢复草稿（**推荐**）

| 项 | 内容 |
|---|---|
| 做法 | 手动保存不变；**另设一份草稿**，只存"未保存的改动" |
| **存储位置** | **IndexedDB**（不是 localStorage）|
| 与手动文件冲突 | ✅ **不冲突** —— 手动文件走下载，草稿走 IndexedDB，两条独立通道 |
| **素材问题** | ✅ **可解决** —— 草稿**不含 `data`**，只存 `path` + `id`（`canvas.js` 支持 `path` 当 URL）|
| 设计识别 | ✅ **需要设计身份**（见 §八）|
| 已保存 vs 草稿 | ✅ 用「保存过之后修改过」标志区分 |
| 创建恢复点 | ✅ **防抖 2~3 秒**（与落盘窗口对齐）+ 手势结束 |
| **结论** | ✅ **推荐** |

#### 方案 C：设计草稿 + 撤销历史独立恢复

| 项 | 内容 |
|---|---|
| 做法 | B 的全部 + 把撤销历史也搬进 IndexedDB 并接上加载 |
| 存储位置 | IndexedDB（草稿 + 历史两个 store）|
| 优势 | 撤销历史**真正可用**（现在是写了不读）|
| 复杂度 | 高 —— 要处理"历史与草稿不匹配"的 6 种情况（§八）|
| **结论** | ✅ **B 之后的第二阶段** |

### 6.3 方案 B 必须回答的 10 个问题（任务第六部分）

| # | 问题 | 建议答案 |
|---|---|---|
| 1 | 数据存哪 | **IndexedDB**（localStorage 只有 5MB 且同步阻塞）|
| 2 | 与手动文件冲突 | ✅ 不冲突 —— 手动保存走下载，草稿走 IndexedDB |
| 3 | localStorage 还是 IndexedDB | **IndexedDB** —— 容量大、异步、不阻塞主线程 |
| 4 | 防素材爆空间 | **草稿剥离 `data`**，只存 `path`；需要时从 assets/ 或原素材库取回 |
| 5 | 如何识别不同设计 | **新增内部 `designId`**（见 §八）|
| 6 | 已保存 vs 未保存草稿 | 记 `lastSavedHash`；草稿 hash ≠ 它 → 有未保存改动 |
| 7 | 何时创建恢复点 | **防抖 2.5s**（对齐落盘窗口）+ 手势结束 + 每 N 次 commit |
| 8 | 保存失败如何提示 | 状态栏「草稿未保存」+ 点击看原因（`QuotaExceededError` / 不可用）|
| 9 | 打开新文件防覆盖 | **打开文件前先 flush 当前草稿**；打开后清除旧草稿标记 |
| 10 | 避免旧草稿覆盖当前设计 | **启动时绝不自动恢复** —— 只提示（§七）|

## 七、恢复 UI 交互设计（任务第十二部分第 9 项）

### 7.1 最小确认流程

启动时若检测到草稿，**不自动恢复**，显示一条**非模态提示条**（不使用阻塞弹窗，避免打断）：

```
┌──────────────────────────────────────────────────────────────┐
│ 💾 发现未保存的草稿                                           │
│    「仪表盘 v3」· 最后编辑 2026-10-18 16:42（2 小时前）       │
│    包含 42 个控件 · 6 张素材 · 未保存的改动                   │
│                                                              │
│    [ 恢复草稿 ]   [ 删除草稿 ]   [ 稍后再说 ]                  │
└──────────────────────────────────────────────────────────────┘
```

### 7.2 三个按钮的精确语义

| 按钮 | 行为 | 安全性 |
|---|---|---|
| **恢复草稿** | 加载草稿到画布；**当前未保存的更改会被替换** → 需二次确认 | ⚠️ 有确认 |
| **删除草稿** | 删除 IndexedDB 里的草稿 | ⚠️ **需二次确认**（删的是唯一副本）|
| **稍后再说** | 关闭提示条，**草稿保留**，状态栏留一个小图标 | ✅ 无副作用 |

### 7.3 硬性约束（任务第七部分）

| 约束 | 设计保证 |
|---|---|
| 不自动覆盖当前已打开设计 | ✅ 只提示，不自动加载 |
| 未经确认不得删除唯一恢复副本 | ✅「删除草稿」需二次确认，且**永不**在启动时自动删 |
| 显示草稿名称 | ✅ `design.name` |
| 显示最后编辑时间 | ✅ 相对时间 + 绝对时间 |
| 显示可恢复内容 | ✅ 控件数 / 素材数 |

### 7.4 异常情况的处理（任务第七部分）

| 异常 | 处理 |
|---|---|
| **草稿数据损坏**（JSON 解析失败）| 不加载，提示「草稿已损坏，可能是存储异常导致」；提供「导出原始数据」自救按钮 |
| **版本不兼容** | 记 `schemaVersion`；不认识的版本**只读不覆盖**，提示用户升级或导出 |
| **素材缺失** | 加载设计，缺失的素材显示为占位框 + 顶部提示「N 张素材缺失」 |
| **存储不可用**（隐私模式）| 静默降级，不阻塞编辑；状态栏提示「本次会话不保存草稿」 |

## 八、数据身份与历史匹配规则（任务第十二部分第 8 项）

### 8.1 实测问题：设计名**不能**作为唯一身份

| 场景 | 实测结果 |
|---|---|
| **同名但内容完全不同的两个设计** | ❌ **`sameNameLoads: true`，历史被错位加载** |
| 不同设计名 | ✅ 不加载 |
| 空设计名 | 存储为 `未命名设计`（**大量设计会撞名**）|

**现有 `designName` 匹配只能防"名字明显不同"，防不住同名。**

### 8.2 建议：内部 `designId`（不改 `icar.ui/2`）

```js
// 生成：首次创建设计时
design._id = "d_" + Date.now().toString(36) + "_" + Math.random().toString(36).slice(2, 8);

// 序列化：nodeToJson 白名单**不包含** _id → 不写进设计文件 ✅
// 草稿存储：IndexedDB 的 key = design._id
```

**为什么这不改 `icar.ui/2`：**

| 通道 | 是否带 `_id` |
|---|---|
| 设计文件（`toV2Json`）| ❌ **不带**（白名单过滤）|
| App 导入 | ❌ 不受影响 |
| **IndexedDB 草稿** | ✅ 带（内部用）|

**兼容性风险**：打开一份旧文件时没有 `_id` → 生成新的，旧草稿无法匹配（可接受，因为旧文件本来就无草稿）。

> ⚠️ **按任务要求，本方案等待批准后再实施。**

### 8.3 六种历史匹配情况（任务第八部分）

| # | 情况 | 建议处理 |
|---|---|---|
| 1 | **只恢复设计，不恢复撤销栈** | ✅ **P4R-1 只做这个** —— 最简单、最安全；撤销栈从"当前状态"重新开始 |
| 2 | 恢复设计 + 恢复撤销栈 | ⏳ P4R-2；必须 `designId` 一致 |
| 3 | 设计恢复成功但历史不匹配 | ✅ 丢弃历史，重建栈（记一条 `console.warn`）|
| 4 | 历史存在但草稿不存在 | ✅ **丢弃历史**（无设计锚点，加载了会跳到别的设计）|
| 5 | 历史超 1.2MB 预算 | ✅ 已有裁剪逻辑，保留最近 40 步 |
| 6 | 部分历史损坏 | ✅ 已有 `isUsableSnapshot` 过滤 + 索引重算（P4P-1B 实测通过）|

### 8.4 硬性保证

> **绝不把 A 设计的撤销历史加载到 B 设计。**
>
> 实现方式：历史记录里存 `designId`，加载时必须 **`designId === 当前 design._id`**，
> 而不是只比 `designName`（实测同名会错位）。
