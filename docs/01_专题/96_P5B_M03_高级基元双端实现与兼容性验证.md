## 一、Android 前台服务最终安全结论

### 1.1 官方规则核对（阶段 A1）

| 项 | 值 |
|---|---|
| `minSdk` | **24** |
| `targetSdk` | **34**（Android 14）|
| `compileSdk` | 35 |
| 前台服务类型 | `connectedDevice\|dataSync` |
| 启动入口 | `MainActivity.startServiceSafely()` → `startService()` |
| 权限 | `FOREGROUND_SERVICE` / `FOREGROUND_SERVICE_CONNECTED_DEVICE` / `FOREGROUND_SERVICE_DATA_SYNC` |

**Android 15+ 对 `dataSync` 的限制**：
- 每 24 小时累计运行上限 **6 小时**
- 超时后系统回调 `Service.onTimeout(startId)`，**不处理会导致 ANR / 崩溃**
- **targetSdk ≥ 35 才强制** —— 当前 34，暂不受限，但升级即生效

### 1.2 本轮设计变更（阶段 A2）

指令 §A2 列出七条原则，其中三条直接否掉了 P5B-M02 的做法：

> · 无蓝牙权限时，不启动真实 OBD 采集
> · **离线主题浏览不应依赖无实际工作的 FGS**
> · **不为延长存活时间而滥用 dataSync 服务类型**

**P5B-M02 的做法**：没权限 → `DATA_SYNC` 保活。
**问题**：实测该状态下 Service 里**没有任何 OBD 通信**（无连接、无轮询），只订阅总线 + 更新通知 —— 占着 `dataSync` 纯属"为了活着而活着"。

**P5B-M03 改为**：

| 情况 | 行为 |
|---|---|
| 有蓝牙权限 | 正常进前台服务（`CONNECTED_DEVICE`，**与既有行为完全一致**）|
| **无蓝牙权限** | **不进前台服务**（不占 FGS 配额、不消耗 dataSync 额度）；App 与主题浏览完全不受影响 |
| 后来授权 | `MainActivity.onResume` 主动补起前台服务 |

### 1.3 🔴 修的两个真实缺陷

#### 缺陷 1【严重，我自己引入的】`stopSelf()` 不能满足 5 秒契约

**第一次修法**：无权限时 `stopSelf()` —— 我以为是官方允许的满足方式。
**实测崩溃**：

```
android.app.RemoteServiceException$ForegroundServiceDidNotStartInTimeException:
Context.startForegroundService() did not then call Service.startForeground():
ServiceRecord{fffc8e7 u0 com.icar.obd/.service.ObdService}
  at com.icar.obd.ui.MainActivity.onResume(MainActivity.kt:167)
```

**真相**：系统**只认 `startForeground()`**，`stopSelf()` 无效。

**最终修法**：调用方改用 **`startService()`**（无 5 秒契约），Service 内部按权限自行决定是否 `startForeground`。

#### 缺陷 2【中】授权后前台服务不恢复

**原因一**（测试方法）：`am start` 到已 resumed 的 Activity **不触发 `onResume`** → 恢复逻辑没执行。
**原因二**（真实缺陷）：恢复逻辑只在 `onStartCommand` 里，但 Activity 常驻时不会重新走 `onStart`。

**修法**：`MainActivity.onResume` 里主动 `startServiceSafely()`（幂等）。

## 四、新主题版本推荐方案

### 4.1 四个候选（指令 §C3）

| 方案 | 可行性 | 依据 |

| D. 旧版静态图像降级 | ⚠️ | 丢失动态能力 |

### 4.2 ✅ 推荐：**方案 B（新增 `icar.ui/3`）+ 新版继续严格读 `/2`**

**证据链**：

1. **旧版遇到 `/3` 会明确拒绝**（`DesignFile.kt:321-323`）：
   ```
   不支持的 schema：`icar.ui/3`（本版本认 `icar.ui/1` 与 `icar.ui/2`）
   ```
   → 比逐个节点报错**更早、更清楚**，用户一眼看懂"版本太旧"

2. **新版读 `/2` 完全兼容** —— 当前版接受 `SCHEMA` 与 `SCHEMA_V2`，新增 `/3` 只是多认一个值，**不影响任何存量主题**

   > 「旧版 App 不认识 `meta.requires` 时，它不能充当有效兼容警告。」

   **真正起作用的是「未知 type 白名单报错」+「schema 白名单」** —— 这两个旧版都有。

4. **不需要双版本导出** —— 因为旧版行为是"明确拒绝"而不是"静默降级"，用户会立刻知道要升级

### 5.2 关键设计遵守（指令 §D）

**「复用 VehicleBus 与现有格式化能力，不新建独立数据采集入口」**
→ `ValueText` 只走 `VehicleBus.value` / `addValueListener`，**不自己读 OBD**。

**「Android 可采用 PathMeasure，但必须与编辑器原型建立独立的几何基准与误差容限」**
→ `ARC_LENGTH_TOLERANCE = 0.02f`（2%）。理由：编辑器用 200 段折线（弦长和 ≤ 真实弧长），Android 用 `PathMeasure`（真实弧长）。

**「路径几何未改变时应缓存计算结果」**
→ `geomDirty` 只在点/曲线类型/线宽变化时置位；**`progress` 变化不触发重算**。

**「不为完整覆盖所有复杂路径而阻塞简单图形」**
→ Shape **不实现**任意贝塞尔 Path（那是 PathProgress 的职责）。

### 6.2 Undo/Redo 的确切证据

```
nAfterAdd=7  nodePresentAfterAdd=true  typeAfterAdd=shape
undoIndexBefore=1 → undoIndexAfter=0
nodePresentAfterUndo=false  nAfterUndo=5
nodePresentAfterRedo=true   typeAfterRedo=shape  xAfterRedo=11
```

**五轮踩坑才拿到这个证据**（全部记录在脚本注释里）：
1. 推 `JSON.stringify(S.design)` 当快照 → 结构不对（真实格式 `{d, sel}`）
2. 用 `nodes[idx]` → 快照恢复后下标失效
3. 先 push 再改属性 → undo 回到"没节点"的更早状态
4. 以为多次 push = 多步可退
5. **真正原因**：编辑器**首次 commit 就是基准**（`init: index=0, size=1, canUndo=false`），`undo()` 返回 `stack[index-1]`
