# 主题格式参考：Sky Gauge

> 来源：社区「Sky Gauge」项目。主题中心 <http://ctos.stevectos.xyz:6003/themes>、
> 在线制作器 <http://ctos.stevectos.xyz:6003/create>。
> 本文是**逆向其主题文件格式**的记录，用于决定 iCarOBD 的主题格式怎么走。

## 一、先澄清一个容易搞混的点

用户最初提到两个来源，它们是**两个不同的项目**：

| 来源 | 是不是 LVGL | 依据 |
|---|---|---|
| `github.com/evilgenius79/Esp32-gauge` | ❌ **不是** | `gauge_render.h` 里 `#include <M5GFX.h>` / `<LovyanGFX.hpp>`，用 sprite 自绘 |
| **Sky Gauge**（主题中心那个） | ✅ **是** | 主题文件里 `"format": "lv_font_bin"` —— 这是 **LVGL 自己的二进制字体格式** |

`Esp32-gauge` 的设计仍然值得抄（见 §五），但它的代码**不能当 LVGL 代码用**。

## 二、Sky Gauge 主题文件结构

单文件，**JSON 头 + 追加的二进制资源**：

```text
[0 .. 1030]        JSON 头（schema + colors + assets 索引 + pages 索引）
[16384 .. ]        二进制资源区（LVGL 字体、layout_data）
```

> 资源区从 16384 开始 —— 头部留了 16KB，JSON 头再长也不会挤到资源。

### JSON 头

```json
{
  "schema_version": "1.0",
  "theme": { "id", "name", "version", "author", "description" },
  "colors": {
    "bg": "0x0A0A0A",          "ring": "0xFF6B00",
    "arc_track": "0x2A2A2A",   "arc_indicator": "0xFFFF00",
    "text_primary": "0xFFFFFF","text_secondary": "0x888888",
    "needle": "0xFF3030",      "panel": "0x1A1A1A"
  },
  "assets": {
    "font_Xperia_48": { "offset": 16384, "size": 34820, "format": "lv_font_bin" },
    "font_Xperia_16": { "offset": 51204, "size": 4620,  "format": "lv_font_bin" },
    "font_Xperia_26": { "offset": 55824, "size": 10804, "format": "lv_font_bin" },
    "font_Xperia_96": { "offset": 66628, "size": 135148,"format": "lv_font_bin" }
  },
  "pages": {
    "theme_pages": [
      { "id": "main_gauge", "type": "custom_layout",
        "layout_data_offset": 201776, "layout_data_size": 2512 }
    ]
  }
}
```

**只有 8 个颜色** —— 比我们 `GaugeTheme` 的 ~15 个字段精简得多，但覆盖了同样的用途。

### layout_data（页面控件树）

`layout_data` 本身**又是一段 JSON**（不是编译后的二进制）：

```json
{
  "page_id": "main_gauge",
  "background_color": "0x0A0A0A",
  "elements": [
    { "type":"arc", "id":"arc_1", "x":0, "y":0, "width":360, "height":360,
      "start_angle":90, "end_angle":180, "rotation":0,
      "data_source":"obd.gear", "range_min":0, "range_max":5,
      "color":"0xA600FF", "bg_color":"0x2A2A2A", "line_width":28 },

    { "type":"label", "id":"label_5", "x":120, "y":84.4, "align":"center",
      "color":"0xFFFFFF", "font_size":48, "font_asset":"font_Xperia_48",
      "data_source":"obd.speed", "format":"%d" },

    { "type":"label", "id":"label_6", "x":120.6, "y":128, "align":"center",
      "color":"0xFFFFFF", "font_size":16, "font_asset":"font_Xperia_16",
      "text":"km/h" }
  ]
}
```

## 三、实测词汇表（6 个真实社区主题统计）

> 从主题中心下载 6 个主题（覆盖 17551 ~ 278248 字节），解析全部 `layout_data` 后统计。
> **不要只凭一个样本设计 schema** —— 下面是全集。

### 元素类型：只有 3 种

| 类型 | 出现次数 | 字段全集 |
|---|---|---|
| `label` | 40 | `align` `color` `data_source` `divisor` `font_asset` `font_size` `format` `id` `text` `type` `x` `y` |
| `arc` | 12 | `bg_color` `color` `data_source` `end_angle` `height` `id` `line_width` `range_max` `range_min` `rotation` `start_angle` `type` `width` `x` `y` |
| `image` | 4 | `asset` `height` `id` `rotation` `type` `width` `x` `y` |

- `label` 的 `data_source`/`format`/`divisor` 与 `text` **二选一** ——
  前者是动态数值，后者是静态文字（如 `"km/h"`）。
- `arc` 的 `start_angle`/`end_angle`/`rotation` 三个角度决定它占哪一段圆弧
  （实测有 90→180、180→270、270→0、0→90 四段拼成一圈的用法，就是「四数据」布局）。

### 颜色：永远这 8 个

```text
bg  ring  arc_track  arc_indicator  text_primary  text_secondary  needle  panel
```

6 个主题**无一例外**。比我们 `GaugeTheme` 的 ~15 个字段精简一半。

### `data_source` 语义名：只有 6 个

```text
obd.speed   obd.rpm   obd.coolant_temp   obd.oil_temp   obd.boost   obd.gear
```

**这是整个格式最值得学的一层**：制作器里选「车速」，而不是填 `01 0D`。
PID 号、公式、单位全被藏起来 —— 所以主题能跨车型共用，而我们的不能。

### 资源格式：只有 2 种

| format | 用途 |
|---|---|
| `lv_font_bin` | LVGL 二进制字体（实测名：`font_Xperia_16/26/48/96`） |
| `rgb565` | 裸 RGB565 位图（实测名：`background`、`asset_0`） |

### 页面字段

```text
id  type  layout_data_offset  layout_data_size  [native_page]
```

`type` 实测只有 `custom_layout` 一种；`native_page` 是可选的（3/6 个主题有）。

### 坐标系

`x/y/width/height` 都在 **360×360 参考画布**里（实测 `width:360, height:360`，
`x` 最大 294.9）。与屏幕分辨率无关。

## 四、三个值得直接借用的设计


### 1. 固定参考画布 360×360

所有 `x/y/width/height` 都在 **360 单位**的坐标系里，与真实屏幕分辨率无关。
在线制作器按这个画布所见即所得，运行时按屏幕尺寸缩放。

> 对比我们：用的是**归一化 0..1**。两者等价，但 **360 是整数**，
> 在 JSON 里可读性好得多（`"x":120` 比 `"x":0.3333` 直观），也避免了浮点误差。
> **建议改成 360 单位制** —— 这是纯粹的改进，不损失任何能力。

### 2. `data_source` 是**语义名**，不是 PID

```text
obd.speed / obd.rpm / obd.gear / obd.coolant_temp
```

制作器里选「车速」，而不是填 `01 0D`。**PID 号、公式、单位都被这一层藏起来了。**

> 对比我们：`GaugeItem.pidId` 直接是 `std_0D`。
> 好处是精确，坏处是**换个车型/换套 PID 就得重做主题**。
> 这是 Sky Gauge 的主题能跨车共用、而我们的不能的根本原因。

### 3. 字体作为**资源**内嵌，按名字引用

`"font_asset": "font_Xperia_48"` → 指向文件内的 `lv_font_bin` 块。

> 这一条解决了我之前提过的「LVGL 用 CJK 字体体积大」问题：
> 字体跟着主题走，用户可以自己选；不用的字体不占空间。
> 我们目前**完全没有字体方案**（用的是编译进去的 montserrat，**不含中文**）。

## 五、`Esp32-gauge` 那边值得抄的（视觉设计）

虽然它不是 LVGL，但**霓虹表盘的设计参数**很成熟，可以直接搬到我们的自绘里：

| 项 | 参数 |
|---|---|
| 扫弧几何 | `ARC_START = 225°`，`ARC_SWEEP = 270°`（7:30 → 4:30） |
| 分辨率无关 | 所有半径从单一 `radius` 推导，`scale = radius / 120`（240px 基准） |
| 半径系数 | `rOuter 117 / rTickOut 113 / rTickMaj 100 / rTickMin 106 / rLabel 85 / rNeedle 97 / rTail 15 / rRingOut 30 / rRingIn 20 / rSweepOut 116 / rSweepIn 108` |
| 辉光宽度 | `bloomWidth = max(6, 10 × scale)` |
| **10 层霓虹辉光** | 每层 `offset = bloomWidth → 0`，`rOut = rSweepOut + offset`、`rIn = rSweepIn - offset` |
| 热芯 | 辉光之上叠橙 + 黄两层窄弧 |
| 指针 | 5 层三角（宽 9/7/5/3.5/2.5 × scale，越宽越暗）+ 黄色芯线 |
| 中心环 | 10 层辉光 + 橙主环 + 黄高光 + 黑内填 + 橙心点 |
| 危险区 | 超过 `dangerVal` 后刻度与弧变红 |

⚠️ **配色必须从主题 accent 派生，不能照抄它的红/橙/黄** ——
否则换主题会串色。我们 Android 版的 `BaseGaugeView.glowColor` 已经在做这件事。

⚠️ **`lv_meter` 做不出多层辉光**（一个弧只能一个颜色）。
要还原必须改成自定义绘制：挂 `LV_EVENT_DRAW_MAIN`，用 `lv_draw_arc()` / `lv_draw_line()` 自己叠层。

## 六、对我们意味着什么（三条路）

| 方案 | 得到什么 | 代价 |
|---|---|---|
| **A. 直接采用 Sky Gauge 格式** | 整个社区主题库 + 在线制作器 + 内嵌字体方案 | 要重做 `GaugeTheme`/`GaugeItem`；`data_source` 语义层要映射到我们的 PID |
| **B. 只借设计**（360 画布 + 元素列表 + 语义数据源） | 大部分好处，格式仍由我们掌控 | 拿不到现成主题与制作器 |
| **C. 保留现有格式 + 加导入** | 不动现有代码，能读 Sky Gauge 主题 | 两套格式长期并存，维护成本 |

**倾向**：先做 **B 里的 360 画布制**（纯改进），再评估 **C 的导入**——
如果导入可行，就能低成本验证 A 值不值得。
