## 一、Release APK 是否存在旧产物问题

### ✅ **不存在**。但发现了一个更严重的问题：**Release 从未被安装过**

#### 1.1 旧产物排查：897 文件逐字节比对

| | 大小 | SHA256 |
|---|---|---|
| 原 Release（M04 构建）| 6,155,333 B | `714BDAA0…AE30B` |
| **干净重建**（`clean assembleRelease`）| 6,155,333 B | `FB0C21D4…E2F3E4` |

→ 大小稳定（两次都是 6,155,333 B）是 **DEX 内容确定性**的结果，**不是缓存误判、不是复用旧产物**。

#### 1.4 🔴 发现：**Release APK 未签名，此前从未被安装过**

```

```

M03 / M04 的「Release 验证」**全部只有文件大小**。「Release 装上能不能跑」这件事**从未被验证**。


#### 现象

```

```

#### 像素级对照（同一主题、同一设备）

| 标志色 | Debug | **Release** |
|---|---|---|

| shape 面板 `#121A24` | 210,061 | 437,855（设置页背景）|

#### 根因

`CanvasSettingsFragment.applyDesign()`：


**只认 `icar.ui/2`**。v3 主题导入后 `designJson` 被写成**空字符串**
→ 渲染层拿不到节点树 → `built == 0` → 空态。

#### 为什么藏了一整轮 —— 三个原因叠加

| # | 原因 |
|---|---|
| 1 | **Debug 版看不出来**：测试套件 `deploy-8styles.js` **直接写 settings.json**，绕过这个函数 |
| 2 | **Release 从未被安装过**：之前的「Release 验证」全部只有文件大小 |
| 3 | **UI 导入是 Release 上唯一可行的路径**（不可 `run-as`）—— 正好是唯一有 bug 的那条 |

#### 修法与验证

```kotlin
// 修复后
Store.settings.designJson =
    if (rawText.isNotBlank() && d.isTreeSchema) rawText else ""
```

新增 `DesignFile.isTreeSchema`（解析阶段已判定 v2/v3）：

## 十、性能和监听器证据

### 10.1 🔑 监听器：**直接计数，不靠堆推断**

**为什么 M04 的做法不够**：M04 用「5 轮主题切换后 Java 堆 −5,024K」当证据。
那是**间接**推断——堆下降只说明没暴涨，而**一个泄漏的监听器比一次 GC 释放的对象还小**，
在堆统计上完全看不出来。指令原文：「不能仅因为一次 GC 后 Heap 减少就判断不存在泄漏。」

**做法**：给 `VehicleBus` 加真实计数器

```kotlin
fun liveValueListenerCount(): Int = valueListeners.size   // 当前存活的闭包数
fun listenerStats(): Map<String, Int>                      // live + 累计加/减
```

`NodeTreeRenderer.release()` 打一行日志：

```
订阅计数 | 释放 本节点=1 存活=9→8 累计加=44 累计减=36
```

**实测（5 轮主题切换）**：

```
每轮：存活 9 → 8（release 退掉 1 个）
累计加-减 = 8 恒定（常驻订阅数，不随轮次增长）
5 轮完全一样 → 无累积泄漏
```

### 10.2 🔴 修的两个监听器缺陷

**缺陷 1：`ObdController.init()` 的 everGotData 订阅永不退订**

```kotlin
// 修复前：返回值被丢弃
VehicleBus.addValueListener { v -> ... }
```

后果：重复 init 会叠加订阅；累计加/减永远不配平（实测 30 加 / 22 减）。

**缺陷 2：`ValueTextPrimitiveView.bind()` 重复订阅**

```kotlin
// 修复前：直接覆盖 unsub
unsub = VehicleBus.addValueListener { ... }
```

若 `bind()` 被调两次（`setPid` 后又 `onAttachedToWindow`），
第一次的 `unsub` 被覆盖，那个闭包**永远退不掉**。

### 10.3 判据的两次修正（诚实记录）

**第一次**：写「每轮 release 后存活**精确回到 0**」→ 实测 8→8，我误判成泄漏。
实际：那 8 个是 `ObdService` 等**常驻订阅**，进程生命期内本来就该活着。
正确判据是「**不增长**」+「加-减差值恒定」。

**第二次**：取日志取错行 —— 一次切换调两次 `release()`：
- 「本节点=1 存活=9→8」← 真正退订
- 「本节点=0 存活=8→8」← 幂等空调用（正确行为）

取最后一条就永远读到 8→8。改成取倒数第二条。
