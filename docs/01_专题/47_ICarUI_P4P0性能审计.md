### 1.4 ⚠️ 关键区分：接管数 ≠ 面板支持数

```

    └─ 其中 15 条（next_*）来自**节点能力**（probe 条目）
                                    ↑ 面板支持了但未 Registry 接管
```

### 1.5 目录条目数 ≠ 真实节点数

| 统计对象 | 含义 |
|---|---|
| **目录条目 215** | 资源库里有 215 个"可拖出来的东西"（key）|
| **真实节点数** | 用户画布上实际摆了几个（0 ~ 数千，取决于设计）|

所以"215 条"与"画布上有多少节点"是两个完全不同的量。

## 二、父容器最终绘制验证结果

### 2.1 六种场景整页像素哈希（可复现基准）

| 场景 | 像素哈希 |
|---|---|
| 空 group | `24b60f21:6228` |
| group + text | `569c2a93:6228` |
| group + image | `fc8a8960:6228` |
| group + gauge | `211edb3c:6228` |
| 三层嵌套 group | `e28e7a6d:6228` |
| `next_speed_oem` | `b8cca06a:6228` |

**六种场景哈希两两不同 → 每种场景都真的画出了不同内容。**

### 2.2 ⚠️ 父容器属性变化后的画面（重要发现）

| 属性变化 | 画面是否变 | 原因 |
|---|---|---|
| `rotation = 45` | ✅ **变** | `localMatrix(n)` 参与子节点矩阵 |
| `x = 120` | ✅ **变** | 同上 |
| `visible = false` | ✅ **变**（变成空画面哈希）| `drawList` 里 `if (!n.visible) return` 跳过整棵子树 |
| **`alpha = 128`** | ❌ **不变** | 见下 |
| **`w = 300`** | ❌ **不变** | 见下 |

### 2.3 根因：这是**既有语义**，不是 P4C 引入的缺陷

查 `canvas.js` 的 `drawNode()`：

```js
if (n.type === window.NODE_GAUGE) drawGaugeNode(n);
else if (isImage) drawImageNode(n);
else if (n.type === window.NODE_TEXT) drawTextNode(n);
// 分组：**不画任何东西**。
//
// 第一版给分组画了个紫色虚线框，用户明确说"不需要紫色的虚线" ——
// 它平时挡视线（分组是逻辑容器，不是可见元素），选中时已经有青色选择框了。
```

**源码注释明确记录这是刻意设计。**

且 `globalAlpha` 在 `drawNode` 里 `ctx.save()/restore()`，**不向子节点继承**：

```js
ctx.save();
ctx.globalAlpha = (n.alpha === undefined ? 255 : n.alpha) / 255;
// ... 画节点（group 什么都不画）
ctx.restore();       // ← alpha 恢复，不回传给子节点
```

`w`/`h` 不影响子节点，是因为 `drawList` 只把**矩阵**（含 x/y/rotation/scale）传给子节点，
**不做裁剪**（P3B 已明确记录"容器不裁剪子节点"）。

### 2.4 ⚠️ 由此产生的一个使用性问题

**P4C 在 Schema 面板开放了 `alpha`、`w`、`h` 的编辑，但对容器没有视觉反馈。**

| 字段 | 面板可编辑 | 视觉反馈 |
|---|---|---|
| `rotation` / `x` / `y` | ✅ | ✅ 有 |
| `visible` | ✅ | ✅ 有 |
| **`alpha`** | ✅ | ❌ **无** |
| **`w` / `h`** | ✅ | ❌ **无**（除非子节点用相对定位）|

**这不是 P4C 引入的问题**（P4C 只是把既有字段开放到新面板），
但**用户在新面板里改这三个字段看不到变化，会以为面板坏了**。

→ **列入剩余风险，建议 P4P-1 或后续阶段评估**（本阶段不修改）。

### 2.5 未验证事项（如实标注）

| 项 | 状态 |
|---|---|
| 六个场景的**像素基准**已建立 | ✅ 可复现 |
| **视觉效果是否符合设计意图** | ❌ **未人工判读** → **待人工视觉验收** |
| Android App 端渲染是否一致 | ❌ 未验证（本阶段不涉及 App）|

> **不能宣称"零回归"** —— 本阶段只证明"哈希可复现且不同场景不同"，
> 没有 P4C 之前的基准可对比（P4C 未建立容器像素基准）。

## 三、refreshAll 完整调用链

### 3.1 调用链（以仓库实际实现为准）

```
用户操作（拖拽/输入/按钮）
    ↓
commit(fn, label)                          [app.js:619]
    ├─ fn()                                ← 先改模型
    ├─ undo.push(snapshot(), label, key)   ← 拍快照
    ├─ saveUndoStack()                     ← ★ 写 localStorage（仅 coalesceKey 变化时）
    ├─ syncJson()                          [app.js]  同步 JSON 编辑器
    ├─ refreshAll()                        [app.js]
    │   ├─ syncAssetImages()               ← 同步素材位图
    │   ├─ renderPageTabs()
    │   ├─ renderPanels()                  [panels.js]
    │   │   ├─ renderTree()                ← 控件树
    │   │   ├─ renderProps()               ← 旧属性面板
    │   │   └─ renderAssets()              ← ★ 素材库（416 条 + 12 分类）
    │   ├─ SchemaPanel.refresh()           ← P4A 新增并行面板
    │   └─ draw()                          [canvas.js:draw]
    │       ├─ resolveDesign()             ← 解析 bindings
    │       ├─ readCanvasColors()
    │       ├─ drawList()                  ← 递归画节点树
    │       └─ ...
    └─ updateUndoButtons()
```

### 3.2 各函数的触发条件与副作用

| 函数 | 触发 | 同步/异步 | 副作用 |
|---|---|---|---|
| `commit` | 用户操作 | **同步** | 改模型、压栈、写 localStorage、全量刷新 |
| `refreshAll` | `commit` / 外部 | 同步 | 重建全部面板 + 重绘画布 |
| `renderPanels` | `refreshAll` | 同步 | `innerHTML` 重建三个面板 |
| `renderAssets` | `renderPanels` | 同步 | **`innerHTML` 重建素材库（最重）** |
| `renderProps` | `renderPanels` | 同步 | `innerHTML` 重建属性面板 |
| `renderTree` | `renderPanels` | 同步 | `innerHTML` 重建控件树 |
| `syncJson` | `commit` | 同步 | 更新 JSON 文本框 |
| `saveUndoStack` | `commit` | **同步** | **写 localStorage（13~18ms）** |
| `draw` | `refreshAll` | 同步 | 重绘画布 |
| `requestDraw` | 实时编辑 | 异步（rAF）| 延迟到下一帧 |

### 3.3 ⚠️ 「一次简单属性修改重复触发」检查

**实测：一次 `setOnce` 会触发**

| 函数 | 调用次数 |
|---|---|
| `renderAssets` | **1** |
| `renderTree` | **1** |
| `renderProps` | **1** |
| `syncJson` | **1** |
| `saveUndoStack` | **1**（或 0，取决于 coalesceKey）|
| `draw` | **1~2**（`refreshAll` 一次 + `__ensureAnimPreview` 可能再一次）|

**结论：没有重复触发**，但**每次都是无条件全量**（不管改的是哪个字段、哪个节点）。

## 四、各阶段耗时统计（60 平铺场景，50 次样本）

### 4.1 独立计时（每个函数单独跑，互不嵌套）

| 函数 | 中位数 | P95 | 最大值 |
|---|---|---|---|
| **`refreshAll`（整体）** | **26.4** | 37.0 | 42.1 |
| **`renderPanels`** | **26.3** | 40.3 | 48.7 |
| ├ `renderTree` | 0.7 | — | — |
| ├ `renderProps` | **0.0** | 0.1 | 0.2 |
| └ **`renderAssets`（推算）** | **25.7** | — | — |
| `draw` | 0.4 | 0.8 | 1.0 |
| `syncJson` | 0.3 | 0.6 | 1.3 |
| `resolveDesign` | 0.1 | 0.2 | 0.3 |
| `readCanvasColors` | 0.0 | 0.1 | 0.1 |
| `JSON.stringify(design)` | 0.1 | 0.2 | 0.3 |

### 4.2 `commit` 路径拆分（20 次样本）

| 环节 | 中位数 | P95 |
|---|---|---|
| 改模型字段（仅赋值） | **0.0** | 0.0 |
| `draw` | 0.5 | 0.9 |
| `syncJson` | 0.3 | 0.5 |
| **`saveUndoStack`** | **18.3** | 21.9 |
| **完整 `commit`** | **43.7** | 73.1 |

**`saveUndoStack` 18.3 + `renderPanels` 约 25 = 43.3ms ≈ 完整 commit 43.7ms** —— 两项解释了 99%。

### 4.3 测量方法说明

- 工具：`performance.now()`
- 样本：每组 50 次（`commit` 路径 20 次、删除 10 次）
- 预热：每次换场景前先跑 8~10 次 `refreshAll`
- 每次读数前清零计数器
- **独占 vs 累计**：本报告用"各函数单独跑 50 次"的方式测**独占**，
  避免嵌套相加的错误（第一版曾把 `renderPanels` 累计值算得比 `refreshAll` 还大）

## 五、控件数量与嵌套关系实验

### 5.1 八个场景（画布 1700×1050、同一 Edge headless、50 样本）

| 场景 | 顶层节点 | 总节点 | 中位数 | P95 | 最大 |
|---|---|---|---|---|---|
| A 空设计 | 0 | 0 | **21.80** | 31.30 | 33.50 |
| B 20 平铺 | 20 | 20 | 28.80 | 36.50 | 56.60 |
| C 60 平铺 | 60 | 60 | 30.60 | 48.20 | 78.80 |
| D 120 平铺 | 120 | 120 | 32.90 | 46.80 | 68.00 |
| E 20 含多层组 | 2 | 16 | **23.70** | 36.10 | 46.30 |
| F 60 含多层组 | 3 | 48 | **24.90** | 38.50 | 48.90 |
| G 60 图片 | 60 | 60 | 25.30 | 37.70 | 50.60 |
| H 60 仪灯 | 60 | 60 | 27.60 | 43.90 | 61.10 |

### 5.2 逐项回答任务的六个问题

#### Q1：耗时是否随控件数量增加？

**几乎不增加。**

| 节点数 | 中位数 | 增量 |
|---|---|---|
| 0 | 21.80 | — |
| 20 | 28.80 | +7.0 |
| 60 | 30.60 | +1.8 |
| 120 | 32.90 | +2.3 |

**从 0 到 120 个节点，只增加 11ms（50%），而节点数增加了 ∞ 倍。**
**空设计就要 21.8ms** —— 这是固定开销。

> ⚠️ 注意：单次对比**不能**直接当因果证明（任务要求）。
> 但"空设计 21.8ms"这个数据点本身证明**存在与节点数无关的大额固定成本**。

#### Q2：嵌套 group 是否明显增加开销？

**不明显，反而更快。**

| 场景 | 总节点 | 中位数 |
|---|---|---|
| C 60 平铺 | 60 | 30.60 |
| F 60 含多层组 | **48** | **24.90** |

F 比 C 快，因为 F 总节点更少（48 < 60）。
**嵌套本身没有可见的额外开销**（`drawList` 递归成本极低，`renderTree` 只有 0.7ms）。

#### Q3：素材目录是否每次编辑都重新渲染？

**是 —— 这是最大瓶颈。**

| 证据 | 数据 |
|---|---|
| `renderAssets` 单独耗时 | **25.7 ms** |
| 占 `refreshAll` | **约 94%** |
| **空设计时** | **21.2 ms**（照样跑）|
| 改动画布节点后 | 22.7 → 29.4 ms（基本不变）|

**结论：素材库每帧无条件全量重建，与"改了什么"完全无关。**

#### Q4：UndoStack / localStorage 写入占多少时间？

**18.3 ms（中位数），占完整 `commit` 的 42%。**

`saveUndoStack()` 单独 50 次测量：**中位 18.3ms、P95 21.9ms**。

> P4A.1 的源码注释提到"实测 13.2 ms / 次，写 1.18 MB 到 localStorage" ——
> 本阶段实测 **18.3ms**，比注释记录更高（可能因设计体积或机器差异）。
> **未沿用历史注释数据，以本次实测为准。**

#### Q5：JSON 序列化是否是瓶颈？

**不是。**

| 项 | 中位数 |
|---|---|
| `syncJson()` | 0.3 ms |
| `JSON.stringify(design)` | 0.1 ms |
| `resolveDesign()` | 0.1 ms |

**合计 < 0.5ms，占 `commit` 约 1%。**

#### Q6：哪些操作完全没有必要调用 refreshAll？

| 操作 | 是否真的需要 `renderAssets` |
|---|---|
| 改任意节点属性 | ❌ **不需要**（素材库没变）|
| 切 locked / visible | ❌ **不需要** |
| 撤销 / 重做（节点数不变时）| ❌ **不需要** |
| 选择节点 | ❌ **不需要**（选择不影响素材列表）|
| 删除节点 | ❌ 只有当节点引用了素材时才可能影响"已用/未用"标记 |
| **新增素材** | ✅ 需要 |
| **改名/改分类** | ✅ 需要 |

**实测 `onSelectionChanged` 只要 3.9ms** —— 因为它不调 `refreshAll`（只调 `renderTree`/`renderProps`/`draw`）。

## 七、用户编辑路径性能比较

### 7.1 九种操作（60 平铺，各 20~50 样本）

| 操作 | 中位数 | P95 | 最大 |
|---|---|---|---|
| **改文字 `setLive`（实时）** | **0.5** | 0.9 | 1.3 |
| 改字号 `setOnce`（落定） | **40.3** | 51.2 | 51.2 |
| 改轨道 `fill` | **45.7** | 54.8 | 54.8 |
| 切 `locked` | **43.8** | 64.3 | 64.3 |
| 切 `visible` | **43.2** | 52.8 | 52.8 |
| 撤销 | **31.1** | 50.0 | 50.0 |
| 重做 | **37.6** | 58.3 | 58.3 |
| **选择节点** | **3.9** | 8.9 | 20.4 |
| 删除节点 | **49.9** | 52.0 | 52.0 |

### 7.2 实时 vs 落定对比（任务重点）

| 路径 | 耗时 | 说明 |
|---|---|---|
| **`setLive`（实时输入）** | **0.5 ms** | 只改模型 + `requestDraw`（rAF），**不重建面板** |
| **`endLive` / `setOnce`（落定）** | **40~46 ms** | 走完整 `commit` → `refreshAll` |

**相差约 80~90 倍。**

**这说明 P4A 的增量刷新设计是有效的** —— 输入过程中不碰面板。
但**落定时的全量刷新仍是瓶颈**，用户每次编辑完都会感到卡顿。

### 7.3 三个阶段耗时（任务要求拆分）

| 阶段 | 耗时 |
|---|---|
| 用户操作 → **模型更新** | **0 ms**（纯赋值）|
| 模型更新 → **画布重绘** | **0.5 ms**（`draw`）|
| **完整交互结束** | **40~46 ms**（含 `saveUndoStack` + `refreshAll`）|

**用户感知的卡顿 100% 来自"完整交互结束"阶段，而不是模型或画布。**

## 八、优化方案评估（仅提出，**本阶段不实施**）

### 方案 1：按需刷新资源库（**最高优先级**）

| 项 | 内容 |
|---|---|
| **瓶颈证据** | `renderAssets` 25.7ms，占 `refreshAll` 约 94%；**空设计也跑 21.2ms**；改动画布节点后 22.7→29.4ms 基本不变 |
| **预计收益** | **20~25 ms**（`commit` 从 43.7 → 约 20ms，**约 50%**）|
| **实施复杂度** | **中** —— 需要判断"素材列表是否真的变了" |
| **兼容性风险** | 低（素材列表内容不变时应完全等价）|
| **新增回归测试** | ① 改节点属性后素材库 DOM 不变 ② 新增/删除素材后素材库必须更新 ③ 素材改名/改分类后必须更新 ④ 素材库折叠状态保持 |
| **是否改数据格式** | ❌ 否 |

**建议实现方式**：引入"素材库脏标记" —— 只有 `design.assets` 或 `BUILTIN_ASSETS` 变化时才重建。

### 方案 2：优化 UndoStack 保存策略

| 项 | 内容 |
|---|---|
| **瓶颈证据** | `saveUndoStack` 18.3ms，占 `commit` 42%；写 1.18MB 到 localStorage（同步）|
| **预计收益** | **10~18 ms**（若改为异步/延迟/增量）|
| **实施复杂度** | **中高** —— 涉及崩溃恢复正确性 |
| **兼容性风险** | **中** —— 若延迟写盘后崩溃，撤销栈可能丢失最后几步 |
| **新增回归测试** | ① 撤销栈跨刷新/重载正确恢复 ② 连续操作后无丢失 ③ 崩溃模拟（可选）|
| **是否改数据格式** | ❌ 否（localStorage key 不变）|

**可选子方案**：
- (a) 用 `requestIdleCallback` 延迟写盘
- (b) 只在"手势结束"时写（P4A.1 已有 `flushUndoStack` 机制）
- (c) 压缩快照（只存 diff 而非全量）

### 方案 3：分层刷新入口替代无条件全量

| 项 | 内容 |
|---|---|
| **瓶颈证据** | 改任何属性都触发全部 `renderTree`+`renderProps`+`renderAssets`+`draw` |
| **预计收益** | 与方案 1 部分重叠（约 25ms 上限）|
| **实施复杂度** | **高** —— 需梳理所有调用点的真实需求 |
| **兼容性风险** | **中高** —— 漏刷会导致"界面不动"的难查 bug |
| **新增回归测试** | 每个调用点各一条"该刷新的刷了、不该刷的没刷" |
| **是否改数据格式** | ❌ 否 |

**建议**：先做方案 1（收益最大、风险最低），验证后再考虑方案 3。

### 方案 4：局部更新属性面板

| 项 | 内容 |
|---|---|
| **瓶颈证据** | `renderProps` 实测 **0.0ms** —— **不是瓶颈** |
| **预计收益** | **几乎为 0** |
| **实施复杂度** | 中 |
| **建议** | **不做** —— 数据不支持 |

> 这条要特别说明：P4A 引入 Schema 面板时以为属性面板是瓶颈，
> **实测证明不是**。`renderProps` 在 60 节点时只要 0.0ms。

### 方案 5：按需刷新节点树

| 项 | 内容 |
|---|---|
| **瓶颈证据** | `renderTree` 0.7ms —— **不是瓶颈** |
| **预计收益** | < 1 ms |
| **建议** | **不做** |

### 方案 6：延迟/合并 JSON 同步

| 项 | 内容 |
|---|---|
| **瓶颈证据** | `syncJson` 0.3ms + `JSON.stringify` 0.1ms = 0.4ms |
| **预计收益** | < 0.5 ms |
| **建议** | **不做** |

### 方案 7：合并重复 draw

| 项 | 内容 |
|---|---|
| **瓶颈证据** | `draw` 0.5ms；`refreshAll` 里 1 次 + `__ensureAnimPreview` 可能 1 次 |
| **预计收益** | < 0.5 ms |
| **建议** | 低优先级 |

### 方案 8：为 refreshAll 引入脏标记

| 项 | 内容 |
|---|---|
| **瓶颈证据** | 与方案 1/3 相同的根因 |
| **预计收益** | 方案 1 的具体实现手段 |
| **实施复杂度** | 中 |
| **建议** | **作为方案 1 的实现方式**（不是独立方案）|

### 8.1 方案优先级汇总

| 优先级 | 方案 | 预计收益 | 复杂度 | 风险 |
|---|---|---|---|---|
| **P0** | 1 按需刷新资源库 | **20~25 ms（50%）** | 中 | 低 |
| **P1** | 2 优化 UndoStack 写盘 | **10~18 ms（40%）** | 中高 | 中 |
| P2 | 8 脏标记（方案 1 的实现）| 同上 | 中 | 低 |
| P3 | 3 分层刷新 | 与 1 重叠 | 高 | 中高 |
| — | 4/5/6/7 | **< 1ms** | — | **不做** |

## 九、推荐的 P4P-1 最小优化方案

### 9.1 建议范围（**只做两件事**）

**步骤 1：按需刷新资源库**（预期 `commit` 43.7 → 约 20ms）

```
为 renderAssets 引入脏标记：
  · design.assets 引用变化     → 脏
  · BUILTIN_ASSETS 长度变化    → 脏
  · 素材 name/kind/path 变化   → 脏
  · 其它情况                   → 跳过重建，保留现有 DOM
```

**步骤 2：优化 saveUndoStack 写盘时机**（预期 20 → 约 10ms）

```
用 P4A.1 已有的 flushUndoStack 机制：
  · commit 时不立即写盘（只更新内存栈）
  · 手势结束 / 防抖 300ms 后 / beforeunload 时写盘
```

### 9.2 P4P-1 的验收建议

| 项 | 要求 |
|---|---|
| 性能 | `commit` 中位数 < 20ms（从 43.7 降 55%+）|
| 功能 | 素材库在**真实变化时**仍正确更新 |
| 功能 | 撤销栈在刷新/重载后仍正确 |
| 回归 | 50 套件全过，断言数不减 |
| 新增 | 素材脏标记的 4 条回归测试 + 撤销栈持久化 3 条 |

### 9.3 ⚠️ 不建议在 P4P-1 做的事

- ❌ 重写 `refreshAll`
- ❌ 引入"分层刷新"（风险高、收益与方案 1 重叠）
- ❌ 改 `draw` / `renderTree` / `renderProps` / `syncJson`（实测都不是瓶颈）
- ❌ 改 `icar.ui/2` 或数据格式
