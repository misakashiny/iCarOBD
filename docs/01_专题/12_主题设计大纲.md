## 一、为什么需要一次重构

v1 的格式（`icar.ui/1`）把仪表盘描述成**一个扁平的 `GaugeItem` 列表**：

```
gauges: [ {pid, style, min, max, x, y, w, h, ...}, ... ]
```

`GaugeItem` 是**复合控件** —— 一个「圆表」在渲染层会展开成弧 + 刻度 + 指针 + 标签。
这个模型对"用预设样式搭盘面"很好用，但对**做设计**有四个硬限制：

| 限制 | 后果 |
|---|---|
| 只能放仪表，**不能放图片** | 做不出"碳纤维底 + 车标 + 装饰线"这类真实主题 |
| 没有**层级**概念 | 控件重叠时只能靠添加顺序，无法显式控制谁盖谁 |
| 没有**变换**（旋转/缩放/透明度） | 指针不能斜着装，素材不能半透明 |
| 没有**状态** | 一个故障灯无法表达"正常/警告/严重"三张图 |

再加上编辑器本身缺**撤销**、**控件树**、**素材管理**，导致"做一个主题"实际是
"手写 JSON + 反复推设备看效果"。

所以格式要升到 **`icar.ui/2`**：从「扁平仪表列表」改成「**节点树**」。

## 二、核心模型：节点树


### 2.100 测试的覆盖缺口会让数据"合法地"漂移（v2.67.0）

`verify-crosslang` 只解析 `std(...)` / `calc(...)`，**不认 `PidDefinition(...)`**。
于是 6 个厂家模板从来没被比对过。

**它不报错，只是安静地不检查** —— 而"工具里多出 N 个 PID"
那条提示还**把缺口伪装成了数据问题**。

| 状态 | 后果 |
|---|---|
| 检查覆盖不到 | 数据可以**合法地**慢慢漂移，没有任何信号 |
| 检查覆盖到但误报 | 至少你会去看一眼 |

> **规律：覆盖缺口比误报危险。** 误报会被修掉，缺口不会 ——
> 除非有人正好去核实那个"看起来不对"的提示。

### 2.10 底框细调（v2.6.0）

`cardStyle` 只有 4 个粗档位，表达不了"半透明 + 大圆角"。再加一个 `card` 对象：

```json
"card": { "show": true, "alpha": 190, "radius": 12 }
```

| 字段 | 含义 |
|---|---|
| `show` | false = 不画底框 |
| `alpha` | 0..255，null = 跟随主题的 `cardAlpha` |
| `radius` | 圆角半径，**画布单位**（不是像素 —— App 侧要乘 density） |

**优先级**：`card` 覆盖 `cardStyle` 的对应项；缺的仍跟随主题。
全为默认时**不写进文件**。

> ⚠️ App 侧**不走 `GaugeTheme.cardBackgroundFor`** —— 那个只认 4 个粗档位。
> `NodeTreeRenderer.cardDrawable()` 自己建 `GradientDrawable`。

### 2.1 一个节点是什么

```json
{
  "id": "n2",
  "type": "gauge",
  "name": "RPM",
  "parent": null,

  "x": 0, "y": 0, "w": 240, "h": 240,
  "rotation": 0,
  "scale": 1,
  "alpha": 255,
  "z": 10,
  "locked": false,
  "visible": true,

  "children": [ { "id": "n3", "type": "image", "name": "Needle", ... } ],

  "pid": "obd.rpm", "style": 0, "min": 0, "max": 8000, "warnHigh": 6500
}
```

**关键决策：`gauge` 节点的字段与 v1 的 `GaugeItem` 同名同义**，不另起一套。
理由是迁移成本 —— v1 的 `gauges[]` 每一项都能**一对一**变成一个 `type: "gauge"` 的
根节点，不需要字段映射表。`GaugeItem.fromJson` 的逻辑可以原样复用。

### 2.101 反向验证本身也会假通过（v2.67 → v2.68）

验"新加的检查会不会红"时，我写了：

```powershell
Set-Location "D:\icarobd"
$KP = "app\src\main\...\BuiltInPids.kt"      # ← 相对路径
$content = [System.IO.File]::ReadAllText($KP, ...)   # 找不到文件
```

**`Set-Location` 不改变 .NET 的当前目录。** 文件根本没被改，
于是"改坏后测试仍然通过" —— 而那是**必然的**，因为什么都没改。

> ⚠️ **反向验证必须确认"破坏真的生效了"** ——
> 加一句 `改动生效: True/False` 打印出来。
>
> 否则你验的是"没改坏时测试通过"，而不是"改坏时测试会红"。
> **这正是 §2.97「假阴性」的另一种形态 —— 出现在验证过程本身里。**

### 2.102 归一化要"只放过无意义的差异"（v2.68.0）

比名字/单位时加了归一化：

```js
const norm = s => String(s ?? "")
  .replace(/\s+/g, "").replace(/（/g, "(").replace(/）/g, ")");
```

| 差异 | 报不报 | 为什么 |
|---|---|---|
| 空格 / 全角括号 | **不报** | 同一个意思的两种写法 |
| 字面不同（转速 vs 转速X） | **报** | 真的漂移 |
| 单位不同（km/h vs mph） | **报** | 数值会差 10 倍 |

> **规律：归一化只该放过"人眼里看不出差别"的差异。**
> 放宽多了，检查就形同虚设；放宽少了，就会有人为了让它变绿而改数据。

### 2.103 "加不了这条断言"是有信息量的（v2.69.0）

想给跨语言校验加"公式比对"，结果 36 条全报 `工具「undefined」`。

**原因不是值不一致，是数据结构不同** ——
工具侧 `BUILTIN_PIDS` 的条目**根本没有 `formula` 字段**。

| 情况 | 该怎么处理 |
|---|---|
| 值不一致 | **加断言**（这正是要抓的） |
| **结构不同**（一边有这字段一边没有） | **先想清楚该不该有** —— 硬加断言只会得到"永远红"或"永远绿" |

> **规律：断言加不上时，先问"是值的问题还是结构的问题"。**
>
> 这里是**分工**：工具只预览（不计算），公式只在 App 侧跑。
> 所以"比不了"是**正确**的 —— 记下来，而不是硬凑一条检查。

### 2.104 "跳过"判断必须比"实际特征"更具体（v2.66 / v2.69）

写补丁脚本时习惯加一句"已经做过就跳过"：

```js
if (t.includes('公式')) { console.log('SKIP 已有'); process.exit(0); }
```

**问题**：`公式` 这两个字在文件里**本来就有**（注释里提过），
于是脚本报 "SKIP 已有"，**而其实什么都没加**。

同一类错犯过两次：

| 版本 | 判断条件 | 误匹配到了 |
|---|---|---|
| v2.66.0 | `includes('resolvePid')` | 文件头注释里的 `window.resolvePid` |
| v2.69.0 | `includes('公式')` | 解析器注释里的"公式" |

**改法**：用**只有真正加完才会出现**的字符串（如 `'公式 工具'`）。

> ⚠️ **这类错的可怕之处：日志看起来完全正常**（"SKIP 已有"），
> 只有去核实"到底加没加"才会发现。
>
> **自检：凡是"跳过"分支，都该顺手确认一下目标状态。**

### 2.105 "我觉得这里有缺口"必须实测（v2.70.0）

v2.69.0 我在文档里写下一条猜测：

> 归一化把 `null` 和 `undefined` 都变成 `null`，**可能掩盖"阈值漏配"**

v2.70.0 实测：**不成立**。删掉工具侧的 `warnHigh` 后立刻报
`std_0C warnHigh 工具undefined App6500`。

**错在哪**：归一化统一的是"**两种表示缺失的方式**"，
而比对的是"**有 vs 无**"（`null` vs `6500`）—— 后者照样能比出来。

| 做法 | 代价 |
|---|---|
| 实测一下 | **1 分钟** |
| 按猜测去"修" | 10 分钟 + **给一条本来正确的检查加多余逻辑**，而多余逻辑本身可能引 bug |

> ⚠️ **"可能有缺口"是假设，不是发现。**
> 写进文档时也该标明"未验证" —— 否则下一个读的人会当成事实。
>
> 这次好在**下一轮就去验了**。如果没验，那条猜测会一直躺在文档里，
> 以后有人照着它去改，就白改了。

### 2.106 结构校验：用"增量"而不是"绝对值"（v2.71.0）

Gradle 卡死时想确认 Kotlin 没被改坏，退路是数括号。

**但绝对值不能当判据**：

```
BuiltInPids.kt  HEAD: ( 61 ) 64   差 -3
                当前: ( 74 ) 77   差 -3   ← 两个都是 -3
```

那个 -3 是**公式字符串**造成的（`"((A*256)+B)/4"` 是 2 开 1 闭）——
**在 HEAD 里就有**，是既有的、无害的。

> ✅ **合格判据是"和已知good版本比增量"**：
> `增量开 == 增量闭` → 结构上没破坏。
>
> 这条在别处也适用：**比较任何"有基线噪声"的指标时，看增量不看绝对值。**

### 2.107 PowerShell 的 `>` 是 UTF-16（v2.71.0）

```powershell
git show HEAD:...BuiltInPids.kt > "$env:TEMP\kt-head.kt"   # ← UTF-16！
```

读出来全是乱码，括号数完全不对 —— 于是报"增量不配对 BAD"，
**看起来像我把 Kotlin 改坏了**。改成
`git show ... | Set-Content -Encoding utf8` 之后才是真结果。

> ⚠️ **PowerShell 里别用 `>` 重定向文本。**
> 用 `Set-Content -Encoding utf8` / `Out-File -Encoding utf8`。
>
> 这类"工具链默认行为"造成的假异常，本轮已经踩了很多次 ——
> **它们的共同点是：症状看起来像"被测对象坏了"。**

### 2.108 「这半边跑不了」不等于「这半边不用跑」（v2.62 → v2.72）

### 2.11 默认字号是 6，不是 16（v2.6.0）

**16 是"像素思维"的产物。** 画布只有 360 单位宽，16 单位的字在 180 单位的表上占 **8.9%**，
满屏都是字。6 单位 ≈ 表高的 3.3%，能看清但不抢戏。

这条写进大纲是因为它**不是随手可改的样式值** —— 改了会让所有存量设计的观感变化，
而且工具与 App 必须同时改（跨语言比对查 `DEFAULT_SIZE`）。

### 2.12 背景的 w / h（v2.8.0）

`background.w` / `background.h` 是**画布单位**的尺寸，`0` = 铺满（默认）。

**语义**：指定了就按那块矩形画，而不是铺满整屏 —— 用于"这张底图只占中间一块"。

> ⚠️ **App 侧曾经完全忽略这两个字段**，于是电脑上缩在中间的图推到设备上
> 会变成全屏拉伸。这类"字段写了没人读"的缺陷**不会崩、不会报错**，
> 只会看起来不太对 —— 所以 `BackgroundSizeTest` 专门钉住它。

**优先级**：`w`/`h` > `fit`（平铺除外 —— 平铺本身就是"铺满"的语义）。

App 侧实现见 `PositionedBackgroundDrawable`：**必须自己写 Drawable**，
因为 View 每次布局都会用 `setBounds(0,0,viewW,viewH)` 覆盖掉
`BitmapDrawable` 的边界，"固定位置"做不到。

### 2.13 撤销栈的持久化上限（v2.8.0）

存 `localStorage`，上限是**字节预算 1.2 MB**（步数 40 只作兜底）。

为什么不是"20 步"：3 个控件的设计和 200 个控件的设计，单步快照差**两个数量级**，
写死步数要么浪费要么写爆。

配额满了**顺手清掉旧数据** —— 留着只会让下一次也失败。

### 2.14 状态系统的阈值（v2.9.0）

图片节点可显式设 `stateWarn` / `stateCritical`（**可选**）：

```json
{ "type": "image", "statePid": "obd.coolant",
  "stateWarn": 95, "stateCritical": 110, "states": { ... } }
```

| 情况 | 行为 |
|---|---|
| 字段缺失 / `null` / 空串 | **跟随 PID 库**的 `warnHigh` |
| 非数字 | 当没设 + 一条警告（**不写 NaN**） |
| 显式设了 | 用它，覆盖库 |

严重阈值没设时默认取"警告线与量程上限的**中点**"。

> 为什么必须能覆盖：不同车/不同传感器的报警线本来就不一样，
> 写死在 PID 库里等于让用户没法用。

### 2.15 控件树的同层重排（v2.9.0）

拖拽按行的**垂直位置**分三个区域：上 1/4 插到前面、下 1/4 插到后面、中间成为子节点。

**同层判定**：`canReorderSameLevel` 只允许同一父级内 —— 跨层是 `reparent` 的职责。

> ⚠️ **重排后必须 `normalizeZ`**。画布是按 `z` 画的，而重排改的是**数组顺序**；
> 不归一化就会出现"控件树里动了、画布上没动"。

### 2.16 多页面（v2.10.0 格式 / v2.11.0 完成）

```json
{ "schema": "icar.ui/2",
  "pages": [ { "id":"p1", "name":"主页面", "nodes":[...] },
             { "id":"p2", "name":"性能页", "nodes":[...] } ] }
```

**核心不变式**：`design.nodes === design.pages[design.pageIndex].nodes`（**同一引用**）。
切页只换引用，所以所有读写 `design.nodes` 的代码都不用改。

**序列化按页数二选一**：

| 页数 | 写什么 |
|---|---|
| 1 页 | **只写 `nodes`**（与 v2.9.0 及以前**逐字节一致**） |
| ≥2 页 | 写 `pages`，**同时**写一份 `nodes` = **当前页**的镜像 |

> ⚠️ 多页那行以前写的是"**不再写** `nodes`" —— **与代码不符**（v2.80.2 核对时发现：
> 实测导出的顶层键是 `schema,meta,canvas,theme,themeColors,pages,nodes`）。
> 真实行为是"两个都写"，而**解析侧（工具与 App 都）`pages` 优先**，
> 所以多出来那份 `nodes` 只是当前页的镜像、不参与渲染：
> App 的 `DesignFile.kt` 也是 `if (hasPages) … nodes = list[0].nodes`（同样 pages 优先）。
> 这里改成与代码一致；要不要干脆不写那份镜像，是另一件事（会改多页文件的字节，需单独评估）。
>
> ⚠️ **不能把"两处真相"当成解法**。第一版就是两个都写、而解析时 `pages` 优先 ——
> 用户在 JSON 里改 `nodes` 会被**静默忽略**（实测：删掉 `nodes[0].pid` 校验却通过）。
> 所以**判据只有一个**：`pages` 存在时，`pages` 说了算。

**兼容**：没有 `pages` 的老文件自动兜成单页「主页面」，行为完全不变。

**工具侧 UI**（v2.11.0）：页签条 —— 点击切换、双击重命名、`＋` 新建、每页 `✕` 删除。
单页时也显示页签条（否则发现不了能加页），但不显示删除按钮。

**App 侧**（v2.11.0）：`DesignFile.pages` + `Store.settings.dashPageIndex`，
渲染时 `design.copy(nodes = pages[idx].nodes)`。索引**越界夹到最后一页**。

> ⚠️ **空页不是错误**。`parseNodeArray` 有 `allowEmpty` 参数：
> 顶层 `nodes` 空要报错（空仪表盘没意义），但 `pages[i].nodes` 空是正常的 ——
> 否则"新建一页"会立刻变成非法状态。

### 2.17 子部件模型（v2.12.0）

```json
{ "type": "gauge", "style": 0,
  "parts": [ { "kind": "dial",   "assetId": "as1", "x":0, "y":0, "w":200, "h":200 },
             { "kind": "needle", "assetId": "as2", "pivotX":0.5, "pivotY":0.9,
               "sweepFrom":135, "sweepTo":405 } ] }
```

| 种类 | 渲染方式 |
|---|---|
| `dial` / `ticks` / `decor` | 图片，静态 `rotation` |
| `needle` | 图片，角度由**值**驱动 |
| `value` | **文字**（不需要素材） |

**顺序 = 绘制顺序**（先画的在下）。有 `parts` 就**不走** `style` 的程序化画法。

> ⚠️ **`pivotX/pivotY` 必须能单独设**。指针素材的轴心基本不在图片中心，
> 固定绕中心转会让指针明显偏心。
>
> ⚠️ **角度公式两端必须逐字一致**（工具 `partAngle()` ↔ App `angleFor()`）。
> 不一致时用户只会觉得"数据不准"，不会想到是布局问题。

### 2.18 面板布局与画布尺寸（v2.13.0）

**三条硬约束**（都是踩过坑才定下来的）：

1. **`.canvasWrap` 必须是列向 flex** —— 页签 / 面包屑 / 画布是竖着摞的。
   不是列向 flex 的话页签会被挤成竖条并压在画布上。
2. **画布不能被 flex 拉伸**（`flex: 0 0 auto; margin: auto`）。
   `applyCanvasSize()` 按**设计宽高比**算尺寸；`flex:1 1 auto` 会纵向拉长它，
   于是「位图尺寸」与「CSS 尺寸」不一致 → **坐标换算全错、手柄点不中**。
3. **面板内容必须有自己的滚动容器**（`.panelScroll`）。
   面板本身是 `overflow:hidden` 的 flex 容器，内容直接塞进去会被裁掉且滚不动。

**素材库固定高度**（`46vh`，可拖拽调整并持久化）—— 否则展开分类会把控件树挤出去。

**内置素材内嵌 data URL** —— `file://` 下按 path 加载会**污染画布**，
导致 `getImageData` / `toDataURL` 抛 SecurityError（**导出 PNG 直接坏掉**）。
data URL 同源，不污染。设计文件里写的仍是相对 path（App 靠它找文件）。

### 2.20 设计文件内嵌主题配色（v2.16.0 / P8-5）

### 2.22 子部件嵌套（v2.18.0）

```json
{ "kind": "needle", "assetId": "as-needle", "rawPid": "obd.rpm",
  "children": [ { "kind": "decor", "assetId": "as-cap", "x": -12, "y": -12, "w": 24, "h": 24 } ] }
```

**坐标系**：顶层部件相对**仪表节点**；子部件相对**父的 pivot**，并继承父的旋转。

> 为什么以 pivot 为原点：嵌套的典型用法是「指针上挂个装饰」——
> 装饰要跟着指针**绕轴心转**。以 pivot 为原点，子部件写 `(0,0)` 就在轴心上；
> 以左上角为原点的话，每加一个装饰都要手算 pivot 偏移。

**绘制顺序**：数组顺序 = 绘制顺序；**父先画、子后画**（装饰盖在主体之上）。

**深度上限 5 层** —— 三处必须一致：

| 位置 | 函数 |
|---|---|
| 工具 · 规范化 | `normalizePart(o, depth)` |
| 工具 · 绘制 | `drawPartTree(n, part, values, depth)` |
| App · 解析 | `GaugePart.parseAll(..., depth)` |
| App · 绘制 | `GaugePartsView.drawPart(canvas, p, k, depth)` |

> ⚠️ 设上限是防「手改文件写出几千层」把栈打爆 —— JSON 不能成环，
> 但深到几千层一样会崩。

> **v2.28.0 补充**：
> - **`value`（数值部件）也能绑 PID** —— 双针表配两个数字读数
> - **`sweepFollow`** —— 扫描范围跟着**第一个指针**走，双针表不用手填两遍
>
> ⚠️ 绑 PID 的判据是 `kind === "needle" || kind === "value"`；
> 表盘/刻度/装饰绑了没有意义（还会污染序列化，每个部件多两个空字段）。

### 2.23 素材分类可排序 / 可新建（v2.19.0）

#### ⚠️ 添加素材时**必须按比例定尺寸**

`w` 与 `h` **不能各自独立夹取** —— 那会破坏宽高比，用户看到的是压变形的图。
正确做法：定最长边，另一边按比例算；夹取时两边乘**同一个系数**。

```js
const ar = nat[0] / nat[1];
if (ar >= 1) { w = LONG; h = LONG / ar; } else { h = LONG; w = LONG * ar; }
// 最短边保护：整体缩放，不是单独夹一边
if (w < MIN) { const k = MIN / w; w *= k; h *= k; }
```

> 素材原始尺寸取 `a.w/a.h`；没有就退回 bitmap 的自然尺寸
> （手改过的设计文件可能没记 w/h，那种情况下「变扁」比「没有尺寸」更糟）。

### 2.3 变换的语义（**必须写死，否则各端实现会分叉**）

| 字段 | 语义 | 范围 |
|---|---|---|
| `x` / `y` | **相对父节点**的左上角（画布单位 0..360） | 可越界（父节点可裁剪） |
| `w` / `h` | 尺寸（画布单位） | ≥ 1 |
| `rotation` | **绕自身中心**顺时针旋转，**在设备空间施加**（见下方⚠️） | 度，任意实数，归一化到 0..360 |
| `scale` | 在 `w/h` 之上的**额外**缩放（绕中心） | > 0，默认 1 |
| `alpha` | 不透明度 | 0..255 |
| `z` | **同一父节点内**的绘制顺序，**大者在上** | 任意整数 |

> ⚠️ `scale` 与 `w/h` 是**乘法关系**，不是替代关系。
> 这样"把素材等比放大 1.5 倍"不需要改 `w/h`（改了会丢原始尺寸信息）。

#### ⚠️ 旋转必须在**设备空间**施加（v2.2.0 的重要修正）

**先排好版、再旋转**，不是"先旋转、再缩放"：

```
盒子矩阵（平移 + 缩放，不含旋转）→ 画布矩阵 → 再在设备空间绕盒子中心转 θ
```

**为什么**：`stretch` 缩放模式下画布矩阵是**每轴独立**的（16:10 屏上是
2.183 × 1.364）。若把旋转写在节点空间（`画布矩阵 · … · R(θ)`），
就成了"先旋转、再非等比拉伸" —— **矩形被拉成平行四边形**。实测：

| 角度 | 外框 | 内容尺度 |
|---|---|---|
| 0° | 矩形 | 1.364 |
| 15° | 平行四边形（相邻边不垂直） | 1.433 |
| 45° | 平行四边形（对角线差 **209px**） | **1.820（+33%）** |
| 90° | 矩形 | 1.364 |

也就是"旋转时外框歪掉、控件还会变大"。

**这与 App 一致**：`view.rotation = θ` 旋转的是**已经排好版的设备盒子**
（`DashRenderer` 先按每轴归一化定位/定尺寸，再设 `rotation`），
所以 App 得到的是旋转矩形、尺寸恒定。编辑器必须照做。

**逐层累积**：每一层的旋转都在设备空间绕**该层自己的盒子中心**施加，
然后子节点在这个已旋转的坐标系里继续排布 —— 所以**分组旋转时子控件跟着转**，
且每一层各自都保持矩形（不被斜切）。

> 实现见 `canvas.js` 的 `withDeviceRotation()` / `deviceMatrix()`。
> **改旋转语义必须同时改这三处**：`deviceMatrix`、`withDeviceRotation`、
> `model.js` 的 `ungroupNode`（取消组合时要在设备空间换算，否则偏 23.7px）。

### 2.36 主题优先级的唯一入口（v2.27.0）

**`GaugeTheme.resolveFor(designJson, settingsThemeId)`** —— 纯函数，可从任何地方调用。

```

没有 themeColors 字段         → 设置里的主题
themeColors 不是对象          → 设置里的主题（parse 给 null）
themeColors 字段缺失/是坏值   → fromJson 逐字段回退到内置霓虹
```

### 2.39 headless 里 alert 会阻塞（v2.34.0）

**这条花了最久才查出来，单独记一笔。**

`window.alert()` 在 headless Chrome 里会**阻塞整个渲染进程** ——
而 CDP 的 `Runtime.evaluate` 也就永远等不到响应，表现成"求值超时"。

```
重名测试 → addAssetKind() → 命中"已经有这个分类了" → window.alert(...)
                                                        ↓
                                             渲染进程卡死 → CDP 求值超时
```

**症状与原因隔了好几层**：报错是"第 3 节的第一个求值超时"，
而那个求值只是读个 `.length`。

> ⚠️ **stub 要在"任何可能触发它的操作之前"，不是"用到之前"。**
> 前者一次搞定，后者迟早漏一个 —— 我就是漏了重名那条。
>
> ```js
> window.alert = function () {};
> window.confirm = function () { return true; };
> window.prompt = function () { return null; };
> ```

**当时试过但没用**（因为都在治"资源/竞态"，而根因是"等一个永远不会点的确定框"）：
`send()` 超时 · 每节 `Page.navigate` 重载 · stub `renderAssets` ·
拆成独立求值 · 隔离脚本对照。

### 2.4 为什么用 `children` 而不是 `parent` 引用

树只有一种表达方式，不会出现"父子指针不一致"的半损坏状态。
`parent` 字段在示例里保留是为了**可读性**（一眼看出层级），解析时以 `children` 为准。

### 2.41 素材路径是设计文件里的契约（v2.35.0 复盘）

工具侧踩过的三次「动了不该动的东西」：

| 动了什么 | 后果 |
|---|---|
| 分类的 `v`（标识） | 老设计文件里的 `"kind":"background"` 找不到分类 → 素材落到"未分类" |
| 素材的 `path`（移动磁盘文件） | 老设计文件的相对路径失效，图**读不出来** |
| 控件的 `key`（重复） | 后一个盖掉前一个，那个控件**永远点不出来** |

**共同点：这些都是「已经写进用户文件里的东西」。**
要改显示（名字、归属分类、排序）就改**另一张表或另一个字段**，不要动它们。

### 2.42 CAT_RULES 的匹配方式是个陷阱（v2.37.0）

控件分类**不是逐个手写的**，而是按 key 前缀规则推导：

```js
[/^gauge_parts/, "拼装表"],
[/^gauge_/, "仪表样式"],
[/^(group|image|text)$/, "容器 / 基础"],   // ← 精确匹配
[/^img_(digit|nums|unit|ticks|seg)/, "数字刻度"],  // v2.86.0 补 ticks/seg
[/^img_ic/, "图标"],                        // v2.86.0 新分类
[/^img_/, "图片 / 底盘"],
// ... 第一条命中的规则生效
```

⚠️ **两个坑**：
1. **`^(group|image|text)$` 是精确匹配** —— 加 `box_card` 这种新前缀时一个都匹配不上，
   会**静默落到「其它」**。失败很安静：控件能加、能拖，只是分组不对。
2. **第一条命中的规则生效** —— 具体规则必须排在宽泛规则**前面**
   （`img_(digit|nums|unit)` 必须排在 `img_` 之前，否则 18 个数字控件被吞掉，
   这个真实踩过；v2.86.0 补 `ticks`/`seg` 时也是插在 `img_` 之前）。

> 加完控件应当验一句：**有没有控件掉进「其它」**。
> v2.86.0 起这条由 `tests/verify-assets-wiring.js` 第 6 节每轮自动验，
> 并且**多验一条**：实际出现的分类必须都在 `CTRL_CATS` 里 ——
> 否则 `ctrlChipsHTML` 会把它们兜底塞进「其它」块（`cat` 是「数字刻度」、
> 面板上却显示在「其它」下，比"掉进其它"更难查）。

### 2.43 撤销栈坏了会「静默失灵」（v2.37.0）

撤销栈**持久化在 localStorage**，内容可能被截断或写坏。

原来 `restore()` 裸调 `JSON.parse` → 坏一条就抛 → `doUndo()` 抛 →
**点了没反应、没有提示**，只有 console 一行红字。

> **「静默失灵」是这类问题里最糟的形态**：用户会以为是「撤销坏了」，
> 而不是「这一条记录坏了」，于是不会想到清一下重来。

现在 `restore()` 内部 try/catch + 校验结构，**返回成败**，调用方据此提示：

```js
if (!restore(r.state)) { toast("这一步的记录坏了，已跳过：" + r.label); return; }
```

> ⚠️ 遗留：坏的那条**仍留在栈里** —— 每次撤销都会再撞一次，应该摘掉。

### 2.43.1 撤销快照的结构判据、恢复事务与坏记录摘除（**未发版**，2026-10-12 · T5-A）

> **本节不是版本记录。** 工具**未发版**（当前仍是 v2.91.0），所以没有版本号、不改 CHANGELOG 正文；
> 它只记录 §2.43 那个"遗留"是怎么关掉的，以及**证据能证明到哪一步**。
> §2.43 的原文（含"仍留在栈里"那句）**保留为历史**，当前有效结论以本节为准。

**① 「解析成功」≠「快照可用」——判据从 `JSON.parse` 升级为最低结构校验**

`JSON.parse` 只说明是合法 JSON。`"null"`、`"[1,2]"`、`"{}"`、`{"d":null}` 全都解析成功，
但一个都不能当快照用。旧代码只查 `o.d` 是不是对象，于是**结构坏了但 JSON 合法**的那一类
（`d` 里没有 `nodes`、`pages` 不是数组、`sel` 是数字）一路放行。

现在只有一份判据（`snapshotProblem()`），`restore()` 与 `loadUndoStack()` **共用**它：

| 检查 | 为什么查 | 刻意**不**查 |
|---|---|---|
| `d` 是对象且 `d.nodes` 是**数组** | 画布/控件树/校验都直接遍历它 | 每个节点的字段形状 |
| `d.pages` 要么没有、要么是数组 | 多页面路径直接遍历 | `pageIndex` 越界（现有代码本来就容错） |
| `sel` 要么没有、要么是数组且元素是字符串 | 选区替换/高亮直接遍历 | 指向已删除节点的 id（`findNode` 自己返回 null） |

> ⚠️ **判据刻意宽松**：多查一项就会**误伤合法旧快照**（"对旧合法快照的无依据硬拒绝"）。
> 验收里专门有一条正例集钉住这一点：只有 `d.nodes` 的旧快照、缺 `sel`、`sel` 指向已删除 id、
> 缺 `canvas`/PID 等字段 —— **四类都必须继续被接受**。

**② 恢复是一个"事务"：校验全部做完才赋值**

旧代码的顺序是「赋值 → `refreshAll()`」。只要刷新那一侧抛一次（设计结构坏到 `draw()` 都不认），
`S.design` 已经被换成坏快照，而异常冒出去 **`restore()` 没返回 false** —— 留下"画布是坏的、
撤销索引却动了"的半套状态。

现在顺序是「校验 → 赋值 → 同步 JSON → 刷新」，失败路径上 `S.design` / `S.selection`
**一个字节都不动**。这条有独立断言（12 条无效快照跑完，序列化前后完全一致）。

**③ 坏记录：跳过 + 就地摘掉（不是"只跳过"）**

- **只跳过不摘**等于每次撤销都重走同一段坏路；**摘掉**才是"不反复撞同一条"。
- ⚠️ **摘的只能是坏记录**。第一版把"目标与当前之间整段"（含好记录）摘掉，后果是
  **正常撤销把重做历史一起删了** —— 既有的「重做能再回到新建之后」与「重做把 x 改回 33」
  两条回归同时报红。现在：扫过的坏记录摘掉、**好记录一条不动**。
- ⚠️ **索引不自己算**。第一版用 `i + removed` 推目标下标，在"摘掉的都在目标右边"时
  会把下标算到栈长之外（实测栈只剩 2 条、索引停在 4）。现在改成**认对象**：
  目标元素摘除后落在哪一格，索引就是哪一格。
- 没有坏记录时，这一步就是**纯粹的一格移动**（与旧行为逐字一致）。

**④ 证据边界（说准，别外推）**

| 说法 | 能不能成立 |
|---|---|
| 加载与 restore 判据一致、失败不留部分状态、坏记录会被摘掉、正常撤销重做不回归 | ✅ 由 `verify-bugfix` 105 条断言 + 全量 33 套 2019 条 + JVM 侧无回归支持 |
| 关键新用例"真实会失败" | ✅ 用 [../../stage](../02_验证记录/20261014_本机证据保管说明.md) 隔离副本把副本还原成**修复前**代码后跑同一套件 → **13 条红**（结构坏 5/6 被放行、`restore` 抛 `designW`、失败后设计被改、`loadUndoStack` 不过滤/索引不重算/全坏不返回 null） |
| **跨会话自动恢复已打通** | ❌ **不成立**。`loadUndoStack()` 仍然只在**设计名一致**时由调用方使用，本卡**没有**加"启动时自动恢复同名旧设计"，也没有改任何调用点 |
| 数据格式/版本变化 | ❌ 没有。v1/v2 文件与加载顺序不变，**未发版** |
| App 侧设计解析跟着变 | ❌ 没有。App 侧一行未动 |
| 设备上的实际观感 | ❌ 未验证（本卡不装设备） |

**⑤ 这一版**只动两处源码**（`js/app.js` 的判据/事务/提示、`js/model.js` 的 `UndoStack` 走法），
加 `../../tools/icarui/tests/verify-bugfix.js` 的回归与 `expected-counts.json` 的下限。
`sample.json`、schema/validate 共享格式、素材/内嵌 data 与 CSS **一个字节都没动**。

**⑥ 判据的真实边界：覆盖"恢复路径真的会读"的最低结构，而不是"数组即有效"**

规划方在真实 `file:` 页面上给出的四类反例，正好各自打在恢复路径的一个真实读取点上：

| 坏快照 | T5-A 判据 | 真实读取点（为什么必然炸） | T5-R 现在 |
|---|---|---|---|
| 缺 `canvas` | 判可用 ✗ | `toV2Json()` / `syncJson()` 直接读 `design.canvas.designW` | **判据仍然接受**（旧快照可以只有 `nodes`，无依据硬拒是禁止的）→ `restore()` 用 `normalizeSnapshotDesign()` 做**纯候选归一化**补缺省，**真实恢复成功** |
| `nodes=[null]` | 判可用 ✗ | `nodeToJson` / `draw` 读 `n.id`、`n.type` | 判**坏**（节点表逐项要求是节点对象） |
| `pages=[null]` | 判可用 ✗ | `currentPage()` / 页签读 `pg.nodes` | 判**坏**（页对象必须带 `nodes` 数组） |
| `assets` 是对象 | 判可用 ✗ | `toV2Json` 遍历 `rd.assets.map` | 判**坏**（要么没有、要么是数组） |
| `children` 非数组 / 页节点非数组 | 判可用 ✗ | 树遍历 / 页切换 | 判**坏** |

⚠️ 判据只**接受 / 拒绝**，**不做归一化**；归一化只发生在 `restore()` 内部的**候选副本**上 ——
否则"失败后 design/selection/JSON/dirty 一个字节都不变"这条就没有保证。

**⑦ 恢复是**真事务**：不是"先校验后赋值"，而是"失败整体回滚"**

T5-A 的"先校验后赋值"只覆盖了**判据自己拦住**的输入。对"判据没拦住、后面才炸"的一类，
实测后果是：`design` 已被替换、`dirty` 已被清、**未应用的 JSON 草稿被覆盖**，而异常冒出去
连 `false` 都没返回。现在：

1. **先准备**（`toV2Json` 算出待写入文本；抛 = 还没动任何状态，直接 `false`）；
2. **捕获现场**（design/selection 的**引用**、`jsonArea` 原文、dirty 与提示条状态）；
3. **再应用**（赋值 → 同步 → 刷新 → 刷按钮），**整体 try/catch**：任何一处抛 →
   全部回滚（含临时标志 `suppressJsonSync` 归位）→ 返回 `false`。

⚠️ `doUndo` / `doRedo` **不许假设 `restore` 必然成功**。⚠️ `UndoStack._step` 的失败返回
是**对象**（`{ok:false, usableLeft}`）而不是 `null` —— 只判 `!r` 会把失败当成功，
于是"整个栈都坏了"被误报成"这一步的记录无法恢复"、索引与计数不再归位（套件实测 `-1 / -1`）。

**⑧ 方向端点：`本方向没有可用目标` ≠ `整个栈都坏了`**

| 起点 | 操作 | T5-A 的后果 | T5-R 现在 |
|---|---|---|---|
| `[坏, current, 好redo]` index=1 | 撤销 | 整栈清空 → 反方向那条好重做记录**永久丢失** | **只摘确认坏的**；当前条与反方向好记录**一条不动**；索引不动；提示"已没有可以撤销的记录了（已清掉 N 条坏记录，其他记录保留）" |
| `[好undo, current, 坏]` index=1 | 重做 | 整栈清空 → 反方向那条好撤销记录**永久丢失** | 同上（坏记录摘掉、好记录保留、索引落在可用的当前条上） |
| 整栈**真的**全坏 | 撤销 | —— | 才允许用**当前设计**重新起基准，提示"…栈里的记录都坏了，已清空（当前设计未改动）"，计数 `0 / 0` |
| 没有坏记录的正常栈 | 撤销/重做 | 一步一格 | **一字不变**：一步一格，一条都不摘 |

⚠️ 实现上还有一条必须记住的教训：**判断与 `splice` 必须分开**。边扫边删会让还没检查的
记录整体下移、于是漏摘（套件三次用 `可用表 11000 → 1101` 精确指到这里）。
现在先整个过一遍判据、把坏的下标**从大到小**记下来，最后照序摘。

**⑨ 证据边界（说准，别外推）**

| 说法 | 能不能成立 |
|---|---|
| 六类坏快照失败后 design / selection / JSON 文本与 dirty / `localStorage` 用户数据**一个字节不变**、且不抛异常 | ✅ `verify-bugfix` 新增段**逐例**验（不靠"全部跑完再聚合比较"，也不用事后人工复位冒充回滚） |

### 2.50 测试的临时目录会攒起来（v2.42.0）

`GaugeThemeTest` **没有 `@After`** —— 36 个测试方法，每次跑泄漏 **36 个**临时目录。
从 10/02 攒到 10/05，`%TEMP%` 里堆了 **2454 个**。

**规律**：`@Before` 里建临时目录的类，必须配 `@After` 删。
漏了不会报错、不会让测试红，**只是安静地占磁盘**。

> ⚠️ **两个清理陷阱**：
> 1. `File.deleteRecursively()` **返回 false 但不抛异常** —— 静默失败
> 2. `File.deleteOnExit()` **对非空目录无效**（Java 只在退出时删空目录）
>
> 还有：**进程被强杀时 `@After` 根本跑不到**，那部分残留只能人工清。

#### 根因：常开文件句柄（v2.42.0 续查）

`BackupTest` 的 `setUp` 调 `AppLog.init(dir)`，而 `AppLog` **为了性能故意保持一个
常开的 `BufferedWriter`** —— **那个句柄占住日志文件，Windows 就删不掉目录**。

`AppLog.clear()` 里的 `closeWriter()` 注释写着"必须先关掉句柄，否则删不掉文件"，
说明代码**早就知道** —— 但它**是异步的**（走 IO 线程），赶不上 `@After`。

补了同步的 `AppLog.shutdown()`。**但还没清零**：残留数会变（3~6），
说明是**和异步 IO 线程的竞态** —— `shutdown()` 关掉之后，队列里没跑完的任务
会把 writer 重新打开。

#### 竞态的解法：清队列 + 屏障（v2.43.0）

只"同步关句柄"还不够 —— 残留数**会在 3~6 之间变**，那就是竞态的信号。

**原因**：常开资源的**生产者是另一个线程**（这里是单线程 `io` 池）。
关掉句柄之后，排在你后面的任务**又会把它打开**。

```kotlin
io.queue.clear()                       // 丢掉没开始跑的
io.execute { closeWriter(); latch.countDown() }   // 屏障
latch.await(2, SECONDS)                // 单线程 → 屏障跑完 = 前面的也结束了
closeWriter()                          // 兜底
```

> **为什么不直接 `io.shutdown()`**：它是**对象级的 `val`，`init()` 不重建** ——
> 关掉之后下一个测试就跑不了了。屏障既不破坏执行器、又能等到队首结束。

### 2.5 分组（v2.2.0）

`type: "group"` 的节点就是分组。**它建成时 `rotation=0`、`scale=1`（纯平移）**，
所以把子控件挪进去只差一个平移量，**视觉位置完全不变**。

| 行为 | 说明 |
|---|---|
| 拖动分组 | 子控件**一起动**（因为子坐标相对组） |
| 旋转/缩放分组 | 子控件跟着转/缩放（逐层设备空间旋转） |
| 点分组内部 | 选中**整个分组**（否则"一起拖动"就形同虚设） |
| 双击分组内部 | **下钻**，选中里面最深的那个控件 |
| 取消组合 | 子控件回到组的父级，**保持视觉位置** |

**打组的前提**：选中项的祖先不能带旋转/缩放。因为 `x/y` 是相对父节点的，
换父级时若原父级带变换，视觉位置会变 —— 而"打组不该让东西跳位置"是基本预期。
不满足时工具会拦下并说明原因（**且不往撤销栈里压空操作**）。

**取消组合的位置公式**（推导过程见 `model.js` 的注释）：
子中心要**在设备空间**绕组中心转 φ，然后转回父空间：

```
父空间中心 → 设备空间 → 绕组中心（设备） 转 φ → 回父空间
```

> ⚠️ 不能在父空间直接转：画布矩阵 `C` 非等比，`C(绕 gc 转 φ) ≠ 绕 C(gc) 转 φ`。
> 实测症状很典型：**父空间中心算得完全正确、设备空间只差一个轴（y 差 23.7px）**。

### 2.57 「靠内容推高度」一定会不一致（v2.45.0）

> 要么接受它会漂。**
>

| "打开的是 Edge 错误页" | **路径算错**：`path.join(__dirname, 'index.html')` 指向 `tests/index.html`，而真正的位置在上一级 |
| "素材格子 118 次内容溢出" | **拿第一个格子的 rect 去比所有格子** —— 不同行 y 不同，必然"溢出" |

> ⚠️ **量出异常时的第一步，是先确认这次测量本身对不对。**
> 尤其"数字大得离谱"或"整个页面的元素少得离谱"时。
>
> 判据：**换个方式再量一次**（换坐标基准、换选择器、加个数）。
> 三次里有三次都变了 —— 那就不是被测对象的问题。

### 2.59 每轮调一次的东西，不要 spawn PowerShell（v2.45.0）

回归从 90 秒涨到 195 秒，查了半天（单套件不慢、新套件不慢、清 profile 无效），
最后发现是**每个套件 spawn 一次清理脚本**：

```
& powershell -ExecutionPolicy Bypass -File kill-test-browsers.ps1 -Kill
```

PS 5.1 里 `Get-Process` **取不到 `CommandLine`**，只能走 `Get-CimInstance Win32_Process`
—— 而**每次新建 PowerShell 进程都要重建 CIM 会话**，单次 **2.9 秒**。
22 个套件就是 **64 秒**。

**内联成同一个进程里的函数调用**（CIM 会话复用）→ 195s 降到 **111s**。

> **规律：凡是"每轮/每项调一次"的操作，都要算上进程启动成本。**
> PowerShell 在 Windows 上冷启动 1~2 秒，循环 20 次就是 20~40 秒。

### 2.60 同一件事在两条代码路径上，很容易只改一条（v2.46.0）

**症状**：搜索时素材分类会隐藏没命中的，**控件分类不会** ——
搜「圆表」还剩 3 个分类头，其中一个是空的「★ 自定义控件 0」，
里面的提示还是「右键控件 → 保存到素材库」（**跟搜索完全无关**）。

**根因**：素材和控件在 `renderAssets` 里分属**两个 `if` 分支**，
素材那条早就写了"搜索时隐藏空分类"（注释还写着「否则 10 个空标题很吵」），
控件那条漏了。

> **规律：一个行为在 N 个分支里各实现一遍时，改的时候必须数一遍 N。**
> 这类"漏改一条分支"的 bug 不会报错，只是**行为不一致** ——
> 而用户看到的恰恰就是那份不一致。

### 2.6 PID 的三种形态（**统一表示，别搞出两套**）

一个 PID 在三个地方有三种写法，必须明确谁是谁：

```
设计文件里            内部（节点上）                画布上
───────────────      ──────────────────────      ──────────────────
"obd.rpm"       →    pid     = "std_0C"      →   标签：发动机转速（友好名）
（语义别名）           rawPid  = "obd.rpm"          🏷 PID：std_0C（解析后的 id）
    或
"std_0C"        →    pid     = "std_0C"      →   同上
（直接写 id）          rawPid  = "std_0C"
```

| 字段 | 是什么 | 谁在用 |
|---|---|---|
| 文件里的 `pid` | 可以是**别名**（`obd.rpm`）或**id**（`std_0C`） | 人写、App 读（`resolvePid` 两者都认） |
| 节点上的 `pid` | **解析后的 id**（`std_0C`） | 内部查表：`BUILTIN_PIDS[pid]` 拿名字/单位/量程/阈值 |
| 节点上的 `rawPid` | **用户写的原样** | 编辑器回显 + 序列化时写回别名。**不写进文件** |
| 画布标签 | `BUILTIN_PIDS[pid].name`（友好名） | 给人看 |
| 🏷 PID 开关 | `pid`（解析后的 id） | 排查"这个表到底绑的哪个 PID" |

**为什么内部只存 id**：查表只能查一次、只有一种 key，不用到处 `resolvePid`。
**为什么还要存 rawPid**：序列化时写回别名（`obd.rpm` 比 `std_0C` 可读得多），
而且 PID 下拉框要能把当前值选中。

> 🔴 **`createNode` 与 `parseNode` 必须用同一套规则。**
> v2.2.1 修过一个 bug：`createNode` 直接把别名当 id 存了，
> 于是"预设建的表画布上写着 `obd.rpm`、导入的表写着发动机转速"，
> 而且预设建的节点**查不到内置库 → 单位丢失**。
>
> `statePid` / `rawStatePid`（状态系统的驱动 PID）同理。

### 2.61 搜索的自检三件套（v2.46.0）

验搜索不是"调 API 看看返回对不对"，而是**真的在输入框里打字**：

| 验什么 | 判据 |
|---|---|
| 能过滤 | 搜前后数量**真的变了**（359→2） |

### 2.64 素材加进画布的尺寸规则（v2.48.0）

完整规则（`addImageNode`）：

```
1. 定长边 = 90，另一边按真实比例算
2. 短边 < 12 → 整体放大到短边 = 12   （太细会点不中）
3. 长边 > 355 → 整体缩到长边 = 355   （**不能超出 360 的画布**）
```

> ⚠️ **第 3 条优先于第 2 条。** 比例比 29.6 更极端时两条无法同时满足 ——
> 宁短边略低于 12，也不能让节点比画布还宽。
>
> 实测：`256×8` 的分隔线在只有第 2 条时会变成 **384×12**，比 360 的画布还宽。

**全程只算一个整体缩放系数 `k`** —— 分别夹 `w` 和 `h` 会破坏比例，
这正是早前「添加进去全是扁的」的成因。

### 2.65 拿不到尺寸时：宁可异步重修，不要静默给正方形（v2.48.0）

`naturalSizeOf` 在"素材没有 `w/h`、位图又没加载"时返回 `null`，
兜底是 `90×90` —— 对一张 256×8 的分隔线来说就是**字面意义的扁掉**。

现在补一次 `refitImageNodeWhenBitmapReady`：位图是异步的，等它到再按真实比例重修
（最多等 3 秒；只修 `w === h` 的节点，不误伤用户改过尺寸的）。

> **规律：任何"异步资源还没到就先给个默认值"的地方，都要配一次"到了再修"。**
> 否则用户看到的就是那个临时默认值 —— 而且它看起来"像是功能坏了"。

### 2.66 画布的配色分两层，别混（v2.49.0）

工具界面上的颜色有**两种来源**，改的时候必须分清：

| 层 | 例子 | 跟着设计主题变吗 |
|---|---|---|
| **设计内容层** | 仪表的弧、指针、刻度、数值、卡片底 | **要**（用 `currentTheme()`） |
| **工具 UI 层** | 选中框、拖拽手柄、多选序号、框选矩形 | **不要**（固定 `#00D8FF`） |

**反例**：`canvas.js` 里 8 处 `#00D8FF`，只有 3 处在设计内容层（`drawGaugeNode`），
另外 5 处在 UI 层（`draw()` 的框选、`drawSelection()`）——
**一起换掉就是 bug**（选中框会跟着主题变红变绿）。

> ⚠️ 建议在 UI 层那几处加注释写明"这里是 UI 层，不用主题色"，
> 否则下一个改的人会一把梭全换掉。

### 2.67 主题色的唯一来源：`window.currentTheme()`（v2.49.0）

```js
window.currentTheme = function () {
  const base = window.GAUGE_THEMES[d.themeId] || window.GAUGE_THEMES.neon;
  return Object.assign({}, base, d.themeColorsOverride || {});
};
```

**规则必须与 `model.js` 的序列化逐字一致**（内置打底 + 局部覆盖）——
否则「画布上看到的」和「导出后 App 看到的」会不一样，
而那种不一致**只有装机才发现**。

### 2.68 画布指纹对"细微灰度变化"不敏感（v2.50.0）

`verify-font` 用这个指纹判断"画布变没变"：

```js
if (d[i+3] > 20) { ... }              // 只看 alpha > 20 的像素
if (n % 401 === 0) { 记一个颜色 }      // 每 401 个非透明像素采一次
```

**问题**：字距 / 斜体改变的是**抗锯齿边缘的细微灰度**。
一旦底色或前景色变化（比如把标签色换成主题色），这些差异可能
**整体落到 `alpha > 20` 阈值以下或采样点之间** —— 于是"画布明明变了，指纹说没变"。

实测：把 `drawGaugeNode` 的调色板换成主题色之后，
`改字距 → 画布变了` / `改斜体 → 画布变了` 两条**红**，
而 `改对齐` / `改颜色` / `改字号` **都还通过** ——
**说明文字画出来了，只是那两处差异测不到**。

> ⚠️ **指纹是测试的"眼睛"。眼睛不灵敏，就会把正常改动报成 bug ——
> 反过来也会把真 bug 放过去。**
>
> 改指纹比改被测代码更该优先：否则会陷入"为了过测试而不敢改功能"。

### 2.69 大范围改动要逐处验证（v2.50.0）

v2.50.0 一次性把 `drawGaugeNode` 的 **8 处**调色板全换成主题色，
结果 `verify-font` 红了 2 条 —— **但事后分不清是哪一处引起的**：

- 先怀疑 `drawGaugeLabel` 的标签色 → 改回工具色 → **无效**
- 又发现回退脚本自己把 `C.textDim` 误换成 `C.textFaint` → 修掉 → **仍然无效**

> **教训：批量替换之后，一旦出问题，"哪一处"的信息就丢了。**
> 换 8 处就该跑 8 次验证（每次一处），定位成本从"重查一遍"降到"看最后一步"。
>
> 尤其是**颜色、字号、间距**这种"改了会互相掩盖"的批量改动。

### 2.7 JSON 文本域的"有错未生效"状态

工具允许**直接编辑 JSON**。解析失败时的规则（v2.2.1 起）：

| 情况 | 行为 |
|---|---|
| 解析失败 | **保留当前设计**（画布不动），文本域标记 `jsonDirty` |
| `jsonDirty` 期间 | `syncJson()` **绝不覆盖文本域** —— 那段文本是"用户的" |
| 视觉提示 | 文本域红框 + 顶部提示条 + 「放弃 JSON 改动」按钮 |
| 修好错误 | 自动生效，标记自动清除 |
| 整体替换设计的操作 | 撤销 / 重做 / 新建 / 套预设 / 打开文件 → 清掉该状态 |

> 🔴 **为什么必须有这条**：v2.2.1 之前，解析失败后只要在画布上动一下，
> `commit()` → `syncJson()` 就会把文本域整个冲掉 ——
> **用户在 JSON 里做的编辑无声无息地消失**。实测复现过。
>
> 遗留：`jsonDirty` 期间画布**仍然可以改**，会出现"画布改了、JSON 没跟上"的分叉。
> 更严格的做法是锁住画布编辑，或做双向合并。

### 2.70 拼音搜索：窄表 + 明确代价（v2.51.0）

**做法**：只收**现有名字实际用到的 368 个字**，而不是通用字库。

| 做法 | 体积 |
|---|---|
| 全字库 | 几百 KB |
| **只收实际用字** | **几 KB** |

> ⚠️ **代价必须写在文件头**：以后名字里出现**生字**就搜不到拼音。
> 不写清楚的话，半年后会有人当成 bug 查半天 ——
> 而真相是"当初有意省了体积"。
>
> **规律：任何"只覆盖当前数据"的优化，都要在代码里写明"新增数据时要做什么"。**

### 2.71 搜索匹配的松紧是个取舍（v2.51.0）

| 匹配方式 | 支持的输入 | 代价 |
|---|---|---|
| 原文 `indexOf` | `碳纤维` / `turn-left` | 中文要切输入法 |
| **+ 全拼** | `tanxianwei` | 需要拼音表 |
| **+ 首字母** | `txw` | 需要拼音表 |
| 子序列（跳字） | `tanwei` → 碳纤维 | **`tb` 也会命中碳纤维 → 噪音大** |

**最后一条有意不做。** 跳字匹配看起来"更智能"，
但它会让几乎任何短输入都命中一堆东西 ——
**搜索的价值在于"把范围缩小"，不在于"总能搜到点什么"。**

> 相关的：首字母匹配要**限定 `q` 全是字母**，
> 否则中文输入也会去比 initials，白跑一趟。

### 2.72 哪些设置该进设计文件，哪些不该（v2.54.0）

加**界面缩放**时定的判据：

| 设置 | 进设计文件吗 | 为什么 |
|---|---|---|
| **主题配色** `themeColors` | **进** | 配色是**作品的一部分** —— 同一份设计在别人机器上也该长一样 |
| **界面缩放** | **不进** | 是**工具本身的偏好** —— 屏幕大小是"这台机器"的事，不是作品的事 |
| 面板宽度 / 面板折叠状态 | 不进 | 同上 |
| 素材分类顺序 / 自定义分类 | 不进（存 localStorage） | 是"我怎么整理素材"，不是设计内容 |

> **判据一句话：换一台机器打开这份文件，这个设置该不该跟着变？**
> 该变 → 进设计文件；不该变 → 存本机。

### 2.73 缩放用 `zoom` 而不是 root `font-size`（v2.54.0）

```js
document.body.style.zoom = String(s.zoom);
```

> ⚠️ **本工程的字号全是写死的 `px`** —— root `font-size` 只影响 `rem`，
> 对它们**完全无效**。想缩放只能走 `zoom`。
>
> 如果哪天要把字号体系改成 `rem`，那是个**大重构**，
> 得连带把 44 条排版断言一起看一遍。

**缩放后必须重算画布**：容器尺寸变了，`applyCanvasSize()` 要再跑一次，
否则画布还是原来的大小（实测会差 100+ px）。

### 2.74 离散档位比滑杆更容易"回到原位"（v2.54.0）

界面缩放做成**三档按钮**而不是滑杆：

| 形式 | 问题 |
|---|---|
| 滑杆 | 拖过之后**很难凭感觉拖回 100%** |
| **离散档位** | 「标准 ✓」一眼可见，点一下就回去；每档还能带一句用途说明 |

> **规律：凡是"用户会想回到某个明确默认值"的设置，用离散档位。**
> 连续滑杆适合"没有正确值、只有偏好"的东西（比如亮度）。

### 2.75 「先怀疑测量」要用在更早的地方（v2.55.0）

v2.50.0 接主题色时 `verify-font` 红了 2 条，**整体回退**。
v2.55.0 先花十分钟验"是不是测试的问题" —— 结果**是**：
把指纹采样加密（331 → 97）并读四通道，**同一份代码 45/0 全过**。

> ⚠️ **"先怀疑测量"不只在单次测量里，也在"整个验证体系可信吗"这一层。**
>
> 前几轮我踩过 8 次"测量错了"，但每次都在**单次测量**的层面。
> 这次是**测试基建**层面 —— 一个抽样太稀疏的指纹，
> 把"正常改动"报成了 bug，代价是一轮返工。

### 2.76 画布指纹应该这样写（v2.55.0）

```js
// 抽样密度：宁密勿疏
for (let i = 0; i < d.length; i += 97)
  // 四通道都读（只读 R 会漏掉色相变化）
  for (let c = 0; c < 4; c++) h = (h*31 + d[i+c]) % 2147483647;
```

| 写法 | 采样次数（866×541） |
|---|---|
| 旧：步长 331 / 只读 R | ~5,662 |
| **新：步长 97 / 四通道** | **~308,000** |

> **代价可以接受**：指纹只在断言前后各算一次，多花几十毫秒。
> 而"测不出来"的代价是**一轮返工**。

### 2.77 「变了没」不够，要验「变成什么了」（v2.55.0）

判"切主题有没有生效"，只验"画布指纹变了"是**不够的** ——
随便改点什么都会通过。真正要验的是**色调本身**：

```js
// 从画布取出现次数最多的几个颜色，核对主题的主色在不在里面
has(neon.top, "#FF8A00")   // neon 的主色真的画上去了吗
```

> **规律：验"输出变了"永远不如验"输出等于期望值"。**
> 前者只能挡住"完全没生效"，挡不住"生效成了别的东西"。

> ⚠️ 本轮**只接了 `accent` 一个字段**，其余 11 个（background / surface /
> track / tick / needle / value / label / dim / accentHot / accentDim / surfaceEdge）
> **还没接**；`drawPartTree`（拼装表主路径）**完全没接**。
> 也就是说"主题功能"目前只是**部分可用**。

### 2.78 相邻两行，一行该跟主题、一行不该（v2.56.0）

`draw()` 里有这么两行：

```js
ctx.fillStyle = C.out;                       // 画布外的留边
ctx.fillStyle = currentTheme().background;   // 画布内
```

| 行 | 是什么 | 跟主题吗 |
|---|---|---|
| `C.out` | 画布**外**的留边 | ❌ 是"这里不是设计区"的**工具提示** |
| `C.in` | 画布**内** = App 里的仪表背景 | ✅ **跟** |

> **画布配色分两层（§2.66）这件事，最容易被忽略的地方就是"底色"** ——
> 因为它是"背景"，看起来不像"控件"，很容易被当成工具的一部分。
>
> 但**面积最大的东西不跟着变，用户就会觉得"主题没生效"** ——
> 哪怕所有控件都正确变色了。

### 2.79 面积越大，越要先接（v2.56.0）

接主题色的**优先级应该按"面积"排**，不是按"代码顺序"：

| 优先级 | 接什么 | 理由 |
|---|---|---|
| **1** | **画布底色** | 占屏幕一半以上 |
| 2 | 仪表的主体（弧、轨道、卡片） | 每个控件都占一块 |
| 3 | 文字 / 刻度 / 指针 | 细，但数量多 |
| 4 | 状态色（告警红 / 警告黄） | 局部、瞬时 |

> v2.55.0 是按**代码顺序**接的（先接了 `drawGaugeNode` 里的 8 处），
> 结果"最大的那块底色"反而漏了 —— 观感上像"只做了一半"。
> **按面积排，能用最少的改动换来最大的观感变化。**

### 2.8 控件库与控件编辑器（v2.3.0）

设计文件新增 **`controls`** 段：`[{id, name, node}]`，存**可复用控件模板**。
与 `assets`（图片）并列 —— 一个存图，一个存控件。

```
素材库
├─ 🧩 控件            11 个内置条目（8 种仪表样式 + 文字 + 分组 + 图片）
├─ 🧩 自定义控件       controls 段里的模板（跟着设计文件走）
└─ 📁 背景/仪表盘/…    图片素材（10 个分类，按相对路径引用）
```

**两种放入方式**：
- **单击** → 打开控件编辑器（"先改再放"）
- **拖拽** → 直接实例化到落点（`instantiateControl` 会深拷贝 + 换新 id）

**控件编辑器**（右键 →「编辑控件…」/ <kbd>F2</kbd>）三个关键设计：

1. **编辑草稿副本**（`S.editDraft`），画布上的原节点不动 —— 取消就是没发生
2. **预览复用画布绘制代码**（`drawNodePreview` 临时替换绘制目标 `ctx`）——
   不另写一份绘制，所以预览与画布**一定一致**。这是 `ctx` 用 `let` 而不是 `const` 的唯一理由
3. 「保存到素材库」写进 `controls`；「导出 JSON」单独下载（`kind: "icar.control/1"`）

> ⚠️ **模板节点会带 `locked`/`visible`**。保存时强制清成 `false`/`true` ——
> 否则"拖出来就是锁住的"，用户会以为工具坏了。

### 2.82 「没设过」和「设成了默认值」分不开（v2.58.0）

拼装表的文字不跟主题，根因是这一行：

```js
ctx.fillStyle = f.color;   // f = Object.assign({}, FONT_DEFAULT, part.font)
```

**用户没设色** 和 **用户设成了和默认一样的色**，在数据上**无法区分** ——
两者都是 `f.color === FONT_DEFAULT.color`。

**处理方式：把"等于默认值"一律视为"没设过"** ——
于是它回到主题色。代价是"用户故意设成默认色"会失效，
但那**肉眼不可区分**，可以忽略。

```js
ctx.fillStyle = (f.color && f.color !== window.FONT_DEFAULT.color)
  ? f.color                       // 显式设过
  : window.currentTheme().label;  // 没设过 → 跟主题
```

> ⚠️ **这个判据要在所有"有默认值 + 需要跟随"的地方保持一致** ——
> `drawGaugeLabel` 和 `drawPartTree` 现在用的是同一条。
> 不一致的话，同一份设计在两条路径上会长得不一样。
>
> **更彻底的做法**（以后可选）：把"没设过"存成 `null` 而不是"省略字段"，
> 那就能真正区分了。现在这样是为了不改数据格式。

### 2.83 把"约定"变成"守卫"（v2.59.0）

主题接线（哪一层该跟主题、哪一层不该）原本只写在文档里。
**文档不会拦住人** —— 新加一个绘制函数、随手写个 `"#00D8FF"`，
主题就漏一处，而且**颜色看着都"挺对"，看不出来**。

**做法**：按**函数归属**扫裸色值，白名单外的就报错。

| 层 | 白名单 |
|---|---|
| 工具 UI 层 | `drawSelection` / `draw` / `drawImageNode` / `drawPartOutlines` |
| 设计内容层 | **不在白名单** —— 必须用 `window.currentTheme()` |

> **规律：凡是"靠人记住"的约定，都该变成机器检查。**
> 判断标准很简单 —— **违反了会不会有明显症状？**
> 会 → 文档够了；不会（像颜色漏接）→ 必须上守卫。

### 2.87 枚举型数据进不了 `min~max` 模型（v2.60.0）

| **B. 文本型 PID** | 扩展 `type: "text"` | 最通用；要改格式 + 两侧 |
| **C. 专用控件** | 单独做 `gear` 部件 | 只解决挡位 |

> **规律：遇到"新数据塞不进老模型"时，先问"还有谁也是这类"。**
> 挡位和 DTC 分开做，会得到两套不一致的方案 ——
> 而它们**本该共用一套**。

### 2.96 实测成本推翻当初的推理（v2.62 → v2.65）

v2.62.0 我在注释里**主张保留**精确条数断言，理由写得挺像回事：

**接下来四个版本改了四次。** 于是 v2.65.0 把它降级成范围。

| 场景 | crosslang | 精确条数 | 降级后 |
|---|---|---|---|
| 单边加/删 | ✅ 红 | ✅ 红 | ✅ 红 |
| 两侧一起删一大批 | ❌ | ✅ 红 | ✅ 红 |
| **两侧一起加** | ❌ | ⚠️ **要手工改** | ✅ 不打扰 |

> **"我当初判断它有价值"不是保留它的理由。**
>
> 判断是**推理**，维护成本是**实测**。当一个东西每版都要动，
> 那就说明它的边界划错了 —— 哪怕当初的理由听起来很对。
>
> ⚠️ 相关的：**一条断言如果需要"每次改数据都跟着改"，它测的是数据不是行为。**

### 2.97 假阴性比不检查更糟（v2.66.0）

### 2.98 PowerShell 变量不区分大小写（v2.66.0）

```powershell
$S = "D:\...\schema.js"          # 想当"路径"
$s = ReadAllText($S)               # 想当"内容" —— 但它是同一个变量！
[System.IO.File]::WriteAllText($S, $s, ...)   # $S 已是文件内容
```

**`$s` 和 `$S` 是同一个变量。** 写入抛了 "Illegal characters in path"，
侥幸没破坏文件。

> ⚠️ **别用大小写区分变量** —— 在很多语言里成立，在 PowerShell 里不成立。
> 用 `$path` / `$text` 这类**拼写不同**的名字。
>
> 更一般的：**凡是"我确信这两个名字不同"的地方，都值得再确认一次** ——
> 尤其是跨语言/跨工具的时候（`.ps1` vs `.js` 的规则不一样）。

### 2.99 解析器"跨条目吞掉"是隐形杀手（v2.67.0）

解析 Kotlin 的 `PidDefinition(...)` 时用了懒匹配 `[\s\S]*?`：

```js
/PidDefinition\(\s*id\s*=\s*"([^"]+)"[\s\S]*?minVal\s*=\s*(-?[\d.]+)f .../
```

**问题**：`std()` 辅助函数里也有一个 `PidDefinition(`（`id = "std_$pid"`）。
那个匹配会一路懒匹配到**第一个真实的 `minVal`**（在 `tpl_oilPressure` 里）——
于是 `tpl_oilPressure` **被前一个匹配吃掉了**。

**症状**：

```
· 工具里多出 1 个 PID（App 侧没有）：tpl_oilPressure
```

看起来像"数据缺失"，**真相是解析器漏读**。

> ⚠️ **判据：如果"我核实过数据是有的，但工具说没有"→ 那就该怀疑工具。**
>
> 这类"跨条目吞掉"在**任何用懒匹配解析重复结构**的地方都会出现。
> 修法：用负向先行断言把匹配限制在**单个条目内** ——
> `(?:(?!下个条目的开头)[\s\S])*?`。

### 2.110 枚举型数据用「数值 + 映射表」，不要改成文本型 PID（P9 方向 A）

**背景**：主题工具里 **18 个控件绑着不存在的 PID**（14 个指示灯 + 挡位 / 续航 / 总里程 / 电量）。
根因不是"忘了配 PID"，而是**模型缺"非连续数值"这一类** ——
现有 PID 是 `min~max` 的连续数值，塞不进 `P/N/R/D`（枚举）、
亮/灭（布尔）、`P0301`（文本）。

**决定（用户 2026-10-05 拍板）**：方向 A —— **值仍然是一个数，显示时查一张映射表**。

| 数据种类 | 怎么进模型 | 需要映射表吗 |
|---|---|---|
| 布尔（指示灯亮 / 灭） | `min=0, max=1` + `warnHigh=0.5` | **不需要** —— 既有三态图直接可用（0 → 正常，1 → 严重） |
| 枚举（挡位 `P/R/N/1..6`） | `min=0, max=N` + `valueLabels` | **需要** |
| 文本（故障码 `P0301`） | **暂不支持**（那要方向 B：格式扩展 `type: "text"`） | — |

**字段**：仪表节点的 `valueLabels`（字符串数组，上限 `ValueLabels.MAX` = **32**）。

```json
{ "pid": "obd.gear", "min": 0, "max": 8,
  "valueLabels": ["P", "R", "N", "1", "2", "3", "4", "5", "6"] }
```

**语义（Kotlin `ValueLabels` 与工具 `valueLabelFor` 必须逐字一致）**：

| 情况 | 结果 |
|---|---|
| 空表 / 全空串 | **不用映射**（读数按量程格式化） |
| 值是 NaN / null | `--` |
| `round(value)` 越界 | **夹到 `0..size-1`**（不报错、也不是不显示） |

> ⚠️ **必须 `round` 而不是截断**：`4.999` 是"第 5 挡"，截断会写成 4 ——
> 指针已经指在第 5 挡的位置。**两者都不报错**，只有盯着看才发现"差一格"。
> Kotlin 侧有一条专门的用例钉着这个行为。

**为什么映射表跟着设计文件走**（而不是存成设备级设置）：
设计文件是"作品"，同一份设计推到两台设备上必须长得一样 ——
与内嵌主题配色（§2.20）同一个理由。

**几何仍然按数值走**：指针角度 / 弧长 / 条长都用 `min~max` 上的数值，
映射表**只换读数文本**。所以挡位的 `min/max` 必须填对（0~8），
否则指针会指在错误的位置。

**没做的（诚实列出）**：

- **文本型数据（故障码）不支持** —— 需要方向 B
- **`value` 部件级映射表不支持** —— 目前只有仪表节点级。
  拼装表里的数值部件要显示名字，得等下一步
- ⚠️ **下面这段是 2026-10-05 的推论，其中"必须等车 / 必须是厂家 Mode 22"已被实车推翻**（见 `接手大纲` §1 与 `迭代清单` P9/P10）：总里程是标准 `01 A6`、转向灯是**广播帧的位**，都不需要 Mode 22。以那两份为准。
- **还剩 14 个控件仍然绑不到真 PID**（**12 个指示灯 + 挡位 + 电池电量**，计数以守卫为准）
  —— 模型通了、**其中 4 个的数据源也已解决**
  （平均油耗 / 故障灯 MIL / 续航里程 / 总里程 `01 A6`，v1.17.4~v1.18.0），剩下的**这次是真的要等车**：
  这些量是**广播帧里的位**（转向灯已用此法确认：`0x09A` bit2/bit3），
  用「CAN 探测 + 对比基准」收，**不需要 Mode 22**。模型只保证"**有了数据之后能正确显示**"，
  它不制造数据。工单见 [`16_上车监控清单.md`](16_上车监控清单.md) §11 工单 A

### 2.112 预览的"会动的东西"：弹簧是**状态**、盘面是**算出来的**、进度弧只改一个标量（v2.81.0）

这一节来自一个**独立的参考实现**（宝马风格仪表盘，SVG + GSAP + 自写弹簧）。
它踩过的坑与我们的画布渲染是同一批问题，所以逐条对照落地。
**结论先写在这里：参考实现的 GSAP 我们不要** —— 工具是零安装形态（§8），
弹簧 10 行自己写；真正值得抄的是它那四条"把动画当状态"的做法。

#### ① 指针 = 真弹簧积分，不是补间

```js
const a = (target - x) * k - v * c;   // 虎克力 - 阻尼力
v += a * dt;  x += v * dt;            // 半隐式欧拉
```

| 参数 | 值 | 判据 / 理由 |
|---|---|---|
| `k` | 150 | 劲度系数 |
| `c` | 19 | 阻尼系数 |
| `dt` 上限 | 0.05 | **切走标签页再切回来 `dt` 可能是好几秒**；不夹的话 `k·dt²` 上千 → 指针飞出屏幕 |
| 稳定判据 | `k·dt² < 4` 且 `c·dt < 2` | 显式积分的发散边界（默认参数下 0.375 / 0.95） |
| 阻尼比 | `ζ = c/(2√k) ≈ 0.776` | **欠阻尼 → 过冲一点再回正**，这就是"像真针" |

> ⚠️ 两个过冲数字要分清（如实记）：**连续系统的理论过冲约 2.1%**，
> 而半隐式欧拉在 `dt=1/60` 下带**数值阻尼**，实测峰值 `100.65`（步进 100）= **0.65%**。
> 比理论小，但"顶一下再回正"仍看得见 —— 测试钉的是"必须 > 100.2 且 < 104"这个区间，
> 不是理论值。

**为什么不用补间**：实时数据每 16ms 变一次，补间永远追不上（每帧重排一段新动画、
旧的被打断），结果是累积延迟 + 互相 `overwrite`。弹簧是**状态**：
目标怎么跳，它都只是"被拉了一下"。

**边界（必须记住）**：弹簧**只驱动"会动的金属件"**（指针 / 盘面进度弧 / 数字鼓）。
读数、条形、状态灯、阈值判定**一律读真值** —— 弹簧到位要时间，
让报警跟着它走就是"晚到"，那是把预览做得和真车不一样，不是美化。

`js/spring.js` 是**纯函数**（不碰 DOM），所以稳定性 / 过冲 / 收敛 / 步长换算
全部能在 Node 里直接断言 —— 不需要跑浏览器动画。

#### ② 盘面是"算"出来的：`buildDial()` + **签名**

极坐标生成刻度与数字（`r = min(w,h)×0.36`、`start=135°`、`sweep=270°`，缺口在正下方）。
大格步长从 `1/2/2.5/5 × 10ⁿ` 里自动挑（能不能整除量程 / 步长是否整数 /
`min` 是否对齐 / 大格数够不够）。实测：`0~8000`→1000、`0~260`→20、
`-40~215`→20（**从 -40 起步**）、`0~20`→2。

**量程 / 单位 / 红区一变就必须重建盘面**：`dialSig()` 是"这块盘面长什么样"的唯一指纹，
`dialFaceFor()` 按它缓存（上限 32 条）。参考实现的坑：页脚写着"能量回收 %"
而盘面还标到 300 —— 它只改了 `max`，刻度是**上一次算好留在那儿的**。

> 一句话：**刻度是算出来的，不是画上去的**。算它的输入变了就必须重算。
> 红区两段都支持（`warnLow` + `warnHigh`）—— 温度/电压是**两端都不正常**的量。

#### ③ 进度弧：`stroke-dashoffset`（路径恒定，进度只改一个标量）

SVG 侧 `strokeDasharray = len; strokeDashoffset = len × (1 - 进度)`；
**canvas 的对应物是 `setLineDash([len])` + `lineDashOffset`**，语义一致。
⚠️ canvas 没有 `getTotalLength()` —— 圆弧解析可算：`len = r·θ`。

不"按比例重画一段短弧"的三个理由：每帧重新构造路径 / 弧两端抗锯齿每帧都在动 /
**进度不再是可插值的标量**（想给它做弹簧或补间都无从下手）。
画完必须 `setLineDash([])` + `lineDashOffset = 0`，否则后面所有线都变虚线。

#### ④ 数字鼓：三个坑（`drumSlot` / `drumDigits`）

| 坑 | 表现 | 对策 |
|---|---|---|
| `yPercent` 是相对**条带自身高度**的百分比（一行 = `100/rows` %） | 10 行改 20 行忘了改 → **数字显示成 2 倍** | 位置**用像素**算，百分比口径每次按当前 rows 重算 |
| 位置**从 DOM 读、不缓存** | 补间被打断时缓存失真 → "重播后锁死 888" | 纯函数、无状态：同样输入永远同样输出 |
| **只向前滚**，不靠 `onComplete` 回位 | 9→0 倒着滑回去就不像里程表 | 取模；位置只由值决定，中途改值/打断都不留错位 |

#### ⑤ 两套系统的让位仲裁（`AnimArbiter`）

参考实现的坑：rAF 主循环负责实时数据、GSAP 时间线负责作者编排的动画，
**两者写同一个 `rotation`** → 主循环每帧覆写，开机自检的扫表**一帧都看不见**。

工具里的契约（没有 GSAP，但坑是同一个）：

- **全工具只有一个** rAF 主循环负责实时数据；它每帧先问 `S.anim.allows("sim")`，
  **不让位就不推弹簧**（不是"先推再被覆盖"）
- 补间（`setTweenValues` / `playBootSweep`）开始前 `claim("tween", 毫秒)`，结束 `release`
- **带超时**：claim 的一方崩了（忘了 release）标志会自己过期 ——
  否则症状是"实时模拟开着但指针不动"，极难定位

> ⚠️ 这条与 §6 的"`draw()` 被十几个地方调用"是同一个约束的两面：
> **同一时刻只允许一个系统写"会动的东西"**，而且要显式声明，不能靠调用顺序碰运气。

#### ⑥ 格式影响：**零**

盘面参数全部从**已有**字段推导（`min` / `max` / `warnLow` / `warnHigh` / PID 单位），
设计文件**一个字段都没加** —— 存量文件导出逐字节不变，App 侧零改动。
弹簧参数（`k`/`c`）放在**界面设置**里（本机偏好），理由同 §2.54 的界面缩放：
它是"预览的手感"，与"主题长什么样"无关，写进设计文件会让同一份设计在不同机器上不一样。

### 2.113 19 个指示灯里 16 个的状态系统是**死的**（v1.20.16 修）

**这是这个库里最贵的一条**：用户从控件库拖一个「胎压灯」出来，
它**永远显示暗的 `lamp-off.png`**。控件能拖、能摆、能存、能导出、构建守卫不报 ——
**用户会以为车没问题**，而不是"这个灯没接上"。

#### 症状与根因链（三处代码，缺一条都看不出来）

| # | 位置 | 做了什么 |
|---|---|---|
| 1 | `presets.js` 第二批 16 个灯 | 写的是 `n.pid = ...` / `n.rawPid = ...`，**不是 `statePid`**（第一批 3 个灯写对了） |

**净结果**：设计文件里既没有 `statePid` 也没有 `pid`。灯永远是 `normal`。

#### 修法与实测

`presets.js` 改成与第一批对齐：

```js
n.rawStatePid = d.pid;
n.statePid = window.resolvePid(d.pid);
```

### 2.114 告警闪烁必须 ≤3 Hz（WCAG 2.3.1，v1.20.16 修）

**这是安全/合规红线，不是观感问题。**

WCAG 2.3.1 Three Flashes or Below Threshold（Level A）原文：

> *"Web pages do not contain anything that flashes more than
> three times in any one second period..."*

**修复前实测三处全部超标**：

| 位置 | 修复前 | 换算 | 修复后 |
|---|---|---:|---|
| `AlertPulse.intensity()` 危险档 | `square(nowMs, 200, 0.5f)` | **5.0 Hz** | 400ms = **2.5 Hz** |
| 控件库第一批灯 `critical.blinkMs` | `220` | **4.5 Hz** | 400ms |
| 控件库第二批灯 `critical.blinkMs` | `260` | **3.8 Hz** | 400ms |
| 工具侧下限 `Math.max(60, …)` | `60` | **16.7 Hz** | 400ms |

**周期的唯一真源**：`NodeState.MIN_BLINK_MS = 400`（数据层，那是设计文件的契约）。
`AlertPulse` 直接引用它；工具侧 `window.MIN_BLINK_MS` 与它同源，
由 `tests/verify-crosslang.js` 逐条比对守着（只改一侧是**静默**失效）。

**三处落地 + 两道守卫**：

| 落地 | 位置 |
|---|---|
| App 渲染路径 | `NodeTreeRenderer.applyStates` 的 `coerceAtLeast(NodeState.MIN_BLINK_MS)` |
| App 解析路径 | `NodeState.parseAll` 的 `coerceAtLeast(MIN_BLINK_MS)`（文件里写 100ms 也不许照闪） |
| 工具侧 | `validate.js` / `app.js` / `editor.js` / `panels.js`（输入框 `min` 也跟着改） |

| 守卫 | 断言 |
|---|---|
| Kotlin（`AlertPulseTest`） | **直接数 10 秒的上升沿**换算 Hz ≤ 3.0 —— 而不是断言"常量等于 400"（后者在有人把 duty 改成 0.25、一轮亮两次时照样绿） |
| 工具（`verify-crosslang.js` + `verify-lamp-state.js`） | 工具与 App 的下限**逐字一致**；全库没有低于下限的闪烁周期；`Math.max(60, …)` 不得残留 |

> ⚠️ **为什么没有把危险档的 `square` 一起降成 `pulse`**：
> `DashRenderer` 只以 **5 Hz 的 tick** 采样状态相位（"不引入第二个动画驱动"，§6）。
> 400ms 周期下每周期恰好 **2 个采样点**，闪烁照旧可见 ——
> 反而比原来更稳：修复前的 200ms 周期**正好等于一个 tick**，
> `(nowMs / 200) % 2` 与 tick 同频，采样点可能**恒落在同相位**（灯看起来不闪）。
>
> **"爆闪"的观感取舍**：危险档与警告档仍有肉眼可分辨的快慢差（2.5Hz vs 1.7Hz），
> 但危险档不再是"刺眼硬方波"。若装机后觉得冲击力不够，
> 可评估的替代方案是**只换颜色、不做明暗交替**（纯色相变化理论上不构成 flash）——
> 但那是重写 `tintMix` 那一层，**本次没做**。

### 2.115 三条"写一侧、漏一侧"的契约（v2.83.0，ICarUI 改名 + 六轮复盘）

v2.83.0 做了一次六轮复盘（每轮换一个角度）。**结论里有三条是架构级的** ——
它们不是"某个 bug 修了"，而是**两处实现之间必须有契约、而当时没有守卫**。
三条的共同形态是本仓库最贵的那一类：**改了 A 忘了 B，两边都不报错**。

#### (1) 序列化写出的字段，解析侧必须读回来

`model.js` 的 `nodeToJson` 与 `validate.js` 的 `parseNode` 是**同一份格式的两侧**。

| 事故 | 写 | 漏读 | 症状 |
|---|---|---|---|
| v1.20.16 | `statePid` | `rawStatePid` | 指示灯**永远是暗的**，用户以为车没问题 |
| **v2.83.0** | **`valueLabels`** | **从不还原** | 挡位读数从 `P/R/N/1..6` 变回 `0..8`；**再存一次就把映射表从文件里抹掉** |

判据：**`nodeToJson` 写出的每一个字段，`parseNode` 都必须有对应还原**。
由 `tests/verify-fields.js` 双向守着（行为面：**全部**控件模板 + 全字段节点逐个往返深比；
结构面：两侧字段名做集合差）。⚠️ 该套件的结构面**反向验证过** ——
换回修复前的 `validate.js`，它精确报出 `valueLabels` 一个。

#### (2) 状态灯的**阈值推断与回退链**：工具预览必须等于真机

工具的画布预览与 App 的 `NodeTreeRenderer` 是**两套实现**，但决定"同一个数值显示哪张图"的
规则必须逐条相同：

| 规则 | App | 工具 |
|---|---|---|
| 阈值来源 | `node.stateWarn ?: pid.warnHigh` | 同 |
| 危险线推断 | `warnAt + (max - warnAt) * 0.5`（`max > warnAt` 才成立） | 同 |
| 比较方向 | `>=` | 同 |
| **回退链** | `critical ?: warn ?: normal` | **原来是 `critical ?: normal`** ← v2.83.0 实测抓到的真分歧 |
| 状态素材为空 | 回落到 `node.assetId` | 同 |

回退链那一条的症状最隐蔽：一份**只填了 `normal`/`warn`、没有 `critical` 键**的设计，
数值超过危险线时**工具预览显示 `normal` 的图、真机显示 `warn` 的图** ——
用户会以为"危险态没接上"（预览里灯根本没变），而车上却是黄灯。
由 `verify-crosslang.js` 的「状态灯」一节逐条比对 + `verify-lamp-state.js` §11 行为面守着。

#### (3) 三态默认值只能有一个真源

`STATE_NAMES` 说"有哪几个状态"，`STATE_DEFAULTS`（v2.83.0 新增）说"各自默认什么"，
`defaultStates(assetId)` 把两者合起来。在此之前，同一份 `normal/warn/critical` 字面量
在 **`app.js` / `editor.js` 各写一遍**，`setState` / `ceSetState` 的**兜底还写了第三遍**
—— 而第三遍里 `critical` 的 `blink` 是 `false`（与"启用状态系统"那条路径创建的 `true` 不一致）。
**加第四个状态时只改一处就会漏**，漏掉的那侧"永远不亮"且不报错。
`verify-lamp-state.js` §10 钉住「`STATE_NAMES` 里每一个都必须在 `STATE_DEFAULTS` 里有默认值」。

#### (4) 顺带新增的两条边界

| 项 | 内容 |
|---|---|
| `window.MAX_NODE_DEPTH = 32`（工具侧，`schema.js`） | `parseNode` 是递归的。2 万层嵌套的 `group` 会把调用栈打爆（`RangeError`），而这个异常会冒到 `jsonEdited` 的 `setTimeout` 里（**那里没有 try/catch**）→ 用户看到"粘了文件什么都没发生"。32 层远超真实设计（正常最多 4 层）。**⚠️ App 侧的 `DesignFile.parseNode` 是同样的递归结构，也需要同样的上限 —— 目前还没有。** |
| 校验消息渲染上限 200 条（工具侧，`app.js`） | `parts` 没有条数上限（`nodes` 有 200），而每个没选素材的部件都产生一条警告 —— 实测 20000 个部件 → 20000 条警告 → 20000 个 DOM 行，而这发生在**每次敲键盘**之后。超额时补一行「…还有 N 条」—— **截断必须说出来**。 |

> **规律：跨实现的东西不要靠"我记得两边一样"。** 这个仓库已经栽过四次
> （`statePid` / `valueLabels` / 状态回退链 / `blinkMs` 裸字面量），
> 四次都是"静默"。**能做成一条断言的就不要做成一句注释。**

### 2.116 多段色带 `bands`：**"画出来的分区"和"报警判定"是两件事**（v2.87.0）

仪表上的"分区"以前只能靠两个标量表达：`warnLow`（低于它不正常）与
`warnHigh`（高于它不正常），颜色写死 `#FF4D4F`，最多两段。
油量"绿→黄→红"、转速"黄 6000~7000 + 红 7000~8000"这类表达**做不出来**。

v2.87.0 给节点加了可选字段 `bands`：

```json
{ "type": "gauge", "pid": "obd.rpm", "min": 0, "max": 8000,
  "warnHigh": 6500,
  "bands": [ { "from": 6000, "to": 7000, "color": "#FFB020" },
             { "from": 7000, "to": 8000, "color": "#FF4D4F", "alpha": 200 } ] }
```

| 规则 | 值 |
|---|---|
| 段的形状 | `{ from, to, color?, alpha? }`；`from`/`to` 是**量程上的值**（不是比例） |
| 段数上限 | `MAX_BANDS = 8`（超出的**丢掉**，只警告不报错） |
| `color` | **只认 `#RRGGBB`**；不认 → `null`（绘制时回落 `BAND_DEFAULT_COLOR = "#FF4D4F"`） |
| `alpha` | `0..255`（与节点 `alpha` / `card.alpha` 同一套口径）；没写 → `null` = 按 255 画 |
| 越界 | `from`/`to` **夹到 `[min, max]`**；夹完 `to <= from` 的段**丢掉** |
| 缺省 | 缺省 / 空数组 / 全非法 → **`null`** = **不画分区 = 完全旧行为** |
| 序列化 | **只在非空时写**；`color`/`alpha` 只在非 null 时写（否则"没写"往返一次会变成"写了"） |

#### ⚠️ 这条是**安全语义**，不是观感问题

| | 管什么 |
|---|---|
| `bands` | **只**管"画出来的分区" |
| `warnLow` / `warnHigh` | **报警判定**（App 侧变色 / 闪烁 / 告警条全靠它） |

**让 `bands` 顺带改报警行为 = 静默改变存量设计的安全语义** ——
"给转速表加个红区参考"会变成"这张表开始报警了"。
所以 `gaugeDialOpts()` 是"**有 `bands` 就用它画，没有才回落到 `warnLow`/`warnHigh`**"，
两条路都**只决定画什么**，谁也不改谁的判定语义。`verify-bands.js` §3 钉着：
只加色带 → `warnLow`/`warnHigh` 仍然是 `null`；色带边界 ≠ 报警阈值。

#### 绘制上的两个刻意选择

| 位置 | 顺序 | 为什么 |
|---|---|---|
| 盘面（style 0 / 7） | 分区画在**进度弧之后**（v2.88.0 **修**；修前是"之前"） | 分区与进度弧**半径、线宽完全相同** → **后画的整段盖住前一个**。修前是进度弧在后，于是**值一进红区就把红区盖掉** —— 红区的意义恰恰是"现在危险"，等于这个功能在最关键的时刻失效。现在分区在后：**安全信息赢**，而重叠只发生在已经进红区的那一段，出了红区两件事照样同时看得见。⚠️ **这会动到存量红区的像素**（重叠段由 accent 变红区色），是**预期的、往正确方向**的变化（见 §2.117） |
| 条形表（style 2） | 分区画在**填充之下** | 条上的填充是**主读数**。分区压在填充上会把读数整段盖住（50% 的油量条会显示成"整条绿"）。压在下面则两件事同时看得见 |

#### ⚠️ App 侧还没做（v2.87.0 只做了工具侧）

App 侧 `GaugeItem` 只有 `warnLow`/`warnHigh` 两个标量，**读不懂 `bands`** ——
带色带的设计在设备上**只会少画分区**（不报错，是"静默失效"）。
补齐时必须**同时**补一条 `verify-crosslang.js` 断言把
`MAX_BANDS` / `BAND_DEFAULT_COLOR` / `BAND_ALPHA_MIN` / `BAND_ALPHA_MAX` 两侧钉住；
**这一版故意没加**（单边常量，加了必红）—— `verify-bands.js` 现在反过来守着这件事
（"跨语言比对里还没有 `MAX_BANDS`"，谁提前加了那条就红）。

### 2.117 同半径的两层：**谁后画谁可见** —— 安全信息必须赢（v2.88.0）

**这是一个"绘制顺序 = 语义优先级"的坑**，而它不会报错、不会让任何静态检查变红。

盘面的**分区**（红区/`bands` 色带）与**进度弧**：

| | 半径 | 线宽 |
|---|---|---|
| 分区 | `r = min(w,h) × 0.36` | `max(1.5, r × 0.12)` |
| 进度弧 | **同一个 `r`** | **同一个 `max(1.5, r × 0.12)`** |

两层**完全重合**，所以 `ctx.stroke()` 的顺序**唯一**决定谁可见 ——
**后画的整段盖住前一个**，没有"半透明混合"这回事（默认都是不透明的）。

修前 `canvas.js` 的顺序是「第 4 步 分区 → 第 5 步 进度弧」，
于是 **值一进红区，进度弧就把红区盖掉**：

```
值 = 95（量程 0~100、红区 80~100、进度弧到 391.5°）
  重叠段 354°~388.5°  →  修前 100% accent（红区消失）
                      →  修后 100% 红区色
```

**修法**：把两步对调（分区画在进度弧**之后**）。

**为什么方向是这个**（不是"换个东西被盖住"）：

| | 是什么 | 重叠时谁赢 |
|---|---|---|
| 分区（红区） | **安全信息** —— "红线在哪 / 我现在在不在里面" | ✅ **它赢** |
| 进度弧 | **读数** —— "现在是多少" | 让位 |

而且重叠**只发生在已经进红区的那一段**：出了红区，弧在前、红区在后，两件事照样同时看得见。
"读数的最后一小段被红区盖住"和"危险指示在最危险的时刻消失"不是一个量级的事。

> ⚠️ **这会动到存量红区的像素**（重叠段由 accent 色变成红区色）。
> 这是**预期的、往正确方向**的变化。**不重叠的那些像素逐点不变** ——
> 分区的位置、线宽、颜色、透明度都没动，只是"谁在上面"变了。

**判据（`../../tools/icarui/tests/verify-spring.js` 第 20 节，像素级）**：
沿弧中心线以 1.5° 步进取样、逐点分类，钉住四条 ——
① 值进红区后重叠段 ≥90% 是红区色；② 重叠段里 **accent 像素为 0**；
③ 对照：值 = 0（弧为空）时红区整段是红的；④ **不在红区的那段弧仍然是 accent 色**
（证明只是"重叠段让位"，不是"进度弧整段没了"）。

> ⚠️ **遗留**：分区与进度弧**同半径**这个结构本身还在。
> 更彻底的做法是让红区**换一个半径**（比如略靠外）—— 那样两者**永远同时可见**，
> 不必二选一。**没做**：那会动到**所有**存量红区的**位置**（比这一版动的
> "重叠段颜色"大得多），而且要先有观感上的拍板。

### 2.118 **文件名就是 API**：四个角标的"命名镜像"（v2.88.0）

`assets/decor/corner-tl|tr|bl|br.png` 是"四角标"素材。
**用户按名字选"左上角"** —— 名字就是它的调用接口。

修前实测（自写 PNG 解码器数**四个象限各自的不透明像素**）：

| 文件 | 象限分布 `[左上,右上,左下,右下]` | 实际装的是 |
|---|---|---|
| `corner-tl.png` | `[0, 0, 0, 522]` | **右下** ❌ |
| `corner-tr.png` | `[0, 0, 522, 0]` | **左下** ❌ |
| `corner-bl.png` | `[0, 522, 0, 0]` | **右上** ❌ |
| `corner-br.png` | `[522, 0, 0, 0]` | **左上** ❌ |

**每个文件装的是对角那个角** —— 四个全错，一个不落。

**根因：双重取负。** `gen-assets-more.js` 的四角循环里
`ox = x + sx*56` 先把原点挪到一个角，紧接着 `c.rect(ox, oy, -sx*40, -sy*6)`
**又用 `-sx/-sy` 往回画** —— 两次取负 = 没取负，落点跑到对面去。

**修法**：符号表改成"`(sx,sy)` 就是墨迹所在的象限"（`-1` = 左/上，`+1` = 右/下），
名字按 `tl/tr/bl/br` 顺序一一对应：

```js
[["corner-tl", -1, -1], ["corner-tr", 1, -1], ["corner-bl", -1, 1], ["corner-br", 1, 1]]
```

修后四张各 **522** 个不透明像素，**全部落在名字那个象限**，且**只有一个象限有墨迹**。

> ⚠️ **注意"四个符号对"的顺序陷阱**：把 `[[-1,-1],[-1,1],[1,-1],[1,1]]`
> （先 `sx` 后 `sy` 的嵌套序 = **列优先**：左上/左下/右上/右下）
> **位置对位置**贴进上面那个数组**是错的** —— 名字是**行优先**（tl/tr/bl/br），
> 那样 `tr`/`bl` 会继续留在镜像位置。要么按名字顺序写正确的四对（如上），
> 要么把名字也改成 `tl/bl/tr/br` 的顺序。**这种"枚举顺序"的坑不会报错，只会静默错位。**

**为什么这算 bug 而不是风格**：按名字选"左上角"却拿到右下角，是**可证明的错**；
让**内容对上名字**是修 bug。四个角标**没有任何控件引用**
（控件 `img_corners` 引用的是另一张 `frame/frame-corners.png`），
所以修它**不会动到任何存量设计的观感**。

**判据（`../../tools/icarui/tests/verify-assets-wiring.js` 3c 节）**：四个各一条
"墨迹全在它名字那个象限" + "四个落在四个不同象限" + "每个只有一个象限有墨迹"。

> **推广**：素材的**文件名**、控件的 **key**、JSON 字段名，都是**对外契约**。
> 名字与内容不符时，"看着能用"是最坏的状态 —— 它不会红，只会让使用者按错的前提做事。
> 同类前科：§2.45（文档里的数字悄悄过期）、§2.115（写一侧漏一侧）。

### 2.119 指示灯：19 个灯的 normal/warn 态原来**逐像素共用同一张图**（v2.91.0）

**用户原话**：「指示灯需要优化、而不是全部都是一个图、联网查看相应素材、要高清」。

**先量，再改**（[../../stage/recon-v291.js](../02_验证记录/20261014_本机证据保管说明.md)，脚本统计而不是肉眼）：

```
normal 去重：{"assets/warning/lamp-off.png": 19}     ← 19 个灯**全是同一张**
warn   去重：{"assets/warning/lamp-warn.png": 19}    ← 19 个灯**全是同一张**
critical 去重：19 个里 18 张不同（coolant-warn 被 lamp_coolant / lamp_temp 共用）
```

旧灯盘是 `gen-assets.js` 里画的一个 **64×64 的彩色圆**（`lamp(col, glow, ringCol)`），
三张只差颜色。**所以拖 5 个灯到画布上，平时看到的是 5 个一模一样的圆** ——
只有严重态才认得出是哪个灯。

**修法：新增 57 张（19 类 × 3 态），一个都不动旧的**

| 项 | 内容 |
|---|---|
| 命名 | `assets/warning/lamp-<key>-<off\|warn\|crit>.png` |
| 分辨率 | **192×192**（旧 64×64 = **9 倍像素**） |
| 生成器 | `../../tools/icarui/gen-lamps.js`（新文件）—— 19 个图形各写一遍，全部用 `png.js` 的绘图原语 |
| 版权 | 形状按 **ISO 2575 的常见语义**自画几何图形；**没有下载任何第三方图片**，也没有逐点复刻官方图版 |
| 旧素材 | `lamp-off` / `lamp-warn` / `lamp-crit` **一个字都没改**（存量设计按 path 引用它们，见 §2.41） |

> ⚠️ **为什么不是 256×256**：256 实测 base64 合计 **397.8 KB**，会把内嵌总量顶到
> **1196 KB / 上限 1200 KB**（余量 4 KB —— 再加一个灯就红）。192 是 **1091 KB**，
> 留 109 KB。而 192 对"画布上 56 单位的灯"（典型显示约 112 px）已经是 1.7 倍过采样，
> 肉眼与 256 无差别。**这个账每次加灯都要重算**（见 §2.40 末尾的体积账）。

**两个自己踩出来的坑（都留在 `gen-lamps.js` 的注释里）**

1. **图形画到盘外**：19 个图形里 **14 个**超出盘半径 78 —— 最离谱的 `door` 逻辑半径
   **117**、`belt` 110。这些数字**光看代码看不出来**：`line(178,58,204,196)` 的端点
   半径就是 110，还要再加 7 的逻辑线宽。
   → 改成**机器量**（`measureGlyphs`）：把图形画到空画布上，取包围盒中心 +
   **最远像素半径**，自动缩放居中。
   ⚠️ **只按"包围盒缩到方框"是不够的**：148×148 的方框四角到中心是 104.6，仍在盘外
   （第一版就是这么错的，`door` 还剩 91.6）。
2. **图形与盘色对比不足**：warn/crit 的图形色第一版是 `#241605` / `#2A0606`，
   与盘色亮度差只有 ~40，"车门"那个图形**几乎看不见**（像素体检报它只剩 201 个墨迹像素，
   同类都是 2000+）。→ 改成 `#1A1004` / `#1A0404`（亮度差 ~90）。

**判据（`../../tools/icarui/tests/verify-v291.js` 第 ① 节 + [../../stage/probe-lamp-check.js](../02_验证记录/20261014_本机证据保管说明.md)）**

- 19 个控件在**三态下各自引用 19 张不同的图**（不是"有几张不一样"）；
- 图都来自新的 `lamp-*`；**旧的三个文件仍在磁盘上**；新灯盘实测 192×192；
- 逐张量「图形墨迹 vs 同盘不带图形的对照图」：墨迹像素数、最远半径（上限 78）、
  平均色差（≥60）；md5 去重**唯一 17 / 19**，重复的正好是刻意共用图形的
  `coolant=temp`（水温灯 / 水温报警）与 `batt=charge`（电池灯 / 充电提示）。

> ⚠️ **"按颜色猜墨迹"会静默漏判**（实测）：图形色与盘色接近时，从成品图上按色差
> 找图形会**漏掉它**。判据必须落在"**同一块盘 + 不带图形**"的对照图上
> —— 这也是 `drawPlate` / `drawLamp` 分成两个入口的原因。

### 2.120 条形轨道：**代码绘制**，`trackStyle` 字段（v2.91.0）

**用户原话**：「条形轨道：想办法以代码绘制、而不是以图片的形式添加、缩放会导致模糊」。

**现状**：28 个「条形轨道」控件**全是** `NODE_IMAGE` + 一张 256×24 的 PNG
（`gen-assets-more.js` 的 `genBars`）。拉长到 600 宽 = 位图横向拉伸 = 糊。

**⚠️ 为什么不是"加一个新节点类型 `track`"**

试过，**被跨语言守卫挡住了**：`verify-crosslang.js` 有一条
「节点类型的名字与顺序一致」，拿 `window.NODE_TYPES` 与 App 侧 `DesignNode.kt` 的
`TYPES` 逐条比。加类型就必须**同时改 App** —— 而 v2.91.0 的范围明确是「不要碰 `../../app`」。

**所以走字段**：`NODE_IMAGE` 上加 `trackStyle`。三条同时成立：

1. **节点类型表不动** → 跨语言守卫照旧绿，App 侧零改动也不炸；
2. **缺字段 = 老行为**（画那张 PNG）→ **存量设计逐像素不变**；
3. App 侧以后要跟，只要在 `NodeTreeRenderer` 里加一个分支，**不动格式版本号**。

```json
{ "id": "n1", "type": "image", "name": "代码轨道(水平)", "x": 40, "y": 40, "w": 240, "h": 16,
  "assetId": "",
  "trackStyle": { "orient": "h", "radius": 8, "inset": false, "gradient": "gloss",
                  "glow": false, "segments": 0, "ticks": 0, "band": false,
                  "fill": null, "color": null, "accent": null } }
```

| 字段 | 取值 | 缺省 | 说明 |
|---|---|---|---|
| `orient` | `"h"` / `"v"` | `"h"` | 方向（决定圆角与刻度朝向） |
| `radius` | 0..64 | 短边的一半（胶囊） | 圆角；`0` = 直角 |
| `inset` | bool | `false` | 内凹：上/左暗、下/右亮（刻进面板的槽） |
| `gradient` | `null` / `"fade"` / `"gloss"` | `null` | `fade` 沿长边淡出；`gloss` 沿短边明暗 |
| `glow` | bool | `false` | 整条发光（"这条是活的"） |
| `segments` | 0..64 | `0` | >1 时画等分格 |
| `ticks` | 0..64 | `0` | 长边上的短刻度数 |
| `band` | bool | `false` | 绿/黄/红三段色带铺底（**静态**阈值参考） |
| `fill` | 0..1 | `null` | 画一段填充到该比例；`null` = 只画轨道 |
| `color` | `#RRGGBB` / `null` | `null` | `null` = 跟随主题 `track` |
| `accent` | `#RRGGBB` / `null` | `null` | `null` = 跟随主题 `accent`（填充 / 发光 / 刻度） |

> ⚠️ **`trackStyle.band` 与仪表的 `bands` 不是一回事**（别混）：
> `bands`（§2.116）是**仪表**上的"按量程算出来的分区"，随数值与量程变；
> `trackStyle.band` 是**静态**的绿黄红三段底色，**不需要任何数据**
> —— 就是"印在条上的刻度区"（与 `bar_band3h/v` 那张素材同义，只是改成代码画、可缩放）。

**归一化在 `schema.js` 的 `normalizeTrackStyle(o, w, h)`（唯一真源）**：
`null` / 缺字段 / 空对象一律返回 **`null`**（= 老行为）；非法值**夹住或丢掉、不抛错**
（拒收存量文件比"少画一格"贵得多），但 `validate.js` 会**出声警告**。

| 文件 | 改了什么 |
|---|---|
| `js/schema.js` | `normalizeTrackStyle` / `trackUsable` / `TRACK_FIELDS` / `TRACK_ORIENTS` / `TRACK_GRADIENTS` / `MAX_TRACK_SEGMENTS` / `MAX_TRACK_TICKS` |
| `js/model.js` | `createNode`（`NODE_IMAGE` 分支）归一化；`nodeToJson` **只在非 null 时写出** |
| `js/validate.js` | `parseNode` 读回来（**与 `createNode` 同源**）；畸形值给警告不给硬错误 |
| `js/canvas.js` | `drawTrackNode()` —— `drawImageNode` 第一行分流；全部 canvas 原语 |
| `js/panels.js` | 属性面板新增「条形轨道（代码绘制）」组（开/关 + 全部字段） |
| `js/app.js` | `setTrackField` / `toggleTrackStyle`（写入都过 `normalizeTrackStyle`） |
| `js/presets.js` | 28 个 `cd_*` 控件（新分类「条形轨道(代码)」）+ `CAT_RULES` 加 `/^cd_/` |

**⚠️ 与 `bar_*`（贴图版）的关系：两批都留着**

- `bar_*`（图片）—— 存量设计的观感锚点。设计文件按 `path` 引用它们，
  删掉 = 存量设计在设备上**空白**（§2.41）。
- `cd_*`（代码）—— 新做的设计用这一批。

**为什么不是"把 `bar_trackh` 改成代码画"**：那会让**已经拖过它的设计**在重新打开后
**换一张脸**（PNG 有纹理细节，代码版是干净的几何形）。新增而不是替换，是为了
"存量设计看起来一模一样"这条硬约束。

**判据（`verify-v291.js` 第 ⑤ 节）**

- 28 个控件归到新分类；`cd_*` 的 `assetId` **为空**（不可能贴图）；
- **老图片节点导出时不写 `trackStyle`**，解析回来是 `null` → 走贴图分支；
- **"老设计 → 导出 → 导入 → 再导出"逐字节相同**（存量文件不会被改写）；
- `trackStyle` 非 null 时**逐字段往返不变**；
- 畸形值夹住 + 出声（`orient:"q"`→`h`、`segments:9999`→64、`ticks:-3`→0、
  `fill:5`→1、`gradient:"zzz"`→null、`color:"red"`→null）；
- **像素级**：画一个代码轨道，相对空白底改了 6 万多个像素；把 `trackStyle` 去掉后
  画面又差了 6 万多个像素 → 证明**绘制路径真的分流了**。

> 🔴 **App 侧待办**：现在导出带 `trackStyle` 的设计到设备上，App 不认识这个字段
> → 当普通图片节点处理（`assetId` 为空 → **画不出来**）。要跟的话：在
> `NodeTreeRenderer` 的图片分支里加一段"有 `trackStyle` 就按上表画"，
> **不动格式版本号**；老设计（没有该字段）行为完全不变。

## 三、素材（assets）

### 3.1 只存引用，不内嵌

```json
"assets": [
  { "id": "as1", "name": "碳纤维底", "kind": "background",
    "path": "assets/as1.png", "w": 1920, "h": 1080, "bytes": 240000 }
]
```

**为什么路径是相对的 `assets/as1.png`**：
设计文件与素材一起放在 `files/design/` 下，`design.json` 引用同目录的 `assets/`。
绝对路径换台设备必然失效（v1 已经踩过这个坑 —— `background.path` 只警告不报错）。

### 3.2 素材管理器里的"内置素材"从哪来

工具的分类（背景/仪表盘/指针/刻度/图标/转向灯/警告灯/汽车品牌/装饰/自定义）
只是**标签**，不预置任何图片 —— 因为：

1. 仓库里不放第三方二进制（沿用项目既有约定，见 `19_LVGL-放弃记录.md` 的同类决策）
2. 版权风险：车标、仪表盘素材绝大多数不是自由许可

工具提供的是**分类 + 拖入即用 + 缩略图**，素材由用户自己导入。
`kind` 字段决定它出现在哪个分类下。

### 3.3 ⚠️ 浏览器存储的硬约束（实测过，别绕）

工具必须**双击即用**，也就是跑在 `file://` 下。实测（无头 Edge）：

| API | `file://` 下 | 结论 |
|---|---|---|
| 经典 `<script src>` | ✅ 可用（含子目录、顺序保持；24 个 `.js` 全 200） | 可以拆多文件 |
| `localStorage` | ✅ 可用 | 用来缓存**缩略图**与界面状态 |
| `IndexedDB` | ✅ **可用**（`indexedDB.open()` 成功） | 但**没用它** —— 素材字节走内嵌 base64（见下），没必要再存一份 |
| `fetch` / `XHR` / ES module | ❌ 被 CORS 挡住 | **不许用**（约束 4） |
| `showOpenFilePicker` / `showSaveFilePicker` | 构造函数**存在**（`file://` 是 secure context）；真调用抛 `SecurityError` —— 一半是**手势限制**（`Must be handling a user gesture`），一半是不透明源 | 用 `<input type=file>` / `<a download>` |
| 按**路径**（非 data URL）加载的图画进画布 | ❌ **污染画布**，`toDataURL()` 抛 `SecurityError` | 内置素材必须内嵌 data URL（见 §「内置素材内嵌 data URL」） |

> ⚠️ **v2.90.0 用 [`../../tools/icarui/tests/probe-file-url.js`](../../tools/icarui/tests/probe-file-url.js) 把这张表逐条重测了一遍**，
> 改了上面两行：
>
> - **`IndexedDB` 原来是"❌ 被拒绝（`SecurityError`）"，实测是"✅ 可用"**。
>   结论不变（工具确实没用它），但**理由要改**：不是"不能用"，
>   而是"素材字节已经内嵌在 `builtin-data-*.js` 里了"。
>   ⚠️ 诚实标注：这是**默认 profile 的无头 Edge** 下的结果；旧结论可能是别的
>   浏览器版本或 profile 下测的。**换机器 / 换版本时重跑那条命令即可**。
> - **`showOpenFilePicker` 那行的"实际会抛"要分开看**：
>   `showSaveFilePicker()` 真调用抛的是 `SecurityError: Must be handling a user gesture`
>   —— 那是**手势限制**，不是 `file://` 限制（在有手势的路径里它是可用的）。
>   工具仍然选 `<input type=file>` / `<a download>`，但理由从"不能用"变成"更简单、无手势依赖"。
>
> 这张表的**结论一条没变**（不用 fetch/XHR、素材走内嵌 data URL 或相对路径）。
> 留这段是因为它是个教训：**"以前实测过"不等于"现在还对"** ——
> 所以每一条都该能被一条命令重跑。

**所以素材是"按相对路径引用"而不是"存进浏览器"**：

```
design.json  引用 → assets/carbon.png
                    ↑ 用户把图片放到设计文件同目录的 assets/ 下
```

- **预览**：用户选/拖入文件时，把 `File` 留在内存里 → `URL.createObjectURL(file)`
- **跨会话的缩略图**：把小图（约 64px）转成 data URL 存进 `localStorage`
  （几十 KB 量级，不污染设计文件）
- **完整图片不进设计文件**：那会让它变成几 MB 的不可读二进制块（与 §3.1 同一条理由）

> 这条约束的**好处**：工具的素材模型与 App 完全一致（都是 `assets/` 相对路径），
> 不需要"导出时把内嵌图片拆出来"这一步。

### 3.4 设计包（`.icarzip`）：设计与素材**一起走**（v2.79.0 工具侧 / App 侧正在做）

> ⚠️ **这一节是 2026-10-09 补记的**：格式是 v2.79.0 引入的，当时**漏了同步本文**
> （工具 CHANGELOG 记了，大纲没记）—— 按本文自己的规矩（文件头"格式/架构变了必须同步本文"）
> 这是欠账，现在补上。

#### 它治的是什么病

§3.3 定的是"素材按**相对路径**引用"，这在**工具**里没问题（用户把图片放在设计文件旁边）。
但在 **App 侧**出事：App 导入走 SAF **单文件**，拿不到设计文件旁边的 `assets/`，
于是 `designBaseDir` 永远是空 → **所有素材加载失败** →
由控件（素材图片）拼出来的表盘只剩空卡片。用户看到的现象是"画布不显示我做好的内容"。

App 侧 v1.20.3 加了「选素材文件夹」兜底，但那是**两步操作**，
而且用户得先知道"要把 assets 目录一起拷过去"。

#### 格式

```
<设计名>.icarzip          ← 就是 zip（**store 不压缩**），换扩展名是为了让人一眼认出来
├── design.json           ← 与「保存」写出的**逐字节相同**（走同一个 toV2Json）
├── assets/…              ← **只打包这份设计真正引用到的**素材，路径原样保留
└── manifest.json         ← icar.pack/1：格式版本 / 设计名 / 素材清单（路径 + 字节数 + CRC32）/ 导出时间
```

**包内路径 = 设计里写的相对路径**，这一条是整个方案的关键：
解压后目录结构与 `design.json` 里的引用**天然一致**，
App 侧只要把 `designBaseDir` 指到解压目录就能按原样解析，**不需要任何路径映射**。

`manifest.json` 的字段（`js/pack.js` 是权威实现）：

| 字段 | 内容 |
|---|---|
| `format` | `"icar.pack/1"` —— **包**的格式版本（与 `design.json` 的 `schema` 是两个东西） |
| `designSchema` | `"icar.ui/2"` —— 解压端拿它判断"这份 design.json 我认不认" |
| `design` | 名字 / 作者 / 描述 / 主题 / `designW` / `designH` / `scaleMode`（给人看 + 免解压预览） |
| `entry` | `"design.json"` |
| `assets` | 逐条 `{path, bytes, crc32}` —— **解压后逐条校验**，对不上就是解压失败 |
| `missing` | 引用了但没拿到字节的素材（**如实写出来**，不假装完整） |
| `counts` | 素材数 / 缺失数 / 条目数 |
| `exportedAt` | 导出时间。⚠️ **不参与可复现性承诺**（zip 条目时间戳固定 1980），只给人看 |

#### 为什么"只打引用的"，而不是把 `assets[]` 全打进去

`assets[]` 是**素材清单**，会留着用户试过又删掉的图。全打包的后果：
一个 5 个表的盘面可能带出 300 多个文件、几十 MB，而设备上真正要用的只有 12 个。

收集要**六处一个都不能漏**（漏一处的症状都是"某一处是空的"）：
`nodes[].assetId` · `nodes[].states.*.assetId`（三态是**三张不同素材**）·
`nodes[].parts[].assetId` · `parts[].children[].assetId`（递归）·
`background.path`（**不在 `assets[]` 的引用里**，最容易整个忘掉）·
**每一页**（只走 `design.nodes` 的话，非当前页的素材不进包）。

#### App 侧要做什么（**正在做，未完成**）

选一个 `.icarzip` → 解压到 `files/design/<时间戳>/` → 按 `manifest.json` 逐条校验
（`bytes` + `crc32`）→ 把 `designBaseDir` 指到解压目录 → 重新应用。

## 四、状态系统

### 4.1 为什么它比"多张图"更值得做

一个发动机故障灯在真车上有三种外观（正常/警告/严重）。若用三个独立控件表达：

- 三个控件都要手动摆到**同一个位置**，改一次位置要改三处
- 三个控件的**层级**要各自维护
- 想"严重时闪烁"还要写规则

状态系统把这三件事收进**一个节点**：

```json
{
  "id": "n9", "type": "image", "name": "发动机故障灯",
  "x": 300, "y": 40, "w": 24, "h": 24,
  "statePid": "std_0C",
  "states": {
    "normal":   { "assetId": "as_off",  "alpha": 77,  "blink": false },
    "warn":     { "assetId": "as_warn", "alpha": 255, "blink": false },
    "critical": { "assetId": "as_crit", "alpha": 255, "blink": true, "blinkMs": 200 }
  }
}
```

**位置、尺寸、层级只写一次**，三张图共用。

### 4.2 状态怎么判定

复用 `AlertPulse` 的**迟滞**语义（否则数值在阈值附近抖动会让灯乱闪）：

```
statePid 的值 → 与 warnHigh / criticalHigh 比较（带迟滞）→ normal / warn / critical
```

阈值来源，按优先级：

1. 节点自己的 `stateThresholds`（显式覆盖）
2. 该 PID 在 PID 库里的 `warnHigh` / `criticalOf()`（默认，与仪表报警同一套）

> **为什么复用而不是另起一套**：如果故障灯和仪表盘的报警用不同阈值，
> 会出现"表已经变红了、灯还是绿的"—— 那是必然会被当成 bug 的。

### 4.3 闪烁由谁驱动

`blink: true` 时由 **`GaugeTicker`**（已有的共用动画时钟）驱动，
相位与 `AlertPulse` 共用同一套时间基准 —— 不新增第二个动画驱动。
`blinkMs` 缺省 200ms（与 `AlertPulse.CRITICAL` 的方波周期一致）。

## 五、分辨率与缩放

### 5.1 问题

设计师在 PC 上按某个尺寸做图（比如 2560×1600 平板横屏），
但设备可能是 1600×2560 竖屏、或 1200×1920。

v1 的做法是**每轴独立的归一化坐标**（`x/w` 与屏宽成比例、`y/h` 与屏高成比例）——
好处是"自动铺满"，坏处是**宽高比一变就变形**：圆表被拉成椭圆。

### 5.2 方案：设计分辨率 + 缩放模式

```json
"canvas": {
  "unit": 360,
  "designW": 2560,
  "designH": 1600,
  "scaleMode": "fit"
}
```

| scaleMode | 行为 | 适用 |
|---|---|---|
| `stretch` | 每轴独立拉伸（= **v1 的行为**，默认，保证旧文件不变） | 纯仪表盘，能接受轻微变形 |
| `fit` | **等比缩放**，短边留黑边（letterbox） | 有图片素材/圆形元素，**不能变形** |
| `fill` | 等比缩放铺满，超出部分裁掉 | 背景图，宁可裁也不要黑边 |

**实现方式**：渲染时算一个统一的 `k` 与偏移 `(dx, dy)`，所有节点的像素坐标
都过一遍这个变换。这样"设计分辨率"只影响这一处换算，节点坐标语义不变。

> ⚠️ **默认必须是 `stretch`**。否则存量 `dash.json` / `design.json`
> 导入后观感会变（留黑边），用户会以为是 bug。

## 六、编辑器架构

### 6.1 为什么拆成多文件

单文件在 1500 行时还能读，加上这次 12 项功能会到 **4000+ 行**，没法维护。

**拆分的代价**：需要确认双击 `index.html` 还能用。
已实测（无头 Edge）：经典 `<script src="js/x.js">` 从 `file://` 加载**正常**，
含子目录、执行顺序也保持。只有 `type="module"` / `fetch` / `XHR` 会被 CORS 挡住 ——
所以**不用 ES module、不用 fetch**，全部用经典脚本 + 全局命名空间。

> **v2.90.0 把"双击还能用"这句话验到底了**（不再只是"脚本能加载"）：
> 新增 [`../../tools/icarui/tests/probe-file-url.js`](../../tools/icarui/tests/probe-file-url.js)，
> 逐条实测**页面加载 / 24 个 `.js` 全 200 / 素材 / 导出 JSON·PNG·`.icarzip` / 导入（对话框 + 拖放）/
> `localStorage`·`IndexedDB`** —— **20 条 OK、0 条 NO**。
> 结论：`file://` 直开**功能完整**，没有任何一条功能必须起本地服务器。
>
> **启动入口**（v2.90.0）：用户原来不知道该双击哪个文件，现在有
> `start-icarui.cmd`（主入口，默认浏览器直开 `index.html`）、
> `启动 ICarUI.cmd`（中文名别名，只 `call` 主入口）、
> `serve.cmd` + `serve.ps1`（**兜底**本地服务器：PowerShell `HttpListener` 自写，
> **不要求装 Node/Python** —— 用 `python -m http.server` / `npx serve` 等于把零安装破掉；
> 端口默认 8765、被占自动往后找；只绑 `127.0.0.1` 免得要管理员权限）。
> ⚠️ 平时**只用第一个**，服务器只在直开出问题时做对照排查。

### 6.2 文件划分

```

  start-icarui.cmd      ★ 主启动入口（v2.90.0）：双击 → 默认浏览器直开 index.html
  启动 ICarUI.cmd       中文名别名（只 call 上面那个，逻辑只有一份）
  serve.cmd             兜底：起本地服务器并打开浏览器（可传端口）
  serve.ps1             兜底服务器本体：PowerShell + HttpListener（零依赖，约 100 行）
  css/studio.css        样式
  js/schema.js          ★ 与 App 同源的常量（别名 / 样式 / CARD / FIT / 节点类型 / 状态名）
  js/model.js           节点模型：树操作、变换矩阵、序列化、**撤销栈**
  js/validate.js        ★ 校验与解析（含 v1 → v2 自动升级）
  js/presets.js         预设布局 + 「与 App 规则的差异」清单
  js/canvas.js          画布渲染 + 交互（拖动/缩放/旋转/多选/吸附/框选）
```

> **为什么合并成 7 个 js 而不是原计划的 10 个**：
> 拆得越碎，**加载顺序**与**跨文件引用**出错的机会越多 —— 而这类错误的症状

> 加载顺序有依赖，见 `index.html` 末尾的注释：
> `schema → model → validate → presets → canvas → panels → app`

## 八、不可妥协的约束

1. **v1 文件必须继续可用**。`schema: "icar.ui/1"` 仍被接受，
   解析后自动升级成 v2 的 gauge 根节点（不改用户观感）。
2. **`stretch` 是默认缩放模式**。改默认会让存量设计变形。
3. **校验规则必须与 `DesignFile.kt` 同源**，由跨语言比对脚本守着。
   两边分叉的后果是"编辑器说没问题、App 加载报错"。
4. **不引入构建步骤**。不用 ES module、不用打包器 ——
   双击 `index.html`（或 `start-icarui.cmd`）必须能用（这是这个工具的核心价值）。
   ⚠️ **这条已被逐条实测过**（v2.90.0，`tests/probe-file-url.js`），不是"应该能用"。
   ⚠️ 同理**不许要求用户装 Node / Python** —— 兜底的本地服务器也是
   PowerShell 自写的（`serve.ps1`），不是 `python -m http.server`。
5. **仓库不放第三方素材**（含车标）。分类只是标签，素材由用户导入。
6. **不新增第二个动画驱动**。状态闪烁复用 `GaugeTicker`。
7. **节点字段与 `GaugeItem` 同名**，避免出现两套词汇表。
8. **`nodes` / `pages[].nodes` 里永远不出现 `$` 引用**（v2.80.0 起工具侧强制）。
   它们是**编译产物**：由 `tokens` + `modes` + `activeMode` + `bindings` + `library`
   唯一决定，必须全是字面值。理由是 App 不认识 `$`，拿到引用串会**静默回落**成默认色
   —— 不报错、不崩，就是颜色不对，直到推上设备才发现（本项目最该避免的失效方式）。
   工具侧已把它做成**硬错误**（`validate.js`，"引用不能写在 nodes 里"）。
   ⚠️ **`nodes[].text` 上"以 `$` 开头"只是警告**（不是硬错误）：它**永远是字面值**，
   写什么显示什么。v2.80.1 曾经用 `$$` 当转义，**v2.80.2 已取消**（规格 §十二.3）——
   那是工具单方面的约定，App 原样渲染，会造成"工具里 `$100`、平板上 `$$100`"。
   详见 §2.111。
   v2.80.2 起这四个顶层键**开始写出去**（`model.js` 的 `toV2Json`），
   但**只写非空的** —— 没有变量系统的存量文件导出结果逐字节不变；App 侧一行都不用改
   （它用 `optJSONObject` / `optJSONArray` 读，未知键返回 null）。
   规格：[`23_下一步-变量模式与组件变体.md`](23_下一步-变量模式与组件变体.md) §3.1 / §4.2。

### B. 每个控件的数据契约

每条语义记录至少含稳定ID、中文名、类型、数据源/别名、单位、小数位、量程来源、阈值来源、源可用状态、支持能力、三外观映射、素材及依赖清单、默认像素目标尺寸、测试样例。样例数值/量程标为演示，不能直接作车辆安全标定。PID存在不等于设备支持，未知CAN/PID不默认启用。

1. 数值：转换单位后显示，进度按夹取后的(min,max)计算；越界可标记但不静默换量程。断连/未绑定/无效值显示无数据占位及未知，不用0、半格或上次值伪装当前值。陈旧数据需有标记；演示模式必须显式标明。
2. 状态：关闭、开启、未知为基础；提示/告警只有明确规则才出现。布尔灯使用关闭/开启，不统一强塞normal/warn/critical；数值阈值方向与源定义一致，枚举按映射。禁止用水温推断机油压力、用供电电压推断某个不存在的故障信号。关闭态暗、未知态有标记，不能只让用户靠颜色猜。
3. 报警阈值来自已有可配置规则或车辆配置；转速红区不能默认硬编码代表所有车型。色带只画分区，不改变报警判定。不自动高频闪烁；动效不是入库条件。
4. 挡位：字母/数字有明确枚举来源；未知为无数据占位，未支持时不出现在可用控件列表。G值：纵向、横向、合成量分开命名、单位一致、负值方向可验证；缺第二轴则不生成二维球。
5. 工具预览、JSON往返、App实际渲染语义一致才能标“可用”。渲染器不支持的能力先补实现/测试，或留在待实现清单，不能用预览动画掩盖。

### C. 美术与素材契约

所有生产素材重新生成，采用统一线宽、圆角、数字层级和对齐基线；同一功能的三风格有明显结构差异，不只换颜色。最小尺寸32/48/64像素检查图标识别；仪表在默认和缩小尺寸检查主读数、单位、刻度不重叠。

数值、量程刻度、进度/填充、指针位置由渲染器按数据计算；PNG只提供适合静态层的图标/盘壳/轨道，不把完整数字烘焙成盘面，也不把decor fill-h当油量动态填充。能由原生矢量/代码画的轨道、边框优先保留代码；有语义的图标用原创几何SVG源，生成引擎可读PNG及内嵌数据。源文件、导出物、透明范围、锚点、缩放方式、可重着色策略及来源说明随manifest登记。
