# ICarUI 控件重构调研与方案

日期：2026-10-18（Asia/Shanghai）
任务：`T-UI-REFACTOR-SURVEY`（**仅调研，未改任何代码**）
用户原话：「现在很多控件问题都很大、我想重构ICARUI的控件」
用户选择：六类痛点全选 + 「先调研出方案再说」

## 一、先说结论

**六类痛点全部有据可查，但它们不是六个独立问题，而是同一个根因的六个症状：**

> ICarUI 的控件体系是**「素材摆放工具」**逐步演化成**「设计工具」**的产物。
> 控件库、属性面板、数据模型三者没有共同抽象，每加一个能力就往三处各打一块补丁。

因此**单独修任何一项都会反弹**。重构必须以「控件到底是什么」这个抽象为核心，
其余五项随之收敛。

## 二、六类痛点的证据

### 2.1 控件库太臃肿 —— 证据最硬

| 分类 | 数量 | 占比 |
|---|---|---|
| 控件库条目总数 | **192** | 100% |
| 带 `pid`（能显示数据） | **37** | **19%** |
| 仅静态素材（无 pid、无 parts） | **155** | **81%** |

按前缀分布：

```
img_*   76   ← 纯图片素材
cd_*    28   ← 表盘装饰
bar_*   28
lamp_*  19   ← 警示灯（13 个无数据源，见 §2.3）
g_*     18   ← 有数据的控件
t*       8
gauge_*  6
box_*    6
```

**76 个 `img_*` 素材和 28 个 `cd_*` 装饰混在"控件库"里** —— 用户想找"能显示转速的表"，
要先翻过 104 个不会显示任何数据的图片条目。

### 2.2 属性面板太乱 —— 结构决定

| 项 | 数量 |
|---|---|
| `panels.js` 里的属性行 | **62** |
| `DesignNode`（App 侧）字段 | **57** |
| `presets.js` 行数 | 907 |
| `panels.js` 行数 | 1701 |

**57 个字段平铺在同一个面板上**，没有「常用 / 高级」分层，也没有按节点类型裁剪。
用户改一个转速表的字号，要在几十个不相关字段里找。

### 2.3 数据绑定绑了不生效 —— 两侧认知不一致

| 层 | 数量 | 说明 |
|---|---|---|
| 工具 `BUILTIN_PIDS` | 40 | 25 个 `std_*` + 9 个 `calc_*` + 4 个 `tpl_*` + 2 个 `mon_*` |
| 工具 `PID_ALIASES` | 36 | 别名 → 通道 id |
| App 内置 PID | **25** | `BuiltInPids.kt` |
| App 别名表 | 36 | `DesignFile.kt` |

**关键缺口**（`T11-ISURVEY` 已详查）：

- **13 个车辆状态灯**（`obd.abs`/`obd.tpms`/`obd.door` …）在 App 侧**没有任何数据源**
  （App 只有 `mon_turn_left`/`mon_turn_right`）。
- **4 个 `tpl_*` 厂家模板**没有标准 PID，工具自己标注「未验证」。

工具面板里能选、能放、能绑定；到 App 上**静默消失**（`DashRenderer` 只在 `built==0` 时提示）。

**这就是"绑了不生效"的完整解释：不是绑定逻辑坏了，是两侧对"什么可绑"的认知不同。**

### 2.4 性能卡顿 —— 全量重建

`app.js` 的 `refreshAll()`：

```js
if (window.syncAssetImages) window.syncAssetImages();
renderPageTabs();
if (!S.suppressPanelRender && window.renderPanels) window.renderPanels();  // ← 重建全部面板
if (window.draw) window.draw();
if (window.__ensureAnimPreview) window.__ensureAnimPreview();
```

**每次设计变更都重建「素材库 + 控件树 + 控制库」。**
代码注释自己记录了实测：*"实测 60 个控件时 8.8ms，占一次滚轮事件 17.8ms 的一半"*。

现有缓解手段是 **`suppressPanelRender` 开关**（缩放期间跳过，收尾补一次）——
这是**补丁，不是结构**。控件再多一点就兜不住。

### 2.5 外观问题 —— 素材与控件的边界模糊

19 个警示灯共用 `lamp-off`/`lamp-warn` 两张图（`docs/01_专题/27` 已记录，
用户原话：「指示灯…而不是全部都是一个图」）。

根因同 2.1：`lamp_*` 这类"控件"实际是"一张图 + 一个状态通道"的拼接，
没有统一的控件抽象去表达"一个灯应该长什么样"。

### 2.6 底层结构该重搭 —— 全局状态分散

| 文件 | 行数 | `window.*` 全局导出 |
|---|---|---|
| `app.js` | 2705 | 大量 |
| `canvas.js` | 2184 | 大量 |
| `panels.js` | 1701 | 大量 |
| `schema.js` | 1267 | **114 个** |
| `model.js` | 1150 | 46 个 |
| **合计** | **12633** | — |

**`schema.js` 一个文件导出 114 个全局符号**，同时承担：
常量、数值字段表、别名映射、内置 PID 表、归一化函数、角度计算…

所有模块通过 `window.XXX` 互相调用，**没有模块边界**。改任何一处的影响面都不可预估 ——
这正是"越加越乱"的机制。

## 三、重构方案（三档）

### 方案 A：**控件抽象层**（推荐）

**核心思想**：引入一个统一的 `Control` 抽象，把"控件是什么"变成一个对象，
而不是"预设 + 特判"。

```
Control {
  id, name, category, icon
  build(props) -> Node          // 如何生成节点树
  schema: PropSchema[]          // 这个控件有哪些属性（决定面板）
  dataSlots: DataSlot[]         // 需要哪些数据通道（决定绑定检查）
  validate(node) -> Issue[]     // 能否在设备上渲染
}
```

**三处收益是乘法关系**：

| 痛点 | 怎么解决 |
|---|---|
| 控件库臃肿 | 库按 `category` 分组；`img_*`/`cd_*` 降级为「素材」，与「控件」分开 |
| 属性面板乱 | 面板由 `schema: PropSchema[]` **自动生成**，只显示本控件真有的属性 |
| 绑定不生效 | `dataSlots` 明确声明需求；工具侧就能**提前检测**"这台设备没有该数据源" |
| 外观 | 控件自带 build 逻辑，不再靠外部拼 |
| 性能 | 面板按 `schema` 增量渲染，不再全量重建 |
| 结构 | 每个控件自包含，不再是散在 presets/panels/schema 三处的隐式约定 |

**代价**：193 个条目要逐个映射到 `Control`；预计是**大工程**（数周量级）。

### 方案 B：**渐进分层**（折中）

不动控件抽象，只做三件事：

1. **库分组**：把 155 个静态素材从「控件库」移到「素材库」（纯 UI 调整，1-2 天）
2. **面板分层**：57 个字段按「常用 8 个 / 高级 49 个」折叠（2-3 天）
3. **绑定前置检查**：工具侧加载时对照 App 别名表，把不可用通道标红（1-2 天）

**收益**：立刻解决"找不到"、"面板乱"、"绑了不生效"三个最痛的点。
**代价**：治标不治本 —— 下次加控件仍要改三处。

### 方案 C：**格式级重构**（激进）

连 `icar.ui/2` 设计文件格式一起重设计。

**不建议**：格式一变，用户已有设计全部需要迁移，App 与工具两端同时大改，
且当前格式本身**没有明显缺陷**（问题在工具实现，不在格式）。

## 四、我的建议

**分两步走**：

1. **先做方案 B**（约一周）：立刻缓解三个最痛的点，且**不改变任何设计文件格式**，
   用户已有设计零影响，风险可控。
2. **再做方案 A**（数周）：在 B 的基础上把控件抽象建起来。
   B 产出的库分组与面板分层，正好是 A 的 `category`/`PropSchema` 雏形 —— **B 是 A 的垫脚石，不是白做**。

**关键前置**：无论哪条路，都必须先补上「**工具侧与 App 侧的通道一致性检查**」——
这是当前最危险的地方（用户能绑一个设备上不存在的通道，还看不到任何警告）。

## 五、风险与边界

| 风险 | 说明 |
|---|---|
| **测试基线** | 现有 36 个 verify-* 浏览器测试套件 + 跨语言守卫。重构必然触碰基线，**只能走既有 UpdateBaseline 流程**，不能下调门槛 |
| **用户已有设计** | 方案 A/B 都不改格式，已有设计零影响；方案 C 会破坏 |
| **双端一致性** | 工具与 App 的 `icar.ui/2` 契约由 `verify-crosslang.js` 守护，重构必须保持 |
| **工作量大** | 方案 A 是数周级；当前没有排期承诺 |
| **本次未验证** | 全部结论来自**静态代码分析**，未做性能实测（`8.8ms` 是代码注释里的历史数据）、未在浏览器里逐步操作复现 |

## 六、需要你定的事

1. **选哪条路**：先 B 后 A（推荐）/ 直接 A / 只做 B / 其他
2. **优先级**：六类痛点里你最想先解决哪个（我建议先"绑定不生效"——它影响正确性，不只是体验）
3. **时间预期**：方案 A 是数周级，你能接受吗？还是先只做 B 看看效果
4. **是否允许动设计文件格式**（我建议：不动）

⚠️ 本卡**未修改任何代码**。以上方案未经批准，不激活实施。
