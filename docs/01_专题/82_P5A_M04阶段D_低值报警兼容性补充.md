## 二、旧版 App 的风险（关键）

Android 的 `DesignNode` 解析未知字段时是**忽略**（`optString` 缺省空 → `stateDir` 取不到）。

于是：

| 场景 | 旧版 App（不认 stateDir）的行为 | 是否危险 |
|---|---|---|
| 设计里 `stateDir: "low"`、`stateWarn: 11.8` | 按 **high** 判：`value >= 11.8` → 电压正常时（13.8V）**判成 warn**！ | 🔴 **危险**：会一直亮黄灯 |
| 设计里 `stateDir: "low"`、`stateWarn: 11.8`、`stateCritical: 10.5` | critical 条件 `value >= 10.5` → 电压 13.8 直接 **critical 红灯** | 🔴 **更危险** |
| 设计里只有 `stateDir: "low"`、无阈值 | 旧版回落 `def.warnHigh`（15.2）→ 电压 13.8 接近 15.2，可能误报 | 🟠 中 |

**结论**：低值报警主题在旧版 App 上会**反向报警**（正常电压亮红灯）。
这不是"功能不生效"，是**更糟的错误行为**。

## 三、导入/版本兼容检查方案

### 3.1 编辑器导出时（推荐，成本最低）

导出 `.icarzip` 时，若设计里**存在任何** `stateDir: "low"`：

1. 在 `manifest.json` 里写一个可选字段：
   ```jsonc
   "requires": { "stateDir": 1 }      // 需要 App 支持 stateDir 的最低能力版本
   ```
2. 编辑器弹出**明确警告**：
   > 这个主题用了「低值报警」。**旧版 App（不支持 `stateDir`）会反向判断**——
   > 正常电压可能显示红灯。请确认设备已升级到支持版本后再分发。

### 3.2 App 导入时

- 支持 `stateDir` 的版本：正常导入
- 不支持的版本：**无法感知**（这正是问题所在）→ 只能靠 3.1 在导出端拦住

> ⚠️ 因此**必须**在导出端做提示。指望旧版 App 自我保护是不可能的
> （它不认识这个字段，行为已经错在那里了）。

### 3.3 编辑器打开旧/新文件时

- 打开含 `stateDir` 的文件、而当前编辑器版本不认识 → 现在就会**静默丢字段**（保存后丢失）
- 本轮补：**认识该字段**（读写都支持），即使暂不实现判定，也保证**不丢数据**

## 五、阈值优先级与非法阈值校验

### 5.1 优先级（必须唯一、无歧义）

```
① 节点显式阈值（stateWarn / stateCritical）
② PID 库同方向阈值（low 方向 → warnLow；high 方向 → warnHigh）
③ 都没有 → 恒 NORMAL（不猜）
```

**方向隔离**：`low` 方向**永不**读 `warnHigh`；`high` 方向**永不**读 `warnLow`。

### 5.2 非法阈值校验（导入时给 warning，不拒收）

| 情况 | 处理 |
|---|---|
| `stateDir` 取值不是 `high`/`low` | 按 `high` 处理 + warning「未知判定方向，已按高值处理」 |
| `stateDir:"low"` 且 `stateWarn` 缺失、PID 也无 `warnLow` | 恒 NORMAL + warning「设了低值方向但没有可用阈值」 |
| `stateDir:"low"` 且 `stateCritical >= stateWarn` | warning「低值方向下 critical 应小于 warn，否则永远不会触发 critical」 |
| `stateDir:"high"` 且 `stateCritical <= stateWarn` | warning（同上，镜像）|
| `stateWarn` 超出 `[min, max]` | warning「阈值不在量程内」 |

> 原则：**能拒收的少，能出声的多** —— 与项目既有的 `normalizeBands` / `normalizeTrackStyle` 同哲学。

## 六、"不能静默宣称有效"

低值报警最容易骗人的地方：**用户以为设了，其实永远不触发**。必须防：

| # | 场景 | 要求 |
|---|---|---|
| 1 | `stateDir:"low"` 但无任何阈值 | 编辑器面板**红字提示**「当前不会报警」；App 导入时打 warning |
| 2 | 阈值方向设反（critical ≥ warn） | 同上，明确说「critical 永远不会触发」 |
| 3 | 旧版 App 打开低值主题 | 导出端警告（见 3.1）；编辑器**不能**显示"已生效" |
| 4 | 自动化测试 | **必须**有"不生效"的负面用例（断言它确实不变色），M02 的 C6 已是范例 |

---

## 七、与编辑器预览一致性

编辑器 `js/canvas.js` 的状态灯预览与 Android `NodeStateResolver` 是**两份实现**。
M03 已指出这是跨端一致性风险点。

本轮补充要求（批准后实施）：

1. **同一份判定函数**：把方向逻辑抽成 `stateRule(dir, value, warn, critical, min, max)`，
   编辑器与 Android 各自调用，**判定表逐行对齐**
2. **`verify-crosslang.js` 增加方向维度**（现在只比阈值，不比方向）
3. **测试复用**：M03 的 13 行判定矩阵 + 本轮 5 条校验，两侧都跑
