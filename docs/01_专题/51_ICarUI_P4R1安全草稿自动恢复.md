## ⚠️ 零、最重要的一条：P4R-0 的"剥离 data"建议是**错的**

P4R-0 报告曾建议：

> 草稿**不含 `data`**，只存 `path` + `id`（`canvas.js` 支持 `path` 当 URL）

**P4R-1 实测证明这会导致用户图片永久丢失：**

| 素材来源 | 刷新后 `path` 还有效吗 |
|---|---|
| 内置图片 `assets/xx.png` | ✅ 有效（仍是同一文件系统）|
| **用户拖入的图片** | ❌ **失效** |

**决定性实测**：

```
当前会话：  fetch(blobUrl) → OK status=200  url=blob:null/d3feef6d-...
刷新之后：  fetch(同一 blobUrl) → **FAIL: Failed to fetch**
```

`blob:null/xxxx` 这种 objectURL **只活在创建它的那个文档里**，刷新即失效。
除非同时存下 `data`（dataURL），否则图片**永久丢失**。

**所以本阶段实施方案 A：完整保存设计快照，含 `asset.data`。**
任务第二部分明确要求"如果图片只有 asset.data 可以恢复，则必须把它保存到 IndexedDB"。

## 二、IndexedDB 数据结构与事务设计（任务第十二部分第 2 项）

### 2.1 为什么用 IndexedDB（实测对比）

| 项 | localStorage | **IndexedDB** |
|---|---|---|
| 配额 | 5 MB | **10.7 GB**（实测 `navigator.storage.estimate`）|
| 写入 | **同步阻塞**（10.2ms）| **异步**（1.0ms）|
| 事务 | 无 | **有原子事务** |

设计里内嵌 base64：5 张素材 = 518 KB（P4R-0 实测），localStorage 完全不够。

### 2.2 ⚠️ file:// 下的可用性（任务第三关明确要求验证）

**任务警告**："当前报告使用 file:// 环境，不能默认 file:// 与 localhost 的 IndexedDB 行为完全一致。"

**实测（在项目真实运行环境 `file://` 下）**：

| 检查 | 结果 |
|---|---|
| origin | `file://` |
| `typeof indexedDB` | ✅ `object` |
| **open** | ✅ `OK` |
| **事务提交** | ✅ `COMMITTED` |
| **读回** | ✅ `{"k":"a","v":"hello"}` |
| **配额** | ✅ **10,737,419,880 字节（10.7 GB）** |

**结论：IndexedDB 在 `file://` 下完全可用。**
（注意：这是 Edge/Chromium 的行为。Firefox/Safari 在 `file://` 下可能不同 —— 见 §十二未验证。）

### 2.3 数据结构

```
数据库 icar-studio-drafts（版本 1）
├── store "drafts"  keyPath: "draftId"
│     draftId          内部草稿 ID（"draft_" + designId）
│     designId         内部设计身份（≠ design.name）
│     designName       仅用于显示
│     savedAt          最后编辑时间（ms）
│     schemaVersion    草稿格式版本 = 1
│     designJson       完整设计 JSON（含 assets.data）
│     selection        当前选择
│     nodeCount        显示用
│     assetCount       显示用
│     byteSize         显示用
│     checksum         designJson 的 FNV-1a 校验和
│     manualSavedAt    上次手动导出时间
│     complete         ★ 完成标记（true 才可恢复）
└── store "meta"  keyPath: "key"
```

### 2.4 事务设计：三层原子性保证

1. **单事务原子提交**：一次 `put` 就是一条记录，要么整条写入要么完全没写
2. **完成标记双保险**：只有 `complete === true` 的记录才算可恢复
3. **校验和**：`designJson` 被截断/篡改时能被发现

**实测验证**：

| 检查 | 结果 |
|---|---|
| 缺 `complete` | ✅ 判为"未完成写入" |
| `complete: false` | ✅ 判为"未完成写入" |
| **数据被截断** | ✅ "校验和不符（数据被截断或损坏）" |
| 非法 JSON | ✅ 检测 |
| 缺 `nodes` 数组 | ✅ "设计缺少 nodes 数组" |

### 2.5 8 种设计场景写入实测

| 场景 | 原始字节 | 写入 | 读取 | 校验 |
|---|---|---|---|---|
| 空设计 | 239 B | 44.8ms（首次开库）| 0.4ms | ✅ |
| 60 控件 | 64 KB | 2.2ms | 0.8ms | ✅ |

## 三、设计身份管理方案（任务第十二部分第 3 项）

### 3.1 为什么不依赖 `design.name`

P4R-0 实测：**同名但内容完全不同的两个设计，历史被错位加载**。
且空名字一律存成「未命名设计」，大量设计撞名。

### 3.2 方案：内部 `designId`（**不写进设计文件**）

```
designId 存在哪里？
  · 内存：DraftManager 的模块状态
  · 持久：IndexedDB 草稿记录的 designId 字段
  · **绝不进 design 对象，也不进 toV2Json 输出**
```

**关键设计**：`designId` **不挂在 `S.design` 上**，而是 `DraftManager` 模块自己的状态。
这样 `toV2Json(S.design)` 根本看不到它。

**实测验证**：

| 检查 | 结果 |
|---|---|
| `designId` 出现在导出 JSON 里 | ❌ **不出现** |
| 设计文件有 `_id` 字段 | ❌ **没有** |

### 3.3 身份生命周期

| 场景 | 处理 |
|---|---|
| 新建设计 | `replaceDesign()` → `resetDesignId()` |
| 从 JSON 导入 | 同上（都走 `replaceDesign`）|
| 刷新页面 | 新 `designId`（旧草稿靠 UI 提示恢复）|
| 恢复草稿 | `state.designId = record.designId`（落回原身份）|
| 手动另存为 | 不改身份（只是导出）|
| 撤销重做 | 不改身份 |
| 多个草稿 | 每个 designId 一个 draftId |
| **两个标签页** | 各自独立 designId → 各存各的，**不互相覆盖** |

### 3.4 同名不混淆实测

```
同名设计「同名设计」存 2 份草稿 → count: 2, distinctIds: 2  ✅
```

## 四、自动保存触发与防抖实测（任务第十二部分第 4 项）

### 4.1 设计变更入口审计

| 入口 | 是否触发草稿 | 说明 |
|---|---|---|
| 改控件属性 | ✅ | 走 `commit()` |
| 拖动 / 缩放 / 旋转 | ✅ | 走 `commit()` |
| 新增 / 删除控件 | ✅ | 走 `commit()` |
| 修改素材 | ✅ | 走 `commit()` |
| 撤销 / 重做 | ✅ | 走 `commit` 后的 markDirty |
| 导入 / 替换设计 | ✅ | 走 `replaceDesign()` |
| **选择节点** | ❌ **不触发** | 纯 UI 状态 |
| **面板折叠** | ❌ **不触发** | 纯 UI 状态 |
| **鼠标移动** | ❌ **不触发** | 纯 UI 状态 |

**实现方式**：接在 `commit()` 和 `onDragEnd()` 上 —— 它们是**所有数据变更的唯一通道**。

### 4.2 防抖参数与实测依据

**防抖间隔 = 1200 ms**，依据：

| 实测数据 | 值 |
|---|---|
| 60 控件草稿序列化 | 0.2ms |
| IndexedDB 写入 | 1.0ms（P95 3.6ms）|
| 连续打字 commit 间隔 | 约 200~400ms |

取 1200ms：比打字间隔长（避免每字符写盘），又短于用户"停下来想一想"的时间。

### 4.3 防抖有效性实测（关键数据）

```
30 次连续 commit（100ms 间隔，共 5 秒）
  → 实际保存次数 = 1 次
```

**防抖把 30 次编辑合并成 1 次写入。**

### 4.4 必须明确记录的四件事（任务第六部分）

| 项 | 值 |
|---|---|
| **用户编辑后何时触发保存** | commit 后**立即**标记 dirty，但**延迟 1200ms** 才真正写 |
| **保存何时真正完成** | 防抖到期 + IndexedDB 事务 `oncomplete`（约 1ms）|
| **连续编辑产生多少次写入** | **1 次**（30 次编辑实测）|
| **异常退出可能损失的窗口** | **最多约 1200ms + IndexedDB 落盘时间**的最近编辑 |

> **不承诺零数据丢失。** 上面就是明确的最坏情况。

### 4.5 手势结束时立即写

`onDragEnd()` 和 `endBatch()` 会调用 `flush("gesture-end")` —— 不等防抖。

## 十三、P4R-2 撤销历史跨会话恢复的前置条件（任务第十二部分第 13 项）

要恢复撤销历史，**必须先满足**这五条：

| # | 前置条件 | 当前状态 |
|---|---|---|
| 1 | **IndexedDB 落盘窗口已实测** | ❌ **未做** —— 不知道崩溃存活率 |
| 2 | **`loadUndoStack` 有合法调用点** | ❌ D-15：从未被调用；且 `init()` 里 `undo.reset()` 会覆盖 |
| 3 | **设计身份与草稿一致** | ✅ P4R-1 已建立 `designId` |
| 4 | **历史与设计强绑定** | ⏳ 需在历史记录里存 `designId`，加载时校验 |
| 5 | **草稿恢复成功才加载历史** | ⏳ 未实现（当前"只恢复设计，不恢复历史"）|

### 13.1 建议的 P4R-2 顺序

1. **先测 IndexedDB 落盘窗口**（1 天，用 P4R-0 的强制终止方法论）
2. 把撤销栈从 localStorage 迁到 IndexedDB（或保留双写）
3. 历史记录加 `designId`，加载时强校验
4. `init()` 里在 `undo.reset()` **之后**调 `loadUndoStack()`，且只在草稿恢复成功时
5. 六种历史不匹配情况按 P4R-0 §8.3 处理

### 13.2 P4R-2 **不应该**做的事

- ❌ 不要在 `init()` 里无条件调 `loadUndoStack()`（会被 `undo.reset()` 覆盖，且设计名不匹配）
- ❌ 不要用 `designName` 作为匹配判据（同名会错位）
- ❌ 不要把 A 设计的历史加载到 B 设计
