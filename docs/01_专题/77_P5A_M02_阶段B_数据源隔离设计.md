## 一、问题：M01 的注入方式破坏了来源归属

见 [76 阶段A](76_P5A_M02阶段A_数据源归属审计与基线核查.md) 第二节差异 1。
一句话：`VehicleBus.put(v)` 会 `currentOwners.remove(pidId)`，
于是「关掉真实来源」时失效不了这条 PID，留下一个**看起来还是实时**的陈旧值。

实测证据（`VehicleBusSourceSemanticsTest`，13 项全过）：

| 场景 | 行为 |
|---|---|
| `put(source,v)` → `closeSource` | 值 `ok=false`、`error="采集来源已停止"`、`value()` 返回 null ✅ |
| `put(v)` → `closeSource` | 值 **仍 `ok=true`** ❌ |
| 同 owner 重复 `openSource` | 旧来源失效，旧来源写入被拒 ✅ |
| 快速切换来源 | 旧来源迟到写入被拒（不复活）✅ |
| 关闭来源只失效它写过的 PID | ✅ |
| TTL 过期 | `value()` 返回 null，`get()` 保留原因 ✅ |

## 二、决策：为什么是「严格互斥」，而不是「优先级共存」

| 方案 | 能否证明安全 | 结论 |
|---|---|---|
| A. 模拟与真实并存，模拟优先 | ❌ 两者写同一 PID，归属在两者间跳；画面会交替闪烁 | 否决 |
| B. 真实优先，模拟仅在无真实值时写 | ❌ 需要"真实值是否存在"的额外状态机，且仍有竞态 | 否决 |
| C. **严格互斥**：开模拟前停真实轮询，真实轮询起来时模拟自动退让 | ✅ 项目既有做法，语义清晰 | **采用** |

任务原话：

> 「如果不能证明 Debug 与真实采集可以安全并存，则采取**严格互斥、默认关闭模拟**的策略。」

**依据 1（项目既有）**：`SimulatorActivity.toggle()`（`main`，v1.5.0 起）：

```kotlin
engineWasRunning = ObdController.engine.running
if (engineWasRunning) ObdController.engine.stop()   // 先停真实采集
SignalSimulator.start()                             // 再开模拟（openSource）
…
SignalSimulator.stop()                              // 关模拟 → closeSource → 正确失效
restorePolling()                                    // 再恢复真实采集
```

**依据 2（源码注释）**：`SignalSimulator` 文件头写明
「开启时会停掉 ObdEngine，否则合成值会和真实值交替写入总线，画面会来回跳」。

**依据 3（本轮实测）**：两种写法都跑了一遍，`put(v)` 版在断开场景下
`BUSD` 显示 `ok=1`（错误）；`SignalSimulator` 版显示 `ok=0 err=采集来源已停止`（正确）。

## 三、实现

### 3.1 分层

```
app/src/debug/java/com/icar/obd/sim/     ← 只有 Debug 编译
  SimScenario.kt     场景 → 目标值表（纯函数，可单测）
  SimPidSource.kt    场景 → SignalSimulator.Channel；互斥；看门狗；上下线
  SimControl.kt      adb 广播入口（enable/disable/scenario/dump）
  SimInitProvider.kt 空 ContentProvider 当钩子，首个 Activity resume 后注册广播
app/src/main/                             ← 一行未改
  SignalSimulator    既有：openSource + put(source,v) + 10Hz ticker
  VehicleBus         归属 / epoch / TTL / 失效
```

### 3.2 场景 → 通道映射

`SignalSimulator.Channel` 用 `WAVE_CONSTANT` + `min == max == 目标值`
得到固定输出（`waveAt(CONSTANT)==1` → `base = lo+(hi-lo)*1 = hi = 目标`）。

| 场景 | 通道配置 |
|---|---|
| `normal` | 车速 60 / 转速 800 / 水温 90 / 电压 14.2 / 负荷 22 / 节气门 12 |
| `accel` | 车速 140 / 转速 5500 / 负荷 85 / 节气门 80 |
| `decel` | 车速 20 / 转速 900 |
| `warmup` | 水温斜坡 20→90（`WAVE_RAMP`）|
| `alarm` | 150 / 6800 / 115（跨 warnHigh，**未到 critical**）|
| `critical` | 200 / 7400 / 170（跨自动算出的 critical）|
| `multi` | 7 个通道按不同周期（正弦/锯齿/斜坡）|
| `disconnect` | **`SignalSimulator.stop()`** → `closeSource` → 全部 `ok=false` |
| `recover` | 重新 `start()` 并给正常值 |
| `nullpid` | 目标通道 `enabled=false` + `stop→start`（只有它们保持未知）|
| `missing` | 只留 2 个通道，其余同上 |

`alarm` / `critical` 的取值**来自 `NodeStateResolver` 的实际算法**，不是编的：

```
warnAt     = pid.warnHigh
criticalAt = warnAt + (pid.maxVal - warnAt) * 0.5
  车速: 120 → 190     转速: 6500 → 7250     水温: 105 → 160
```

### 3.3 互斥与看门狗

```kotlin
fun enable(s, extra) {
    engineWasRunning = ObdController.engine.running
    if (engineWasRunning) ObdController.engine.stop()   // 1) 互斥
    SignalSimulator.rebuildFromPids()
    applyScenario(s)                                    // 2) 场景 → 通道
    SignalSimulator.start()                             // 3) openSource + put(source,v)
    if (enabled) startWatchdog()
}
fun disable() {
    stopWatchdog()
    SignalSimulator.stop()                              // 4) closeSource → 正确失效
    restoreEngineIfNeeded()                             // 5) 按需恢复真实轮询
}
```

**看门狗**：每 2 秒检查 `enabled && ObdController.engine.running`。
真实轮询被别的界面（连设备 / 切页 / 重启用 PID）拉起时，模拟**自动退让**并写
`lastYieldReason = "真实轮询已启动，模拟自动退让"`。
这样即使有第三方路径调用 `startPolling()`，也不会出现两个来源长期打架。

### 3.4 默认关闭与可见标记

- **默认关闭**：进程启动不 `start()`，必须显式 adb 广播或 `enable()`
- **可见标记**：App 既有横幅「⚠ 模拟数据（非真车）· 到「连接 → 模拟信号」关闭」
  在 `SignalSimulator.running` 时显示（`DashFragment.kt:344` 一带），本轮实测出现
- **自然失效**：`disable()` 后 `BUSD` 全部 `ok=0`，仪表回落 `--`

### 3.5 Release 隔离（需要说准）

| 内容 | 是否在 Release |
|---|---|
| `app/src/debug/**`（场景化模拟源 + adb 广播入口）| **否** |
| `SignalSimulator` / `SimulatorActivity`（v1.5.0 既有产品功能）| **是** |

所以准确表述是：**Release 不含本轮新增的 adb 广播入口与场景化模拟源**；
它仍带既有的波形发生器与「连接 → 模拟信号」界面 —— 那是产品既有能力，不在本轮范围内。

## 四、验证结果

### 4.1 JVM（`VehicleBusSourceSemanticsTest`，13 项）

覆盖任务 §B1 的 7 个问题：

| 任务问题 | 对应测试 | 结论 |
|---|---|---|
| 1 模拟值能否覆盖真实采集值 | `两个不同来源同时写同一 PID 后者归属后者` | 能覆盖 → **所以必须互斥** |
| 2 模拟值是否会取消真实采集来源归属 | `put(v) 会摘掉归属…` | **会**（M01 写法的实际危害）|
| 3 真实 OBD 断开时能否正确失效 | `put(source,v) 建立归属 关闭来源时值被标失效` | ✅ |
| 4 模拟源关闭后是否残留有效值 | `数据断开 replace 空表后 valueOf 变 null` + 关闭来源用例 | ✅ 不残留 |
| 5 Debug 模拟开启时能否同时启动真实采集 | 设计上**禁止**（enable 先停引擎；看门狗反向退让）| ✅ 互斥 |
| 6 快速切换来源是否出现过期值复活 | `快速切换来源时旧来源的写入不会复活` | ✅ 不复活 |
| 7 重复广播是否并发问题 | `重复 openSource 与 closeSource 不泄漏不崩溃`（200 轮）+ `多线程同时写不同 PID 不丢值` | ✅ |

### 4.2 模拟器实测（BUSD 总线 dump）

| 场景 | `BUSD` 输出 | 判定 |
|---|---|---|
| normal | `std_0C ok=1 v=800.0` 等 6 条 | ✅ 有值 |
| disconnect | **全部** `ok=0 err=采集来源已停止` | ✅ **正确失效**（M01 版这里全是 `ok=1`，是错的）|
| recover | `ok=1` 且值恢复 | ✅ |
| 状态灯三态 | 见阶段 C（27 断言） | ✅ |
| 子部件 | 见阶段 D（19 断言） | ✅ |

`SimPidSource` 日志确认互斥：`互斥：已停止真实轮询，改由模拟源供数`（真实轮询在跑时）。

## 五、残余风险

| # | 风险 | 说明 |

| B-R1 | 第三方代码绕过 `SimControl` 直接 `startPolling()` | 看门狗 2 秒内退让，期间可能有一次数据跳变 |
