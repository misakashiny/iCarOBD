## 一、OBD 错 PID 匹配的实际结论

### 1.1 缺陷实证（探针测量，非推测）

`ObdProtocol.matchData()` 有一条**从 v1.15.0 首个公开版本就在**的兜底分支：
「响应模式字节对得上、但 **PID 字节对不上**」时，把 respMode 之后的**全部字节**当数据返回。

探针实测 **6 个用例全部 `ok=true`**（即生成了"有效值"）：

| 输入 | 被当成 | 错误结果 |
|---|---|---|
| `41 00 BE 3F 80`（PID 支持位图）| 车速 0D | **0.0 km/h** |
| `41 0D 1A F8`（车速响应）| 转速 0C | **838.5 rpm** |
| `41 0C 1A F8`（转速响应）| 车速 0D | **12.0 km/h** |
| `41 05 7B`（水温响应）| 转速 0C | **350.75 rpm** |
| `41 00 BE 3F A8 13`（位图）| 水温 05 | **-40.0 ℃** |
| `41 20 00 00 00 00`（不支持位图）| 车速 0D | **32.0 km/h** |

**这正是任务 §三 的红线**：「不能让无法可靠归属的响应悄悄生成另一个 PID 的有效值」。
危害是仪表上显示**假数**，而用户完全无法察觉。

### 1.2 兼容性调查（为什么可以删）

既有测试的注释说兜底是为了「请求 `01 0D` 却收到 `01 00` 的**支持位图响应**」。

查调用方后确认：**位图有自己的正当通道** ——

| 调用方 | 用法 |
|---|---|
| `PidScanner` | `extractData(reply, 1, "00")` **显式请求 01 00** → 走精确匹配 |
| `ElmSession` L121 | 同上（初始化探针）|
| `CanSniffer` L249 | 同上（链路健康度）|

也就是说：**位图从来不需要兜底**。兜底唯一的实际效果就是让"请求 A 收到 B"变成假数据。

### 1.3 修复方式（最小改动）

**删除兜底分支**，并补一条**可排障的失败原因**：

```
响应 PID 不匹配：请求 0C，收到 0D（已拒绝，不产生数值）
```

这样：
- 正常车型**完全不受影响**（本来就回对了 PID）
- 请求/响应串了、或用户在编辑器里填错 PID 时，日志能**直接看出原因**
- 位图扫描（`PidScanner`）照常工作（走精确匹配）

> 遵照任务要求「不得为了所谓安全直接删除全部兼容逻辑」——
> 这里删的只是**没有正当用途**的那一条；位图的正当通道原样保留，
> 并有正向断言（A12）钉住。

### 4.1 关于 M1：为什么是"顺序验证"而不是"端到端"

任务要求：「**验证互斥钩子是否真正被调用**，以及模拟来源是否在真实来源开始写入之前退出。
**不能仅通过检查方法存在来认定无竞态**。」

本轮做不到端到端的原因（如实记录）：
- `ObdController` 是 `object`，**类初始化时**就 new 了 `Handler(Looper.getMainLooper())`
  → JVM 单测里抛 `Method getMainLooper not mocked`，无法构造
- `SimPidSource` 在 debug 源集，依赖 `android.util.Log` + `Handler` → 同样不可 JVM 测

所以 M1 的做法是：**照抄 `ObdController.startPolling()` 的真实结构**（钩子 → engine.start）
跑一遍，并断言「钩子执行那一刻，模拟已不在运行」。这验证了**顺序语义**与**退让有效性**，
但**不等于**端到端证明 `startPolling()` 真的调了钩子。

→ 已在问题清单登记 `P5A-M06-MUTEX-E2E`，建议补充 Android 仪器化测试或用 Robolectric。

## 五、连接页面实际验证

### 5.1 两轮阻塞的真正原因（终于查清）

M04/M05 都卡在"AVD 到不了 ConnectFragment"。本轮审计 `MainActivity` 找到：

```
applySystemStatusBar("dash") → setRailVisible(false)
  → navView 平移出屏幕 + alpha→0 + 最终 visibility = GONE
```

**仪表盘页会自动收起导航**，所以 uiautomator 永远找不到 `navView`。
**不是产品缺陷，是"沉浸式导航可收起"的有意设计。**

呼出导航的**既有手势**有两条（`MainActivity` L661 / L699）：
1. 双指右滑
2. **双击**（间隔 <400ms、位移 <24dp）← 本轮用这个

`adb shell input tap` 两次即可，**不需要多指模拟**。

### 5.2 验证结果（`verify-p5a06-connect.js`，6/6 通过）

| # | 用例 | 实测 |
|---|---|---|
| D1 | 未连接 | ✅ 阶段「未连接」+ 原因「未连接：还没有开始搜索设备」|
| D2 | 模拟数据运行 | ✅ 阶段「正在采集」+ 原因「**模拟数据运行中（不是真实车辆数据）**」|
| D3 | 有数据时状态 | ✅ 显示「正在采集」|
| D4 | 关闭模拟后 | ✅ 回到「未连接」，**不留假数据** |
| D5 | 权限不足 | ⏭ **环境限制**（见 5.3）|
| D6 | 切页往返 | ✅ 切到仪表盘再回来，阶段一致（未连接 → 未连接）|

**这证明阶段 B（M05）的 UI 改动真实显示在 Android 页面上**，不只是 JVM 单测通过。

### 5.3 D5 为什么没验证（如实记录）

`adb shell pm revoke <pkg> BLUETOOTH_CONNECT` 会把系统「应用信息」页推到前台，
与随后的 App 启动**互相竞争**；即使点掉一次权限对话框，App 主动请求权限时**会再弹一次**，
两次轮询之间容易被系统页抢占 → 读不到连接页。

**但「权限不足」的产品逻辑本身已被 23 条 JVM 断言覆盖**：
- `ObdLinkStatusTest` **B11**（缺权限 → `Phase.NO_PERMISSION`，`dataLive=false`）
- `ObdLinkStatusTest` **T4**（权限优先级最高，即使链路 READY 也不冒充可用）

Android 端 `ConnectFragment.hasBluetoothPermission()` 只是把这个值喂给聚合器。

→ 已登记 `P5A-M06-D5-PERMISSION-UI`，建议用仪器化测试补。

2. **`SimRealMutexTest` M10 的注释判定太松**：`substringBefore("//")` 对 KDoc 的 `*` 行无效 →
   误把 `ObdController` 注释里提到 `SimPidSource` 当成代码引用。→ 跳过整行注释。
