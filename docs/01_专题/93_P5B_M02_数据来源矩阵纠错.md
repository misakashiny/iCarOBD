## 三、修正后的数据可用性结论

### 3.1 参考图 4 里那 4 个"读不到"的字段 —— 实际是 3 种不同情况

| 字段 | 之前我的说法 | **正确说法** |
|---|---|---|
| **油温** | ❌ 需 CAN | ✅ **标准 PID `01 5C` 已定义，App 已支持**；车型是否实现**未知，需真车测** |
| **油压**（机油压力）| ❌ 需 CAN | ✅ **确实无标准 PID**，必须 CAN/DBC 或外置传感器 |
| **BOOST** | ❌ 需 CAN | ✅ **可由 MAP(`0B`) − 大气压(`33`) 派生**，App 已有 `calc_boost` |
| **Lambda** | ❌ 需 CAN | ⚠️ **标准有定义（`01 24`–`2B` 宽域 λ），但 App 未实现**；宽域车型可用，窄域车型只有开关式 `14` |

**只有「机油压力」一项真的必须厂商 CAN/DBC。** 其余三项都不该被标成"读不到"。

### 3.2 关于 `dashboard-proto.js` 的 `DataSource` 表

原表把这 5 项一律标 `src: "can"`，**不准确**。已在原型里改为五类标注
（`obd` / `obd-optional` / `calc` / `not-implemented` / `can-only`），
并在 UI 上用不同措辞区分：

| 标注 | 界面显示 | 含义 |
|---|---|---|
| `obd` | 正常读数 | 标准 PID + 已实现 |
| `obd-optional` | 读数 或 「本车未实现」 | 标准 PID，但车型可能不实现 |
| `calc` | 正常读数 | 由标准 PID 派生 |
| `not-implemented` | 「暂未实现」 | 标准有定义但 App 没做 |
| `can-only` | 「需 CAN/DBC」 | 确无标准 PID |

## 四、教训（写给自己）

**不要把"我没查到"写成"不存在"。**

- 「油温无标准 PID」是**错的** —— `01 5C` 就在项目自己的 `BuiltInPids.kt:65` 里
- 「BOOST 需 CAN」是**错的** —— MAP 就在 `0B`，项目早就有 `calc_boost`
- 正确表述应该是：**标准有定义 → 车型可能不支持 → 需要真车确认**

指令 §E 的原话是「**不得伪造不支持的车辆数据**」。同样重要的是：
**不要把支持的写成不支持** —— 那会让用户以为功能没法做，白放弃一个能力。
