## 三、通信模拟与自动化联调结果

### 3.1 关键发现：传输层抽象**早已存在**

审计第一件事就发现 `ObdTransport`（`ble/ObdTransport.kt`，42 行）已是完整接口：

```kotlin
enum class State { IDLE, SCANNING, CONNECTING, DISCOVERING, READY, CLOSED }
interface Callback { onStateChanged; onScanResult; onRx; onRawChunk }
fun startScan/stopScan/connect/disconnect/send/flushRx/isReady/describe
```

而 `ElmSession(transport: ObdTransport)` 是**纯构造注入、无 Android 依赖** →
**不需要改任何生产代码**就能做完整链路测试。

> 任务要求「优先使用已有接口；如需添加依赖注入接口，只做最小兼容扩展」
> —— 本轮**零扩展**，因为接口已经够用。

### 3.2 新增 `ObdLinkIntegrationTest`（15 项全绿）

从 `ScriptedTransport`（可编程假传输层）出发，走**真实** `ElmSession` → `ObdProtocol` → `VehicleBus`：

| # | 用例 | 覆盖的错误路径 |
|---|---|---|
| C1 | 连接成功后 PID 请求落地到 VehicleBus | 正常全链路（6888 rpm 端到端）|
| C2 | 连接被拒 | 状态→CLOSED、零发送 |
| C3 | 初始化失败 | `InitResult.ok=false` + steps 明细 |
| C4 | 响应超时 | 返回空串不抛错；parse 明确"无有效响应"|
| C5 | 空响应 / 错误响应 | `"" / "  " / "OK" / "?" / "NO DATA" / "SEARCHING..."` 全判无数据 |
| C6 | 无效响应 | 字节不足 / 非十六进制 / 错误帧 |
| C7 | 适配器中途断开 | 后续请求**立即**超时而不是挂住 |
| C8 | 重复连接 | 不产生重复发送、不泄漏 waiter |
| C9 | 重复停止 | disconnect 幂等，仍可恢复通信 |
| C10 | PID 不支持 | **「ECU 明确拒绝」与「没人回答」必须能分开** |
| C11 | 响应延迟 | 超时内拿到 / 超时外为空 |
| C12 | 多 PID 轮询 | 各自解析互不串扰 |
| C13 | 连接恢复 | 断开→重连→继续通信 |
| C14 | 数据不完整 | 截断响应不产生值 |
| C15 | 危险命令拦截 | 通信层零发送（请求安全回归）|

### 3.3 调试过程中发现的两个「我自己写错」的地方（如实记录）

1. **忘了接 transport 回调**：`ScriptedTransport.callback` 一直是 null，导致 6 个用例
   报 `expected:<...> but was:<>` 的**假失败**。真实链路由 `ObdController.wireTransportCallback()`
   负责接线，测试必须自己接 —— 已补 `wire(t, s)` 辅助函数并注释说明。
2. **rpm 期望值算错**：`41 0C 0F A0` 我以为 = 4000，实际公式是 `((A*256)+B)/4` → **1000**。
   产品是对的，是我的期望值错。

### 3.4 一个既有的容错行为（记录，不是缺陷）

`ObdProtocol.matchData` 有兜底分支（L367-371）：PID 字节对不上时，
只要响应模式字节存在就把其后全部字节当数据 —— 注释写明"部分 ECU 会回 `41 00` 之类的位图响应"。
所以 `41 0D 1A F8` 拿 `0C` 去解析**会成功**（得 834.5）。已写成显式断言固定该行为，
避免以后有人误当 bug 改掉。

## 七、修复的真实缺陷（2 个）

### 7.1 缺陷 1：比例预览比例**跨主题残留**（编辑器）

| 项 | 内容 |
|---|---|
| 现象 | 在主题 A 点了「车载宽屏」预览，然后**新建 / 导入 / 恢复草稿**，画布仍以上一个主题的比例显示 → 用户以为主题坏了 |
| 根因 | `S.previewAspect` **只在 `clearScreenPreset()` 里被清**，`replaceDesign()` 没清 |
| 修复 | 在 `replaceDesign()` 里清除（它是 新建/打开/导入/恢复草稿 的**唯一公共入口**）|
| 回归 | `verify-p5a04-preview` **B7 三条断言**（新建/导入/恢复草稿各一条），13→**16** |

### 7.2 缺陷 2：模拟退让存在 2 秒窗口（运行时互斥）

| 项 | 内容 |
|---|---|
| 现象 | 真实轮询启动后，`SimPidSource` 靠**每 2 秒**一次的看门狗才发现并退让 → 这段时间两个来源同时写同一 PID，仪表可能来回跳 |
| 根因 | 反方向（真实先起）只有轮询式看门狗，没有事件驱动 |
| 修复 | `ObdController` 新增 `onRealPollingStarting` **可空钩子**，在 `startPolling()` 的同一回合内先通知模拟退让；Debug 侧注册；**看门狗保留作兜底** |
| 为什么是钩子 | `SimPidSource` 在 debug 源集，Release 不存在；main 直接引用会让 Release 编译失败（隔离守卫硬约束）。Release 下钩子恒 null → 零成本零泄漏 |
| 效果 | 窗口从 **0~2000ms → ≈0ms**（同一次调用内）|

> **仍需诚实说明**：这消除的是「真实轮询**启动瞬间**」的窗口。
> 若未来出现「真实轮询已在跑、模拟被别处强行打开」的路径，
> `enable()` 里的 `engine.stop()` 仍是第一道闸（窗口 ≈0），看门狗是第二道。
