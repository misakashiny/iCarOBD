# 未知字段安全透传方案（P2A 风险核验 B）

日期：2026-10-18（Asia/Shanghai）
任务：`T-UI-REFACTOR-P2A` 风险核验 B
状态：**方案 + 测试样例已提交，未改 `nodeToJson`**

---

## 一、问题定义

P0.5 已实证：**现有 `nodeToJson` 是逐字段白名单，会丢弃全部未知字段。**

三层实测（设计根 / 节点 / 嵌套 `gauge`）注入的未知字段，读取→保存后**全部消失**。

风险场景：

```
新版工具（v2.92）存的文件含新字段 X
  → 旧版工具（v2.91）打开、改了个位置、保存
  → 字段 X 静默消失，用户无感知
```

这是**单向数据损坏**，且因为「保存看起来成功了」，用户永远不会发现。

---

## 二、必须先区分两类"未知字段"

这是本方案的核心。**不能一刀切保留**。

### 2.1 A 类：合法扩展字段（应当保留）

| 特征 | 例子 |
|---|---|
| 来自设计文件、由未来版本写入 | `node.futureProp`、`canvas.newScaleMode` |
| 不在编辑器内部命名约定内 | 无 `_` 或 `__` 前缀 |
| 值是可序列化的 JSON | 数字/字符串/布尔/对象/数组 |

### 2.2 B 类：编辑器内部临时数据（**不应写盘**）

实测到的内部字段（来自 `model.js`）：

| 字段 | 位置 | 用途 | 能否写盘 |
|---|---|---|---|
| `rawPid` | `model.js:65` | 用户输入的原始别名（如 `obd.rpm`），用于下拉框回显 | ⚠️ 由 `nodeToJson` **显式**写为 `pid` 别名，字段名本身不该出现 |
| `rawStatePid` | `model.js:106` | 同上，状态灯用 | ⚠️ 同上 |
| `pid`（解析后的 `std_0C`） | `model.js:64` | 内部查表用 | ❌ 不写原始 id，只写别名 |
| `__controlKey` | P1A 新增 | 标记来源控件 | ❌ 内部标记 |
| `__meta` | P2A Catalog | 分类诊断信息 | ❌ 只在目录里，不在节点上 |
| `unknown` | `StateImageView` | 运行时 UI 状态 | ❌ 运行时不进设计文件 |

**结论：带 `__` 前缀的一律排除；`raw*` 前缀的需要白名单确认。**

## 三、方案（三档，推荐 B 档）

### 方案 A：全局透传（**不推荐**）

```js
function nodeToJson(n){
  const o = Object.assign({}, n);   // 先全拷
  delete o.rawPid; ...              // 再删内部字段
}
```

**风险**：

- 内部字段一旦漏删就写盘 → 设计文件被污染（`rawPid` 进了文件，App 侧解析时多一个未知字段）
- 无法区分"未来字段"与"脏数据"
- **不可回退**：一旦有用户文件被污染，再改回来就复杂了

### 方案 B：**显式扩展位 + 安全透传**（推荐）

在设计文件里给一个**专门的扩展容器**，而不是把未知字段混进已知结构：

```json
{
  "schema": "icar.ui/2",
  "nodes": [{
    "id": "n1", "type": "gauge", "pid": "obd.rpm",
    "ext": {                     // ← 唯一允许透传的位置
      "v292": { "futureProp": 123 }
    }
  }]
}
```

**为什么这样可以**：

1. **App 侧完全不受影响** —— `DesignNode.kt` 不认 `ext`，解析时忽略（已验证：未知字段被丢弃不影响解析）
2. **旧工具打开新文件**：`ext` 是不认识的字段 → 但**只要把 `ext` 加进"已知字段"白名单并原样写回**即可
3. **可审计**：所有扩展集中在一处，不会污染已知语义

**实施要点**：

```js
// nodeToJson 里加一行（未来阶段）
if (n.ext && typeof n.ext === "object") o.ext = n.ext;

// parseNode 里加一行
ext: (o.ext && typeof o.ext === "object") ? o.ext : undefined,
```

**验收**：`ext` 往返保持；`rawPid`/`rawStatePid`/`__*` **仍然不进文件**。

### 方案 C：白名单保留（折中）

维护一份 `PASSTHROUGH_FIELDS` 表，只有列进去的未知字段才保留。

- 优点：风险最低
- 缺点：**新字段仍需要改代码**，等于没解决"向后兼容"

---

## 四、推荐：方案 B

理由：

1. **不破坏现有契约** —— App 侧无需改动（`ext` 被忽略）
2. **不需要"猜"哪些是合法字段** —— 扩展必须显式放进 `ext`
3. **不与内部字段混淆** —— `rawPid` 等仍在节点顶层，不进 `ext`，因此不会被透传

## 五、测试样例（本阶段已写，但**未接入** `nodeToJson`）

### 5.1 样例数据

```json
{
  "schema": "icar.ui/2",
  "meta": { "name": "透传测试" },
  "canvas": { "unit": 360, "designW": 2560, "designH": 1600, "scaleMode": 0 },
  "theme": "neon",
  "assets": [],
  "nodes": [
    {
      "id": "n1", "type": "gauge", "name": "转速",
      "x": 0, "y": 0, "w": 120, "h": 120,
      "pid": "obd.rpm", "style": 0, "min": 0, "max": 8000,
      "ext": { "v292": { "futureProp": 123, "nested": { "deep": [1, 2, 3] } } }
    }
  ]
}
```

### 5.2 期望行为（三个场景）

| # | 场景 | 期望 |
|---|---|---|
| T1 | `ext` 往返 | 保留，逐字段相等 |
| T2 | 节点顶层注入 `futureProp`（**不在 ext 里**） | **仍被丢弃**（这是有意的：未声明的一律丢弃，避免脏数据） |
| T3 | 节点含 `rawPid` | **不写进文件**（内部字段不泄漏） |

### 5.3 当前实测结果（未实施 = 如实记录）

| 场景 | 现状 |
|---|---|
| T1 `ext` 往返 | ❌ **丢弃**（`ext` 也是未知字段） |
| T2 顶层未知 | ❌ 丢弃 |
| T3 `rawPid` | ✅ 不泄漏（本来就白名单） |
