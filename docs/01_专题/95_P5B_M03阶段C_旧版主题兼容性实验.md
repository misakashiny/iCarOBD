## 一、为什么不用装旧版 APK

指令 §C1 说「尝试通过 Git worktree 创建隔离工作副本，从明确的旧版本提交构建 APK」。

**我构建了旧版 APK**（`D:\_p5b03_old_v1150`，独立 `GRADLE_USER_HOME`，**主工作区零污染**，
`app/build/outputs/apk/debug/app-debug.apk` 7,068,350 B）。

但发现一个**数据安全风险**：

```
新版 applicationId = com.icar.obd
旧版 applicationId = com.icar.obd     ← 相同
```

装旧版会**覆盖新版并可能丢失用户主题**。指令 §十 明确「**不覆盖用户主题**」。

**所以改用更安全、更精确的方法**：把**旧版自己的源码**在 worktree 里编译成 JVM 测试，
直接验证旧版解析逻辑。这测的是**旧版真实代码**，不是模拟。
（旧版 APK 已构建留存，如后续需要真机验证可直接使用。）

## 二、⚠️ 我纠正了自己的一个错误判断

**第一版分析（错的）**：我只看了 `DesignNode.kt` 的 `when (type)`（L346-393），
发现**没有 `else` 分支**，就断定「旧版会静默跳过未知节点」。

**实测结果推翻了这个判断**：

```

          （本版本认：gauge / image / text / group）", ...]
```

旧版在**更早的 `DesignFile.parseNodeArray`** 就做了**类型白名单校验**，
未知 type 直接**拒绝整份主题**。

**教训**：静态看代码结构不够，**必须跑起来看真实行为**。
差一点就把"旧版会静默丢数据"这个错误结论写进协议决策依据。

## 四、新旧版行为对照（关键差异）

| | 旧版 `v1.15.0` | 当前版 |
|---|---|---|
| 解析层 | **类型白名单**，未知直接报错 | **不校验**，未知照常建节点 |
| 未知节点 | 整份拒绝 | **加载成功**，渲染时跳过 |
| 提示 | `errors`（用户可见） | `BuildReport.rptUnknown`（只在诊断里）|
| 用户感知 | 「主题打不开」+ 原因 | 「打开正常」但**缺一块**（若没看诊断就不知道）|

    rec(rptUnknown, "${node.id}(${node.type})")
    null
}

## 五、版本路线评估（指令 §C3）

### 5.1 四个候选方案

| 方案 | 说明 | 实测证据支持度 |
|---|---|---|
| **A. v2 兼容增量扩展** | 在 `icar.ui/2` 里加新 type，不升版本 | ⚠️ **旧版会拒绝整份主题** |
| **B. 新增 v3，新版兼容读 v2** | `schema: "icar.ui/3"`，新版同时认 `/2` | ✅ **最安全** |
| **C. 双版本导出** | 同一设计导出 `/2`（降级版）+ `/3`（完整版） | ✅ 可行，但增加复杂度 |
| **D. 旧版静态图像降级** | 把新节点烘焙成图片供旧版看 | ⚠️ 丢失动态能力 |

### 5.2 关键实测事实（决定推荐）

1. **旧版对未知 type 是「拒绝整份 + 精确报错」，不是静默** → 用户**不会**遇到"内容少一半却不知道"
2. **旧版不改写原文件** → 用旧版打开新主题**不会损坏数据**
3. **新版目前不拒绝未知 type**，只在 `BuildReport` 记录 → **新版能读旧版主题**（向后兼容已成立）
4. **旧版只认 4 种 type**（`gauge` / `image` / `text` / `group`）

### 5.3 ⚠️ 关于 `meta.requires` 的重要结论（指令明确要求记录）

> 「旧版 App 不认识 `meta.requires` 时，它不能充当有效兼容警告。」

**实测印证**：旧版的 `DesignFile` **完全没有读取 `meta` 里的任何兼容性字段**
（`meta` 只读 `name` / `author` / `description`）。所以写 `meta.requires: ">=1.16"` 这类
字段，**旧版会完全忽略，不产生任何警告**。

**真正起作用的警告机制是「未知 type 白名单报错」** —— 这个旧版**已经有**，
而且质量已经够用。这比 `meta.requires` 可靠得多。

## 六、推荐方案（有证据）

### ✅ 推荐：**方案 B（新增 `icar.ui/3`）+ 新版继续严格读 `/2`**

**理由（每条都有实测支撑）**：

1. **旧版遇到 `/3` 会怎样？** —— 需补充测试。旧版有 schema 校验
   （`不支持的 schema：$schema（本版本认 $SCHEMA 与 $SCHEMA_V2）`），
   所以 **`/3` 会被旧版明确拒绝**，且错误信息**指向 schema 而不是逐个节点**，
   用户理解成本更低。

2. **新版读 `/2` 完全兼容** —— 当前版接受 `SCHEMA` 与 `SCHEMA_V2`，
   新增 `/3` 只是多认一个值，**不影响任何存量主题**。

3. **不需要 `meta.requires`** —— 旧版对未知 type 的白名单报错已经够用，
   而对 `/3` 的 schema 报错更早、更清楚。

4. **不需要双版本导出（方案 C）** —— 因为旧版的行为是"明确拒绝"而不是"静默降级"，
   用户能立刻知道要升级，不会误用残缺主题。

### ⚠️ 方案 A（在 `/2` 里加新 type）的问题

**技术上可行**（因为旧版是"拒绝+报错"而不是"静默丢"），但语义不干净：
- `/2` 的契约是"4 种 type"，加第 5 种等于**悄悄改了 v2 的定义**
- 违反用户此前明确的「**不得修改 `icar.ui/2` 既有字段语义**」

**所以推荐 B 而非 A。**
