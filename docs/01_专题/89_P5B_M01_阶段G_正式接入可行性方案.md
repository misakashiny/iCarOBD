## 一、现有字段是否足够

### 1.1 现状盘点

`icar.ui/2` 的 `gauge` 节现有字段（`PidModels.kt` / `schema` 一致）：

| 字段 | 语义 |
|---|---|
| `style` | 0~7 封闭枚举 |
| `pid` / `extraPids` | 主/副 PID |
| `min` / `max` | 量程 |
| `warnLow` / `warnHigh` | 阈值 |
| `cardStyle` / `ringStyle` | 卡片/环样式 |
| `parts` | 子部件（`GaugePartsView` 叠加层）|
| `bands` | 色带 |
| `neonPreset` | 霓虹调色 |

`track` 节有 `trackStyle`（fill/色带/渐变/刻度/分段/发光/纵向）。

### 1.2 结论：**不够，但缺口很窄**

| 组合仪表需要的能力 | 现有字段能否表达 | 结论 |
|---|---|---|
| 分段圆弧（段数、空隙、按段着色）| ❌ `ringStyle` 只有固定几档 | **缺** |
| 沿曲线路径的进度 | ❌ 无路径概念 | **缺** |
| 任意位置独立数值文本 | ⚠️ 只能靠 `style=1` 整块数字表 | **勉强，但布局僵** |
| 基础图形（底板/分割线/装饰）| ⚠️ 靠 `image` 贴图 | **能凑合，但糊** |
| 多色分段报警 | ⚠️ `bands` 只能用于 style 0 | **受限** |

**核心判断**：现有 8 档 style 是**封闭皮肤**，无法组合出参考图 3/4 那种布局。
但缺口**不是"字段太少"，而是"缺少可组合的几何基元"**。

## 二、哪些需要新增持久化字段

### 2.1 三个候选路线（必须先选定一条）

| 路线 | 做法 | 优点 | 缺点 | 评价 |
|---|---|---|---|---|
| **A. 继续加 `gauge.style=8,9,10…`** | 每来一种新外观加一个 style | 改动最小 | **线性膨胀**，编辑器与 App 都要加分支；组合能力永远为零 | ❌ **任务明确否定** |
| **B. 把路径塞进 `orient` 字段** | 复用既有字段承载任意复杂几何 | 零新字段 | **语义污染**，`orient` 是方向枚举；旧 App 会误解析 | ❌ **任务明确否定** |
| **C. 新增独立基元节点类型** | 新增 `arc` / `pathProgress` / `valueText` / `shape` 四种 node type | 可组合、可演进而无需加 style | 需要双端渲染器 + schema + 旧版降级 | ✅ **推荐** |

## 三、新旧 App 兼容策略

### 3.1 旧 App 打开新主题

`DesignFile.kt` 的解析特征（M05 已核实）：

```kotlin
// 未知顶层键用 optJSONObject / optJSONArray 读 → 返回 null，不报错
```

所以：
- 新节点类型对旧 App 是**未知节点** → 解析时跳过
- **风险**：`DesignFile` 若有"节点数不符就报错"的校验，会整份失败

**必须先验证**：旧版对未知 `type` 的处理是"跳过"还是"报错"。

### 3.2 推荐的三段式兼容

| 阶段 | 做法 |
|---|---|
| **1. 引入期** | 新节点只在**新版本**导出时写入；旧版打开时**跳过**并在顶部提示"此主题含 N 个新版控件，当前版本不显示" |
| **2. 过渡期** | 导出时可选"兼容模式"：把 `arc`/`pathProgress` **烘焙成图片**（`image` 节点 + 位图），旧版能看不能改 |
| **3. 成熟期** | 旧版不再维护后移除兼容代码 |

### 3.3 schema 版本策略

- **不升 `icar.ui/2` → `/3`**：新节点是**增量**，老节点语义不变
- 改为在 `meta` 里加 `requires: "1.21+"`（可选），让旧版知道"这份文件我读不全"
- 理由：升大版本会让**所有存量主题**都被判为"旧格式"，代价太大

## 四、Windows / Android 双端修改点

### 4.1 Windows（ICarUI 编辑器）

| 文件 | 改动 |
|---|---|
| `tools/icarui/js/model.js` | `createNode` 加 4 个分支；`toV2Json` / `parseDesign` 序列化 |
| `tools/icarui/js/canvas.js` | `drawNode` 分派：`drawArcNode` / `drawPathNode` / `drawValueTextNode` / `drawShapeNode` |
| `tools/icarui/js/advanced-primitives-proto.js` | **原型已写好**，去掉 `PROTO` 标记、接到 canvas.js 即可 |
| `tools/icarui/js/registry/*` | 新增 4 个控件族 + schema |
| `tools/icarui/js/ui/schema-props.js` | 4 套属性面板 |
| `tools/icarui/index.html` | 控件库目录增加 4 项 |

**工作量估计**：编辑器侧约 **1.5~2 人日**（原型已覆盖绘制逻辑，主要是接 schema 与面板）。

### 4.2 Android（App）

| 文件 | 改动 |
|---|---|
| `data/PidModels.kt`（或 `DesignFile.kt`）| 新增 4 个节点数据类 + 解析 |
| `ui/view/` | 新增 `SegmentedArcView` / `PathProgressView` / `ValueTextView` / `ShapeView` |
| `ui/dash/DashRenderer.kt` | 按 `type` 分派创建 View |
| `GaugeViewFactory.kt` | **不改**（style 语义不变）|

**关键移植点**：
- `PathProgress`：Android 用 `PathMeasure.getLength()` + `getSegment()`；**编辑器用弦长采样**（原型已实现 `SAMPLE_N=200`）
  → **两端需统一采样密度**，或把采样点数写进设计数据
- `SegmentedArc`：两端都能用 `drawArc`，几何公式（原型的 `segmentedArcLayout`）可直接照搬

**工作量估计**：Android 侧约 **2~3 人日**。

## 五、性能风险

| 风险 | 评估 | 缓解 |
|---|---|---|
| **PathProgress 采样开销** | 200 点/帧 × N 个路径节点。原型实测 320×180 单路径约 0.3ms | 缓存采样结果（路径不变就只算一次）；节点数 >8 时降采样 |
| **SegmentedArc 段数** | 36 段 = 36 次 `drawArc`。实测 <0.2ms | 段数上限 128；>64 段时改用单弧 + 遮罩 |
| **View 数量** | 组合仪表可能 20+ 节点 | 沿用现有 `DashRenderer` 的 View 复用池 |
| **内存** | 4 个新 View 类，各自 Paint 缓存 | 与 `BaseGaugeView` 同策略（`palette` 复用）|

**结论**：单节点开销可接受；**风险在节点总数**。建议正式接入时限制"单页基元节点 ≤ 24"。

## 六、模板与控件的边界

| 概念 | 定位 | 本轮原型属于哪边 |
|---|---|---|
| **控件** | 可单独拖入、有 schema 面板、可改属性 | 阶段 E 四个基元 → 将来做成控件 |
| **模板** | 一组控件的预设组合，一次插入整块 | 阶段 F 两套示例 → 将来做成模板 |
| **gauge style** | 封闭皮肤，一档一套画法 | **不再新增** |

**推荐的分层**：
```
基元控件（arc / pathProgress / valueText / shape）
        ↓ 组合
模板（"赛车环" = arc + 4×valueText + shape；"数据屏" = pathProgress + 6×valueText）
        ↓ 用户可改
用户在编辑器里自由调
```

这样 `gauge.style=8,9,10…` 就**不需要再加了** —— 新外观用基元拼。
