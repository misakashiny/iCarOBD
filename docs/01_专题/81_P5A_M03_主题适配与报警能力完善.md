## 二、拼装仪表量程改进（阶段 B）

### 2.1 审计发现的真实缺口（实证，非推测）

| # | 事实 | 证据 |
|---|---|---|
| 1 | `createNode(NODE_GAUGE, {pid:"obd.rpm"})` → `min=0, max=100`，而 PID 真实量程 **0..8000** | 探针输出 |
| 2 | `assignControlBinding`（换 PID）**无条件覆盖** `min/max` | 用户设 999~7777 → 换成 0~260 |
| 3 | parts 指针未显式绑 PID 时回落到**节点量程**(0..100) → 转速 800 早已 ≥100 → **指针钉在端点** | 阶段 D 的 M02 结论 |

### 2.2 修复 1：`createNode` 按 PID 填量程（model.js）

```js
// 调用方给了 min/max 就照用（用户/预设显式值优先），没给才查 PID 定义；
// 查不到（自定义 PID）仍回落 0..100（老行为）
const pidDef = window.BUILTIN_PIDS && window.BUILTIN_PIDS[pidId];
const defMin = pidDef && Number.isFinite(pidDef.min) ? pidDef.min : 0;
const defMax = pidDef && Number.isFinite(pidDef.max) ? pidDef.max : 100;
min: num(o.min, defMin),
max: num(o.max, defMax),
```

### 2.3 修复 2：换 PID 时**尊重用户手填量程**（data-bindings.js）

新增 `rangeWasDerived(n, oldPid)`，只有「量程是派生来的」才跟随新 PID：

| 情形 | 判定 | 结果 |
|---|---|---|
| 量程 == 旧 PID 定义（预填写入的）| 派生 → 跟随 | 0~8000 换车速 → 0~260 ✅ |
| 量程仍是 0..100 而旧 PID 不是 0..100 | 旧默认 → 跟随 | 0~100 换水温 → -40~215 ✅ |
| **用户手填 999~7777** | **不是派生 → 保留** | 换车速后仍 999~7777 ✅ |
| 旧 PID 是自定义（不在内置库）| 无从判断 → 跟随 | 已知限制，已注释说明 |

`applyPidDefaults`（面板「回填量程」按钮）仍可**强制**对齐 PID。

### 2.4 验证（16 断言，`verify-p5a03-range.js`）

B1 五个 PID 建立即正确量程；B2 显式值优先；B3 自定义 PID 回落 0..100；
B4 派生量程跟随；**B5 手填量程不被覆盖**；B6 老表 0..100 跟随；
B7 回填按钮强制；B8 Undo/Redo 还原；B9 导出→解析一致；
B10 指针角度：旧默认 0..100 时转速 800 → **405°（钉在端点）**，按 PID 0..8000 → **162°（正常）**。

### 2.5 与既有契约的关系

- **未改动** `icar.ui/2` 任何字段
- 既有套件 `verify-data-bindings`（217 断言）全绿 —— 因为它明确要求 "source range follows binding"，本轮的 `rangeWasDerived` 正是按这个既有语义实现的


## 四、低值报警兼容方案（阶段 D）——**受契约限制，本轮未实施**

### 4.1 为什么必须改契约

现有 `NodeStateResolver.select()` **只有高值判定**（`value >= warnAt`）。
不加字段想支持低值，三条路都被否掉：

| 方案 | 为什么不行 |
|---|---|
| 让 `stateWarn` 自动选方向 | **静默改语义**：旧主题 `stateWarn=105`（水温高报）在低温 20℃ 会被判成报警 |
| 回落 PID 的 `warnLow` | 同上：所有绑电压/油量的现有灯会突然开始报警 |
| 用负值表示低值 | 与既有语义冲突（水温 min=-40 合法），产生模糊优先级 |

### 4.2 提交的设计（待批准）

新增**可选**字段 `stateDir`：`"high"`（缺省=现有行为）/ `"low"`。
- `high` 方向**永远不看** `warnLow`；`low` 方向**永远不看** `warnHigh`
- 无值 / NaN / 断连 → **先走 unknown**（顺序不动）
- 缺省不写字段 → 旧文件**逐字节不变**

完整内容见 [80_P5A_M03阶段D_低值报警兼容设计与测试矩阵](80_P5A_M03阶段D_低值报警兼容设计与测试矩阵.md)：
**13 行判定矩阵 + 4 项兼容回归 + 3 项跨端一致性 + 8 处修改点 + 迁移策略**。

### 4.3 本轮做了什么

- ✅ 把「当前不支持」的事实**钉成断言**（M02 阶段 C 的 C6：电压 11.03 < warnLow 11.8 时灯仍绿）
- ✅ 完整方案与测试矩阵备好
- ⏸ **不擅自改协议**（任务明确要求）

## 五、状态灯闪烁验证（阶段 E1，10/10）

### 5.1 为什么不能靠单张截图

闪烁 = 同一区域在两个状态间来回。单张只能证明"此刻在/不在"，无法区分「在闪」与「根本不显示」。
所以做**定时连续采样**：连拍 20 张（间隔 150ms，小于半个周期），对同一灯区域算"素材像素占比"，
判据是**序列里出现 ≥2 次跨越**（证明真的在开-关之间来回）。

### 5.2 结果

| 用例 | 序列（摘要）| 判定 |
|---|---|---|
| E1-a warn 档（blinkMs=400）| `0.886, 0, 0, 0.886, ...` | ✅ 跨越 **9 次** |
| E1-b critical（blink=true）| `0, 0, 0.847, 0.847, 0, ...` | ✅ 跨越 **10 次** |
| E1-c 对照（blink=false）| `0.681 × 12`（恒定）| ✅ **正确地不闪** |
| E1-d 断开 | `0.007 × 10`（不画素材）| ✅ 未知态 |
| E1-e 恢复 | `0.662 × 12`（恒定且已画出）| ✅ 不闪 |
| E1-f 切后台再回前台 | `0,0,0,0.681,0.681,0,...` | ✅ 跨越 **9 次** |

**结论**：闪烁开关、周期、多个灯独立更新（同屏只让 `l_coolant` 闪，`l_speed` 不闪）、
断开/恢复、前后台切换后不卡在"关"那半拍 —— 全部成立。

> 中途踩的坑：第一版采到的是**上一把主题**（导航漂到 `RuleEditorActivity`，且模拟器还是**横屏**状态），
> 区域占比恒为 0.074 却看起来像"闪烁失效"。修正方式：先 `am force-stop` 重进 + 复位竖屏 +
> 核对 `settings.json` 里的设计名，才允许采样。

→ STRETCH 每轴独立缩放（形变 0.5~2.43 倍）；**FIT 三档都≈1.000，等比不变形** ✅

**T2 纵向方向**：6 张截图全部"内容高 > 宽"，方向没被搞反 ✅

### 6.2 未解决的 2 项（**如实记录，不假装通过**）
