## ⚠️ 零、必须先看这一条

**关卡 A 审计发现：`saveUndoStack()` 写进 localStorage 的撤销历史，在产品代码里从来没有被读回来。**

| 事实 | 证据 |
|---|---|
| `saveUndoStack()` 在每次 commit 时写盘 | `app.js` `commit` 分支 |
| `loadUndoStack()` **从未在启动流程中被调用** | 全库搜索：只有 `window.loadUndoStack = loadUndoStack` 赋值 + **测试套件**调用 |
| 没有设计自动保存 | 全库无 `autosave` / 自动保存实现 |
| 刷新页面后实测 | 数据**完好保留**（26627 字节），但 `loadedSteps: 0` |

**含义：这 15.8 ms/次 的同步写盘，换来的用户可见恢复能力实际为 0。**

> 本阶段按用户指示**只报告、不扩大范围** —— 未修改加载逻辑。
> 修复方案见 §十一「后续建议」。

## 一、UndoStack 完整调用链（任务第十二部分第 1 项）

```
用户操作（属性输入 / 拖动 / 按钮）
    │
    ├─ commit(fn, label, coalesceKey)          [app.js]
    │     ├─ fn()                              ← 先改模型
    │     ├─ undo.push(snapshot(), label, key) [model.js]
    │     │     ├─ 合并判定：coalesceKey === lastKey ? 替换栈顶 : 新起一条
    │     │     └─ trim()                      ← 超出 limit(100) 时 shift
    │     ├─ 【持久化判定】key !== lastPersistKey 才写盘
    │     │     └─ saveUndoStack()             ← ★ 同步 localStorage
    │     ├─ syncJson()
    │     ├─ refreshAll()                      ← P4P-1A 后约 2ms
    │     └─ updateUndoButtons()
    │
    ├─ beginBatch(label) → batch 压一条
    ├─ endBatch() → flushUndoStack()  ← 批量最终状态必须落盘
    ├─ onDragEnd() → flushUndoStack()
    │
    ├─ doUndo() → UndoStack.undo() → restore() → refreshAll()
    └─ doRedo() → UndoStack.redo() → restore() → refreshAll()
```

### 1.1 关键函数职责

| 函数 | 位置 | 职责 |
|---|---|---|
| `snapshot()` | `app.js` | `JSON.stringify({d: design, sel: selection})` → **返回字符串** |
| `UndoStack.push()` | `model.js:1466` | 合并/压栈/trim |
| `UndoStack.trim()` | `model.js:1486` | 超 `limit` 时从底部丢弃 |
| `saveUndoStack()` | `app.js:538` | 按字节预算裁剪后写 localStorage |
| `loadUndoStack()` | `app.js:565` | 读回 + 过滤坏记录 + 索引重算 |
| `flushUndoStack()` | `app.js:613` | `lastPersistKey = null` + 写盘 |
| `commit()` | `app.js:619` | 改模型 → 压栈 → 条件写盘 → 刷新 |

### 1.2 持久化常量

```js
const UNDO_KEY    = "icar-studio-undo";
const UNDO_MAX    = 40;              // 步数硬上限
const UNDO_BUDGET = 1200 * 1024;     // 字节预算 1.2 MB
```

### 1.3 localStorage 数据格式

```json
{
  "stack": [ {"state": "<JSON字符串>", "label": "<标签>"}, ... ],
  "index": 39,
  "designName": "我的设计"
}
```

**⚠️ `state` 本身是一个 JSON 字符串**（`snapshot()` 的返回值）。

**⚠️ 写入了，但从不自动加载。**

### 2.3 C：浏览器崩溃时可能丢失什么？

## 三、写盘耗时分段统计（任务第十二部分第 3 项）

### 3.1 saveUndoStack 内部拆解（60 控件 / 20 步 / 50 样本）

| 环节 | 中位数 | 最大 |
|---|---|---|
| `snapshot()` | **0.1 ms** | — |
| **`saveUndoStack` 合计** | **15.1 ms** | — |
| ├ 逐条 `JSON.stringify(entry)`（**只为量字节**）| **5.1 ms** | 7.3 |
| ├ payload `JSON.stringify` | **4.5 ms** | 10.1 |
| └ `localStorage.setItem` | **10.2 ms** | 12.5 |

**数据量：1,187,774 字节（1.19 MB）**

### 3.2 四场景对比（40 步历史）

| 节点数 | 栈深 | `saveUndoStack` med | P95 | 数据量 |
|---|---|---|---|---|
| 0 | 40 | **0.1 ms** | 0.2 | 13 KB |
| 20 | 100 | **11.2 ms** | 15.6 | 1.19 MB |
| 60 | 100 | **13.7 ms** | 19.1 | 1.19 MB |
| 120 | 100 | **12.0 ms** | 17.9 | 1.14 MB |

**规律**：
- 空设计 → 0.1ms（几乎无成本）
- **一旦有内容，立即触到 1.2MB 预算上限** → 耗时稳定在 11~14ms
- **耗时由"数据量"决定，不是"节点数"** —— 因为字节预算已经封顶

### 3.3 结论：耗时主要来自哪

| 来源 | 占比 | 能否优化 |
|---|---|---|
| **`localStorage.setItem`（同步存储）** | **约 67%** | ❌ **不能** —— 同步 API 硬成本 |
| 逐条 stringify（纯浪费） | 约 34% | ✅ **可以**（本阶段已消除） |

## 四、重复写盘机会分析（任务第十二部分第 4 项）

逐条核对任务第四部分的 6 个候选：

| # | 候选 | 实测结论 |
|---|---|---|
| 1 | 完全相同的撤销栈内容是否重复写盘 | ❌ **不存在** —— `commit` 用 `lastPersistKey` 判据 |
| 2 | 一次手势内是否多次冗余持久化 | ❌ **不存在** —— 实测拖动 10 帧写盘 **0 次** |
| 3 | `coalesceKey` 是否已避免部分写盘 | ✅ **已完全生效**（见下）|
| 4 | **`saveUndoStack` 是否存在重复序列化** | ✅ **存在** —— `entry.state` 已是字符串，却又被 `JSON.stringify(entry)` 包一层 |
| 5 | 能否减少重复计算而不改存储时机 | ✅ 可以（本阶段实施）|
| 6 | 能否在保持格式与恢复行为下减少无意义写入 | ⚠️ **没有可减少的** —— 写入时机已经最优 |

### 4.1 coalesceKey 实测（关键证据）

```
模拟一次拖动，同一 coalesceKey 连发 10 次 commit：
  拖动中写盘次数 = 0
  flush 后写盘次数 = 1
  撤销栈深度 = 1 步
```

**✅ 已有机制完整：拖动/滑块的每一帧都不写盘，只在手势结束时写一次。**

### 4.2 唯一的重复计算

```js
// 旧实现（两处序列化）
for (let i = undo.index; i >= 0; i--) {
  const one = JSON.stringify(entry);   // ① 只为了量字节，结果立刻丢掉
  ...
}
localStorage.setItem(UNDO_KEY, JSON.stringify(payload));   // ② 真正写下去的内容
```

而 `entry.state` **本来就是 `snapshot()` 返回的 JSON 字符串** —— ①相当于"把一个字符串再转义一遍"，纯白算。

## 五、实施或未实施优化的原因（任务第十二部分第 5 项）

### 5.1 ✅ 已实施：消除重复序列化（无损）

| 项 | 内容 |
|---|---|
| **改动** | 逐条 `JSON.stringify(entry)` 改为直接拼 JSON 片段 |
| **为什么无损** | 写下去的**字节完全相同**（实测 6 个边界场景 + 主场景全部 `identical === true`）|
| **收益** | payload 构建 **5.8 → 3.6 ms**；端到端 **14.6 → 11.9 ms（-18.5%）** |
| **风险** | 极低 —— 格式、key、恢复逻辑、调用时机全部未变 |

**⚠️ 实施中踩到的坑（已修）**：
第一版给 `label` 补了默认值 `"改动"`，结果写出的字节比原来多 14 个字符，
`identical` 是 `false` —— 因为 **`JSON.stringify` 会整个省略 `undefined` 属性**，而不是写成 `null`。
现在逐字段判断 `!== undefined` 才写，6 个边界场景全部字节一致。

### 5.2 ❌ 未实施：延迟写盘（任务第五部分要求）

按任务要求**先论证，不实施**：

| 方案 | 论证结论 |
|---|---|
| `requestIdleCallback` | ⚠️ **`setItem` 仍是同步 API**，只是挪了时间点，不改变"写盘瞬间卡主线程" |
| 定时/防抖写盘 | ⚠️ 引入"最长未落盘窗口"，削弱恢复保证 |
| 按手势写盘 | ✅ **已经是当前实现**（`coalesceKey` + `flushUndoStack`）|

**未实施理由**：
1. 收益上限只有 **10.2ms（setItem 硬成本）**，且必须牺牲持久化保证
2. 任务明确要求"如果改动会削弱原有恢复保证，必须先报告风险，本阶段停止实施"
3. **更重要**：既然 `loadUndoStack` 从不被调用（§零），为它牺牲写入保证毫无意义

### 5.3 ❌ 未实施：让 `loadUndoStack` 生效

属于**功能变更**（超出性能阶段），且用户已明确指示只报告不扩大范围。

## 十二、后续性能优化建议与剩余风险

### 12.1 🔴 最高优先级：撤销历史实际不可用（必须决策）

| 项 | 内容 |
|---|---|
| **现状** | `saveUndoStack` 每次 commit 写 1.19MB（15.6ms），但 `loadUndoStack` **从不被调用** |
| **用户影响** | 刷新页面后撤销历史消失；崩溃后整个设计丢失 |
| **可修复** | 在 `init()` 里调用 `loadUndoStack()`（约 20 行）|
| **但要配合** | 设计本身也需要持久化，否则名字不匹配，照样不加载 |
| **建议** | **独立开卡**（功能变更，超出性能范围）|

### 12.2 若撤销历史最终决定「不加载」

那么 `saveUndoStack` 的 15.6ms 就是**纯浪费**，可以直接停掉写盘，
`commit` 立即降到 **约 2~5ms（-70%）**。

**这是比任何微优化都大的收益，但属于产品决策，本阶段不实施。**

### 12.3 剩余风险

| # | 风险 | 级别 |
|---|---|---|
| R1 | **撤销历史写入但不加载**（本阶段发现）| **高** |
| R2 | **设计无自动保存**，崩溃即丢 | **高** |
| R3 | 真实桌面浏览器崩溃恢复未验证 | 中 |
| R4 | `setItem` 10.2ms 同步硬成本无法消除 | 中 |
| R5 | 数据量 1.19MB 已触顶 1.2MB 预算，更大设计会**静默丢步** | 中 |
| R6 | 容器 `alpha`/`w`/`h` 无视觉反馈（P4P-0 遗留）| 中 |
| R7 | `ext` 透传未实施 | 高 |

### 12.4 关于 R5 的补充

`UNDO_BUDGET = 1.2MB`，实测 40 步已经写到 **1,187,570 字节**（**99% 满**）。

再大一点的设计，`saveUndoStack` 会**从最旧的一步开始丢弃**，且**不给用户任何提示**。
这是既有设计（注释里写了"存 20 步够用"），但**实际只能存约 40 步且已触顶**。
