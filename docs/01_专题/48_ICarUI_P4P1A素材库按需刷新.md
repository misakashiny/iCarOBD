### 2.1 ⚠️ 三个「闭包变量」的坑（本阶段踩到）

`assetQuery`、`collapsed`、`panelCollapsed` 都是 `panels.js` **闭包里的 `const`/`let`**，
**外部模块（签名模块）根本访问不到**。

第一版试图读 `panelCollapsed.assets`，`typeof` 永远返回 `"undefined"` —— **折叠状态从未进入签名**。

**修法**：不试图读取闭包变量，改为在**操作入口处强制刷新**（见 §三）。

## 三、新增的失效与刷新机制

### 3.1 设计：内容签名 + 显式强制

```
renderAssets(force)
    │
    ├─ force === true ────────────────→ 强制重建（用户显式操作）
    │
    └─ force 未设
          ↓
    AssetsSignature.needRebuild()
          ├─ 首次渲染 ────────────────→ 重建
          ├─ 签名不同 ────────────────→ 重建
          ├─ 签名相同 ────────────────→ **直接 return，一个 DOM 节点都不碰**
          └─ 计算异常 ────────────────→ 重建（保守兜底，绝不漏刷）
```

### 3.2 为什么用内容签名而不是引用/长度比较

审计确认 `design.assets` 是**原地 push** 的（6 处），**数组引用永远不变**，
且"删一个加一个"时**长度也不变**。

实测验证（P4P-1A 套件）：

```
删+加（长度不变，内容变）  ✅ 重建
```

**引用/长度比较会漏掉这种情况，内容签名不会。**

### 3.3 签名覆盖的 12 类场景（任务第五部分逐条）

| # | 场景 | 实测 |
|---|---|---|
| 1 | 新增素材 | ✅ 重建 |
| 2 | 删除素材 | ✅ 重建 |
| 3 | 素材重命名 | ✅ 重建 |
| 4 | 修改素材分类 | ✅ 重建 |
| 5 | 修改素材路径 | ✅ 重建 |
| 6 | 导入新设计 | ✅ 重建 |
| 7 | 新建/切换设计 | ✅ 重建 |
| 8 | **撤销/重做导致素材变化** | ✅ **都重建** |
| 9 | 搜索和分类筛选变化 | ✅ 强制重建 |
| 10 | 内置素材列表变化 | ✅ 重建 |
| 11 | **节点引用状态变化** | ✅（`havePath` 来自 `design.assets`，含在签名内）|
| 12 | 其它（自定义控件/内置控件变化）| ✅ 重建 |

**12/12 全部覆盖，无一漏刷。**

### 3.4 保守兜底

`needRebuild()` 内部**自己 try/catch**（不只是 `compute` 里）：

```js
let sig;
try { sig = API.compute(); }
catch (e) { return { need: true, reason: "signature-error" }; }
```

`markRendered()` 同样 try/catch，失败时把 `lastSignature` 置 null → 下次必然重建。

**实测**：注入 `compute` 抛异常后，`refreshAll` 仍能正常完成且**强制重建**。

> 这个兜底是本阶段**修了两次**才对的：第一版只在 `compute` 里 catch，
> 但异常从 `needRebuild` 的 `API.compute()` 调用点冒出来，中断了整个面板渲染。

## 十二、P4P-1B 撤销栈写盘优化的独立建议

### 12.1 现状

| 项 | 实测 |
|---|---|
| `saveUndoStack()` 中位数 | **18.3 ms** |
| P95 | 21.9 ms |
| 占剩余 commit 耗时 | **约 95%** |

**这是当前 `commit` 的**唯一**大额开销。**

### 12.2 建议方案（三选一，需独立评估）

| 方案 | 预计收益 | 复杂度 | 风险 |
|---|---|---|---|
| **(a) 用 `requestIdleCallback` 延迟写盘** | 18.3 → ~0（移到空闲）| 低 | 中（页面关闭时可能丢最后一步）|
| **(b) 只在手势结束时写**（用已有 `flushUndoStack`）| 18.3 → ~0（连续操作时）| 中 | 低（P4A.1 已有该机制）|
| **(c) 压缩快照**（只存 diff 而非全量）| 18.3 → 约 3~5 | 高 | 中（恢复逻辑要重写）|

### 12.3 建议优先 (b)

理由：

1. **P4A.1 已经实现了 `flushUndoStack()`** 和 `coalesceKey` 机制 —— 基础设施现成
2. 源码注释已写：「合并序列里只落盘第一步」—— 说明设计意图本就是**按手势写盘**，不是每帧
3. 风险最低：手势结束时写，与用户感知一致

### 12.4 P4P-1B 必须先验证的事

| 项 | 原因 |
|---|---|
| **崩溃恢复**：浏览器强制关闭后，撤销栈还能恢复多少步 | 延迟写盘会丢最后 N 步 |
| **`beforeunload` 是否可靠** | 现代浏览器对同步 IO 有限制 |
| **连续快速编辑（每秒 10 次）** | 防抖策略要覆盖 |

### 12.5 P4P-1B 的验收建议

| 项 | 目标 |
|---|---|
| `commit` 中位数 | 17.8 → **< 5 ms** |
| 撤销栈持久化 | 刷新/重载后步数与内存一致 |
| 崩溃模拟 | 最多丢失最后 1 步（可接受）|
| 回归 | 51 套件全过，断言数不减 |

### 13.1 性能测试与功能测试分离（任务第十部分要求）

- **功能套件**（`verify-p4p1a-assets-refresh.js`）：只测**重建次数**这个确定性指标，

**CI 中不会因机器慢而红。**
