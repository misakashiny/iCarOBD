## 三、实施内容

允许修改范围（严格白名单，实际改动仅 2 文件）：

### 1. `app/src/main/java/com/icar/obd/obd/FrameMonitor.kt`

- 新增 `MONITOR_SOURCE_OWNER`：监听通道固定 owner。`VehicleBus.openSource(owner)` 对同一 owner 会**自动关闭旧来源并分配递增 epoch**，天然满足"同通道新一轮取代旧一轮"。
- 新增 `monitorSource: VehicleBus.Source?`（`@Volatile`）与 `closeMonitorSource()`（**幂等**，只关当前挂着的那一个）。
- `start()`：在 `running = true; busy = true; val generation = ++epoch` 之后**先开新来源，再关旧的残留来源** —— 旧来源的 close 只会失效它自己那一轮拥有的 PID，不会结束刚开的新来源。
- `feedLine()`：由无来源的 `VehicleBus.put(PidValue(...))` 改为 `VehicleBus.put(src, PidValue(...))`；`put` 对已关闭来源返回 `false`，此时 `continue` 丢弃该帧 —— 收尾后到达的晚到帧**不能**再写当前值/历史。
- `stop()`：
  - 正常/断连收尾路径在 `rawMode=false` 与回调摘除**之后**调用 `closeMonitorSource()`（先断流再失效，避免收尾期间晚到帧写回）。
  - `if (!running) return` 分支改为**兜底调用** `closeMonitorSource()`，覆盖"未在运行但来源仍挂着"的情形。
- 准备失败路径（`onFailure`）同样调用 `closeMonitorSource()`，避免"开过又失败"留下残留 owner。

### 2. `app/src/test/java/com/icar/obd/obd/FrameMonitorLifecycleTest.kt`

- 新增 `settleStop()`：`stop()` 后**等待 `!FrameMonitor.active`**（最多 3 s），`@Before`/`@After` 与各用例停源均改用它 —— 修复 §二 所述整例间污染。
- 用例 3 补强断言：其他来源接管同 PID 后停止监听，该值必须**仍为 99 且 `ok=true`**（`monitor stop must not clobber another source's current value`）。
- 用例 1、2 断言与语义**未放松、未删除、未跳过**。

### 未修改

`VehicleBus.kt` 未改 —— 现有 `Source` / `openSource` / `closeSource` / `put(source,…)` / `sourceActive` 已完整满足需求，`closeLocked()` 本身即实现"置 `ok=false`、保留 history、跳过已被其他来源接管的 PID"。
未触碰 Controller、其他来源业务、协议/过滤/信号定义/JSON/UI、构建配置。

### 5. 设备上**未能**验证的关键项（不得宣称已验）

**常驻监听停源的真实路径本轮无法在设备上走通**，原因是硬条件缺失：

- `FrameMonitor.start()` 第 244 行硬性要求 `runtime.connected`，未连适配器时直接 `AppLog.w("设备未就绪，无法开启常驻监听")` 并 `return`。
- `oncar-check` 实测判定：**"还没连上适配器"**；日志无 GATT 表、`TX=0 RX=0`、无"初始化完成"。
- 本机 `files/config/pids.json` 为 `[]`、`enabled.json` 为 `{}`，设备上**没有已配置的监听型 PID**（内置 `mon_turn_left`/`mon_turn_right` 归属 `0x09A` 广播帧，需进入「CAN 探测」页开启常驻监听，而开启又以连接为前提）。

因此本轮设备侧只证明到：**新包可构建、可安装、可启动、数据完好、无崩溃/ANR、仪表盘正常渲染**。**"停止监听后转向灯信号变为未知"这一本卡核心行为未在设备上验证**，须连接真实 ELM327 适配器后另开授权执行。不将"装得上、跑得起来"表述为停源修复已通过设备验收。
