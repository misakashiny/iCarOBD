### 3.3 关键判断：**这 16 个不是"补个别名"能解决的**

分两类，性质完全不同：

**类 A：`tpl_*` 厂家模板（3 个）**

工具侧自己就标注为「厂家模板（未验证）」，`schema.js:1511` 起：

```
"tpl_oilPressure": { name: "示例-机油压力", unit: "Bar", g: "厂家模板（未验证）" }
```

**它们本来就没有对应的标准 OBD PID** —— 是靠厂家扩展（Mode 22 之类）才拿得到。
App 解析不到**是正确行为**，硬给一个假别名反而是错的。

**类 B：车辆状态灯（13 个）**

`obd.abs`、`obd.tpms`、`obd.door` 这些**不是 OBD 标准 PID**，
标准 OBD 不提供"ABS 灯亮不亮"。它们要靠 **CAN 监听**（`mon_*` 通道）。

实测 App 侧只有两个 `mon_` 来源：

```
"mon_turn_left"
"mon_turn_right"
```

**13 个灯在 App 侧根本没有数据源** —— 不是别名缺失，是**数据不存在**。

### 3.4 用户实际会看到什么

`NodeTreeRenderer` 对解析不到的节点：**静默跳过**，但会记进 `BuildReport`。

而 `DashRenderer.kt:236` 的规则是：

```kotlin
if (built == 0) { emptyView.text = v2EmptyReason(rpt); emptyView.visibility = VISIBLE }
else { emptyView.visibility = View.GONE }
```

**只有"一个都没画出来"时才提示。** 所以：

| 场景 | 用户看到 |
|---|---|
| 设计里全是解析不到的节点 | ✅ 显示"这套设计渲染不出任何东西 · N 个节点绑的通道不存在" |
| 设计里**既有能画的、也有画不出的** | ❌ **画不出的部分静默消失，一个字提示都没有** |

**后者才是常态**：用户拖一个 ABS 灯 + 几个正常表，那个灯就凭空不见了，只剩日志里一行 warning。

## 四、若要推进，三种做法的取舍

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 把"部分节点画不出"变成**看得见的提示**：`built > 0` 但有 `skippedNoPid` 时，在画布角落显示一条小提示或让用户能查到 | 不造假数据；纯本地可验证 |
| B | 给 13 个灯在 App 侧加 `mon_*` 空通道 | **只是把"缺"换成"空"** —— 没有真实数据来源，灯永远不亮。会误导用户以为"车没问题" |
| C | 给 `tpl_*` 补假别名 | ❌ **明确错误**：伪造厂家扩展 PID，违背项目"不造假数据"取向 |

**方案 B 尤其危险**：19 个警示灯共用一张图的问题（`27_下一步` 专题已记录）之外，
再叠一层"有通道但永远无值"，用户更难分辨是"车没故障"还是"读不到"。
