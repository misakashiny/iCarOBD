# T-App-A2-MAF0：油耗派生链的合法 0 值语义修复

日期：2026-10-18（Asia/Shanghai）
任务：`T-App-A2-MAF0`（问题清单 `App-A2 / P1` 的第一项）

## 一、用户视角：修的是什么

**仪表上的油耗数字可能算错。**

- 车明明在**滑行/熄火断油**（没烧油），屏幕却显示 `--`（以为读不到）
- 更糟：车明明没烧油，屏幕却显示一个**看起来很正常**的油耗数字

第二件事用户几乎不可能发现——因为那个数字"看着挺合理"。

问题清单原文（第 37 行）：

> `| App-A2 / P1 | MAF估算、015E合法0优先级及单位/物理量正确性 | 按原审查表建立正式生产回归；历史G力重复换算已修，不重复误标未修 |`

## 二、缺陷定位（代码级）

`app/src/main/java/com/icar/obd/obd/VehicleBus.kt` 的 `Derived.computeAll()`：

```kotlin
// 修复前
val fuelSource = fuelRate?.takeIf { it.value > 0f } ?: maf?.takeIf { it.value > 0.5f }
```

而同文件的取值入口语义是：

```kotlin
private fun input(readings: Map<String, PidValue>, id: String): PidValue? =
    readings[id]?.takeIf { it.ok && it.value.isFinite() }
```

**`input()` 已经认定 0 是合法值**，但紧跟着的 `takeIf { > 0 }` 又把它当成"没读到"丢掉。
两层判据自相矛盾。

### 三种真实场景的后果

| 场景 | 物理含义 | 修复前实际行为 |
|---|---|---|
| `015E = 0`，MAF 不可用 | 滑行断油，真没烧油 | 落到 `null` → `calc_lh` 未知 → 显示 `--` |
| `015E = 0` 且 `MAF = 3 g/s` | 同上，且 015E 是权威读数 | **丢掉 0 → 改用 MAF 推算 ≈ 8.4 L/h** → 凭空造油耗 → **累计用油虚增** |
| `MAF = 0`，无 015E | 柴油/电动化滑行，0 进气 ⇔ 0 燃油 | 落到 `null` → 显示 `--` |

`MAF` 的 `> 0.5f` 是同一类问题。

## 三、修复

**判据统一为：只要 `input()` 认为有效（`ok` 且有限）就用它，包括 0。**

```kotlin
// 修复后
val fuelSource = fuelRate ?: maf
```

核心原则：**"失效"与"0"是两件事** ——
失效由 `ok=false` 表达（超时、断线、解析失败），**不该靠数值阈值去猜**。

### 4.2 用例清单

| # | 用例 | 守什么 |
|---|---|---|
| 1 | `015E 合法零且无 MAF 时 calc_lh 必须是有效的 0` | 0 不能变成未知 |
| 2 | `015E 为零时不得改用 MAF 推算造出油耗` | **本卡最重要**：015E 优先，不许凭空造油耗 |
| 3 | `MAF 合法零且无 015E 时 calc_lh 必须是有效的 0` | MAF 的 0 同样合法 |
| 4 | `015E 不可用时仍按 MAF 推算` | **不回归**：车不支持 01 5E 时的唯一来源 |
| 5 | `015E 失效时视为不可用并回落到 MAF` | **0 ≠ 失效**：`ok=false` 才是失效，此时不能当 0 |
| 6 | `015E 与 MAF 都不可用时 calc_lh 保持未知` | 不能默认成 0 |
| 7 | `015E 为非有限值时视为不可用` | NaN 不能参与计算 |
| 8 | `015E 为零时下游瞬时油耗是有效的 0` | 修复要能流到下游（`calc_l100`） |

## 五、明确未做（本卡边界）

1. **换算系数未裁决**：`G_S_TO_L_H = 3.6 / GAS_DENSITY` 的物理正确性**不动**。
   问题清单原文里还有"单位/物理量正确性"，本轮只修**可确定的 0 值语义缺陷**；
   系数是否正确需要独立证据（查 PID 标准或真车对比），本卡无权凭猜测改。
2. **其它派生分支未动**：`calc_l100` 的车速阈值、`calc_boost`、`calc_range`、
   `integrateDistance` 的积分口径均保持原样。
3. **未在真车/适配器上验证**：本卡只做本地 JVM。真车油耗读数须另开设备/车辆授权卡。
4. **`PidMerge` / `PidDedup` 未动**：它们只影响显示合并，不影响数值语义。

## 六、影响面

- 改动：`VehicleBus.kt` 的 `computeAll()` 中燃油来源选择（**删掉两个错误的阈值判据**）+ 新增测试。
- 用户可感知的变化：滑行/断油时油耗显示 `0` 而不是 `--`；不再出现"没烧油却有油耗"。
- **不会**改变：正常行驶时的油耗数值（此时 015E 和 MAF 都 > 0，判据改动无效）。
