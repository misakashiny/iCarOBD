## 阶段 A：OBD 响应归属安全（最高优先级）—— **发现并修复严重缺陷**

### 缺陷实证

`ObdProtocol.matchData()` 有一条**从 v1.15.0 就在**的兜底分支：
响应模式字节对得上、**PID 字节对不上**时，把 respMode 之后**全部字节**当数据。

探针实测 **6/6 全部 `ok=true`**：

| 输入 | 当成 | 错误值 |
|---|---|---|
| `41 00 BE 3F 80`（位图）| 车速 | **0.0 km/h** |
| `41 0D 1A F8` | 转速 | **838.5 rpm** |
| `41 0C 1A F8` | 车速 | **12.0 km/h** |
| `41 05 7B` | 转速 | **350.75 rpm** |
| `41 00 BE 3F A8 13` | 水温 | **-40.0 ℃** |
| `41 20 00 00 00 00` | 车速 | **32.0 km/h** |

即「无法可靠归属的响应悄悄生成另一个 PID 的有效值」—— 这正是任务红线。

### 兼容性调查（为什么可以删）

既有测试说兜底是为了「请求 01 0D 收到 01 00 位图」。但查调用方：
`PidScanner` / `ElmSession` / `CanSniffer` **都是显式 `extractData(reply, 1, "00")` 请求 01 00**，
走精确匹配，**不依赖兜底**。→ 兜底没有正当用途。

### 修复

删除兜底 + 补可排障原因：

```
响应 PID 不匹配：请求 0C，收到 0D（已拒绝，不产生数值）
```

位图的正当通道（`PidScanner` 显式请求 01 00）**原样保留**，有正向断言 A12 钉住。

### 新增 `ObdAttributionTest`（17 项：12 正向 + 5 负向）

覆盖任务 §三 的 12 项：正常匹配 / 010C↔41 0D / 010D↔41 0C / 错误服务模式 /
缺 PID 字节 / 报文截断 / 多帧 / 多 ECU / 带不带 Header / NO DATA / 延迟混入 / 位图兼容。

### 修复的旧断言（**方向反转，不是删**）

- `ObdProtocolTest`：「PID 对不上走兜底」→ **「拒绝归属」** + 「显式 01 00 仍正常」
- `ObdLinkIntegrationTest` C6：「已知容错 ok=true」→ **「错 PID 不得生成转速值 ok=false」**

## 阶段 D：连接页实际验证（**两轮阻塞已解除**）

### 真正原因（终于查清）

`applySystemStatusBar("dash")` → `setRailVisible(false)` → `navView` 平移出屏幕+alpha0+**GONE**。
**仪表盘页会自动收起导航** → uiautomator 永远找不到它。

**不是产品缺陷，是"沉浸式导航可收起"的有意设计。**

呼出导航的既有手势有两条：双指右滑 / **双击**（<400ms、位移<24dp）→ 本轮用双击。

两次轮询间被系统页抢占。产品逻辑由 `ObdLinkStatusTest` **B11/T4** 覆盖。
已登记 `P5A-M06-D5-PERMISSION-UI`。
