## 二、缺陷定位

`app/src/main/java/com/icar/obd/ui/view/MultiValueGaugeView.kt` 的 `drawCell()`：

```kotlin
val labelSize = cellH * 0.19f
val valueSize = cellH * 0.44f
val unitSize  = cellH * 0.17f

canvas.drawText(label, cx, top + labelSize, labelPaint)
val valueBaseline = top + labelSize + valueSize * 1.02f
```

### 两层问题

**第一层：把「字号」当成「行距」**

`drawText` 的 y 是**基线**不是顶部。`baseline = top + labelSize` 等于假设「行高 = 字号」。
但真实字形高度 = `(ascent 绝对值 + descent)` 倍字号，中文字体约 **1.4 倍**。

**第二层：字号占比本身就不够**

三个占比 `0.19 + 0.44 + 0.17 = 0.80 < 1`，**看着**放得下。
但那是「字号之和」；真实占位要乘字形高度倍数：

```
label: 1.40 × 0.19 = 0.266
value: 1.40 × 0.44 = 0.616
unit : 1.40 × 0.17 = 0.238
                     合计 1.12 × cellH  > 1  → 必然向下溢出
```

## 三、修复

新增纯函数模块 `TextFit.kt`（不依赖 `android.graphics`，可 JVM 单测）：

| 函数 | 作用 |
|---|---|
| `computeSizes()` | 按真实度量算出三行字号；**放不下就整体等比缩小**，保持"标题小、数值大"的比例 |
| `layout()` | **按字形矩形**从上往下排：每行顶部 = 上一行底部 + 间隙，基线 = 顶部 − ascent |
| `estimateMetric()` | 没有真实字体时的保守估算（ascent = −1.0×size，覆盖中文字形） |

`drawCell()` 改为调用这两个函数，三行按算出的基线绘制。

## 四、验证

### 4.1 先证红：两个"我猜错了"的地方

测试写完后**红了 2 条**，而这两条红**都是我的假设错了，不是实现错了**：

| 我原本的假设 | 实测结果 |
|---|---|
| 「拉丁字体不重叠，中文才叠」 | ❌ **拉丁也重叠**（`labelBottom=23.56 > valueTop=22.96`），只是幅度小所以肉眼看不出 |
| 「字号占比 0.80 < 1，放得下」 | ❌ **放不下**：真实占位 1.12 × cellH，`cellH=60` 时内容底部 68.5 越界 |

**这两条红非常有价值**：
- 第一条说明问题是**普遍的**（不是中文特有），只是中文更明显
- 第二条说明**光改行距不够**，字号本身就得缩

于是设计从"只修行距"变成"行距 + 字号缩放"。测试保留这两条断言，作为这份事实的记录。

## 五、边界：哪些刻意没做

1. **不改用户设计文件** —— 历史记录明确要求"不擅自改用户设计"。本卡只改渲染层的排版算法。
2. **不改字号占比的视觉意图** —— 仍是标题 0.19 / 数值 0.44 / 单位 0.17；只在放不下时整体等比缩小。
3. **不改 `BarGaugeView`** —— 它的标题与数值是**左右并排**，机制不同，不在本次重叠报告范围内。
4. **不关闭 T11-I / T7 总项** —— 问题清单原文要求"无依据不关闭总项"，本卡只关掉其中这一条已确认的可见问题。
5. **真机实屏观感未验** —— 本卡做的是 JVM 几何验证（字形矩形不重叠、不越界），
   "看起来舒不舒服、缩小后会不会太小"需要用户目视。
6. **用户原设计的实际效果未验** —— 历史记录要求"使用用户原设计和实际数值/不同宽高验证"，
   本卡用参数化几何验证替代了尺寸维度，但用户那份具体设计仍需真机确认。
