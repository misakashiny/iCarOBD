## ⚠️ 关卡 A 最重要发现（D-15）

`saveUndoStack()` 每次 commit 同步写 1.19MB（15.6ms），
但 `loadUndoStack()` **在产品代码里从未被调用**（全库只有赋值 + 测试套件调用）。

→ 这 15.6ms 换来的恢复能力**实际为 0**。
→ 且全库**没有设计自动保存**，崩溃后整个设计会丢。

**按用户指示只报告、不扩大范围**，未修。

## 一、写盘耗时拆解（60 控件 / 20 步 / 50 样本）

    ├ payload JSON.stringify      4.5 ms
    └ localStorage.setItem       10.2 ms  ← 同步硬成本，不可优化

## 四、已实施：消除重复序列化（无损）

逐条 JSON.stringify(entry) → 直接拼 JSON 片段。

**为什么无损**：entry.state 本来就是 snapshot() 返回的 JSON 字符串。

**验证**：主场景 + 6 个边界场景全部 `identical === true`（字节完全一致）。

**实施中踩的坑**：第一版给 label 补默认值 "改动"，结果多 14 个字符 ——
因为 **JSON.stringify 会整个省略 undefined 属性**，不是写成 null。
改为逐字段判断 !== undefined。

**收益**：payload 构建 5.8 → 3.6ms；端到端 14.6 → 11.9ms（**-18.5%**）。

## 五、未实施：延迟写盘

按任务第五部分要求先论证：
- requestIdleCallback：setItem 仍是同步 API，只是挪时间点
- 定时/防抖：引入"最长未落盘窗口"，削弱保证
- 按手势写盘：**已经是当前实现**

未实施理由：收益上限只有 setItem 的 10.2ms，且必须牺牲持久化保证；
更重要 —— 既然 loadUndoStack 从不调用，为它牺牲写入保证毫无意义。

## 六、未达到 commit < 5ms（如实说明）

setItem 硬成本 10.2ms + refreshAll/draw 约 2~5ms = 理论下限 12~15ms。
本阶段**没有挪动写盘时机**，15.6ms 是真实用户感知耗时。

按任务第九部分：无法兼顾时应保留原实现并如实报告，不强行追求。
