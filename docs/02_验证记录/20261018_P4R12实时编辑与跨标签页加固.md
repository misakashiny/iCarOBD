# 20261018 P4R-1.2 实时编辑与跨标签页加固

详见专题：[53_ICarUI_P4R12实时编辑与跨标签页加固](../01_专题/53_ICarUI_P4R12实时编辑与跨标签页加固.md)
历史问题：[37_LegacyBehaviorDebt](../01_专题/37_LegacyBehaviorDebt.md)（新增 D-19）

## ⚠️ 关卡 A 两个风险都确认成立

### 风险1：实时编辑期间草稿完全不保存（D-19）

修复前实测：持续 setLive 6 秒（15 次调用，font.size 10→25）
  写盘次数 = 0
  IndexedDB 仍是 {"rev":1,"size":10}

根因：setLive 只做 PropertyAccessor.set + requestDraw()，**不走 commit()**，
而 markDirty 原本只挂在 commit 上。

### 风险2：跨标签页静默覆盖

修复前实测：两标签页各自恢复同一草稿（都从 rev=1），分别改不同属性
  最终 DB: {"rev":1,"size0":20,"x1":40}  两边改动都没进去，无任何提示

根因：旧逻辑只比较「库里 revision > 本次 revision」，两个标签页各自 ++ 到
同一数字时比较不成立 → 后写的赢，无人知道。

## 一、setLive 与草稿保存调用链（修复后）

  beginLive      → 记下 startValue
  setLive        → PropertyAccessor.set（改模型）+ requestDraw
                   + **DraftManager.markLiveDirty()** ← P4R-1.2 新增
                     · 已脏则直接 return（不重排定时器）
                     · dirty=true, revision++, 起防抖/最长定时器
                     · **不创建 UndoStack 记录**
  endLive        → 值没变不产生记录；否则还原 start → commit(end) 压实为一步
  abortLive      → 丢弃 liveEdit

markLiveDirty vs markDirty：前者不压栈（撤销栈语义不变），后者已压栈。

| 场景 | 修复前 | 修复后 |

## 四、跨标签页 CAS（乐观并发控制）

调用方传 lastKnownRevision，在同一读改写事务里比对：
  库里有记录 → 期望必须等于它的 revision
  库里没记录 → 期望必须是 null
  否则 → { ok:false, reason:"conflict", currentRevision, expectedRevision }

IndexedDB 事务串行 → 检查是原子的 → **存储层真实保护**（不依赖通知）。

实测 5 步全部符合预期：
  1 lastKnown=null 首次      → ok=true  rev=1
  2 lastKnown=1 正确         → ok=true  rev=2
  **3 lastKnown=1 过期       → ok=false reason=conflict current=2 expected=1**
  4 lastKnown=2 正确         → ok=true  rev=4
  **5 lastKnown=null 但库有   → ok=false reason=conflict current=4**

最终库中 rev=4，冲突写入没有污染任何数据。

## 五、冲突处理

六条要求逐条满足：不覆盖对方、不删本地、明确提示、可另存独立草稿、
不擅自合并、不强刷画布。

冲突提示条（顶部红色）：
  「本页基于 rev 5，但存储里已经是 rev 6。
   对方的数据没有被覆盖，你当前的编辑也还在画布上。」
  [另存为独立草稿] [稍后处理]

另存实测：ok=true, idChanged=true, **origStillThere=true**（原草稿未被覆盖）。

**未使用 BroadcastChannel** —— 完全依赖存储层 CAS（任务要求）。

## 六、墓碑过期测试

当前：内存墓碑 TTL 60 秒。
实测：删除后立刻写入被拒 ✅；**删除 60 秒后写入会复活** ⚠️（墓碑已过期）。

**重要发现：CAS 已部分兜底**：
  B 删除后写入时库里已无记录（exists=false）但 lastKnownRevision 非 null
  → CAS 判定 conflict，不会复活

但若 B 的 lastKnownRevision 恰好是 null（首次写入）则会成功。

建议把墓碑 TTL 延长到会话级（待批准，本阶段未改）。

  实际事务 durability                        **default**
  显式 {durability:'strict'}                 ✅ 可用
  显式 {durability:'relaxed'}                ✅ 可用

Chromium 里 default **通常**等价 strict，但这是实现选择，不是 W3C 硬性保证。

### 修正后的正确表述

  正确：「在本环境（Edg155/headless/file:///default durability）实测：
        事务 oncomplete 后立即强杀进程，数据 7/7 存活。
        这**不等于**跨环境跨浏览器的绝对保证 —— 系统断电与实现差异仍未知。」
  错误：「IndexedDB 事务完成后在任何情况下都保证 0ms 落盘。」
