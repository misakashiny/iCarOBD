## 二、换算系数验证（独立推导，不读被测常数）

物理定义：

```
L/h = MAF[g/s] ÷ 745[g/L] × 3600[s/h]
    = MAF × 4.8322...
```

代码 `G_S_TO_L_H = 3.6 / GAS_DENSITY(0.745)`：

| 写法 | 值 |
|---|---|
| `3.6 / 0.745` | 4.832214765100671 |
| `3600 / 745` | 4.832214765100671 |
| 相同 | **True** |

两者数学等价（分子分母同乘 1000，因为 0.745 是 **kg/L** 而分母按 **g** 算）。

**用不依赖具体密度取值的恒等式交叉验证**：
`MAF = 745 g/s` ⇒ 1 L/s ⇒ **3600 L/h**。测试 `MAF 745g-s 应换算出 3600 L-h` 钉住这条 ——
如果将来有人改了 `GAS_DENSITY` 却忘了同步 `3.6`，这条会立刻红。

## 三、PID 公式核对（对照 SAE J1979 / ISO 15031-5）

| PID | 标准公式 | 代码 | 一致 |
|---|---|---|---|
| `0x10` MAF | `((256A+B)/100)` g/s | `((A*256)+B)/100` | ✅ |
| `0x5E` 燃油消耗率 | `((256A+B)/20)` L/h | `((A*256)+B)*0.05` | ✅（`1/20 = 0.05`） |

`5E` 标准满量程：`65535 / 20 = 3276.75 L/h`。

## 五、发现并修掉的缺陷：高油耗被丢弃

### 缺陷

`VehicleBus.kt` 的 `integrateDistance()` 原来写：

```kotlin
val fuel = input(readings, "calc_lh")?.takeIf { it.value in 0f..100f }
```

**这个 100 没有任何依据**，而 PID 5E 标准满量程是 **3276.75 L/h**。

现实中轻松越过 100：

| 工况 | MAF | 换算 L/h |
|---|---|---|
| 中等排量提速 | 30 g/s | ≈ 145 L/h |
| 大排量全油门 | 200 g/s | ≈ 966 L/h |

### 后果比"少算一次"严重

```
calc_lh = 150 L/h（合法）
  → 被 takeIf { in 0..100 } 丢掉
  → liters = null
  → tripComplete = false     ← 关键
  → 平均油耗变失效
  → 【整个行程永久失效】，只能 resetTrip() 恢复
```

用户看到的现象：**"跑着跑着平均油耗变成 `--` 了，而且再也不回来"**。

### 修复

```kotlin
private const val FUEL_RATE_MAX_LH = 3276.75f   // PID 5E 物理满量程
val fuel = input(readings, "calc_lh")?.takeIf { it.value in 0f..FUEL_RATE_MAX_LH }
```

上界改为**按 PID 标准推导**的物理满量程，不再是拍脑袋的 100。超出才说明解析异常 ——
**宁可让行程失效，也不要把坏数据积进去**（这条设计原则保持不变）。

## 七、一个刻意没改的地方

`calc_l100` 与 `calc_avg_l100` 的输出都有 `coerceIn(0f, 99f)` 上界（99 L/100km）。

**这是刻意的仪表显示上限**（两位数满格），不是缺陷。150 L/h @ 120 km/h 理论值 125 L/100km
会被夹到 99 —— 属于显示层行为。

测试里特意把这条写清楚：断言 **99 而不是 125**，理由是"验证积分真的发生了"，
若积分被丢弃结果是 `null` 而不是 99。**改显示上限不在本卡范围**（会影响仪表刻度设计）。
