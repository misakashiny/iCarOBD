# 20261018 P4P-0 性能审计

详见专题：[47_ICarUI_P4P0性能审计](../01_专题/47_ICarUI_P4P0性能审计.md)

**本阶段只读审计，产品源码零改动。**

## 一、覆盖数量复核（四口径）

| 口径 | 数量 |
| --- | --- |
| 目录条目数 | **215** |
| Registry 正式接管 | **69** |
| **Schema 面板支持（按节点能力）** | **59** |
| 仅用旧面板 | **156** |

**接管数 ≠ 面板支持数**：
- 接管 69 中只有 44 条被面板支持（仪表 6 + 状态灯 19 接管了但面板没接）
- 面板支持 59 中有 15 条（next_*）是靠节点能力而非 Registry 接管

**目录条目 ≠ 真实节点数**：一个 next_speed_oem 条目产出 3 个节点。

## 二、瓶颈排行榜（60 平铺，中位数）

| 排名 | 项 | 耗时 | 占 commit |
| --- | --- | --- | --- |
| **1** | **renderAssets** | **25.7 ms** | **57%** |
| **2** | **saveUndoStack** | **18.3 ms** | **42%** |
| 3 | renderTree | 0.7 ms | <2% |
| 4 | draw | 0.5 ms | 1% |
| 5 | syncJson | 0.3 ms | 1% |
| 6 | renderProps | **0.0 ms** | **0%** |

**前两名合计约 99%。**

## 三、关键测量数据

八个场景（50 样本）：
| 场景 | 中位数 |
| --- | --- |
| A 空设计 | **21.80 ms** |
| B 20 平铺 | 28.80 |
| C 60 平铺 | 30.60 |
| D 120 平铺 | 32.90 |
| E 20 含多层组 | 23.70 |
| F 60 含多层组 | 24.90 |
| G 60 图片 | 25.30 |
| H 60 仪灯 | 27.60 |

**关键结论**：
- **耗时几乎不随控件数增加**：0→120 个节点只 +11ms
- **空设计就要 21.8ms** —— 存在与节点数无关的大额固定成本
- **嵌套 group 无额外开销**（F 比 C 还快，因总节点更少）

## 四、输入体验

| 路径 | 中位数 |
| --- | --- |
| **setLive（实时输入）** | **0.5 ms** |
| setOnce（落定提交） | **40~46 ms** |
| 撤销 / 重做 | 31~38 ms |
| 选择节点 | 3.9 ms |

**实时 vs 落定相差 80~90 倍** —— P4A 增量刷新设计有效，
但**落定时全量刷新仍是瓶颈**。

## 五、关键实验证据

临时置空 BUILTIN_ASSETS（416 素材）后：
  renderPanels 26.4ms → **12.9ms**
  → 素材列表渲染贡献 **13.5ms（51%）**

## 六、推荐的 P4P-1 最小方案（两件事）

1. **按需刷新资源库**：脏标记，只在 design.assets / BUILTIN_ASSETS 真变时重建
   预期 commit 43.7 → 约 20ms（**50%**）
2. **优化 saveUndoStack 写盘时机**：用 P4A.1 已有的 flushUndoStack
   预期 20 → 约 10ms

**建议不做**：局部更新属性面板（renderProps 实测 0.0ms）、
按需刷新节点树（0.7ms）、延迟 JSON 同步（0.3ms）—— 数据不支持。

## 七、重要发现：容器 alpha/w/h 无视觉反馈

实测父容器改 alpha=128 或 w=300，画面**完全不变**。

根因是 canvas.js drawNode 的既有语义：
  分组"不画任何东西"（源码注释：用户明确说不需要紫色虚线框）
  globalAlpha 在 drawNode 里 save/restore，不向子节点继承
  容器不裁剪子节点（P3B 已记录）

**不是 P4C 引入的**，但 P4C 在面板开放了这三个字段，
用户改了看不到变化会以为面板坏了 → **列入风险，需产品决策**。

## 八、未验证

renderAssets 内部 25.7ms 未细分（只知素材列表占 13.5ms）；
saveUndoStack 18.3ms 未测序列化 vs 写入各占多少；
