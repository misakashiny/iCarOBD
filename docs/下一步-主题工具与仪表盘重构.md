# 第一部分：主题制作工具

## 1.1 要做什么

一个**在电脑上可视化编辑仪表盘主题/布局**的工具，产出 `icar.ui/1` 格式的设计文件，
推给 App 加载。

格式定义见 [UI设计指南.md](UI设计指南.md)，解析器已实现（`data/DesignFile.kt`，22 个测试）。

**现在缺的是编辑器**：设计文件只能手写 JSON，改一个坐标要重新数一遍。

## 1.2 技术选型（**建议：单文件 HTML**）

| 方案 | 优 | 劣 | 结论 |
|---|---|---|---|
| **单文件 HTML + Canvas** | 零安装、双击即用、跨平台、改起来快 | 不是原生观感 | ✅ **推荐** |
| Electron | 原生观感 | 要装 Node + 几百 MB 运行时 | ❌ 为一个编辑器不值 |
| Python + Tkinter | 简单 | 界面丑、Canvas 能力弱、要装 Python | ❌ |
| Android 端编辑 | 不用传文件 | **和"在电脑上设计"的诉求矛盾** | ❌ |

**关键理由**：这个工具的寿命取决于**改起来快不快**。
单文件 HTML 没有构建步骤，改一行刷新就见效；
而且**用户不需要装任何东西** —— 双击打开就能用。

## 1.3 功能清单（按优先级）

### P0 —— 没有就不算能用

| 功能 | 说明 |
|---|---|
| **画布** | 360×360 参考网格，画出每块表的矩形 + 名称 + 读数占位 |
| **选中 / 拖动 / 缩放** | 鼠标拖拽；边角手柄缩放；吸附到 15 单位网格（和 App 的 `Drag.STEP` 一致） |
| **属性面板** | 选中后编辑 `pid` / `style` / `min` / `max` / `warnHigh` / `neonPreset` |
| **打开 / 保存** | File API 读写 `design.json` |
| **校验** | **用和 `DesignFile.kt` 完全相同的规则**，错误/警告分色显示 |

### P1 —— 显著提升效率

| 功能 | 说明 |
|---|---|
| **实时预览** | 用 Canvas 画出仪表的**大致样子**（弧、条、数字），不用推设备就能看比例 |
| **预设布局** | 一键生成"1 大 4 小""2×2""全条形"等常见排布 |
| **对齐辅助线** | 拖动时显示与其他表的对齐关系 |

| **主题切换预览** | 在 neon / ice / amber 之间切，看配色 |

### P2 —— 锦上添花

| 功能 | 说明 |
|---|---|
| 撤销/重做 | 编辑器的基本素养 |
| 导出为 PNG 预览图 | 方便分享/存档 |
| 读取现有 `dash.json` 反向生成设计文件 | 从 App 里导出的布局继续改 |

## 1.4 校验必须"同源"

**最容易出错的地方**：HTML 里的校验规则和 `DesignFile.kt` 里的**不一致** ——
编辑器说没问题、App 加载报错。

**解决方案**：把校验规则抽成**一份数据驱动的规则表**（JSON），两边都读它。
或者更简单：**HTML 里直接抄 `DesignFile.kt` 的错误文案**，并在测试里断言两边一致。

**至少要保证的规则**（与 `DesignFile.kt` 逐条对应）：

```
硬错误：
  schema 缺失 / 不是 "icar.ui/1"
  canvas.unit 不是 360
  gauges 缺失 / 为空 / 超过 32 项
  pid 缺失
  min >= max

软警告：
  x/y 为负
  x+w > 360 或 y+h > 360
  w < 10 或 h < 10
  pid 不在内置库
  没有 meta
```

## 1.5 交付物

```
tools/theme-studio/
  index.html          ← 单文件，双击可用
  README.md           ← 怎么用、怎么扩展
  sample.json         ← 一个示例设计文件
```

## 1.6 验收标准

1. 双击 `index.html` 能打开，无需任何安装
2. 能打开一个 `design.json`，画布上出现对应的矩形
3. 拖动/缩放后坐标变化符合 360 单位制，且吸附到 15 的倍数
4. 保存出的 JSON 能被 `DesignFile.parse()` 成功解析（**用单元测试验证**）
5. 故意写错（如 `min > max`）时，界面上显示和 `DesignFile.kt` 一样的错误文案

# 第二部分：仪表盘逻辑重构

## 2.1 现在的问题（基于代码实测）

### 问题 1：`BaseGaugeView` 背了 **6 个互不相关的概念**（357 行）

| 概念 | 涉及成员 |
|---|---|
| 值管理 | `value` `extraValues` `colorOverride` |
| 缓动动画 | `displayValue` `animating` `lastFrameMs` `stepFrame` `shown` `shownRatio` `settleEpsilon` |
| 报警 | `warn` `alertLevel` `criticalOf` `alertIntensity` `alertTint` `alertMix` `alertGlowColor` |
| 主题颜色 | `palette` + **10 个** `cXxx` 字段 + `bind` |
| 绘制工具 | `neon` `dp` `sp` `newTextPaint` `glowColor` |
| 文本格式化 | `format` `fmtByRange` `label` `unit` `extraFormat` `primaryFormat` |

**后果**：想改缓动要翻 357 行；想加一种报警档位要动基类；
子类拿到的是一大把 `protected` 成员，**没有边界**。

### 问题 2：**两套并存的报警概念**（最容易出错的一处）

```kotlin
protected var warn: Boolean          // 来自 isOutOfRange()，含 warnLow
protected var alertLevel: Int        // 来自 AlertPulse.level()，只认 warnHigh
```

- `warn` 用于**选颜色**（数值超范围就变色）
- `alertLevel` 用于**驱动爆闪**

**两个概念有重叠但不相等**：`warnLow` 触发时 `warn=true` 但 `alertLevel=NONE`。
读代码的人一定会困惑"到底哪个才是报警"。

### 问题 3：`DashRenderer` 混了 5 件事（191 行）

视图创建、像素换算、5Hz 值推送、主题应用、网格叠加层、尺寸变化处理。

**后果**：想单独测"坐标换算"或"值推送节奏"都做不到 —— 它们和 View 创建缠在一起。

### 问题 4：`GaugeItem` 是**上帝对象**

20+ 字段混了：身份（`pidId`）、布局（`x/y/w/h`）、样式（`style`）、
数据绑定（`extraPids`）、量程（`min/max`）、阈值（`warnLow/warnHigh`）、
外观（`ringStyle/neonPreset`）。

**后果**：改布局相关的逻辑要 import 一个包含报警阈值的类。

### 问题 5：`DigitalGaugeView` 用 `ratio(value)` 而不是 `shownRatio()`

装饰弧**跳变**，和其他表观感不统一。（一行可修，见 [动画实现.md](动画实现.md)）

## 2.2 重构方案（**分步、每步可独立验证**）

> ⚠️ **不要一次全做**。每一步都要保证 288 个测试通过 + 装机无崩溃。

### 步骤 1：统一报警概念（**最小、收益最大**）

```kotlin
// 删掉 warn，只留 alertLevel；颜色由 alertLevel 决定
protected var alertLevel: Int = AlertPulse.NONE
protected fun alertColor(): Int = when (alertLevel) {
    AlertPulse.CRITICAL -> cDanger
    AlertPulse.WARN -> cWarn
    else -> mainColor()
}
```

但 `warnLow`（下限报警，如电压过低）**目前不走 AlertPulse**。
要么扩展 `AlertPulse.level` 支持下限，要么把下限也归入 `alertLevel`。

**验收**：所有视图的颜色/爆闪行为与重构前一致（可用截图对比）。

### 步骤 2：把动画抽成独立类

```kotlin
/** 单值缓动。只管 displayValue，不碰 View、不碰主题 */
class ValueEasing(private val tauMs: Float = 45f) {
    var target: Float? = null
    var display: Float? = null
        private set
    fun step(nowMs: Long, epsilon: Float): Boolean   // 返回是否还需继续
    fun snapTo(v: Float?)
}
```

**收益**：`BaseGaugeView` 少 ~60 行；缓动可**单独单测**（现在是静态函数，测不了状态机）。

### 步骤 3：把主题颜色抽成值对象

现在有 10 个 `protected var cXxx`。改成：

```kotlin
/** 一次解析好的调色板。视图只读它，不再散落 10 个字段 */
class GaugePalette(theme: GaugeTheme) {
    val accent; val accentHot; val track; val tick
    val needle; val value; val label; val dim
    val warn; val danger
}
protected val pal = GaugePalette(palette)
```

**收益**：`bind()` 从 10 行赋值变成一行；新增颜色只改一处。

### 步骤 4：拆 `DashRenderer`

```
DashLayoutEngine   ← 纯函数：GaugeItem + 容器尺寸 → 每块的 RectF（**可单测**）
DashValuePump      ← 5Hz 推送节奏（**可单测**）
DashRenderer       ← 只剩：建视图、挂到容器、把上面两者接起来
```

**收益**：像素换算和推送节奏第一次变得**可测**。

### 步骤 5：`GaugeItem` 分组（**破坏性最大，放最后**）

```kotlin
data class GaugeItem(
    val pidId: String,
    val layout: GaugeLayout,      // x/y/w/h
    val range: GaugeRange,        // min/max/warnLow/warnHigh
    val look: GaugeLook,          // style/ringStyle/neonPreset/color
    val extraPids: List<String>
)
```

⚠️ **JSON 兼容性**：现有 `dash.json` 是扁平结构。
必须写迁移（`fromJson` 认扁平 → 转成分组；`toJson` 写扁平以保持兼容），
或者写一次性迁移 + 版本号。

**这一步骤风险最高，建议单独一轮做，且必须有迁移测试。**

## 2.4 ⚠️ 被反复推迟的那件事：性能基准

**从 v1.9.0 起就没量准过。** 这是唯一一个"可能推倒重来"的风险点：

- 9 层霓虹辉光能否在 8 个仪表下守住 60fps —— **未验证**
- `DrawStats` 已经装好（`BaseGaugeView.onDraw` 是 `final`，统一计时），
  但一直没跑出数据（测的时候仪表没在动）
- `dumpsys gfxinfo` 在这台设备上**给不出数据**（只有头部，没有帧统计）

**建议做法**：写一个**不依赖数据源**的基准 ——
直接让 8 个表进入持续动画（比如临时给每个表一个正弦变化的假值），
跑 10 秒，读 `DrawStats` 的输出。

**这件事的优先级应该高于任何重构** —— 因为如果 9 层辉光守不住 60fps，
`NeonStyle` 的默认值和 `layersFor` 的档位都要重调，重构的基线就变了。

### ✅ 实测结果（v1.10.1 完成）

按上面的建议做法做了，并**修正了建议里的一个错误**（见下）。
入口：连接页 →「运行选项」→「性能基准」。

| 档位 | 仪表 | 帧间隔 平均 | p99 | 最大 | 超时帧 |
|---|---|---|---|---|---|
| 8 表 · 主题默认 | 8 | 8.33 ms | 8.39 ms | 8.43 ms | **0** |
| 8 表 · 夸张（11 层） | 8 | 8.33 ms | 8.38 ms | 8.41 ms | **0** |
| 8 表 · 关闭辉光 | 8 | 8.33 ms | 8.38 ms | 8.43 ms | **0** |
| 12 表 · 夸张（极限） | 12 | 8.33 ms | 8.38 ms | 8.41 ms | **0** |

**结论：12 个圆表 + 11 层辉光跑满 120fps，零掉帧。**
所以 `NeonStyle` 的默认值和 `layersFor` 的档位**不需要因为性能而调整**，
重构的基线**没有变**。

> **⚠️ 修正：不能读 `DrawStats` 的输出下结论。**
>
> 本节的建议是"读 `DrawStats` 的输出"。实测发现**那个数不能当判据**：
> Android 开了硬件加速后，`onDraw` 只是把绘制指令**记录**进 DisplayList，
> 真正的光栅化在**渲染线程**上做。`DrawStats` 量到的是"记录耗时"（0.2~0.34ms），
> **不是绘制成本** —— 拿它下结论会得出"还有 50 倍余量"这种过于乐观的答案。
>
> 真正的判据是**帧间隔**（主线程 + 渲染线程 + 合成器的最终结果）。
> 报告里现在把 `DrawStats` 明确标成"旁证"，主判据换成帧间隔。
>
> 顺带一个佐证：`关闭辉光` 的**记录**耗时（0.34ms）反而**高于** `夸张`（0.28ms）——
> 说明那一列量的是视图层代码，与辉光层数基本无关。

**另外两个必须注意的测量条件**：

1. **预热**：重建视图后第一帧要付 `Paint` 光栅化 / 字体度量 / tessellation，
   峰值 **11393µs**。不预热会让峰值污染统计。现在预热 1.5 秒后才开始计数。
2. **屏幕刷新率会封顶帧率**：同一页两次测量分别读到 30Hz 和 120Hz
   （`mActiveModeId` 在 30/60/120 之间切）。拿 fps 当判据会得出"刚好达标"的错觉。

## 3.2 必须遵守的（前一份会话用血换来的）

1. **改完立刻量。** 不要凭推断说"优化了" —— 前一份会话因为这条栽了三次

3. **不要用 8×6 像素探针判断画面。** 它每 ~200×340 像素才采一个点，整片漏掉文字。
   用亮像素统计，或者**直接截图 + 解码成色彩网格**。
4. **adb 传二进制用 `adb push` + `chmod` + `run-as cp`。**

5. **跑自动化验证前先锁方向**（`accelerometer_rotation 0`）。
