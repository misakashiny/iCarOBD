### 各版本要点与遗留

<details open>
<summary><b>v1.3.0 · 实车缺陷修复</b>（最重要的一版）</summary>

**改了什么**
- BLE 写类型写死 `WRITE_TYPE_DEFAULT` → 改为按 `properties` 自适应
- 特征选择只看 UUID 不看属性 → 改为属性驱动 + 同服务内重新配对
- 写入失败无限重试 + 逐次写日志 → 有界重试 + 限流 + 去抖
- **新增连接后自动转储整张 GATT 表**（含 properties / writeType / descriptor）
- `LogAdapter` 环形缓冲溢出时只发插入通知 → 改为成对通知（崩溃根因）
- `AppLog` 新增四条自我保护；落盘改批量；`exportText` 只导末尾 2MB
- `LogFragment` 统计改用 `AppLog.size()`，UI 刷新合并到 250ms

**验证**
- 压力注入 6000 条 → 适配器稳定在 3000 上限并持续溢出，**无崩溃**（旧版在此崩溃）
- 4000 条相同消息 → 压成 20 条「重复 200 次，已抑制」
- 启动时发现 57MB 遗留日志 → 自动归档重开

**遗留** ⚠️
- **BLE 写入修复未经实车复验** → 见待办 P0
- 辉光效果（`glow=true`）只在有真实数值时绘制，**未目视验证** → 见待办 P0-3
</details>

**前置**：车（马自达阿特兹）、iCar Pro 2S 适配器、已装 **v1.3.1** 的平板
（⚠️ **必须 v1.3.1**：v1.3.0 的公式引擎是坏的，即使 BLE 通了也算不出任何数值 —— 见 CHANGELOG v1.3.1）

> **取证工具**：上车后先跑 `tools\oncar-check.ps1`。它会一次性收齐 P0-1~P0-4 需要的
> 全部证据（GATT 表 / AT 命令 TX-RX / 超时 / 初始化结果 / 轮询与规则 / 扫描器日志），
> 并按 GATT 表直接给出「下一步做什么」的判定，不必手动翻日志页。

- [ ] **P0-1 连接并转储 GATT 表**
  - 步骤：适配器插 OBD 口 → 点火开关拧到 **ON**（不用发动）→
    App「连接」页 → 扫描 → 连接 → 等「已就绪」→ 切「日志」页
  - 找 `===== GATT 表开始 =====` 段，记录写特征那行的 `props=`
  - **验收**：拿到完整的 GATT 表（含每个特征的 props / writeType / descriptor 数）

    且 `ATZ` / `ATE0` / `0100` **不再超时无响应**
  - 若仍超时：把 P0-1 的 GATT 表段导出，据此确定正确的特征与写类型

### P2 · 质量与健壮性

- [x] **P2-1 补单元测试（纯函数优先）** —— ✅ v1.3.1 完成
  - 结果：`app/src/test/java/com/icar/obd/` 下 4 个文件 / **86 个用例，全部通过**

    ③ `0xFF` 十六进制字面量永远不可达（文档却宣称支持）。三者均已修。
  - ⚠️ **原文写错了**：`RuleEngine` **不是**纯函数（依赖 `VehicleBus` / `AppLog` / `Store`，

  - ⚠️ 覆盖不到的：`PidModels` 的 `toJson` / `fromJson` 依赖 `org.json`（Android 框架桩），
    JVM 单测无法覆盖，需要 Robolectric 或仪器测试。

- [x] **P2-4 处理「非 ASCII 路径导致单测跑不了」** —— ✅ 已决策：**不移动工程**（2026-10-02）

  - 本项**不再作为待办**，但下面这条约束长期有效：

## 三、每次发版的固定动作

发版前逐项确认，**不要跳**：

- [ ] 1. `app/build.gradle.kts` 的 `versionCode` +1、`versionName` 更新
- [ ] 2. `./gradlew assembleDebug` 通过
- [ ] 3. 装机：`adb install -r -d dist/iCarOBD-debug-vX.Y.Z.apk`
- [ ] 4. **`adb logcat -d -b crash` 为空**
- [ ] 5. **`adb logcat -d | grep -icE "ANR in"` 为 0**
- [ ] 6. 横屏 + 竖屏各走一遍 5 个页面 + 相关编辑器
- [ ] 7. 检查应用内日志文件体积是否正常（正常一天 < 2MB）
- [ ] 8. `dist/` 归档新 APK，**删除被取代的旧 APK**
- [ ] 9. `CHANGELOG.md` 追加一条：版本 / 日期 / 变更 / **验证方式** / 遗留问题
- [ ] 10. 本文「版本清单」加一行，完成的待办打勾并移到已完成
- [ ] 11. `FILE_MAP.md` 若有文件增删改名，同步 §2 / §3
- [ ] 12. 若改了边界规则，**只改 `ARCHITECTURE.md` §4**（唯一权威清单）；
      其他文档只做索引，不要去同步复制条目
- [ ] 13. 若动了渲染层 / 动画，**重跑性能基准**（见 P7-1）
- [ ] 14. 若动了 `GaugeItem` / `DesignFile` 的字段，**同时改
      `tools/theme-studio/index.html` 与 `sample.json`**，
      否则工具的校验会和 App 分叉（`ThemeStudioSampleTest` 会失败，这是有意的）

## 四、验收标准写法

写待办时请照这个格式，避免「做完了」但说不清做到了什么：

```
- [ ] 事项标题
  - 前置：依赖什么（数据、设备、其他待办）
  - 步骤：具体怎么做（可执行）
  - 验收：**可观测的判据**（数字、日志关键字、界面表现）
  - 涉及文件：改哪里
```

> **判据必须落到可观测的事实上。**
> 本项目有过一次教训：压力测试「没崩」就以为通过，
> 实际上注入的数据被队列截断，**根本没走到被测分支**。
> 后来从界面上读到 `3000 条（缓冲 3000）` 这个数字，才确认分支真的被执行了。
