### 1.2 【最严重】19 个指示灯里 16 个的状态系统永远不切

**实测**（脚本加载 `model.js` + `schema.js` + `presets.js`，给 `ensureBuiltinAsset` 打桩后逐个 `make()`）：

| | 数量 | 结果 |
|---|---:|---|
| `n.states` 有值 | 19 | 都建了状态表 |
| `n.statePid` **有值** | 3 | `lamp_coolant` → `std_05`、`lamp_oil` → `tpl_oilPressure`、`lamp_batt` → `std_42` |
| `n.statePid` **为空** | **16** | `lamp_brake` / `lamp_pad` / `lamp_tpms` / `lamp_airbag` / `lamp_belt` / `lamp_abs` / `lamp_esp` / `lamp_engine` / `lamp_fuel` / `lamp_door` / `lamp_washer` / `lamp_service` / `lamp_temp` / `lamp_charge` / `lamp_lane` / `lamp_collision` |

**为什么这 16 个永远是"正常"**：

1. 它们在 `presets.js:501-502` 写的是
   `n.pid = window.resolvePid(d.pid); n.rawPid = d.pid;` —— **不是 `statePid`**。
2. App 侧 `NodeTreeRenderer.resolveState()`（`ui/dash/NodeTreeRenderer.kt:486-489`）读的是
   `c.node.statePid`，`isBlank()` 就**直接 `return STATE_NORMAL`**，根本不看 `pid`。
3. 更要命的是这 16 个 `pid` / `rawPid` **连文件都进不去**：
   `model.js:826-831` 对 `NODE_IMAGE` 只写 `statePid` / `states` / `stateWarn` / `stateCritical`，
   **`pid` 与 `rawPid` 不写**。所以设计文件里既没有 `statePid` 也没有 `pid`。

**净结果**：用户从控件库拖一个"胎压灯"出来，它**永远显示暗的 `lamp-off.png`**（`normal` 的 `alpha: 255`，
`presets.js:504`），永远不会亮。控件能拖、能摆、能存、能导出、守卫不报 ——
这是这个库里**最贵的一条**：用户会以为"车没问题"，而不是"这个灯没接上"。

**顺带**：`guard-pid-probe.js` 把这 16 个里的 12 个报成"等 P9 上车逆向"。
但它们的 `statePid` 是空的 —— **数据有没有根本不影响它们的状态**。
这条待办在"等一个用不上的东西"，真正要修的是接线，不是 P9。

### 1.3 PID 绑定：守卫的结论是准的（我最初的怀疑被实测推翻）

| | 数量 | 说明 |
|---|---:|---|
| 运行时真的绑了 PID 的控件 | **37 / 122** | 用 `make()` 实例化后读 `n.pid` / `n.statePid` / `n.parts[].pid` |
| 其中 PID 在 `BUILTIN_PIDS` 里真实存在 | 37 | 含 4 个 `tpl_*`（存在，但量程是猜的） |
| `guard-pid-probe.js` 报的"已知待办" | 14 | 12 个指示灯 + `g_gear` + `g_soc` |
| `guard-pid-probe.js` 报的"新问题" | **0** | ✅ 实测确实没有新问题 |

**我最初的怀疑是错的，记在这里**：我一开始以为守卫有假阴性 ——
`g_afr` 绑 `tpl_afr`、`g_gearbox` 绑 `tpl_atf`，我猜这两个"厂家模板"不在 PID 库里、
守卫的正则 `[^}]*?` 又抠不到它们。**实测推翻了**：

- `guard-pid-probe.js:123` 的正则从源码抠出 **40 条** `key + pid`（含 `lamp_*` 与 `g_*`）；
- `BUILTIN_PIDS` 里 `tpl_oilPressure` / `tpl_afr` / `tpl_atf` / `tpl_steer_angle`
  **四个都在**（`schema.js:1213-1220` 的 `MANUFACTURER_TEMPLATES`）；
- 所以守卫报 14 条待办、0 条新问题，**是准的**。

**真正的问题不是守卫，是语义**：`g_afr`（"空燃比"）和 `g_gearbox`（"变速箱油温"）
在控件库里和 `g_coolant`（"水温"）**长得一模一样**，但后者绑的是真的 `std_05`，
前两者绑的是 `g="厂家模板（未验证）"`、`schema.js:1214` 注释写着"**PID 号是猜的**"的占位。
用户看不出这个差别。→ 这值得单列一条小建议，见下面 **P2 的建议 7b**。


### 1.4 冗余 / 低质（实测比对，不是印象）

| 控件 A | 控件 B | 实测差异 | 判断 |
|---|---|---|---|

| `gauge_7`（G力值） | `g_gforce`（G 值） | 同 `pid=calc.gforce`、同 `style=7`；`w=120` vs `160` | 同上 |

| `img_ring`（圆环底盘） | `img_glowring`（发光环） | 都是环状图 | 名字分不清"底盘环"和"装饰光环" |

**名字含糊**：`img_ring`、`img_plate`、`img_cap`、`img_seg20`、`img_ticks90`、
`img_plateblank`、`img_carbonblk` —— 光看名字说不出用途，得点开看大图。

**分类错位**：`img_ticks90`（90 格刻度）、`img_seg20`（20 段弧）、`img_needle`（指针素材）、
`img_cap`（轴心盖）被分到「图片 / 底盘」，而 `CAT_RULES`（`presets.js:660`）
专门有一条 `[/^img_(digit|nums|unit)/, "数字刻度"]` —— 说明作者本来就想把"刻度类"单独分出来，

### 1.5 缺口：常见车载 HMI 元件**没有**的

按"App 侧有没有渲染能力"分三档，**这决定了它值不值得做**。

| 缺的东西 | App 侧能力 | 有数据源吗 | 现在能怎么凑 |
|---|---|---|---|
| **红区 / 多段色带**（转速红区、油量绿黄红） | ✅ 能画（`NeonPainter` 已在做危险区染色） | ✅ 不需要新数据 | 只能用 `warnHigh` 单阈值染色；素材 `ticks-band.png`/`ticks-gradient.png` **没进控件库** |
| **刻度标签跳级**（8000rpm 只标 0/2/4/6/8） | ✅ | ✅ | `nums-*` 是**固定图片**（`nums-arc-9`=0~8 共 9 个），跳级要么再生成素材、要么改 App 画字 |
| **双刻度 / 主副量程**（转速 + 增压） | ✅（`GaugePartsView` 已支持多 `needle` 各绑 PID） | ✅ `calc.boost` 在库里 | 只能手拼，**没有模板** |
| **阈值标记**（`marker-h/v`） | ✅ | ✅ | 素材有，控件没有 |
| **能量流 / 功率回收双向条** | ❌ 没有双向条渲染 | ❌ 混动/电车无 CAN 数据 | 做不了，见「拿不准」 |
| **挡位大字**（P/R/N/D 占满屏） | ✅（`valueLabels` 已在 `ValueLabels.kt` 实现） | ⚠️ `obd.gear` 不存在，等 P9 | `g_gear` 模板已带 `valueLabels`，但 PID 是空的 |
| **续航环 / 电量环** | ✅ 环形进度 | ✅ `calc.range` 在库里 | `g_range` 是**条形**（`style:1`），没有环形版本 |
| **温度条**（水温/油温竖条） | ✅ `BarGaugeView` | ✅ `obd.coolant` | `g_coolant` 是圆表；拼装表里没有"温度条" |
| **胎压四轮图** | ⚠️ 只能当 4 个图片节点摆 | ❌ 无 4 轮独立数据 | **做不了**（只有 1 个 `obd.tpms` 灯） |
| **ADAS 状态条 / 俯视图** | ❌ 没有 | ❌ | **做不了**；而且设计上有争议（见表 2 的 Turn Signal） |
| **告警条（非闪烁）** | ⚠️ 有 `MonitorWarnBar.kt`，但不在控件库 | ✅ | 控件库里**没有任何"告警条"控件** |
| **数字鼓 / odometer 滚动** | ❌ | ✅ `obd.odo` | 做不了（要新 View）；`g_odo` 是普通数字 |
| **行程/平均车速等 `icon` 类小件** | ✅ | ✅ `calc.km` 有 | 48 个 icon 素材全没进控件库 |

### 1.6 现状小结（一句话）

> 库的**数量**够（122 个控件 / 355 个素材），**结构**也对（子部件拼装 + 状态系统 + 分类守卫）。
> 问题全在**接线**和**成色**上：
> **16 个指示灯状态是死的**、**红区/阈值标记这类"仪表之所以像仪表"的东西一个都没有**、
> **同一份库里两种字体写法三种闪烁策略**、**12 个最常用的素材类别没暴露**。

## 表 3 · 建议清单

**优先级判据**（三条，按顺序）：
`P0` = 现在就是错的（用户会被误导）；`P1` = 高性价比（依据硬、代价小）；
`P2` = 值得做但依赖别的改动；`P3` = 方向对但收益/代价不划算。

> ⚠️ **改哪侧** 里的 `工具侧` = `tools/icarui`（本次范围外，只写建议不落手）；
> `App 侧` = `app/src/main/java/com/icar/obd`。**两边都要改的会在"代价"里点明。**

### P0 —— 现在就是错的

#### 建议 1 · 修 16 个指示灯的 `statePid`（把 `pid` 改成 `statePid`）

- **改什么**：`presets.js:501-502`
  ```js
  n.pid = window.resolvePid(d.pid);
  n.rawPid = d.pid;
  ```
  改成
  ```js
  n.rawStatePid = d.pid;
  n.statePid = window.resolvePid(d.pid);
  ```
  （与第一批 `presets.js:245` 的 `statePid: d.pid` 对齐）
- **为什么（依据）**：
  - `NodeTreeRenderer.kt:486-489` —— `resolveState()` 只读 `statePid`，`isBlank()` 直接返回 `normal`；
  - `model.js:826-831` —— `NODE_IMAGE` 序列化**只写 `statePid`/`states`**，`pid`/`rawPid` 被丢掉；
  - 实测 19 个带 `states` 的控件里 **16 个 `statePid` 为空**。
- **改哪侧**：**工具侧**（App 侧不用改，它读的就是 `statePid`）
- **代价**：**小**。一个 4 行的改动 + 一条新测试（"所有 `states` 非空的控件必须 `statePid` 非空"）。
  风险：这 16 个灯绑的 PID 大部分还不存在（等 P9），改完它们的 `statePid` 会指向不存在的 PID ——
  但那正是 `guard-pid-probe.js` 该报的东西，**语义变对了**（现在是"数据没到所以不亮"，
  而不是"压根没接"）。
- **优先级**：**P0** —— 这是唯一一条"用户会被明确误导"的问题。

#### 建议 2 · 告警闪烁降到 ≤3 Hz

- **改什么**：四处
  1. `AlertPulse.kt:163` —— `CRITICAL -> square(nowMs, periodMs = 200, duty = 0.5f)` → `periodMs = 400`（2.5 Hz）
  2. `presets.js:249` —— 第一批灯的 `critical.blinkMs: 220` → `≥340`
  3. `presets.js:506` —— 第二批灯的 `critical.blinkMs: 260` → `≥340`
  4. `app.js:1000` / `editor.js:387` / `validate.js:587` ——
     `Math.max(60, ...)` 的下限从 **60ms 提到 340ms**
     （60ms 一轮 = **16.7 Hz**，比红线高 5 倍多；`AlertPulse.kt` 那边还自己夹了
     `coerceAtLeast(60)`，两边要一起改）
- **为什么（依据）**：
  - WCAG 2.3.1 原文："**not ... more than three times in any one second period**"；
  - 实测换算：`220ms → 4.5 Hz`、`260ms → 3.8 Hz`、`200ms → 5 Hz`，**全部超标**；
  - `presets.js:505` 的 `warn: 600ms` = 1.7 Hz **是对的**，可以照它对齐。
- **改哪侧**：**两侧都要**（App 侧 `AlertPulse` 是真正在闪的那个；工具侧只是预览与写入值）
- **代价**：**小到中**。改动本身很小，但要重跑动画相关的实测
  （`docs/动画实现.md:275-276` 记的"两档节奏"是**有意设计**的观感取舍：
  *"低等级用硬方波太刺眼……危险档用平滑脉冲又不够冲击力"*）。
  **一个可选的替代方案**（代价更大，我**没有实测验证**）：
  保留快节奏，改成**只换颜色、不做明暗交替**。WCAG 的 general flash threshold
  算的是**相对亮度**的变化，纯色相变化（红↔橙）理论上不构成"flash"。
  但 `AlertPulse.tintMix()`（`AlertPulse.kt:174-176`）现在是把系数同时乘进
  **辉光透明度与危险区亮度**的，要拆成"色相变、亮度不变"是重写那一层。
  **建议先做 400ms 这一条；观感不够再评估替代方案。**
- **优先级**：**P0** —— 红线，且有明确标准原文。

### P1 —— 高性价比

#### 建议 3 · 给仪表模型加「多段色带」`bands`

- **改什么**：设计文件 schema 里给仪表节点加一个字段
  ```json
  "bands": [ { "from": 0, "to": 6000, "color": "#39D98A", "alpha": 40 },
             { "from": 6000, "to": 7000, "color": "#FFD400", "alpha": 60 },
             { "from": 7000, "to": 8000, "color": "#FF4D4F", "alpha": 90 } ]
  ```
  渲染成**弧带 / 条带**；工具侧在控件编辑器里加一个"色带"列表编辑区，
  并给控件库补 2~3 个带红区的样板（转速红区表、油量绿黄红条）。
- **为什么（依据）**：
  - Canvas Gauges 的 `highlights: [{from, to, color}]` + `highlightsWidth` +
    `highlightsLineCap`（[配置文档](https://canvas-gauges.com/documentation/user-guide/configuration)）；
  - Highcharts `stops: [[0.1,'#55BF3B'],[0.5,'#DDDF0D'],[0.9,'#DF5353']]`
    （[demo](https://www.highcharts.com/demo/highcharts/gauge-solid)）—— **两家独立实现都这么做**；
  - **我们自己的证据**：素材里 `assets/scale/ticks-band.png`、`ticks-gradient.png`
    已经存在（`builtin-index.js`），但**没有任何控件引用它们** —— 素材先行、模型没跟上；
  - App 侧 `NeonPainter` / `AlertPulse.tintMix` 已经在做"把危险区推向危险色"，
    说明渲染能力有，缺的是**数据模型**。
- **改哪侧**：**两侧都要**。工具侧（schema + 编辑器 + 素材引用）是主要工作量；
  App 侧要在 `BaseGaugeView`/`CircularGaugeView`/`BarGaugeView` 里按 `bands` 画弧段。
- **代价**：**中**。这是本清单里**收益最大的一条**：它一次性解决
  "红区 / 油量绿黄红 / 阈值可视化 / 电压危险区"四个需求。
  注意 **PNG 编码器能程序化生成素材**这一点可以省掉美术工作 ——
  色带用现有 `ticks-band.png` 按角度裁，或直接程序化生成。
- **优先级**：**P1**（若要按"只做三件"排，这是第一件）

#### 建议 4 · 把 `marker`（阈值标记）做成控件

- **改什么**：控件库新增 `bar_marker_h` / `bar_marker_v`，引用已存在的
  `assets/bar/marker-h.png`、`marker-v.png`、`marker-glow-h/v.png`；
  并让 `marker` 能绑一个 PID 阈值（而不是纯装饰）。
- **为什么（依据）**：
  - Canvas Gauges 把阈值标记作为 `highlights` 的一部分（同上）；
  - **素材已经在仓库里**（`assets/bar/` 下 4 个 marker 文件），**控件库 0 引用**（实测）；
  - 车载场景里"红线在哪"必须**看得见**，不能只在越线时才染红 ——
    FHWA 那条"color coding should be redundant with other coding"支持"用位置/形状冗余表达"。
- **改哪侧**：**工具侧**（App 侧 `NODE_IMAGE` 已能渲染任意素材）
- **代价**：**小**。纯控件库条目 + 一个 `markerAt` 数值字段（可先用固定坐标，
  不绑 PID 就是纯静态标记，也算可用）。
- **优先级**：**P1**

#### 建议 5 · 补"告警条"控件（非闪烁）

- **改什么**：控件库新增一个 `alert_bar` 控件（一条横幅 + 图标 + 文字），
  三态复用**已有的状态系统**（`states` + `statePid`），**不引入新的闪烁**。
- **为什么（依据）**：
  - App 侧**已经有** `MonitorWarnBar.kt`（105 行）在做这件事，但**控件库里没有对应控件** ——

  - FHWA：关键信息要"颜色 + 形状"冗余 —— 横幅天然是形状编码。
- **改哪侧**：**工具侧**（做成 `NODE_GROUP` + 子节点，App 侧已能渲染分组）
- **代价**：**小**。
- **优先级**：**P1**

#### 建议 8 · 统一字体写法与分类前缀

## 如果只做三件

### 第一件：修 16 个指示灯的状态接线（建议 1）

**理由**：这是清单里**唯一一条"用户会被明确误导"**的问题。现在拖一个"胎压灯"出来，
它永远显示暗的 `lamp-off.png`，**用户会以为车没问题**。而且改动最小
（`presets.js:501-502` 两行），依据最硬（`NodeTreeRenderer.kt:486-489` +
`model.js:826-831` 两处代码 + 19/16 的实测计数）。

### 第二件：告警闪烁降到 ≤3 Hz（建议 2）

**理由**：这是**唯一一条有明确标准原文**的红线
（WCAG 2.3.1："not more than three times in any one second period"），
而我们现在是 **5 Hz 硬方波**（`AlertPulse.kt:163` 实测），工具侧下限还能调到 16.7 Hz。
这是**安全和合规**问题，不是观感问题。

### 第三件：加「多段色带」（建议 3）

**理由**：它一次性解决**四个**需求（转速红区 / 油量绿黄红 / 阈值可视化 / 电压危险区），
而且是**两家独立开源库都当核心配置**的东西（Canvas Gauges 的 `highlights`、
Highcharts 的 `stops`）。**我们自己的仓库已经在为它做准备了** ——
`assets/scale/ticks-band.png` 和 `ticks-gradient.png` 已经躺在素材库里没人用。
PNG 编码器能程序化生成素材这一点，还能把美术成本压到接近零。

> **为什么不选"补拼装表样板"或"接闲置素材"**：那两条（建议 6、9）性价比也很高，
> 但它们是**"把已有的东西接上"**；前三条里，建议 1 和 2 是**修错的**，
> 建议 3 是**补缺的模型层**。先修错的、再补模型、最后才是扩充。
